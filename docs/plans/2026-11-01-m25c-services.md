## 3. Design

### 3.1 Decisions

1. **Schedule = versioned, append-only tenant data (ADR-031).**
   - A version is `periods`: 1–`app.service_max_periods()` (6) entries `{key, name, startsAt}`:
     - `key` `^[a-z][a-z0-9_]{1,31}$`, stable across versions (a rename keeps it);
     - `name` trimmed, 1–30 characters, unique case-insensitively in the version;
     - `startsAt` `HH:MM` (00:00–23:59), unique in the version.
   - **Default** (no row): `app.default_service_periods()` = `[{"key":"pranzo","name":"Pranzo","startsAt":"11:00"},{"key":"cena","name":"Cena","startsAt":"16:00"}]` (Q220). md5-pinned in `286`: changing it would re-assign the history of tenants that never saved.
   - **In force at instant X** = the version with the greatest `(created_at, seq)` and `created_at ≤ X`; none → the default.
   - **Saving** writes a new version that applies to sessions opened from that instant on (Q222). An identical save writes nothing (`changed: false`).
   - A new period sent with `key: null` gets `'s_' || left(replace(gen_random_uuid()::text, '-', ''), 10)`. A non-null key must exist in the version in force (else `key_unknown`), so a client cannot mint keys.
2. **Windows by start time; no gaps, no overlaps.**
   - Business-clock minute of a wall time `t`: `m(t) = (minutes(t) − minutes(cutoff) + 1440) % 1440`.
   - Periods are ordered by `m(startsAt)`. A session's **auto key** is the period with the greatest `m(startsAt) ≤ m(local opened_at)`; if none, the first period (so 02:00–10:59 → Pranzo by default).
   - `endsAt` of a period = the next period's `startsAt`; the last one's = the cut-off. Shown as "Pranzo 11:00–16:00 · Cena 16:00–02:00", with the hint "Prima delle 11:00 conta come Pranzo".
   - **Local time:** `(opened_at at time zone tenant.timezone)::time`. On the autumn night both 02:30s give minute 30 (Pranzo); on the spring night 03:30 CEST gives minute 90 (Pranzo). Both are tested (step 2).
3. **Derived at read time; no backfill (the "existing data" decision).**
   - Existing sessions have `opened_at`, and the default version applies to everything opened before a tenant's first save. So old and new sessions follow the same rule, and no migration touches `table_session`. The migration is therefore safe on staging data by construction: it inserts nothing and updates nothing.
   - **Frozen vs derived, weighed:** a frozen column is set once, but needs `open_table` and the guard replaced (pinned; the offline path) and an UPDATE of immutable closed sessions for the backfill. The derived value is equally stable here, because every input is immutable or forward-only: `opened_at` never changes, versions apply only forward, overrides stop at finality. The two residual movers (a cut-off change, a change to the built-in default) are guarded (§6).
4. **Overrides are append-only events.**
   - `public.set_session_service(p_session, {serviceKey})`; `serviceKey` a key, or null ("Automatico").
   - **Who:** owner, admin (Q224). **When:** while the session is open, or closed with `p_now < kpi_cutoff_end(closed_business_date) + kpi_finalise_grace()`. After that → P0001 `service_day_final`.
   - **Which keys:** the keys of the version in force at the session's `opened_at` (else `service_unknown`).
   - **Effective key** = the latest override's key (by `created_at`, `seq`) when not null; else the auto key. A request equal to the current state writes nothing (`changed: false`).
   - **Lock:** the session row `FOR SHARE` (like the line writers), so an override waits for a running close and then sees `closed_at`. Nothing else is locked. No cycle (§3.3).
5. **Lines follow the session** (Q223). Covers, coperto, total and every line of a session count in that session's service.
6. **One split source, live** (ADR-031 decision 6).
   - `app.kpi_service_split(p_tenant, p_from, p_to) returns jsonb` joins `app.kpi_sales_lines` and `app.kpi_session_rows` (unchanged) with `app.session_services` and aggregates per key with **the same expressions as `app.kpi_day_row` and `app.kpi_block`**.
   - So `Σ services = total` by construction (numeric addition is exact), and `total` equals `kpi_report.current` for the same keys (tested on a live day and on a stored, final day).
   - **Service list in a reply:** every key of the versions in force during the range, plus any key with data; ordered by the current version's business-clock order, then the others by name. Name = the latest version's name for that key. A service without data shows zeros and null ratios.
7. **Day close.** The register total stays **per day** (Q225).
   - `public.day_services(p_date)` → the split of the app side for D and the list of D's sessions with their service.
   - **Variance:** app vs register stays a single day figure (M21, unchanged). Per service there is no register figure, so the screen says "La cassa si chiude una volta al giorno: la differenza è sul totale." Moving a table between services never changes the day's app total, so it never changes the variance.
   - **Effect of V4 (a per-service register):** the variance would be per service plus the day; it needs a per-service reading from the RCH (Q233), a `day_close` column and a re-pin of `app_vs_register_json` (§5b V4).
8. **Report:** `public.kpi_services(period, date, from, to)` with the `kpi_report` period rules. Per service and in total: `covers, tables, revenueGrossEur, revenueNetEur, avgSpendPerCoverEur, avgTicketEur, plates, foodCostEur, foodCostPct, costedRevenueNetEur, costedSharePct, revenueSharePct`. Owner and admin get the same keys (no fixed-cost key). No comparison period (Q228 → V8).
9. **Dashboard:** `yesterday.byService = [{key, name, covers, tables, revenueNetEur}]`, from the same `app.kpi_service_split(D, D)`. Covers and net revenue only (Q227).
10. **Roles and privacy.**
    - Every new public function: `app.require_day_closer()` first (owner, admin); chef and waiter 42501; tenant from `app.tenant_id()`; user from `app.app_user_id()`. The waiter never sees a total; the chef never sees €.
    - Replies carry no staff name; `created_by` is stored for accountability and never returned.
11. **No data logic in React.** SQL computes every assignment, window end, order, sum, share and the `canChange` flag. `src/lib/services/services-view.ts` only formats ("Pranzo 11:00–16:00").
12. **Implicit defaults, each tested with ≥ 2 candidates:** before/after the first start (2); at/after the cut-off (2); CET vs CEST vs both DST nights (2); cut-off 02:00 vs `"00:30"` (2); two vs three services (2, 3); versions before/after/at an instant (2); auto vs override vs override back to null (2, 4); open vs closed vs final (4, 5); grace − 1 s vs + 0 s (4); owner vs admin vs chef vs waiter (3–5, 8–10); two tenants (1, 2, 4, 16); live vs stored day (5).

### 3.2 Data model and SQL

**Common rules:** every function `security definer`, `set search_path = ''`; every `app.*` revoked from `public, anon, authenticated, service_role`; every public function `revoke all … from public, anon, service_role; grant execute … to authenticated`; public functions are thin wrappers (role first) over `app.*_at`/`_json` twins taking `p_now`, which pgTAP calls with fixed instants (the M21/M22 rule).

**`20261120100000_service_core.sql`** (step 1)

```sql
create function app.service_max_periods() returns integer language sql immutable set search_path = '' as $$ select 6 $$;
create function app.default_service_periods() returns jsonb language sql immutable set search_path = '' as $$
  select '[{"key":"pranzo","name":"Pranzo","startsAt":"11:00"},{"key":"cena","name":"Cena","startsAt":"16:00"}]'::jsonb $$;
-- true when p is an array of 1..6 objects with exactly {key,name,startsAt}; keys, names (case-insensitive) and starts unique; formats as §3.1.1
create function app.service_periods_ok(p jsonb) returns boolean language plpgsql immutable set search_path = '' as $$ … $$;

create table public.service_schedule (
  tenant_id uuid not null references public.tenant (id),
  id uuid not null default gen_random_uuid(),
  seq bigint generated always as identity,
  periods jsonb not null check (app.service_periods_ok(periods)),
  created_at timestamptz not null default clock_timestamp(),
  created_by uuid not null,
  primary key (tenant_id, id),
  constraint service_schedule_user_fkey foreign key (tenant_id, created_by) references public.app_user (tenant_id, id)
);
create index service_schedule_at_idx on public.service_schedule (tenant_id, created_at desc, seq desc);

create table public.service_override (
  tenant_id uuid not null references public.tenant (id),
  id uuid not null default gen_random_uuid(),
  seq bigint generated always as identity,
  table_session_id uuid not null,
  service_key text check (service_key ~ '^[a-z][a-z0-9_]{1,31}$'),   -- null = back to automatic
  created_at timestamptz not null default clock_timestamp(),
  created_by uuid not null,
  primary key (tenant_id, id),
  constraint service_override_session_fkey foreign key (tenant_id, table_session_id) references public.table_session (tenant_id, id),
  constraint service_override_user_fkey foreign key (tenant_id, created_by) references public.app_user (tenant_id, id)
);
create index service_override_session_idx on public.service_override (tenant_id, table_session_id, created_at desc, seq desc);
```

- Both tables: triggers `app.append_only` (before update or delete) and `app.append_only_truncate`; RLS on; `revoke all … from anon, authenticated, service_role; grant select … to authenticated, service_role`; policy `*_select` with `tenant_id = (select app.tenant_id()) and (select app.role()) in ('owner','admin')`. **No write grant, no write policy.**
- **T1:** `table_session` has a unique `(tenant_id, id)` usable by the composite FK. If not, the FK is `table_session_id → table_session (id)` plus a tenant check in the writer, and `280` asserts that a cross-tenant insert is refused.

**`20261120100100_demo_purge_tables_m25c.sql`** (step 1): `create or replace function app.demo_purge_tables()` = the M23 list (`20261114100100`) with `'service_override'` immediately before `'table_session'` and `'service_schedule'` immediately after `'dashboard_open'`. `app.tenant_has_operational_data` is **not** replaced: a saved schedule counts as data (Q231).

**`20261120100200_service_assign.sql`** (step 2)
- `app.service_minute(p_t time, p_cutoff time) returns integer` (immutable): the §3.1.2 `m(t)`.

### 3.3 Sequence of calls and lock order

1. **Owner edits services:** `/tavoli/impostazioni` → `GET /api/settings/services` → `service_periods()` → card. Save → `PATCH /api/settings/services {periods}` → `set_service_periods` (advisory lock, insert) → the reply replaces the card.
2. **A table opens** (unchanged M17/M20 path). Nothing service-related is written.
3. **Day close:** `/chiusura?data=D` → `GET /api/reports/app-vs-register?date=D` (unchanged), then `GET /api/day-close/services?date=<report.businessDate>` → "Per servizio" card. "Cambia servizio" on a row → sheet → `POST /api/table-sessions/:id/service {serviceKey}` → re-read `/api/day-close/services`.
4. **Report:** Andamento → `GET /api/reports/kpis?…` (unchanged) and `GET /api/reports/services?…` (same query) → panel; "Scarica CSV" → `/api/exports/services.csv?…`.
5. **Home:** `GET /api/dashboard` (one RPC, unchanged) → Ieri tile with `byService`.

**Locks:** `set_session_service` takes `table_session` FOR SHARE and nothing after it (the line writers' position in M21 §3.3). `set_service_periods` takes only its advisory lock. Reads take none. No new cycle.

## 4. Alternatives considered

- **A `service_key` column set by `open_table`, with a backfill:** rejected (ADR-031): pinned `open_table` and guard, the offline path, and an UPDATE of immutable closed sessions.
- **Derived from the current windows only:** rejected: an edit would rewrite history.
- **Start and end per service (gaps, overlaps):** not the default (Q220 → V1); overlaps are never allowed.
- **Assignment per line (dish) by send time:** rejected (Q223): one bill would split across services, and covers and the coperto would need an allocation rule.
- **Assignment by closing time:** rejected: the founder asked for opening time, and the M21 closing date already decides the day.
- **`byService` inside `kpi_report`:** rejected: it changes `kpiReportOutput`, `kpis.csv`'s 54 rows, the monthly pack and M24's parity tests. A sibling function with the same period rules is cheaper and keeps the totals identical by test.
- **A per-service snapshot table in the rollup:** rejected (ADR-031): the rollup is pinned, and the inputs are frozen after finality.
- **Replacing `app_vs_register_json` to embed the split:** rejected: pinned by `240`; the day screen can read two endpoints.
- **Waiters choosing the service when opening a table:** rejected for now: one more tap per table during service; V3 lets them correct it on open tables if asked.
- **A separate settings page `/tavoli/servizi`:** rejected: a card on the existing settings page needs no nav, back-link or route-list change. Revisit if the page grows long.
- **Service names translated in code:** rejected: names are data the owner types, and a third service must need no code (Q232).

## 6. Risks and mitigations

- **Security and privacy**
  - *Wrong role writes or reads:* the role first in SQL (3–5), 403 before any RPC (8–10, 15), RLS select owner/admin and no write grant (1).
  - *IDOR:* a session id of another tenant → `session_not_found` (4); every read filters by `app.tenant_id()`; cross-tenant checks (2, 5, 16).
  - *Input:* strict Zod and SQL validation, a 2 KB body cap, codes-only DETAILs (3, 8). Service names are rendered as text and formula-escaped in CSV (15).
  - *Personal data (GDPR):* `created_by` on both tables holds staff ids, kept for accountability and never returned (5, 9); retention follows project Q14; no guest data. Nothing leaves Supabase (EU). Logs carry codes and SQLSTATEs only.
  - *Waiters and the chef:* no new endpoint is open to them (3–5, 8–10); V3 would keep amounts out of the waiter's reply.
- **Correctness**
  - *Split ≠ day total:* by construction (one aggregate, exact numeric sums) and by test against `kpi_report`, `daily_kpi` and `app_vs_register` (5, 6, 16).
  - *History moving:* versions apply forward only (2); overrides stop at finality (4); the built-in default is md5-pinned (7).
  - *Cut-off changed later:* sessions opened between the old and the new cut-off can change service. Mitigation: the settings card's preview shows where the last service ends, which is the cut-off (12); a cut-off change is rare and owner-only (M11). Recorded in ADR-031.
  - *Offline opens:* `opened_at` is the server's arrival time (M20), so a table opened offline just before 16:00 can land in Cena; the override fixes it (Q230).
  - *DST nights:* the wall-time rule is tested on both nights (2).
  - *Concurrency:* an advisory lock on saves, the session SHARE lock on overrides, two race cases (3, 4).
- **Unverified (proved in the named step)**
  - **T1:** `table_session` has a unique `(tenant_id, id)` usable by a composite FK. Proved in 1; the fallback is in §3.2.
  - **T2:** `withApi` accepts `PATCH` with a body schema, as the coperto route does on `main`. Proved in 8.
  - **T3:** the nested static route `src/app/api/day-close/services/route.ts` coexists with `src/app/api/day-close/route.ts` in Next.js 16 (standard App Router nesting). Proved over HTTP in 16 and 17.
- **Performance and cost:** no figure is promised. The split reads the same lines as the items report; a perf net is in 5. No new provider, job or paid service; CI adds one lean spec.
- **Dependencies:** none added (`tests/config/no-new-deps.test.ts` unchanged).
- **Plan changes to record in DigiAlto-Ops `clients/osteria-dei-rossi/context.md`:** ADR-031 proposed; services configured in Sala › Tavoli › Impostazioni; the register stays per day; M25's simulation places tables by override (§3.9); the pgTAP `267` clash between M25a V4 and M25b, for the lead.
