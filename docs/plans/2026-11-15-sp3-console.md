## 0. Summary

SP3 builds DigiAlto's own back office next to the venue app, in the same Next.js app and the same Supabase project:

1. **Who.** `platform.staff` holds exactly one active `platform_admin`: the platform admin account (address held by DigiAlto). A protected
   GitHub workflow creates the staff row; the account then enrols its second factor in the app. Triggers keep that account to `admin`
   memberships only.
2. **Where.** A console host (`CONSOLE_HOST`, e.g. `console.<product domain>`, FD10). `src/proxy.ts` serves the console only there and
   answers 404 for console paths on every other host, and for venue paths on the console host.
3. **How it reads.** In **console mode** the access-token hook gives the session the Postgres role `platform_staff`. That role has no grant on
   any table. It can only call `public.platform_*` definer functions, which return **metadata only** (a key whitelist test, AT5). The role
   is unusable until the account has a verified factor and an `aal2` session.
4. **What it records.** `platform.audit_event`, append-only for every role. Every console write and every state-changing script writes one row
   with codes and ids only (no `@`, ever).
5. **What it shows.** Locali, the venue detail, Registro della piattaforma and Avvisi (sub-processor notices), with only the fields that
   exist in SP3 (§3.8). Status, plan, modules, health and usage arrive with SP5, SP6 and SP11. Organisation data is read-only.
6. **Entering a venue.** "Entra nel locale" opens the venue app on the app host, where the same account selects the venue with SP2's
   `select_tenant`. In SP3 this works only where the account already holds an active `admin` row. SP4 attaches the account everywhere and adds
   the owner-visible audit (§3.7).
7. **Secret-key scripts** run only as a manual workflow in the protected GitHub environment `platform-ops`, approved by the founder's GitHub
   account; no secret enters a chat, a file or a log (§3.13).

## 3. Design

### 3.1 Data model (all in schema `platform` unless named)

**3.1.1 Organisation-side VAT guard (step 1).** Trigger `organisation_vat_locked` `before update of vat_number on platform.organisation for
each row`, function `platform.organisation_vat_locked()` (definer, `search_path = ''`, closed to every API role). When
`new.vat_number is distinct from old.vat_number` and any `public.tenant` row has `organisation_id = old.id`, it raises P0001
`organisation_vat_in_use`. It fires for every role, the migration owner included. A name change, a no-op VAT update and a VAT change on an
organisation no tenant points at stay allowed. With SP2's tenant-side trigger this closes both sides. Moving a tenant to another legal entity
stays "update both tenant columns together" (SP2 build notes).
- The function lives in `platform`, not `app`, so the `app` catalogue pins (359) do not move for it.
- **Organisation data is read-only in SP3.** No SP3 function or route writes `platform.organisation`; the console only reads its `id` and
  `name` (decided, §7a).

**3.1.2 `platform.staff` (step 2).** `(auth_id uuid primary key references auth.users (id), role text not null check (role in
('platform_admin', 'platform_support')), display_name text not null default 'DigiAlto' check (length between 1 and 60), is_active boolean
not null default true, created_at timestamptz not null default now(), created_by uuid null)`. Partial unique index
`staff_one_active_admin on platform.staff ((true)) where role = 'platform_admin' and is_active` (FD28). RLS on; no grant to `anon`,
`authenticated`, `service_role`; `select` for `supabase_auth_admin` with policy `staff_read_by_auth_hook` (step 14). A staff row may exist
before the account has a factor (Q-P5); the row alone grants nothing (§3.3.1).

**3.1.3 `platform.audit_event` (step 2).** `(id bigint generated always as identity primary key, at timestamptz not null default now(),
actor_auth_id uuid null, origin text not null check (origin in ('console', 'script')), action text not null check (action = any
(platform.audit_actions())), tenant_id uuid null, detail jsonb not null default '{}' check (platform.audit_detail_ok(detail)))`.
- **No foreign key on `tenant_id`**: an erased tenant's rows must survive (ADR-040 tombstone; UX §7 "Locale cancellato").
- `platform.audit_actions()` (immutable) is the action registry. It equals `PLATFORM_AUDIT_ACTIONS` in `src/lib/platform/codes.ts`
  (step 21a); a source test in `sp3-preserves` compares the two (step 2). SP3's actions: `platform_admin.bootstrapped`,
  `platform_admin.factor_enrolled`, `console.entered`, `console.left`, `console.tenant_opened`, `notice.created`, `notice.tenant_notified`,
  `script.create_tenant`, `script.mfa_reset`, `script.set_mfa_enforcement`. Later milestones add theirs to both lists.
- `platform.audit_detail_ok(jsonb)` (immutable): a flat object; keys from `platform.audit_detail_keys()` (`tenantId`, `appUserId`,
  `authId`, `noticeId`, `kind`, `version`, `mode`, `slot`, `changed`, `sessionsRevoked`, `outcome`); values are uuid strings, integers,
  booleans, `null`, or codes `^[a-z0-9_.:-]{1,64}$`; no `@` anywhere. A CHECK may call an immutable function (SP1 test 1's rule).
- Append-only: `audit_event_no_update_delete` (`before update or delete … for each row`) and `audit_event_no_truncate` (`before truncate …
  for each statement`) raise P0001 `platform_audit_append_only` for every role (AT7).
- Writer: `platform.audit_write(p_origin, p_action, p_tenant, p_detail)` (definer, closed to every API role), used by every platform function.

**3.1.4 Staff/member guards (step 3, AT2).**
- On `platform.staff` (`staff_member_guard`, before insert or update of `auth_id, role, is_active`): a `platform_support` row is refused
  (`platform_support_has_member_row`) when the auth user has any `app_user` row; a `platform_admin` row is refused
  (`platform_admin_member_role`) when the auth user has any non-`admin` `app_user` row, active or not.
- On `public.app_user` (`app_user_platform_staff_guard`, before insert or update of `auth_id, role`; function
  `app.app_user_platform_staff_guard()`): when the auth user has a `platform.staff` row, the row is refused (`platform_staff_member_role`)
  unless that staff row is an active `platform_admin` and the new role is `admin`. This trigger is in `public`: pgTAP 365's count moves 128 →
  129 here (ratified).

**3.1.5 `platform.console_session` (step 13).** `(session_id uuid primary key, auth_id uuid not null references platform.staff (auth_id),
selected_at timestamptz not null default now())`. Session state, not a ledger: written by `select_console`, deleted by
`platform_leave_console`, `select_tenant` and the purge (step 22). RLS on; `select` for `supabase_auth_admin` only (policy
`console_session_read_by_auth_hook`). No foreign key to `auth.sessions` (same reason as SP2 §3.1.4).

**3.1.6 `platform.notice` (step 12, AT9).** `(id uuid pk, kind text check (kind in ('subprocessor')), version integer check (version >= 1),
created_at, created_by uuid null, unique (kind, version))`. The kind list equals `PLATFORM_NOTICE_KINDS` in `codes.ts`. Append-only like the
audit. The per-tenant "notified" date is a `platform.audit_event` row `notice.tenant_notified` (`tenant_id`, `detail.noticeId`); no second
table. The text of a notice is not stored: the screen renders a sentence from `kind` and `version`.

**3.1.7 `platform.mfa_failure` (step 9).** `(id bigint identity pk, auth_id uuid not null references platform.staff (auth_id), stage text
check (stage in ('login', 'enrol')), at timestamptz not null default now())`. Platform staff's own failed codes, for the lock. It reuses
`app.mfa_lock_failures()` and `app.mfa_lock_minutes()` (P2-1 constants). Rows older than the lock window are purged (step 22). Accepted into
ADR-037's list (Q-P14, decided).

**3.1.8 Named catalogue test (step 2, extended by each step).** pgTAP 375 lists the `platform` tables by name (`organisation`, `staff`,
`audit_event`, then `mfa_failure`, `notice`, `console_session` as their steps land): RLS on, no privilege for `anon`, `authenticated`,
`service_role` and (from step 10) `platform_staff`; no other table in `platform`; `usage` on schema `platform` only for `supabase_auth_admin`
(from step 14).

### 3.2 The hook's console mode (step 14)

`create or replace function app.custom_access_token_hook(event jsonb)`: same signature, owner, grants, `stable`, `search_path = ''`. Order:

1. **Strip** (unchanged): `tenant_id`, `app_role`, `login`, `session_state`.
2. **PIN branch** (unchanged, the text of `20261025100500_access_token_hook_pin.sql:70–94`; SP2's source-equality test keeps proving it).
3. **Console branch (new), in its own `begin … exception when others` block:** if the input `session_id` is a well-formed uuid, and
   `platform.console_session` has that `session_id` with `auth_id = user_id`, and `platform.staff` has an active `platform_admin` row for
   `user_id`: set `role` to `platform_staff`, add no tenant claim, return. Any error → fall through.
4. **E-branches** (SP2's E1–E4, unchanged). If the incoming `role` is `platform_staff` (a stale value), it is set back to `authenticated`.

| Case | Claims | Proof |
|---|---|---|
| Console row, active platform admin | `role = platform_staff`, no `tenant_id`, `app_role`, `login` | 384 |
| Console row, staff row inactive or missing | E-branches: `authenticated` | 384 |
| Console row of another auth user (forged `session_id`) | ignored | 384 |
| `console_session` unreadable (grant revoked inside the test) | E-branches | 384 |
| PIN session | M11 branch exactly | 085 unchanged; SP2 source test |
| Every tenant #1 user (no console row) | exactly SP2's claims | 003, 085, 340 and SP2's 370 unchanged |
| Incoming `role = platform_staff`, no console row | `authenticated` + E-branches | 384 |

No new claim key. Only the value of `role` changes in console mode. A console row can only exist after `select_console`, which needs a
verified factor and `aal2` (§3.3.2), so the hook needs no factor check of its own.

### 3.3 Functions

All definer, `search_path = ''`, owned by `postgres`, `revoke all … from public` first.

**3.3.1 `app.require_console()` (step 10).** In this order: 42501 `console_required` unless `auth.jwt() ->> 'role' = 'platform_staff'` and
`auth.uid()` is the active `platform_admin`; P0001 `mfa_factor_required` unless `app.mfa_has_verified_factor(auth.uid())`; P0001
`mfa_required` unless `app.jwt_aal() = 'aal2'` (AT3). Closed to every API role. Every console `platform_*` function calls it first.

**3.3.2 Console mode switches (step 13).**

### 3.4 API — FINAL (lead, 2026-11-15)

This section is the contract builder 2 builds the screens against, with mocks, before the routes exist. Changing it needs the lead.

**3.4.1 Rules for every route**
- Implemented with `withApi`; strict Zod input (an unknown key → 400 `invalid_request`); strict Zod output; `cache-control: no-store`
  (`with-api.ts:261`); none is offline-cacheable.
- Writes (`POST`) need `Content-Type: application/json` (else 415 `unsupported_media_type`); a body of `{}` where none is needed.
- Error body, every route: `{ "error": { "code": string, "message": string, "details"?: object } }` (`errors.ts:293–294`). `message` is
  Italian and may be shown; the screen branches on `code` only.
- Common errors on every non-public route: 401 `unauthenticated` (signed out), 401 `session_expired` (30 days, ADR-029), 500 `internal`.
- Common errors on every `platform` route (access kind `{ platform: true }`): 409 `console_selection_required` (an `authenticated` session
  that is not in console mode: the client posts `POST /api/platform/console` and reloads), 403 `mfa_required` (`aal1`, or the database
  answered `mfa_required`), 403 `mfa_factor_required` (no verified factor: the client goes to `/login/attiva-codice`), 403 `forbidden`
  (the database answered 42501).
- A `platform_staff` token on any non-platform route → 403 `console_session` before any RPC (except `POST /api/platform/logout`).
- Hosts: every `/api/platform/**` route answers only on the console host; `/api/auth/mfa/account/**` answers on both hosts (§3.5). Elsewhere
  the proxy answers 404 with no body contract.
- Types: `uuid` = lowercase uuid string; `Instant` = ISO 8601 UTC string with `Z`; `Day` = `YYYY-MM-DD`; integers are JSON numbers.
- Shapes are exported as Zod schemas and types from `src/lib/platform/api.ts` (client-importable, step 21a); the server's
  `src/server/platform/output.ts` parses with the same schemas.

### 3.6 Sign-in and sessions

**Console host (platform staff):**
1. `/login` (console) → `POST /api/platform/auth/password`. Not the active platform admin → signed out, 403 `not_console_account`, the form

1. `/login` → password → hook: several memberships (or none) → no tenant claim.

**Two sessions on one device** (Q-P3, decided). The console session and the app session are separate. Signing out of one does not sign out of
the other. The break-glass reset ends both (§3.9.3).

### 3.13 Who runs the secret-key scripts, and where

**Nobody runs a secret-key script from a laptop or a chat.** Every script that needs the Supabase secret key runs as a job of one manual
workflow, `.github/workflows/platform-ops.yml`, in the protected GitHub environment `platform-ops` (set up by the founder, FS-1).

- **Values:** the founder types every secret value only into GitHub's own "Add environment secret" form. No value is ever pasted into a chat,

## 4. Alternatives considered

- **Console in a separate Supabase project** (platform plan V1): the strongest separation; but the console would need the product project's
  secret key to read metadata. Rejected; **V1**.
- **Console sessions as `authenticated` with a platform claim** (platform plan V2): no custom Postgres role; but any tenant policy that
  forgets to exclude console sessions leaks to them. Rejected as default; **V2** if T2.H fails.
- **One session across both hosts** (a parent-domain cookie): saves one sign-in; but it widens every session cookie to every subdomain and
  needs the product domain first. Rejected (Q-P3, decided); **V3**.
- **Console on the app host under `/console`**: one cookie jar; but every venue session could be pushed into console mode by a link, and
  ADR-037 decides a separate host. Rejected.
- **A second root layout for the console:** needs no top-level `app/layout.tsx`; the repo has one. Rejected.
- **Reusing the tenant code page for the platform admin with a fake tenant claim:** rejected; it would mint claims the hook never gave.
- **Refusing a venue account on the console only after its code** (UX §4 order): rejected (Q-P4, decided); **V6**.
- **A terminal script to enrol the platform admin's factor** (this plan's first draft, step 8): no app change; but the TOTP seed would pass
  through a terminal and could land in a log or a transcript, and the founder does not run secret-key scripts. Rejected by the lead (Q-P5).
- **Bootstrap after the factor** (platform plan §2.4 point 1): bootstrap could keep refusing an account without a factor; but a fresh account
  then has no way to enrol. Rejected by the lead (Q-P5): staff row first, factor in the app, role unusable until then.
- **Running secret-key scripts from the founder's laptop:** no workflow to maintain; but the key then lives on a laptop and its output in a
  terminal. Rejected (Q-P7 as amended).
- **Workflow inputs for the owner's or admin's address:** simplest form; but inputs of a public repository's runs are readable. Rejected for
  environment secrets.
- **A console button for the break-glass reset:** rejected (Q-P7); **V4** records a request instead.
- **A per-tenant "notified" table for notices; a foreign key from the audit to `tenant`; platform trigger functions in `app`; widening
  pgTAP 365:** rejected for the reasons in §3.1 and Q-P2 (V11 keeps the last open).

## 6. Risks and mitigations

**Security and privacy**
- **R1. Tenant #1 locked out by the hook change.** The console branch runs only with a console row; 003, 085, 340 and SP2's 370 unchanged in the
  same commit; staging first; SP2's fix-forward pattern applies.
- **R2. `platform_staff` refused or mishandled hosted.** T2.H gates steps 10–12; V2 is drafted.
- **R3. The console reachable from a venue host, or venue pages from the console host.** Proxy rules (AT6, read line by line by the lead);
  the real boundary is Postgres.
- **R4. The platform admin account is the strongest credential.** `aal2` and a verified factor for every console function and for
  `select_console`; the account-level lock (step 9); no "Password dimenticata?" on the console (Q-P6); a venue account is signed out at once
  (Q-P4). A staff row without a factor grants nothing (steps 10, 13). Residual: the founder's password manager and authenticator; a hardware
  factor stays F-5.
- **R5. A metadata key leaks business data.** The whitelist and deny-pattern test (AT5).
- **R6. An e-mail address in the platform audit, a script's output or a workflow run.** The `detail` CHECK; script output tests; no address
  input in the workflow (config test); addresses only as environment secrets, which GitHub masks.
- **R7. Realtime tells a console subscriber that an event happened.** No client, `connect-src 'self'`, publication pinned empty; V5.
- **R8. The platform admin cannot pass its code without a tenant.** Step 9's account routes; step 15's mapping; step 23 end to end.
- **R9. A break-glass reset signs the person out of every venue, and the console.** Accepted; the two confirmations of §3.9.3. **Lost factor
  of the platform admin:** the account keeps two factors (`MFA_MAX_FACTORS`, slot "riserva"); if both are lost, the founder removes the
  factors of that auth user in the Supabase dashboard (exact menu not verified here), signs in on the console with the password and enrols
  again on `/login/attiva-codice` (the staff branch of `mfa_enrol_check` allows a first factor at `aal1`). No terminal, no seed in a log.
  Runbook (step 24).
- **R10. The wrong venue name on screen.** The wordmark is a constant until SP9; SP2's account control shows the venue.
- **R11. Two sessions confuse the founder.** The confirm text and the runbook say so.
- **R12. Personal data.** `platform.audit_event` holds auth ids, tenant ids and codes; `console_session` session ids for at most 31 days;
  `mfa_failure` failure times for the lock window. Audit retention: F-4.
- **R13. Secret-key holders can write any platform audit row.** By design; every such row says origin `script` ("Script", C7).
- **R14. A staff row exists before its factor** (Q-P5). Between bootstrap and enrolment anyone with the account's password could enrol a
  factor on the console. Mitigations: bootstrap is approved by the founder in GitHub and the founder enrols right after; the Registro shows
  `platform_admin.factor_enrolled` with its time; the account had a password only the founder holds. Residual accepted by the lead.

**Delivery**
- **R15. Stacked on an unmerged branch.** SP3 rebases and re-takes the 346/359/229 values after each SP2 change.
- **R16. Migration timestamp collision.** `sp3-preserves` and the newest-migration pins turn CI red.
- **R17. The VAT guard blocks a legitimate VAT correction.** Move the tenant (both columns) to the right organisation; a typo on a shared
  organisation needs a privileged procedure later. Runbook note.
- **R18. Public Actions logs.** The repository is public; run logs and inputs are readable. Mitigations: inputs are ids and codes; secrets
  are masked and never echoed; script output holds ids and codes only. Residual: tenant and `app_user` uuids (pseudonymous) appear in the
  run page; accepted unless the lead decides otherwise.

**Performance:** console reads are a handful of definer calls by one person; the hook adds one indexed lookup plus one on `platform.staff` only
when a console row exists. No target number is promised.

**Dependencies (name, licence, why):** none added.
