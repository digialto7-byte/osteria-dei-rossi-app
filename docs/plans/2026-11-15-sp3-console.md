## 0. Summary

SP3 builds DigiAlto's own back office next to the venue app, in the same Next.js app and the same Supabase project:

1. **Who.** `platform.staff` holds exactly one active `platform_admin`: the platform admin account (address held by DigiAlto). A script
   bootstraps it. Triggers keep that account to `admin` memberships only.
2. **Where.** A console host (`CONSOLE_HOST`, e.g. `console.<product domain>`, FD10). `src/proxy.ts` serves the console only there and
   answers 404 for console paths on every other host, and for venue paths on the console host.
3. **How it reads.** In **console mode** the access-token hook gives the session the Postgres role `platform_staff`. That role has no grant on
   any table. It can only call `public.platform_*` definer functions, which return **metadata only** (a key whitelist test, AT5).
4. **What it records.** `platform.audit_event`, append-only for every role. Every console write and every state-changing script writes one row
   with codes and ids only (no `@`, ever).
5. **What it shows.** Locali, the venue detail, Registro della piattaforma and Avvisi (sub-processor notices), with only the fields that
   exist in SP3 (§3.8). Status, plan, modules, health and usage arrive with SP5, SP6 and SP11.
6. **Entering a venue.** "Entra nel locale" opens the venue app on the app host, where the same account selects the venue with SP2's
   `select_tenant`. In SP3 this works only where the account already holds an active `admin` row. SP4 attaches the account everywhere and adds
   the owner-visible audit (§3.7).

## 3. Design

### 3.1 Data model (all in schema `platform` unless named)

**3.1.1 Organisation-side VAT guard (step 1).** Trigger `organisation_vat_locked` `before update of vat_number on platform.organisation for
each row`, function `platform.organisation_vat_locked()` (definer, `search_path = ''`, closed to every API role). When
`new.vat_number is distinct from old.vat_number` and any `public.tenant` row has `organisation_id = old.id`, it raises P0001
`organisation_vat_in_use`. It fires for every role, the migration owner included. A name change, a no-op VAT update and a VAT change on an
organisation no tenant points at stay allowed. With SP2's tenant-side trigger this closes both sides: a tenant and its organisation can never
disagree on the VAT number. Moving a tenant to another legal entity stays "update both tenant columns together" (SP2 build notes).
- The function lives in `platform`, not `app`, so the `app` catalogue pins (359) do not move for it.

**3.1.2 `platform.staff` (step 2).** `(auth_id uuid primary key references auth.users (id), role text not null check (role in
('platform_admin', 'platform_support')), display_name text not null default 'DigiAlto' check (length between 1 and 60), is_active boolean
not null default true, created_at timestamptz not null default now(), created_by uuid null)`. Partial unique index
`staff_one_active_admin on platform.staff ((true)) where role = 'platform_admin' and is_active` (FD28). RLS on; no grant to `anon`,
`authenticated`, `service_role`; `select` for `supabase_auth_admin` with policy `staff_read_by_auth_hook` (step 14).

**3.1.3 `platform.audit_event` (step 2).** `(id bigint generated always as identity primary key, at timestamptz not null default now(),
actor_auth_id uuid null, origin text not null check (origin in ('console', 'script', 'migration')), action text not null check (action = any
(platform.audit_actions())), tenant_id uuid null, detail jsonb not null default '{}' check (platform.audit_detail_ok(detail)))`.
- **No foreign key on `tenant_id`**: an erased tenant's rows must survive (ADR-040 tombstone; UX §7 "Locale cancellato").
- `platform.audit_actions()` (immutable) is the action registry. SP3's actions: `platform_admin.bootstrapped`, `console.entered`,
  `console.left`, `console.tenant_opened`, `notice.created`, `notice.tenant_notified`, `script.create_tenant`, `script.mfa_reset`,
  `script.set_mfa_enforcement`. Later milestones add theirs.
- `platform.audit_detail_ok(jsonb)` (immutable): a flat object; keys from `platform.audit_detail_keys()` (`tenantId`, `appUserId`,
  `authId`, `noticeId`, `kind`, `version`, `mode`, `changed`, `sessionsRevoked`, `outcome`); values are uuid strings, integers, booleans or
  codes `^[a-z0-9_.:-]{1,64}$`; no `@` anywhere. A CHECK may call an immutable function (SP1 test 1's rule).
- Append-only: `audit_event_no_update_delete` (`before update or delete … for each row`) and `audit_event_no_truncate` (`before truncate …
  for each statement`) raise P0001 `platform_audit_append_only` for every role (AT7).
- Writer: `platform.audit_write(p_origin, p_action, p_tenant, p_detail)` (definer, closed to every API role), used by every platform function.

**3.1.4 Staff/member guards (step 3, AT2).**
- On `platform.staff` (`staff_member_guard`, before insert or update of `auth_id, role, is_active`): a `platform_support` row is refused
  (`platform_support_has_member_row`) when the auth user has any `app_user` row; a `platform_admin` row is refused
  (`platform_admin_member_role`) when the auth user has any non-`admin` `app_user` row, active or not.
- On `public.app_user` (`app_user_platform_staff_guard`, before insert or update of `auth_id, role`; function
  `app.app_user_platform_staff_guard()`): when the auth user has a `platform.staff` row, the row is refused (`platform_staff_member_role`)
  unless that staff row is an active `platform_admin` and the new role is `admin`. This trigger is in `public`: pgTAP 365's count moves 128 →
  129 here.

**3.1.5 `platform.console_session` (step 13).** `(session_id uuid primary key, auth_id uuid not null references platform.staff (auth_id),
selected_at timestamptz not null default now())`. Session state, not a ledger: written by `select_console`, deleted by
`platform_leave_console`, `select_tenant` and the purge (step 22). RLS on; `select` for `supabase_auth_admin` only (policy
`console_session_read_by_auth_hook`). No foreign key to `auth.sessions` (same reason as SP2 §3.1.4).

**3.1.6 `platform.notice` (step 12, AT9).** `(id uuid pk, kind text check (kind in ('subprocessor')), version integer check (version >= 1),
created_at, created_by uuid null, unique (kind, version))`. Append-only like the audit. The per-tenant "notified" date is a
`platform.audit_event` row `notice.tenant_notified` (`tenant_id`, `detail.noticeId`); no second table. The text of a notice is not stored: the
screen renders a sentence from `kind` and `version`.

**3.1.7 `platform.mfa_failure` (step 9).** `(id bigint identity pk, auth_id uuid not null references platform.staff (auth_id), stage text
check (stage in ('login')), at timestamptz not null default now())`. The platform admin's own failed codes, for the lock. It reuses
`app.mfa_lock_failures()` and `app.mfa_lock_minutes()` (P2-1 constants). Rows older than the lock window are purged (step 22). Not in
ADR-037's list: Q-P14.

**3.1.8 Named catalogue test (step 2, extended by each step).** pgTAP 375 lists the `platform` tables by name (`organisation`, `staff`,
`audit_event`, then `mfa_failure`, `notice`, `console_session` as their steps land): RLS on, no privilege for `anon`, `authenticated`,
`service_role` and (from step 10) `platform_staff`; no other table in `platform`; `usage` on schema `platform` only for `supabase_auth_admin`
(from step 14).

### 3.2 The hook's console mode (step 14)

`create or replace function app.custom_access_token_hook(event jsonb)`: same signature, owner, grants, `stable`, `search_path = ''`. Order:

1. **Strip** (unchanged): `tenant_id`, `app_role`, `login`, `session_state`.
2. **PIN branch** (unchanged, the text of `20261025100500_access_token_hook_pin.sql:70–94`; SP2's source-equality test keeps proving it).
3. **Console branch (new), in its own `begin … exception when others` block:** if the input `session_id` is a well-formed uuid, and
   `platform.console_session` has that `session_id` with `auth_id = user_id`, and `platform.staff` has an active `platform_admin` row for
   `user_id`: set `role` to `platform_staff`, add no tenant claim, return. Any error → fall through.
4. **E-branches** (SP2's E1–E4, unchanged). If the incoming `role` is `platform_staff` (a stale value), it is set back to `authenticated`.

| Case | Claims | Proof |
|---|---|---|
| Console row, active platform admin | `role = platform_staff`, no `tenant_id`, `app_role`, `login` | 384 |
| Console row, staff row inactive or missing | E-branches: `authenticated` | 384 |
| Console row of another auth user (forged `session_id`) | ignored | 384 |
| `console_session` unreadable (grant revoked inside the test) | E-branches | 384 |
| PIN session | M11 branch exactly | 085 unchanged; SP2 source test |
| Every tenant #1 user (no console row) | exactly SP2's claims | 003, 085, 340 and SP2's 370 unchanged |
| Incoming `role = platform_staff`, no console row | `authenticated` + E-branches | 384 |

No new claim key: the key sets pinned by `085_access_token_hook_pin.test.sql` stay exact. Only the value of `role` changes in console mode.

### 3.3 Functions

All definer, `search_path = ''`, owned by `postgres`, `revoke all … from public` first. "Console caller" = `app.require_console()`.

**3.3.1 `app.require_console()` (step 10).** Raises 42501 `console_required` unless `auth.jwt() ->> 'role' = 'platform_staff'` and
`auth.uid()` is the active `platform_admin`; then raises P0001 `mfa_required` unless `app.jwt_aal() = 'aal2'` (AT3). Closed to every API
role. Every `platform_*` function for the console calls it first.

**3.3.2 Console mode switches (step 13).**
- `public.select_console() returns jsonb`, execute to `authenticated` only. Session id from the token (malformed → P0001 `session_missing`);
  the caller must be the active `platform_admin` (else 42501 `not_platform_staff`); `aal2` (else P0001 `mfa_required`). Deletes the
  session's `app.session_tenant` row; inserts its `console_session` row; writes `console.entered` when a row was added. Returns
  `{"changed": bool}`.
- `public.platform_leave_console() returns jsonb`, execute to `platform_staff` only: deletes the session's console row, writes
  `console.left` when one was deleted. A console token cannot call `select_tenant` (granted to `authenticated`), so this is the way out of
  console mode inside one session (AT12).
- `public.select_tenant(uuid)` (SP2 S4) is re-created with one more statement: it deletes the session's `console_session` row first.

**3.3.3 Metadata reads (step 11, AT4, AT5).** Execute to `platform_staff` only.
- `public.platform_tenants() returns jsonb`: `[{"id", "name", "organisation": {"id", "name", "tenantCount"}, "createdAt", "members":
  {"owner", "admin", "chef", "waiter"}, "digialtoAttached", "lastActivityDate"}]`, ordered by `lastActivityDate` desc nulls last, then name.
  - `members`: counts of active `app_user` rows by role; never a name.
  - `digialtoAttached`: an active `admin` row exists for the active platform admin's auth id.
  - `lastActivityDate`: the date, in the tenant's `timezone`, of its newest `public.audit_event.created_at`
    (`20261022140000_audit_event.sql:47`); null when there is none. A date only, as UX §3 asks.

### 3.5 Hosts and `src/proxy.ts` (step 16, AT6)

- **Configuration:** `CONSOLE_HOST` (server env, e.g. `console.<product domain>`, FD10; host and optional port) and `APP_ORIGIN` (the venue
  app's origin, for "Entra nel locale"). Neither is a secret. **Unset `CONSOLE_HOST` = no console anywhere** (Q-P12): every console path is
  404 on every host. Validated in `src/lib/env/index.ts`.
- **Host kind:** `request.nextUrl.host` equals `CONSOLE_HOST` → console host; anything else → app host.
- **Console pages live at `src/app/(platform)/console/**`** (Q-P11), so their URLs are internally `/console/...`. On the console host the
  proxy rewrites the visible path `/<p>` to `/console/<p>` (`NextResponse.rewrite`, the nonce headers kept). The person sees the UX's URLs
  (`/`, `/locali/[id]`, `/registro`, `/avvisi`, `/login`, `/login/codice`), which would otherwise collide with the venue app's `/`,
  `/registro` and `/login`.
- **Rules:**

| Host | Request | Answer |
|---|---|---|
| app | `/console` or `/console/**` | 404 |
| app | `/api/platform/**` | 404 |
| console | any page path | rewritten to `/console/<path>`; no console page there → 404 (so every venue page is 404) |
| console | `/console/**` typed directly | 404 (it would become `/console/console/…`) |
| console | `/api/platform/**`, `/api/auth/mfa/account`, `/api/health` | passed on |
| console | any other `/api/*` | 404 |
| console | every answer | `x-robots-tag: noindex`; the page CSP is the same `cspForRequest` policy (`connect-src 'self'`) |

- **Signed out on the console host:** `updateSession` redirects to `/login?next=…` as today; the proxy then rewrites it to the console's sign-in
  page. The device cookie is never read there (no PIN path).
- **Host header:** the boundary is Postgres, not the host. A forged `Host` reaches only the console sign-in; console data needs the platform
  admin's password, code and console mode (R3).
- **Local and e2e:** app host `localhost:3000`, console host `127.0.0.1:3000`. Both are loopback hosts in `cookies.ts:8`, and cookies are
  host-only, so the two jars stay apart with no change to `cookies.ts`.

### 3.6 Sign-in and sessions

**Console host (the platform admin):**
1. `/login` (console) → `POST /api/platform/auth/password`. The hook gives E3/E4 claims (one admin row → that tenant; none or several → no
   tenant). If the account is not the active platform admin: sign out, 403 `not_console_account`, the form shows "Questo account non ha
   accesso alla console." (Q-P4).
2. `/login/codice` → `GET /api/me/mfa` (works with one tenant claim) or the account pair (no tenant claim) → code → `aal2`.
3. The console shell calls `POST /api/platform/console` on arrival → `select_console` → refresh → hook console branch → `platform_staff`.
4. Locali. A `platform_*` answer of `mfa_required` sends the person back to `/login/codice` with "Per continuare inserisci il codice."

**App host, the same account (to enter a venue):**
1. `/login` → password → hook: several memberships (or none) → no tenant claim.
2. SP2's 409 → `/login/scegli-locale` → `GET /api/me/tenants` → `my_memberships` at `aal1` → **`mfa_required`** (step 15) → 403 → client →
   `/login/codice`.
3. `/login/codice` → `GET /api/me/mfa` answers 403 `no_tenant` / 409 → the account pair → `aal2` → back to the chooser.
4. The chooser lists the venues (names and role) → tap → SP2's `switchTenant` → `select_tenant` → claims of that venue at `aal2` (T3.H).

**Two sessions on one device.** The console session and the app session are separate (host-only cookies). One mode per session holds on
both. Signing out of one does not sign out of the other. The break-glass reset ends both (§3.9.3).

### 3.9 Scripts

**3.9.1 `scripts/platform-admin.ts` (steps 7, 8, 12).** One entry, logic in `scripts/lib/platform-admin.ts` with injected I/O (the

## 4. Alternatives considered

- **Console in a separate Supabase project** (platform plan V1): the strongest separation; but the console would need the product project's
  secret key to read metadata, widening rule 2. Rejected as default; it is **V1**.
- **Console sessions as `authenticated` with a platform claim** (platform plan V2): no custom Postgres role, so no T2 risk; but any tenant
  policy that forgets to exclude console sessions leaks to them. Rejected as default; it is **V2** if T2.H fails.
- **One session across both hosts** (a parent-domain cookie): matches the UX's F4 and C6 literally and saves one sign-in; but it widens every
  session cookie to every subdomain, cannot work on `*.vercel.app` previews, and needs the product domain (FD10, open) before it can be
  tested. Rejected as default (Q-P3); it is **V3**.
- **Console on the app host under `/console`** (no second host): one cookie jar, no DNS; but every venue session could then be switched
  into console mode by a link, and the platform plan and ADR-037 decide a separate host (§2.2 point 3). Rejected.
- **A second root layout for the console:** Next.js allows several root layouts only without a top-level `app/layout.tsx`; the repo has one
  (`src/app/layout.tsx`). Rejected for a `(platform)/console/layout.tsx` under the shared root, which renders only `children`.
- **Reusing the tenant code page for the platform admin with a fake tenant claim:** no new routes; but it would mean minting claims the
  hook never gave. Rejected for the account-level pair (§3.3.5).
- **Refusing a venue account on the console only after its code** (the UX §4 order): reveals nothing before the second factor; but it would
  store failed-code rows for venue users in `platform`, and the account already proved its password. Rejected as default (Q-P4); **V6**.
- **A console page to enrol the platform admin's factor:** no terminal step; but it needs a "pending staff" state before bootstrap, which
  bootstrap's own rule forbids (AT11). Rejected for `enrol-factor` (Q-P5); **V7**.
- **A console button for the break-glass reset:** one place for the founder; but it needs the secret key in a user-facing route and a person
  on screen. Rejected (Q-P7); **V4** records a request instead.
- **A per-tenant "notified" table for notices:** a clear place; but `platform.audit_event` already holds dated, per-tenant, append-only rows.
  Rejected.
- **A foreign key from `platform.audit_event.tenant_id` to `public.tenant`:** referential safety; but SP10's erasure must keep the rows.
  Rejected.
- **Trigger functions of platform tables in `app`** (as SP2 did for the tenant side): one place for helpers; but it moves the `app`
  catalogue pins for functions no API role can reach. Rejected for `platform`.
- **Widening pgTAP 365 to count `platform` triggers** so that step 1 moves it: matches the brief's expectation; but every platform table's
  append-only triggers would then move a P2-7 pin. Rejected as default (Q-P2); **V11**.

## 6. Risks and mitigations

**Security and privacy**
- **R1. Tenant #1 locked out by the hook change.** The console branch runs only with a console row, which only `select_console` writes for the
  active platform admin; 003, 085, 340 and SP2's 370 unchanged in the same commit; staging first; SP2's fix-forward pattern applies.
- **R2. `platform_staff` accepted locally, refused or mishandled hosted.** T2.H gates steps 10–12; V2 is drafted. Storage and Realtime are in
  T2.H (f, g).
- **R3. The console reachable from a venue host, or venue pages from the console host.** Proxy rules (AT6); the real boundary is Postgres
  (`platform_staff` has no table grant; console functions check role, staff row and `aal2`). A forged `Host` reaches only the sign-in.
- **R4. The platform admin account is the strongest credential** (platform plan §11). SP3 adds a second sign-in surface. Mitigations: `aal2`
  for every console function and for `select_console`; the account-level lock (step 9); no "Password dimenticata?" on the console (Q-P6); a
  venue account is signed out at once on the console (Q-P4). Residual: the founder's password manager and authenticator device; a hardware
  factor stays a founder question (F-5).
- **R5. A metadata key leaks business data.** The whitelist and deny-pattern test (AT5) runs on every `platform_*` function; later
  milestones must extend the whitelist on purpose.
- **R6. An e-mail address in the platform audit or a script's output.** A CHECK refuses `@` in `detail` for every writer; the script tests
  scan captured output; `actor_auth_id` is an id; the bootstrap lookup never echoes the address.
- **R7. Realtime tells a console subscriber that an event happened** (SP0 finding). No client, `connect-src 'self'`, publication pinned empty
  (step 20); V5 for the day a table is published.
- **R8. The platform admin cannot pass its code without a tenant** (flag 3). Step 9's account pair; step 15 maps `mfa_required` to the code
  page; step 23 proves the flow end to end.
- **R9. A break-glass reset signs the person out of every venue, and the console.** Accepted: the factor belongs to the login. The script's
  confirmation says so (step 6). If the platform admin itself loses its factor, `mfa_reset_service_begin` needs one of its `app_user` rows
  as target; before SP4 it may have none. Mitigation: the account keeps two factors (the second slot, `MFA_MAX_FACTORS`); otherwise the
  founder removes the factor in the Supabase dashboard. Runbook note (step 24).
- **R10. The wrong venue name on screen.** The venue wordmark is the constant `t("venue.name")` until SP9 (step 21); inside venue B the
  platform admin sees SP2's account-control venue name (multi-venue login, SP2 Q-S5).
- **R11. Two sessions confuse the founder** (signed out of one host, still in on the other). The confirm text says a separate sign-in is
  needed; the runbook explains it; V3 if it proves a burden.
- **R12. Personal data.** `platform.audit_event` holds auth ids, tenant ids and codes; `platform.console_session` holds session ids for at
  most 31 days; `platform.mfa_failure` holds the platform admin's failure times for the lock window. No new category of data, no new
  processor. The audit's retention is a founder question (F-4).
- **R13. Secret-key holders can write any platform audit row.** They are trusted by design (platform plan §2.2); every such row says origin
  `script`, which the Registro shows ("Script", C7).

**Delivery**
- **R14. Stacked on an unmerged branch.** SP2 can still change S1 or renumber; SP3 rebases and re-computes the 346/359/229 values. The pins
  are re-taken by the builder after each rebase, never copied.
- **R15. Migration timestamp collision.** `sp3-preserves` and the newest-migration pins turn CI red; renumber before merging.
- **R16. e2e host emulation.** `localhost` and `127.0.0.1` are distinct cookie hosts (cookies are host-only), so the pair works without DNS;
  WebKit is not used for the console spec.
- **R17. The VAT guard blocks a legitimate VAT correction.** Correct a tenant's VAT by moving it, with both columns, to the right
  organisation; a typo on an organisation that tenants point at needs a privileged procedure later (SP2 build notes). Runbook note.

**Performance:** console reads are a handful of definer calls by one person; the hook adds one indexed lookup (`console_session` primary key)
plus one on `platform.staff` only when a console row exists. No target number is promised.

**Dependencies (name, licence, why):** none added. The setup key is printed as text (no QR library).

**Where every secret and credential lives (new or changed):**
