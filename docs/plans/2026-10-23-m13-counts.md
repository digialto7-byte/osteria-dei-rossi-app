## 3. Design

### 3.1 Decisions

1. **Balances stay derived (plan §3.6 rule 1).**
   - A count changes stock only through `count` rows in `stock_movement`.
   - `count_line.expected_qty` is a recorded fact of the count (the snapshot the difference is computed from), never read as a balance (ADR-012). The nightly check verifies that the posted rows equal `counted − expected` for every closed line (§3.1.10).
2. **Sessions and lines.**
   - A session belongs to one location (`app.resolve_location`: the only active location by default, else `location_required`).
   - **One open session per location** (partial unique index). Starting the same type again while one is open **resumes** it (200 `resumed: true`); starting the other type → 409 `count_open_exists`.
   - Lines are created at start, one per ingredient, ordered by name (`collate "C"`):
     - `daily`: active, `is_stock`, `is_critical` ingredients; none → 422 `no_critical_ingredients`;
     - `monthly`: every active `is_stock` ingredient, plus any ingredient (active or not) whose total at the location is not zero.
   - States: `open` → `closed` or `cancelled`. Nothing is deleted. A closed or cancelled session and its lines are immutable (triggers).
3. **Entering a line (`count_record_lines`): the snapshot (ADR-012).**
   1. role check; session of the tenant (P0002 `count_not_found`); session row `FOR SHARE` (concurrent savers share; a close waits for them and they wait for a close);
   2. status `closed` → `count_closed`, `cancelled` → `count_cancelled` (409);
   3. every ingredient must be a line of the session (P0002 `count_line_not_found`); a repeated ingredient in one call → `duplicate_line` (422);
   4. `app.lock_ingredient_stock(tenant, ids)` (id order);
   5. per line: `qty` null clears the line (counted, expected, entered_at, entered_by → null); else `counted_qty = app.count_qty_base(…)` (≥ 0, 4 dp, ≤ `COUNT_QTY_MAX`), `expected_qty = app.location_on_hand(tenant, ingredient, location)`, `entered_at = now()`, `entered_by = app.app_user_id()`;
   6. return each line `{ingredientId, expectedQty, countedQty, differenceQty, enteredAt}`.
4. **Closing (`count_close`), one transaction.**
   1. role check; session `FOR UPDATE`; `count_closed` / `count_cancelled` (409);
   2. no counted line → 422 `count_empty` (the user cancels instead);
   3. `app.lock_ingredient_stock(tenant, ids of the counted lines)`;
   4. costs read once: `app.ingredient_unit_costs(tenant, ids, null)`;
   5. for each counted line with `d = counted − expected ≠ 0`: `app.post_count_adjustment(tenant, user, ingredient, location, d, session, now(), unit_cost)` (§3.1.5). Lines with `d = 0` and uncounted lines post nothing (AT2);
   6. session → `closed`, `closed_at`, `closed_by`;
   7. `audit_event` `count_session.closed` with `after {type, lines_counted, lines_skipped, lines_with_difference}` (so a count with no difference is in the audit log too);
   8. return `{sessionId, closedAt, linesCounted, linesSkipped, linesWithDifference, lines: [{ingredientId, differenceQty}]}`. No €.
   - **No `negative_stock` alert from a count.** A total can end below zero only through outflows recorded after the line was entered, and those already alerted.
5. **Posting a difference (`app.post_count_adjustment`, ADR-012).** With the ingredient's buckets at the location under the lock (positive lots `P` from `app.fefo_buckets` with `raw_lot_id not null`, the unlotted bucket `U`, total `E`) and `T = E + d`:
   - `T ≥ P`: one row `T − P − U` on the unlotted bucket (skipped if 0);
   - `0 ≤ T < P`: take `P − T` from the lots in FEFO order (one row `−slice` per lot), and one row `−U` on the unlotted bucket if `U ≠ 0`;
   - `T < 0`: one row `−L` per positive lot, and one row `T − U` on the unlotted bucket.
   - Every row: `type 'count'`, `ref_type 'count_session'`, `ref_id` = session, `reason_code` null, `unit_cost` = the basis passed in (null allowed, never 0), `effective_on = app.venue_date(p_at, tenant tz)`, `created_by` = the closer.
   - The rows of one call sum to `d` exactly; no lot ends below zero (asserted in step 2 and by the property test, step 16).
6. **Cancel (`count_cancel`).** Open → `cancelled` (`cancelled_at`, `cancelled_by`) and `audit_event count_session.cancelled`; else 409. No movement.
7. **Critical flag (`set_ingredient_critical(p_ingredient, p_critical)`).** Owner, admin, chef (PRD 2.1 "the chef flagged"; Q36). Only `is_stock` ingredients (422 `ingredient_not_stock`); P0002 for a foreign id. Writes `audit_event ingredient.critical_changed` (before/after `{is_critical}`) only when the value changes. A definer procedure, so the chef's lack of an UPDATE policy on `ingredient` is unchanged.
8. **Variance (expected vs counted).**
   - `count_variance(p_session)` (owner, admin, chef; closed sessions only, else 409 `count_not_closed`): per line `expectedQty`, `countedQty`, `differenceQty` (= counted − expected) and `postedQty` (Σ of the session's count rows for that ingredient, from the ledger); `linesSkipped`. Quantities only.
   - `count_variance_costs(p_session)` (owner, admin; `app.require_cost_reader()` first): per line `valueEur = Σ(qty × unit_cost)` of the posted rows, null when a row has no cost; totals `valueEur` (net), `lossEur` (Σ of negative line values), `gainEur`, `unvaluedCount`. Numbers rounded to 4 dp; the screen formats cents.
9. **Reconciliation (`stock_reconciliation(p_from, p_to, p_location)`; PRD identity).**
   - Owner, admin, chef; quantities only; `p_location` resolved like the other procedures; `p_from > p_to` → `range_invalid`, more than `RECONCILIATION_RANGE_MAX_DAYS` → `range_too_long`.
   - Per ingredient with any movement at the location dated on or before `p_to`, or a count line there in the period, one row by `effective_on`:
     - `openingQty` = Σ qty with `effective_on < p_from`;
     - in the period: `receiptsQty` (Σ receipt), `consumptionQty` (−Σ consumption, reversals included), `wasteQty` (−Σ waste, reversals included), `transfersInQty` (Σ transfer rows with qty > 0), `transfersOutQty` (−Σ transfer rows with qty < 0), `countAdjustmentsQty` (Σ count), `otherQty` (Σ of any type not listed; 0 today, the guard for future types);
     - `closingQty` = Σ qty with `effective_on ≤ p_to`;
     - `balanced` = (opening + receipts − consumption − waste + in − out + adjustments + other = closing), computed in SQL;
     - the latest closed count line in the period (session `closed_at` Rome date in range, `counted_qty` not null; daily or monthly): `countedQty`, `countedAt` (`entered_at`), `countSessionId`;
     - `afterCountQty = closingQty − countedQty` (movements recorded after that count) and `matchesCount = (afterCountQty = 0)`; both null when not counted.
   - The PRD identity "opening + receipts − consumption − waste ± adjustments = counted" is `balanced and matchesCount`, with "± adjustments" = count adjustments + transfers in − out. On a month that ends with the monthly count and nothing recorded after it, it holds for every ingredient (AT1).
10. **Nightly invariant check (ADR-012; plan §3.6 rule 7, §3.9).**
    - Runner `app.run_ledger_invariants(p_at timestamptz default now()) returns integer`:
      1. `v_run := app.job_run_begin('ledger-invariants')`;
      2. for each tenant (id order), in its own `begin … exception` block: findings = `app.ledger_checks_body(tenant, p_at)` ∪ `app.job_health_checks(tenant, p_at)`; if any, `app.try_raise_alert(tenant, 'ledger_drift', 'tenant', tenant, payload, null, null, p_at, null, 'ledger_invariants')`; on any error `app.record_alert_refusal(tenant, 'ledger_drift', 'tenant', tenant, 'ledger_invariants', 'check_failed', sqlstate)` and `raise warning` with the SQLSTATE only;
      3. `app.job_run_end(v_run, no tenant failed, case when failed then 'check_failed' end, number of tenants with findings)`;
      4. returns that number. Finding drift is not a job failure.
    - **Ledger checks** (`app.ledger_checks_body(p_tenant, p_at) returns table (check_key text, rows_count int, sample_ids uuid[])`): **one SQL statement** (`union all` of the checks), so every check reads one snapshot and a half-committed write is never seen. Each check returns at most one row (count and up to `DRIFT_SAMPLE_IDS` ids). After M12/M13:

      | `check_key` | Finds |
      |---|---|
      | `lot_receipt_missing` | a `raw_lot` without exactly one `receipt` row with the same lot, ingredient, location, `ref_id = invoice_line_id` and `qty = qty_received` |
      | `receipt_lot_mismatch` | a `receipt` row whose lot is missing or differs (ingredient, location, quantity, invoice line) |
      | `movement_user` | a `stock_movement`, `raw_lot`, `audit_event` or `count_session` (`started_by`, `closed_by`, `cancelled_by`) whose user is not an `app_user` of the same tenant ("every movement has a user": the FK is not tenant-composite) |
      | `lot_negative` | an (ingredient, location, lot) bucket below zero (neither M12 nor M13 can write one) |
      | `reversal_mirror` | a reversal row that does not mirror its original (also refused by the M12 trigger) |
      | `transfer_unbalanced` | a transfer operation (`ref_type, ref_id`, per ingredient, reversals included) whose rows do not sum to 0 |
      | `count_mismatch` | a closed session line whose posted rows ≠ `counted − expected` (0 for an uncounted line), or a `count` row whose session is missing, of another location, or not closed |

    - **Job health** (`app.job_health_checks(p_tenant, p_at) returns table (check_key text, rows_count int, sample_ids uuid[], job_key text)`):
      - `job_stale` per job of the cadence list: `alert-rules` with no successful finished run in the last `ALERT_RULES_STALE_HOURS` (3); `ledger-invariants` whose previous run (before this one) started more than `INVARIANTS_STALE_HOURS` (26) ago. A job is not judged before `monitoring_since + its window`, where `monitoring_since` = the oldest `app.job_run` row of any job (so a fresh database never alerts on its first night).
      - `job_failed`: runs with `ok = false` in the last `JOB_LOOKBACK_HOURS` (24), per job.
      - `job_unscheduled`: `extract-invoices`, `alert-rules` or `ledger-invariants` missing from `cron.job` or inactive.
      - `extract_backlog` (per tenant): an invoice of the tenant in `received` whose `created_at` is older than `EXTRACT_BACKLOG_MINUTES` (60) and whose `next_attempt_at` is null or passed (the `extract` job runs only when there is work, so a waiting invoice is the signal).
      - `alerts_refused` (per tenant): rows in `app.alert_refusal` for the tenant in the last 24 h (refused alerts, `rule_failed` of M9, `check_failed` of M8/M12 and of this job).
      - Job-level findings come from `app.job_run` (no tenant) and appear in every tenant's alert (ADR-012).
    - **Alert:** kind `ledger_drift`, entity `tenant`, one per tenant per Rome day (dedup), severity `critical`, audience `{owner}`, not cost-bearing. Payload:

      ```
      {checks: [{check_key, rows_count, sample_ids: [uuid…≤5], job_key?}], checked_at}
      ```

      Codes, counts and ids only: it passes every M6 guard (no money key or value). Owner only, so the chef allow-list does not apply.
    - **Not an email** (M6 founder decision, Q34). DigiAlto support does not read it (M6; Q33 → V1). `job_run` keeps the run with `items` = tenants with findings, which DigiAlto can read with the secret key.
    - **Schedule:** `cron.schedule('ledger-invariants', '45 2 * * *', 'select app.run_ledger_invariants()')`: 03:45 CET / 04:45 CEST, after the proposed 02:00 business-day cut-off (project Q18) and outside service hours. The function takes `p_at`; dates are computed in SQL.
    - **Service wrapper:** `public.ledger_invariants_run(p_at timestamptz default now()) returns jsonb` (`{tenantsWithFindings}`), `service_role` only, for the integration suite.
11. **Audit log (`audit_log`, owner and admin).**
    - One newest-first feed of:
      - stock operations other than receipts (receipts appear as `invoice.approved`): one entry per operation and ingredient (`ref_type, ref_id, ingredient_id`), `action` = `waste`, `consumption`, `transfer`, `count`, `reversal`, with `qty` (net; for a transfer the quantity moved and both locations), `unit`, `reasonCode`, `locationNames`, `at` = `created_at`, `byName`;
      - `audit_event` rows: `action`, `entityType`, `entityId`, `entityLabel` (invoice number, ingredient, recipe or count session label resolved in SQL), `at`, `byName`. `before`, `after` and `reason` are **not** returned.
    - Filters: `p_from`, `p_to` (Rome dates of `at`, default the current month; `range_invalid`, `range_too_long`), `p_kind` (`all`, `stock`, `events`), cursor `(at, id)`, `p_limit` 1–100.
    - No € in any entry.

    - Every public function: `security definer`, `set search_path = ''`, role check **first**, tenant from `app.tenant_id()`, user from `app.app_user_id()`, every query filtered by tenant, execute to `authenticated` only (revoked from `public`, `anon`, `service_role`), except `ledger_invariants_run` (`service_role` only).
    - Names of colleagues: the chef sees "un collega" for sessions started or closed by others (M12 rule); owner and admin see display names.
13. **Concurrency.**
    - Lock order for M13: session row (`FOR SHARE` to save lines, `FOR UPDATE` to close or cancel) → ingredient stock locks (id order). M12 writers take only stock locks, so no cycle exists (a saver holding the session waits for a writer; a writer never waits for a session).
    - Global order unchanged: recipe graph (shared) → ingredient cost locks → ingredient stock locks. Counts read costs without the cost lock (a basis read at close, like M12's outflows).
    - `approve_invoice` takes no stock lock (M12 known limit): a receipt committing while a line is saved is either in the snapshot or applied on top, never both.
    - The invariant check takes no lock; its ledger checks are one statement (§3.1.10).
14. **Quantities and units.** Lines accept `qty ≥ 0` with a unit in `UNITS_FOR_BASE[base_unit]`, converted by `app.count_qty_base` (the M12 conversion without the `> 0` rule): `unit_mismatch`, `qty_invalid` (negative, over `COUNT_QTY_MAX`, or more than 4 decimals after conversion). The count screen sends the base unit (one input per item).
15. **Dates.** `effective_on` of count rows = the Europe/Rome calendar date of the close (A1); counts closed after midnight belong to the new date (DST vectors in step 2). Report periods use `effective_on`.
16. **Personal data and retention.**
    - New personal fields: staff ids on sessions and lines (`started_by`, `closed_by`, `cancelled_by`, `entered_by`), as on movements. No free text (no note on a count; A4).
    - The audit log shows display names to owner and admin, who already read them.
    - The alert payload holds ids and codes, never names.
    - Retention follows the ledgers (project Q14). `app.job_run` (no personal data) is kept for good unless Q38 → V5.

3. **Reconciliation:** `GET /api/reports/reconciliation` → `stock_reconciliation`.
4. **Audit:** `/registro` → `GET /api/audit` → `audit_log`.
5. **Nightly:** pg_cron `ledger-invariants` → `app.run_ledger_invariants()` → `job_run` → per tenant checks → `try_raise_alert('ledger_drift')` → the owner reads it on `/avvisi` (M6).

## 4. Alternatives considered

- **Expected snapshotted at close, or at session start, or by timestamps:** rejected (ADR-012). Close erases movements recorded between counting and closing; start double-counts movements during a long count; `created_at` is the transaction start and misorders commits.
- **One unlotted row per difference:** rejected (ADR-012). Lots keep overstating after a shortage, and a negative unlotted bucket would survive the count.
- **Lot-by-lot counting:** rejected for the MVP; it breaks "one number per item".
- **Zero-net rebalancing when counted = expected:** rejected by AT2; known limit (§6).
- **Count differences as waste with reason `count_correction`:** rejected. Waste is a decision with a reason the chef records; a count difference is a finding. They stay separate types, and the variance report shows the € (Q37 → V4 puts count losses on the waste page too).
- **Reversible counts:** rejected. A count is an observation; a wrong one is replaced by a new observation, which keeps one rule ("the latest count is the truth").
- **Variance € in the same endpoint as quantities, filtered by role:** rejected (M12 pattern): one function and one route per audience keeps the column scans and the 403-before-RPC tests simple.
- **Audit log as a new table written by every procedure:** rejected. The movements and `audit_event` already hold who, what and when; a third copy could drift.
- **Invariant check inside the hourly rules body, or via a cron route with pg_net:** rejected. The first replaces a pinned function and runs 24 times a day; the second adds a network hop and a secret for pure SQL work.
- **Two alert kinds (`ledger_drift`, `job_stale`):** rejected (ADR-012); one alert per tenant per night lists everything.
- **A Postgres enum for `count_session.type`/`status`:** rejected; a text check avoids the `ALTER TYPE … ADD VALUE` transaction issue M12 hit (M12 T1) if a value is added later.
- **`fast-check` for the count property:** rejected (no new dependency); the M12 seeded generator gains a count action.

## 6. Risks and mitigations

- **Security / privacy**
  - *Definer functions bypass RLS:* role check first, empty `search_path`, tenant from `app.tenant_id()`, every query filtered by it, `authenticated` only; `app.*` has no API grant (steps 2–9). Foreign ids → P0002, never another tenant's data; composite FKs stop cross-tenant rows (step 1).
  - *€ reaching the chef or the waiter:* count rows sit in `stock_movement` (owner/admin RLS, unchanged); the quantity reads have no cost key (key scans in steps 4, 9; allow-lists in 13, 14); `count_variance_costs` is in `059`; screens render € only on the variance page for owner/admin (steps 17–19).
  - *The audit log exposes staff names:* owner and admin only, who already read them; no free text (`reason`, `before`, `after` not returned; step 6). The alert payload has no names.
  - *The service wrapper `ledger_invariants_run`:* `service_role` only (step 8); it can only add alerts the nightly job would add.
  - *IDOR:* malformed or foreign ids → 404 (steps 3, 13).
  - *CSRF:* writes require `application/json` (`withApi`).
  - *Personal data / retention:* staff ids on sessions and lines; retention follows the ledgers (project Q14); `job_run` holds none (Q38). No new processor.
- **Correctness (known limits)**
  - **A line counted equal to expected posts nothing**, so a negative "senza lotto" bucket with a correct total stays until a count with a difference (ADR-012). The stock screen keeps its "fai un conteggio" line.
  - **Receipts are posted at approval, dated by invoice date** (M5 Q1): goods delivered but not approved are counted as a surplus and added again at approval. Mitigation: the count screen shows `invoicesAwaitingApproval`; A3 asks to approve before counting.
  - **A reversal after a count** of the same ingredient adds back stock the count already saw missing. M12's `reverse_movement` is not changed (pinned in step 10); the audit log shows both.
  - **Job findings appear in every tenant's alert** (`job_run` has no tenant). Acceptable for one venue; revisit with multi-venue (ADR-012).
  - **No one outside the app hears about drift** (M6 decision): a drift alert waits until the owner opens `/avvisi`. Q33/Q34.
  - **Known limit: `count_close` reads the cost basis without the cost lock.** A price change committed while a close runs freezes the previous basis on the count rows. The ledger stays consistent (quantities are exact); only the variance in EUR of that count is one purchase stale.
  - **A stale open session** keeps old snapshots; the semantics still hold (later movements apply on top). The list shows it with "Riprendi" or "Annulla conteggio".
  - *Replacing nothing pinned:* steps 7–8 only insert a kind and add new functions; `raise_alert`, `try_raise_alert`, `alert_rules_body`, `run_alert_rules` and the M12 engine are pinned unchanged (step 10).
  - *Merge with M11:* `audit_event` and `job_run` lists, kind lists and the cadence list (header). The second to merge re-adds the union and adds `auth-purge` to the cadence list with a pgTAP case.
- **Unverified (checked in the named step)**
  - **T1** `SELECT … FOR SHARE` conflicts with `FOR UPDATE` and not with another `FOR SHARE` ([row-level locks](https://www.postgresql.org/docs/current/explicit-locking.html#LOCKING-ROWS)): proved by `close-vs-line` and `line-vs-line` (step 11).
  - **T2** One SQL statement sees one snapshot under READ COMMITTED ([transaction isolation](https://www.postgresql.org/docs/current/transaction-iso.html#XACT-READ-COMMITTED)): the ledger checks are one statement (source check in `117`) and `invariants-vs-approve` (step 11).
  - **T3** The plain-Postgres `cron` shim exposes `cron.job.active` like pg_cron ([pg_cron](https://github.com/citusdata/pg_cron)); if it does not, the shim gains the column (`supabase/tests-native/platform_shim.sql`) in step 8 and `117`'s `job_unscheduled` case proves it.
- **Performance / cost:** one venue; counts are one indexed sum per line; the reconciliation and audit reads use the new indexes (step 1); the nightly check scans the tenant's ledgers once. No figure is promised. No provider and no running cost.
- **Dependencies:** none added.
- **Plan changes to record in DigiAlto-Ops `clients/osteria-dei-rossi/context.md`:**
  - §3.3 counts row: `GET /api/counts`, `GET /api/counts/:id`, `POST /api/counts/:id/cancel`, `GET/PATCH /api/counts/critical`, `GET /api/reports/variance-costs` (owner/admin €) and `GET /api/reports/reconciliation` added; `GET /api/audit` is owner/admin.

  - §3.6 rule 7 and the PRD NFR: drift is an in-app alert (`ledger_drift`, owner), not an email (M6 decision); M13 AT5 "emailed" superseded.
  - §3.9: `ledger-invariants` at `45 2 * * *` UTC.
  - `audit_event`: entity `count_session`, actions `count_session.closed`, `count_session.cancelled`, `ingredient.critical_changed`.
