## Inputs for the next agent (steps 9 to 11): the exact RPC contract
All three are called with the user-session client (`supabase.rpc`), named parameters. A database error arrives with its SQLSTATE in `code` and, for P0001, the machine code in `message` (for example `total_mismatch`). Dates are `YYYY-MM-DD` strings. Numbers are JSON numbers (`12.0000` parses as 12).

### `invoice_approval_preview` → `rpc('invoice_approval_preview', { p_invoice, p_location? })`
Read-only, any invoice status, owner and admin only (carries prices). Returns:
```
{ status: 'review'|'approved'|..., 
  blockers: [{ code, lineIds: [uuid] }],      // always an array; [] unless status is 'review'; lineIds [] when not line-specific
  receiptDate: 'YYYY-MM-DD' | null,
  payable: { grossAmount, creditedAmount, amount, dueDate: 'YYYY-MM-DD' | null, dueDateSource: 'invoice'|'supplier_terms'|null },
  receipts: <int>,                             // stock lines that would be received (received qty > 0)
  lines: [{ lineId, receivedQty, baseUnit, unitPrice, creditedAmount }],   // every active line, in line order
  locations: { required: <more than one active location>, options: [{ id, name }], defaultId: uuid | null } }
```
Per line: `receivedQty`/`unitPrice` null for a non-stock line or one that cannot be converted; `receivedQty` 0 and `unitPrice` null for a fully credited line; `baseUnit` null for non-stock; `creditedAmount` includes VAT, null when the credit has no VAT rate (that line is then in `credit_vat_rate_missing`). `unitPrice` is EUR per base unit, net of VAT. `payable.grossAmount`/`amount` are null if the invoice has no gross total (then `total_mismatch` is listed). The `p_location` argument only affects the location blocker. Numbers for `payable`, `lines` are exactly what `approve_invoice` would post (same SQL).

### `approve_invoice` → `rpc('approve_invoice', { p_invoice, p_location? })`
Returns `{ payableId, amount, dueDate, receipts }`. Nothing else changes in the response; the route reloads the review.

### `reject_invoice` → `rpc('reject_invoice', { p_invoice, p_reason? })`
Returns void (no body). `p_reason` optional; trimmed in SQL, blank stored as null, over 200 characters after trimming → `invalid_request`. The route should still validate (1 to 200 chars, no control or bidi characters) before calling.

### Errors (SQLSTATE `code`, message)
| SQLSTATE | message | Raised by | Suggested HTTP / `ErrorCode` |
|---|---|---|---|
| 42501 | `insufficient_privilege` | all three, first thing (chef, waiter, anyone not owner/admin; checked before the invoice is looked up) | 403 |
| P0002 | `not_found` | all three (unknown id, or another tenant's invoice, whatever its status) | 404 |
| P0001 | `invoice_already_approved`, `invoice_rejected`, `duplicate_invoice`, `duplicate_warning`, `invoice_not_in_review`, `total_mismatch` | approve (reject uses the first, second and fifth) | 409 |
| P0001 | `supplier_required`, `invoice_date_required`, `invoice_date_in_future`, `due_date_required`, `lines_unmapped`, `line_base_qty_unavailable`, `credit_vat_rate_missing`, `payable_negative`, `no_location`, `location_required`, `location_not_found` | approve | 422 |
| P0001 | `invalid_request` | reject (reason too long) | 400 |
| P0001 | `invoice_line_frozen` | any UPDATE of a line of an approved or rejected invoice (e.g. a review action that raced past the status check; seen when a review lock is missing, not in normal use) | 409 `conflict`, no database text |
| P0001 | `append_only`, `payable_immutable` | ledger triggers | 409 `conflict`, no database text |
| 23505 | unique violation on `payable`, `raw_lot`, `price_history`, `stock_movement_receipt_uq` | backstop only; not reachable in normal use | 409 `conflict` |

Approve raises the first applicable code in the order of the table in plan §3.1.4 (statuses, then `duplicate_warning`, `total_mismatch`, `supplier_required`, date, due date, `lines_unmapped`, `line_base_qty_unavailable`, `credit_vat_rate_missing`, `payable_negative`, location). The preview lists them all, in the same order.

### For the review payload (step 10)
- `decision`: newest `audit_event` with `entity_id = invoice id`, action `invoice.approved` or `invoice.rejected` (owner and admin can read it; RLS applies): `created_at`, `created_by` (join `app_user.display_name`), `reason` (null unless rejected), `after` for approved holds `payable_id, amount, due_date, due_date_source, receipt_date, location_id, receipts`.
- `posting`: `payable` row (`gross_amount, credited_amount, amount, due_date, due_date_source, status`) and the location name from `location`.
- `received` per line: `raw_lot` by `invoice_line_id` (`qty_received`, `base_unit`). Not-posted lines have no lot.
- Never select `stock_movement.unit_cost` or `supplier_item.last_price` into the payload (plan §3.6).
- `app.approval_*` helpers are not callable through the API; the preview is the only way to see them.

## Decisions made
- **Definer conditions met** (lead's list) for `approve_invoice`, `reject_invoice`, `invoice_approval_preview`, so the security-advisor warning for them can be recorded as accepted:
  - (a) `app.require_invoice_approver()` is the first statement (tests: chef and waiter get 42501 even for an unknown invoice id);
  - (b) `set search_path = ''` (pgTAP asserts `prosecdef` and `proconfig` for all three);
  - (c) the invoice is read with `tenant_id = app.tenant_id()`; helpers take the tenant from that invoice row; the item lock, `last_price` update, location list and every insert use `v.tenant_id` (owner B gets P0002 for A's invoice in any status, including approved);
  - (d) pgTAP: chef and waiter 42501, owner B P0002, anon "permission denied for function" (real call as `anon`), `service_role` and `public` without execute, `authenticated` with it (`035`, `036`).
- **Preview and chef:** the preview is owner/admin only (42501 for chef and waiter); nothing the chef can call returns a price.
- **`app.approval_blockers`** takes no locks and trusts no stored flag: totals gate and live-duplicate check are computed now. For a status other than `review` it returns only that status's blocker. Row 14 uses `app.resolve_location` inside an exception block, so the location codes are not duplicated.
- **`invoice_line_frozen`** trigger function is `SECURITY DEFINER` (empty search_path), so the status lookup does not depend on the caller's rights; it applies to every role including the migration owner.
- **Approval order** as in the plan: invoice `FOR UPDATE` → status gates → duplicate-key advisory lock → blockers (fresh statement, after the locks) → one read of the lines → `supplier_item` rows locked `ORDER BY id FOR UPDATE` → lot + movement (one CTE) → prices → `last_price` recomputed from `price_history` (newest `effective_on`, then `seq`) → payable → status → audit.
- **`reject_invoice`** validates the reason after the role check and before the lock.
- **`review_clear_duplicate`** replaced with `create or replace` in `…140600` (no earlier migration edited); same behaviour and grants plus one `invoice.duplicate_cleared` audit row (`before` has status, `duplicate_of`, `duplicate_warning_of`; `after` has status review and the override).

## Deviations from the plan
1. **Fixture credit figure.** The plan's `035` expects payable `credited_amount` 5,50. The fixture's fully credited line (g, 1 kg at 4,00 € with VAT 10) has a credit of 4,40 € by the plan's own formula, so the fixture posts gross 133,65, credited 9,90 (5,50 + 4,40), amount 123,75. The formula and line f's 5,50 are as specified; only the fixture total differs. No acceptance-test behaviour changes.
2. `025` gained three assertions (audit row for a cleared duplicate, for a dismissed warning, none for a not-flagged invoice), plan said one case.
3. **Race cases:** one extra case, `double-approve-nokey` (invoice 5 has no supplier VAT, name or number, so no duplicate key: only the invoice row lock separates the two approvals; with a key the advisory lock is a second, independent protection, see mutation results). `crossed-items` uses a third session that holds item Y so the queue order is fixed, and invoice 3 (later date) names Y first while invoice 4 names X first (the plan only said opposite order). With that, the later invoice commits first and the earlier-dated one last, which is what makes the `last_price` check mean something.
4. Preview detail the plan left open: `locations.required` is "more than one active location", independent of `p_location`; for a non-review status `blockers` is `[]` while `payable` and `lines` are still computed.
5. `app.approval_blockers` always returns `lineIds` (an empty array when the blocker is not line-specific).

## Race-mutation results (scratch copies of the migrations via `MIGRATIONS_DIR`, repo untouched)
| Mutation | Checks that fail |
|---|---|
| `approve_invoice`: invoice select without `FOR UPDATE` | `double-approve-nokey` (error is no longer `invoice_already_approved`), `edit-then-approve` (lot 2,0000 instead of 1,5000; credited 0,00 instead of 7,01). `double-approve` (keyed invoice) still passes: the advisory lock and the freshly computed blockers also stop it. |
| the same plus no advisory lock | the two above and `double-approve` |
| item locks in line order instead of `ORDER BY id` | `crossed-items`: "deadlock detected", invoice 3's approval fails, one payable, wrong `last_price` |
| `last_price` set from the invoice's own price instead of recomputed from the ledger | `crossed-items`: X 11,0000 instead of 10,0000 and Y 8,0000 instead of 12,7500 |
| `app.lock_review_invoice` without `FOR UPDATE` | `approve-then-edit`: the edit fails but with `invoice_line_frozen` instead of `invoice_not_in_review`. The line is still protected, by the second layer (frozen trigger) |
So every new case fails when its protection is removed, and two protections have a backup layer (advisory lock for the approval, frozen trigger for the edit). The lock-order test works because the third session fixes the queue order; no sleeps are used.
