## VT1: is framing the signed-URL PDF in an iframe feasible?

Probably yes, but not proven. Evidence and gaps:

- The Storage API's renderer (`src/storage/renderer/renderer.ts` on `supabase/storage` master, read over `raw.githubusercontent.com`) sets `Accept-Ranges`, `Content-Type`, `ETag`, `X-Robots-Tag: none`, `Content-Length`, `Expires`/`Cache-Control` and, only with `?download`, `Content-Disposition`. It sets no `X-Frame-Options` and no `Content-Security-Policy`. I did not find either elsewhere in the files I could fetch; the tree listing was not available, so this is not exhaustive.
- Our own pages are not an obstacle: `frame-ancestors 'none'` in `security-headers.ts` governs who may frame our pages, not what we frame. M25's nonce CSP must allow the Storage origin in `frame-src` and `img-src`.
- Not checked: the hosted Supabase gateway (it could add headers the Storage code does not), the local stack, and Chrome's own PDF viewer. A CSP with `sandbox` on the response would make Chrome refuse to render a PDF in a frame (risk T2), so the e2e fails on `sandbox` as well as on `frame-ancestors` and `X-Frame-Options`.
- To close it: run `invoice-review.spec.ts` in CI (local stack), and do the manual check on the staging preview that the plan asks for (open `/fatture/<id>/revisione` at 1280 px and check the frame shows the PDF). If either fails, VT1.1 applies: PDFs get the phone's "Apri documento" link on the laptop too, photos stay inline.
