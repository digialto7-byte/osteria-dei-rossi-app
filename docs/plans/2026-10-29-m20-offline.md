## 1. Goal and scope

- **Goal:** a waiter keeps taking orders through Wi-Fi dead spots and a 30-minute Vercel or Supabase outage.
  - Every order write is kept on the phone in an IndexedDB outbox and replayed in order once the connection is back.
  - The server applies each one exactly once and resolves it through the existing procedures.
  - Conflicts and refusals are shown to the waiter, never dropped silently.
- **In scope:**
  - **Op format and IndexedDB outbox** (`src/pwa/outbox.ts`) for the six order writes that exist on `main`: open a table, add a line, edit or move a line, remove an unsent line ("Rimuovi"), send ("Invia"), void ("Storna").
  - **Replay engine** (pure, `src/lib/sync/`):
    - ordered by `seq`;
    - stops on a network error, a 5xx or a 503;
    - keeps 409/422 outcomes and shows them;
    - exponential backoff capped at 15 s;
    - one replayer per device;
    - user binding.
  - **`POST /api/sync`** in front of a new SQL dispatcher `public.apply_op(p_op)`:
    - one transaction per op;
    - idempotent through `applied_op`;
    - calls the existing procedures unchanged;
    - per-op results `applied | duplicate | conflict | rejected`.
  - **`applied_op` table** (append-only, RLS on, no API role reads it), added to the demo purge list.
  - **Hand-written service worker** `public/sw.js`:
    - static assets cache-first;
    - three shell pages network-first;
    - four cost-free waiter reads network-first with a cache fallback, double allow-listed;
    - nothing else cached.
  - **Web manifest** (`src/app/manifest.ts`, Next.js built-in).
  - **Screens:** a pending-ops badge, "In coda" line badges, an offline banner, conflict and refusal notices, the held-ops banner (user binding) and a clock-skew warning, in Italian and English.
  - **The comanda moves to a static route** `/tavoli/comanda?s=<sessionId>` so it can open offline. `/tavoli/<id>` redirects there.
  - **Tests:** pgTAP `208`–`214`, four race cases, Vitest (with `fake-indexeddb`), an integration suite, and Playwright on `phone` and `phone-webkit`.
- **Out of scope:**
  - **Offline for owner and kitchen writes.** These stay online-only: invoices, menu, batches, counts, settings, table and coperto settings, and every chef write. The owner's and admin's **order** writes on the comanda use the same queue as the waiter's (Q117 → V2).
  - Offline changes of covers and "conto richiesto" (`PATCH /api/table-sessions/:id`) (Q123 → V7).
  - Close and bill (M21 adds the `close_table` kind, §3.4).
  - Background Sync, push and periodic sync (ADR-005).
  - Precaching owner pages; offline first load (the first load must be online, ADR-005).
  - PWA icons, until the logo is approved (Q121 → V5).
  - Retention or pruning of `applied_op` (Q120 → V4).
  - The full CSP (M25; §3.4 lists what M25 must allow).

## 3. Design

### 3.1 Decisions

1. **One write path, through the outbox.**
   - On the comanda and the table list, every write of the six kinds becomes an op in the outbox and is replayed through `POST /api/sync`, for waiter, owner and admin alike (Q117 → V2).
   - The online endpoints of §2.1 stay as they are, for tests and as the documented API. The screens stop calling them.
   - Owner and kitchen screens elsewhere keep calling their endpoints online.
2. **Op format (wire).**

   ```ts
   { opId: uuid v4,             // made on the phone; the idempotency key
     seq: int ≥ 1,              // monotonic per device (IndexedDB), the replay order
     kind: "open_table" | "add_line" | "edit_line" | "remove_line" | "fire" | "void_line",
     clientTs: ISO 8601 with offset, // the phone's instant; for line writes it IS clientUpdatedAt
     userId: uuid,              // app_user.id of who queued it (user binding)
     payload: { … } }           // per kind, below
   ```

   | Kind | Payload (strict) | Procedure called by `apply_op` (unchanged) | `clientTs` used as |
   |---|---|---|---|
   | `open_table` | `{tableId, sessionId, covers}` | `public.open_table(tableId, sessionId, covers)` | the 120 s future bound only (opening has no last-write-wins) |
   | `add_line` | `{sessionId, lineId, menuItemId, qty?, course?, segue?, note?, isShared?}` | `public.add_order_line(sessionId, payload − sessionId + {clientUpdatedAt: clientTs})` | `clientUpdatedAt` |
   | `edit_line` | `{lineId, qty?, course?, segue?, note?, isShared?}` (≥ 1 field) | `public.update_order_line(lineId, payload − lineId + {clientUpdatedAt})` | `clientUpdatedAt` |
   | `remove_line` | `{lineId}` | `public.remove_order_line(lineId, {clientUpdatedAt})` | `clientUpdatedAt` |
   | `fire` | `{sessionId, lineIds}` (1–50 distinct) | `public.fire_course(sessionId, {lineIds})` | the 120 s future bound only (firing beats any stamp, ADR-019) |
   | `void_line` | `{lineId, reason}` | `public.void_line(lineId, {reason, clientUpdatedAt})` | `clientUpdatedAt` |

   - **One stamp per op:** the payload never carries `clientUpdatedAt`; it comes from `clientTs` (22023 otherwise).
   - **The stamp:** line-write stamps follow ADR-017's `clientStamp(now, line)`. The stamp is the phone's clock, but at least the stamp of the line **as the phone shows it** (server copy plus queued ops) + 1 ms. It is computed when the op is queued, not when it is sent.
   - **Ids:** session and line ids are made on the phone (`newSessionId` / `newLineId`), so later ops can reference rows created offline (ADR-005).
   - **Large fires:** a fire of more than 50 lines is split into several ops by `chunkFireIds` (M19).
3. **Per-op outcome classes** (decided in SQL, §3.2):

   | Status | Meaning | Examples | Stored in `applied_op` |
   |---|---|---|---|
   | `applied` | the procedure ran and wrote (or found its own replay) | add `created: true/false`; fire with `skipped`; edit `changed: false` | yes |
   | `conflict` | the server's state beat the op: an irreversible state, or a later stamp | edit/remove/void result `{conflict: {reason}}` (`stale`, `fired`, `voided`, `session_closed`); P0001 `session_closed` from add or fire; P0001 `table_already_open` | yes |
   | `rejected` | the op itself cannot apply | P0002 `*_not_found`; P0001 `item_unavailable`, `line_id_conflict`, `session_id_conflict`, `table_inactive`, `covers_invalid`, `client_time_invalid`, `qty_invalid`, `note_invalid`, `course_invalid`, `void_reason_invalid`, `price_missing`, `recipe_not_producible`; 22023 `invalid_request` | yes |
   | `duplicate` | this `opId` was already applied in the tenant | the stored row's status and result are returned as `stored` | no (nothing new) |

   - Any other SQLSTATE is **not caught**: deadlock 40P01, serialization 40001, timeout 57014, connection errors, XX000.
   - The op's transaction then rolls back and nothing is stored. The route stops the batch with `unavailable` (decision 6), so the phone retries later.
4. **Idempotency through `applied_op`.**
   - `apply_op` first takes `pg_advisory_xact_lock(hashtextextended('applied_op:' || tenant || ':' || opId, 0))`. It then looks up `(tenant_id, op_id)`:
     - found with the same `payload_hash` → `duplicate` with the stored result;
     - found with another hash → P0001 `op_id_reused` (nothing written, nothing stored);
     - not found → dispatch, then insert the row **in the same transaction**.
   - A second concurrent call with the same op waits on the advisory lock, then answers `duplicate` (race `sync-same-op`).
   - `payload_hash = encode(sha256(convert_to((p_op -> 'payload')::text || '|' || kind || '|' || clientTs, 'UTF8')), 'hex')`.
     - jsonb text output is canonical (sorted keys), so the same payload gives the same hash.
     - `sha256(bytea)` is built into PostgreSQL 11+, so no extension is needed.
   - The procedures' own idempotency stays underneath (client ids, skip rules, equal-stamp no-ops). A **new** `opId` carrying an old write is still safe (`209` proves it).
5. **Conflict rule (PRD 3.1, 3.5; ADR-005, ADR-017).** `apply_op` adds no rule of its own; it **reuses the procedures**.
   - **Irreversible states win** whatever the stamp:
     - a fired line can only be voided (`update_order_line` → `conflict fired`);
     - a voided line stays voided (`conflict voided`);
     - a closed table accepts nothing (`session_closed`);
     - an open table cannot be opened again (`table_already_open`);
     - firing ignores stamps.
   - **Otherwise last write wins per line by `client_ts`:**
     - an older stamp → `conflict stale`;
     - an equal stamp from another user → `stale`;
     - an equal stamp with equal content from the same user → `changed: false`.
   - **Recorded with the receipt time.** `applied_op` stores `client_ts` beside `received_at` (`clock_timestamp()` when `apply_op` starts). The line itself keeps `client_updated_at` (the stamp) and `updated_at` (server time), as in M18. Any LWW decision can therefore be audited against arrival order (`210`).
   - **Old stamps are accepted:** there is no lower bound, so a 30-minute-old queued edit is judged on its stamp. A stamp more than 120 s ahead of the server is `rejected client_time_invalid` (ADR-017) for every kind.
6. **Batch processing and stops (server).** `/api/sync` receives 1–20 ops with strictly increasing `seq` and applies them **one RPC (one transaction) per op, in order**. It stops early, returning the processed results and `stopped: {opId, reason}`, when:
   - **`unavailable`:** an op's RPC fails with an infrastructure error (decision 3). If that is the first op, the reply is 503 `sync_unavailable`.
   - **`user_mismatch`:** `apply_op` raises 42501 `user_mismatch` (decision 9).
   - **`dead_entity`:** an `open_table` or `add_line` op ends `conflict` or `rejected`, directly or as a `duplicate` of one.
     - The session or line it should have created does not exist, so later ops may name it. The phone prunes them (decision 8) before sending the rest.
     - Without this stop, a queued fire of `[deadLine, okLine]` would be refused whole by `fire_course` (`line_not_found`), and the good dish would not be sent.

   Other conflicts and refusals do **not** stop the batch (AT2: "a 409 op is kept and shown, and later ops continue").
7. **Replay algorithm (client, pure `src/lib/sync/replay.ts`, IO injected).**
   1. **Triggers:**
      - right after an op is queued;
      - the `online` event;
      - `visibilitychange` to visible, and `focus`;
      - a timer while ops are pending, at the backoff delay.

      `online`, focus and a new op bypass the backoff wait. Background Sync is not used (ADR-005).
   2. **Lease:** one replayer per device.
      - `meta.replayLease {holder, until}` is written in an IndexedDB `readwrite` transaction (atomic), with a 30 s lease renewed per batch.
      - Another tab or engine that finds a live lease returns `busy`.
   3. **Backoff:** `delay(n) = min(15 000, 1 000 × 2ⁿ) × jitter`, with jitter uniform in [0,8; 1,2].
      - `n` counts consecutive failed attempts and resets on any reply with a result.
      - Constants: `SYNC_BACKOFF_BASE_MS` = 1 000 and `SYNC_BACKOFF_MAX_MS` = 15 000 (the 15 s of ADR-005).
      - A 30-minute outage costs about 120 small requests per phone.
   4. **Choose:** `sendable(ops, me)` walks the outbox in `seq` order:
      - an op of another user is **held**, and blocks later ops of the same session;
      - my op whose session is blocked **waits**;
      - my other ops are **sendable**.

      `takeBatch` then cuts the first ≤ 20 sendable ops within 64 KiB (`MAX_SYNC_OPS`, `MAX_SYNC_BODY_BYTES`).
   5. **Send** `POST /api/sync {ops}` and handle the reply:
      - **network error, 5xx, 503 or 429:** nothing is settled; `attempts` goes up on the batch's first op; backoff is scheduled and the run ends.
      - **401:** state `signedOut` (banner "Accedi di nuovo per inviare 3 operazioni"); the run ends and the ops are kept.
      - **403 `forbidden`:** state `forbidden`; the run ends.
      - **200:** each result moves its op from `outbox` to `outcomes`, all in **one** IndexedDB transaction, with its status, error or conflict. Then:
        - `stopped.reason = dead_entity` → `prune` (decision 8), then back to step 4;
        - `user_mismatch` → mark that user's ops held, then back to step 4;
        - `unavailable` → backoff, end of run;
        - no stop → back to step 4 until nothing is sendable.
   6. **Stuck op.** Ten consecutive server replies (not network failures) may leave the same first op unsettled (`SYNC_STUCK_ATTEMPTS`). The phone then raises the notice "Un'operazione non riesce a partire: avvisa il titolare." It **never** drops the op.
   7. **Clock skew.** Each 200 carries `serverTime`. When `|Date.now() − serverTime| > 60 s` (`CLOCK_SKEW_WARN_MS`), the badge warns: "L'ora del telefono è avanti di 4 minuti: correggila nelle impostazioni" (or "indietro").
8. **Pruning dead entities (client, pure `src/lib/sync/prune.ts`).** After a `dead_entity` stop, every op still in the outbox (of any user) is checked:
   - **Dead session** (an `open_table` that was not applied): every op on that session moves to `outcomes` as `dropped`, reason `session_not_created`. The notice lists the dishes by name so the waiter can re-enter them on the open table (Q122 → V6).
   - **Dead line** (an `add_line` that was not applied):
     - `edit_line`, `remove_line` and `void_line` on it → `dropped` (`line_not_created`);
     - a `fire` loses that id. If ids remain, the op is **rewritten with a new `opId` and the same `seq`**. If none remain, it is `dropped`.
     - A rewritten payload is a new op. That is safe: the old `opId` was never processed, because the server stopped before it.
   - `dropped` exists only on the phone; the server never sees those ops.
9. **User binding (ADR-005; AT8).**
   - **Phone:**
     - each op stores `userId`, plus `queuedBy {id, displayName}` (local only, never sent);
     - the replayer sends only the ops of the signed-in user. That user comes from `useMe`, or offline from `meta.lastUser`, since a login needs the network;
     - ops of other users stay **held**.
   - **Banner** (`role="alert"`, in the shell, on every screen of a table operator): "Ci sono 3 operazioni di Cameriere Demo non ancora inviate. Accedi come Cameriere Demo su questo telefono per inviarle." When that user logs in, the ops are sent.
   - **Server:** `apply_op` compares `userId` with `app.app_user_id()` **before** the `applied_op` lookup and raises 42501 `user_mismatch` (nothing written, nothing stored). The route stops with `user_mismatch`. A tampered or stale client therefore still cannot apply another person's op.
   - **Logout with pending ops of the current user:** "Esci" shows "Hai 3 operazioni non inviate. Restano su questo telefono e partono quando rientri." and then logs out (Q125 → V8).
   - **Logout and PIN login** clear the service worker's read cache (§3.6.3). They do **not** clear the outbox: held ops must survive.
10. **Negative stock (AT9; M19 §3.4).**
    - **A queued `fire` whose dish is now empty is applied.** `fire_course` books the shortage on the fallback batch and raises the contained `negative_stock` alert (ADR-002, ADR-019). M20 changes nothing on that path; `211` proves it through `apply_op`.
    - **A queued `add_line` whose dish is now at 0 portions is `rejected item_unavailable`.** ADR-017 says: "the replay of a not-yet-created line is refused as sold out … M20's outbox applies the same rule to queued adds". It is a dead entity, so any queued fire loses that id (decision 8). The waiter sees "Spezzatino con polenta (demo) è esaurito: non è stato registrato." (Q118 → V1).
11. **"Scarta" on a queued add (ADR-017 rule, outbox form).**
    - **Never sent (`attempts` = 0):** the add op is deleted from the outbox, together with the queued ops on that line. The line also leaves any queued fire (the decision 8 rewrite).
    - **Already attempted:** a `remove_line` op is queued after it. The add replays idempotently, then the removal voids it with `entry_removed`. If the add turns out refused, the removal is `rejected line_not_found`, shown as "niente da scartare".
    - No other queued op can be cancelled; the waiter corrects with a new edit or with "Storna".
12. **Optimistic display (pure `src/lib/sync/overlay.ts`).** The comanda shows the server view (from the network or the service-worker copy) with that session's queued ops applied on top:
    - `open_table` → a session stub (`tableName` from the op's local label, covers);
    - `add_line` → `pendingLine`;
    - `edit_line` → fields patched;
    - `remove_line` → hidden;
    - `fire` → lines flagged `queue: "fire"`, **state still `draft`**;
    - `void_line` → `queue: "void"`.

    The line badges read "In coda", "In coda per la cucina" and "Storno in coda". A queued fire never shows "In cucina", because the kitchen does not have it yet. The overlay is pure data shaping in `src/lib`; React only renders it (invariant).
13. **Overwritten warning (AT5, second order).**
    - The case: my edit is applied first (I got `applied`), then a colleague's later stamp wins.
    - `outcomes` keeps applied line writes `{lineId, clientTs}` for 24 h.
    - `overwrittenNotices(outcomes, view.lines, me)` flags a line whose server `clientUpdatedAt` is later than my applied stamp and whose `updatedBy` is someone else. The text: "Cameriere Due Demo ha cambiato «Spezzatino con polenta (demo)» dopo di te, alle 20:31."
    - With `conflict stale` in the other order, the losing waiter is always warned.
14. **Local storage of personal data.**
    - **IndexedDB, per device:**
      - ops until they are sent (dish names, notes, table names, staff display names in `queuedBy`);
      - outcomes for 24 h (`OUTCOME_KEEP_MS`).
    - **Service worker:** caches the four waiter reads (sale prices, staff names) until logout or the next version.
    - **Limits:** no guest data (the M18 note hint applies), and nothing leaves the EU path.
    - This is new on-device storage of data the app already shows (Q124).
15. **Implicit defaults, each tested with ≥ 2 candidates (lesson 1):**
    - two waiters on one phone and two sessions (binding and per-session blocking);
    - two lines in one fire, one of them dead (the rewrite);

**`20261109100100_apply_op.sql`** (step 2)
- **`app.sync_conflict_codes() returns text[]`** (immutable) = `{session_closed, table_already_open}`: the raised P0001 messages that count as `conflict`, not `rejected`.
- **`app.apply_op_dispatch(p_kind text, p_payload jsonb, p_client_ts text) returns jsonb`** (volatile, `search_path = ''`, revoked from every API role):
  - checks each kind's payload keys with `app.menu_keys_ok` (`clientUpdatedAt` in a payload → 22023);
  - for `open_table` and `fire`, whose procedures take no stamp, first calls `app.parse_client_time(to_jsonb(p_client_ts))`. A stamp more than 120 s ahead therefore raises P0001 `client_time_invalid` here, inside `apply_op`'s caught block, and is stored `rejected` like every other kind;
  - builds the procedure body (§3.1.2) and calls the **public** procedure: `public.open_table`, `add_order_line`, `update_order_line`, `remove_order_line`, `fire_course` or `void_line`.

  No business rule is re-implemented here.
- **`public.apply_op(p_op jsonb) returns jsonb`** (volatile, **security definer**, `set search_path = ''`, executable by `authenticated` only):
  1. **Role first:** `perform app.require_table_operator()` (owner, admin, waiter; 42501 otherwise). Then `v_tenant := app.tenant_id()` and `v_user := app.app_user_id()`.
  2. **Envelope:** `app.menu_keys_ok(p_op, {opId, seq, kind, clientTs, userId, payload}, same)`.
     - `opId` and `userId` must be uuid strings (`app.order_uuid`); `seq` an integer ≥ 1; `kind` one of `app.sync_op_kinds()`; `payload` an object; `clientTs` must match the M18 ISO regex.
     - Only the shape is checked here. The 120 s bound is judged inside the dispatch (above).
     - Any envelope failure → 22023 `invalid_request`, raised and not stored (there is no valid key to store it under).
  3. `userId <> v_user` → raise 42501 `user_mismatch`.
  4. Advisory lock (§3.1.4). Lookup by `(v_tenant, opId)` → `duplicate` or `op_id_reused`.
  5. `v_received := clock_timestamp()`. Then:
     ```
     begin
       v_reply := app.apply_op_dispatch(kind, payload, clientTs);
       v_outcome := case when v_reply ? 'conflict' then 'conflict' else 'applied' end;
     exception
       when sqlstate 'P0001' or sqlstate 'P0002' or sqlstate '22023' then
         get stacked diagnostics v_state = returned_sqlstate, v_msg = message_text, v_detail = pg_exception_detail;
         v_outcome := case when v_state = 'P0001' and v_msg = any(app.sync_conflict_codes()) then 'conflict' else 'rejected' end;
         v_reply := jsonb_build_object('sqlstate', v_state, 'message', v_msg, 'detail', <v_detail parsed as json, else null>);
     end;
     ```
     The exception block is a subtransaction, so a caught business error rolls back **everything the procedure wrote**. Any other SQLSTATE propagates and the whole call rolls back.
  6. `insert into public.applied_op (…) values (…, v_outcome, v_reply, …)`.
  7. **Return:**
     - normally: `{opId, status: v_outcome, receivedAt: v_received, stop, result: v_reply}`, where `stop = kind in ('open_table','add_line') and v_outcome <> 'applied'`;
     - for a duplicate: `{opId, status: 'duplicate', stop: <stored stop>, stored: {status, receivedAt, result}}`.
- **Errors raised (never stored):** 42501 (role, `user_mismatch`); 22023 `invalid_request` (envelope); P0001 `op_id_reused`; anything unexpected.
- The public name matches no `cost|margin|price`, so the `059` list stays at 13.

**`20261109100200_demo_purge_tables_m20.sql`** (step 7)
- `create or replace function app.demo_purge_tables()`: the list of `20261106100600`, with `'applied_op'` inserted at the head of the "M17/M18/M19 tables" group, before `order_line_cost`. It references `app_user` only, and the list is in delete order. The comment names M20; owner and grants are kept by `create or replace`.

No other migration. **No existing function is replaced:** `add_order_line`, `update_order_line`, `remove_order_line`, `open_table`, `fire_course`, `void_line`, `order_view` and `app.parse_client_time` stay byte-identical (`214`).

### 3.3 Lock order (no deadlocks)

`apply_op` adds one lock class **in front of** the M19 order:

`applied_op advisory (tenant, op_id)` → `dining_table` FOR UPDATE (open) / `table_session` FOR SHARE → `order_line` FOR UPDATE → ingredient stock advisory locks → `batch` rows → batch lot lock

- **The op lock:** only `apply_op` takes it, before anything else, and one op holds one key.
  - Calls with different ops never wait for each other on it.
  - Two calls with the same op: the second waits, then answers `duplicate`.
- **Inside:** each procedure takes its own M17/M18/M19 locks in their documented order. `apply_op` therefore adds no cycle with the online endpoints (races `sync-vs-online-edit`, `sync-fire-vs-online-fire`).
- **Scope:** one op = one transaction (one RPC). `/api/sync` holds no lock across ops.

### 3.5 API (Zod 4; `withApi`, strict bodies → 400, JSON only → 415, `{"error":{"code","message","details?"}}`, `Server-Timing` as M18)

```ts
// src/server/sync/constants.ts
export const SYNC_KINDS = ["open_table", "add_line", "edit_line", "remove_line", "fire", "void_line"] as const; // = app.sync_op_kinds()
export const MAX_SYNC_OPS = 20;
export const MAX_SYNC_BODY_BYTES = 65_536;
export const SYNC_BACKOFF_BASE_MS = 1_000;
export const SYNC_BACKOFF_MAX_MS = 15_000;
export const SYNC_STUCK_ATTEMPTS = 10;
export const SYNC_LEASE_MS = 30_000;
export const CLOCK_SKEW_WARN_MS = 60_000;
export const OUTCOME_KEEP_MS = 24 * 60 * 60 * 1_000;
export const SW_TIMEOUT_MS = 3_000;                     // mirrored in public/sw.js (step 16 checks equality)

// src/server/sync/schemas.ts — payloads reuse the M17/M18/M19 schemas, minus the stamp
const addPayload = addLineBody.omit({ clientUpdatedAt: true }).extend({ sessionId: z.uuid() }).strict();
const editPayload = /* updateLineBody's fields without clientUpdatedAt */ .extend({ lineId: z.uuid() }) /* ≥ 1 field */;
const removePayload = z.strictObject({ lineId: z.uuid() });
const firePayload = fireBody.extend({ sessionId: z.uuid() }).strict();
const voidPayload = z.strictObject({ lineId: z.uuid(), reason: z.enum(VOID_REASONS) });
const openPayload = openTableBody.extend({ tableId: z.uuid() }).strict();
export const opEnvelope = z.strictObject({
  opId: z.uuid(), seq: z.number().int().min(1), kind: z.enum(SYNC_KINDS),
  clientTs: clientUpdatedAt /* the M18 INSTANT regex */, userId: z.uuid(),
  payload: z.record(z.string(), z.unknown()),       // per-kind payload checked per op (below)
});
export const syncBody = z.strictObject({ ops: z.array(opEnvelope).min(1).max(MAX_SYNC_OPS) })
  .refine(/* distinct opIds */).refine(/* strictly increasing seq */);
export const PAYLOADS = { open_table: openPayload, add_line: addPayload, /* … */ } satisfies Record<SyncKind, z.ZodType>;

// src/server/sync/output.ts
const opError = z.strictObject({ httpStatus: z.number().int(), code: z.string(), message: z.string(), details: z.unknown().optional() });
const opResult = z.discriminatedUnion("status", [
  z.strictObject({ opId, status: z.literal("applied"), receivedAt, kind, reply: /* per-kind output: openTableOutput | addLineOutput | lineWriteResult (changed) | fireOutput */ }),
  z.strictObject({ opId, status: z.literal("conflict"), receivedAt, kind, conflict: z.strictObject({ reason: z.enum([...CONFLICT_REASONS, "table_already_open"]), line: orderLine.optional(), sessionId: z.uuid().optional() }) }),
  z.strictObject({ opId, status: z.literal("rejected"), receivedAt: z.string().nullable(), kind, error: opError }),
  z.strictObject({ opId, status: z.literal("duplicate"), kind, stored: /* applied | conflict | rejected as above, without opId */ }),
]);
export const syncOutput = z.strictObject({
  results: z.array(opResult),
  stopped: z.strictObject({ opId: z.uuid(), reason: z.enum(["dead_entity", "unavailable", "user_mismatch"]) }).nullable(),
  serverTime: z.string(),
});
```

- **Mapping (`src/server/sync/results.ts`, `toOpResult(kind, raw)`):**
  - **`applied`:** replies are parsed with each kind's **existing** strict output schema. An undeclared key (a cost slipping into a reply) throws, and the route answers 500; it never leaks.
  - **`rejected`, and `conflict` raised as P0001:** go through the **existing** `mapOrderDbError` / `mapTablesDbError` (chosen by kind), giving `{httpStatus, code, message (Italian), details}`.
  - **Unknown P0001 message:** → `{httpStatus: 422, code: "rejected_unknown", message: t("syncError.rejected_unknown")}`, so the queue never blocks on it.
  - **`table_already_open`:** the conflict carries `sessionId` from the stored DETAIL.
- **Per-op payload check:** a payload that fails its `PAYLOADS[kind]` schema gets `rejected invalid_request`, **without an RPC**. This is deterministic and not stored, and the batch continues. An `add_line` or `open_table` rejected this way is a dead entity (the batch stops).

|---|---|---|---|---|
| `POST /api/sync` | owner, admin, waiter | `syncBody` (≤ 64 KiB) | 200 `syncOutput`, `Cache-Control: no-store` | 400 `invalid_request` (envelope); 401; 403 (chef, before any RPC); 413; 415; **503 `sync_unavailable`** (the first op failed for infrastructure; nothing applied) |
| `GET /api/me`, `GET /api/menu`, `GET /api/tables`, `GET /api/table-sessions/:id/lines` | unchanged | — | unchanged, plus the header `x-offline-cache: 1` on 200 only | unchanged |

- **Service `src/server/sync/apply.ts` (`applyOps(supabase, ops)`):**
  - per op: payload check → `supabase.rpc("apply_op", {p_op})` → `toOpResult`;
  - stop rules of §3.1.6:
    - an RPC error with code 42501 and message `user_mismatch` → `user_mismatch`;
    - any other RPC error, or a thrown fetch → `unavailable`;
  - `serverTime = new Date().toISOString()`.
- **`src/lib/api/offline-cache.ts`:** exports `offlineCacheable(response)`, which sets the header. Only the four route files above may import it (lint test, step 11).
- **Errors and i18n:** `src/lib/api/errors.ts` `ErrorCode` gains `sync_unavailable` and `rejected_unknown`. i18n keys go under `sync.*` and `syncError.*`.

### 3.6 Client: outbox, runner, service worker, screens

#### 3.6.1 IndexedDB schema (`src/pwa/outbox.ts`, database `osteria-sync`, version 1)

| Store | keyPath | Indexes | Record |
|---|---|---|---|
| `outbox` | `opId` | `bySeq` (`seq`, unique), `byUser` (`userId`) | `{opId, seq, kind, clientTs, userId, payload, scope: {sessionId, lineId?}, label: {tableName?, dishName?}, queuedBy: {id, displayName}, attempts, lastAttemptAt}` |
| `outcomes` | `opId` | `bySeq`, `bySession` (`scope.sessionId`) | `{opId, seq, kind, userId, scope, label, status: applied\|conflict\|rejected\|duplicate\|dropped, settledAt, receivedAt?, conflict?, error?, droppedReason?, clientTs, seen}` |
| `meta` | `key` | — | `nextSeq` (number), `replayLease` `{holder, until}`, `lastUser` `{id, displayName, role}` |

- **`enqueue(draft)`:** reads and increments `meta.nextSeq` and adds the op, in **one** `readwrite` transaction over `outbox` + `meta`. So `seq` is unique and monotonic, even with two tabs.
- **One-transaction writes:**
  - `settle(results)` moves ops from `outbox` to `outcomes`;
  - `prune(rewrites, drops)` deletes, rewrites and adds outcomes;
  - `pruneOutcomes(now)` deletes outcomes that are `seen` or older than `OUTCOME_KEEP_MS`.
- **`scope` and `label`:** let the phone show and prune ops without reading the server. `label` holds the dish and table names as shown when the op was queued.
- **IndexedDB unavailable** (open fails, e.g. in a private window): the outbox runs in memory with the same API (`memoryOnly`), and a banner shows "Questo browser non può salvare le comande senza connessione: se chiudi la pagina offline le perdi."
- **Change events:** a `BroadcastChannel("osteria-sync")` message after every write keeps the badge current in every tab.

#### 3.6.3 Service worker scope and caching (`public/sw.js`, hand-written, classic script, no dependency)

- **Why `public/`:** the worker must be served raw at `/sw.js` with scope `/`, and the project keeps no bundler step for it. The project plan's `src/pwa/sw.ts` therefore becomes `public/sw.js` (plan change, §6). Its behaviour is unit-tested by running the file in `node:vm` with fake `self`, `caches` and `fetch` (step 16).
- **Registration** (`src/pwa/register.ts`; called from the shell after `useMe` is ok, in production builds only, when `"serviceWorker" in navigator`):
  - `navigator.serviceWorker.register("/sw.js?v=" + APP_VERSION, { scope: "/" })`;
  - `APP_VERSION` is `NEXT_PUBLIC_APP_VERSION`, set in `next.config.ts` `env` from `VERCEL_GIT_COMMIT_SHA` (`"dev"` locally). A new deploy gives a new script URL, and so a new install;
  - once, `navigator.storage.persist()` when it exists (T3).
- **Caches** (names carry `v` from `self.location.search`):

  | Request | Strategy | Cache |
  |---|---|---|
  | Cross-origin, any non-GET (writes, `/api/sync`), RSC requests (header `RSC: 1` or `_rsc` param) | **not intercepted** (no `respondWith`) | — |
  | `GET /_next/static/*` | cache-first (hashed, immutable) | `static-<v>` |
  | Navigation to `/`, `/tavoli`, `/tavoli/comanda` (search ignored) | network-first with a 3 s timeout (`SW_TIMEOUT_MS`), then the cached page | `shell-<v>` |
  | Navigation to any other page | network only. Offline → a static Italian page "Sei offline. Questa pagina serve la connessione. Torna ai tavoli." with a plain link to `/tavoli` (no script) | — |
  | `GET /api/me`, `/api/menu`, `/api/tables`, `/api/table-sessions/<uuid>/lines` | network-first with a 3 s timeout, then the cached copy with `x-offline-cached-at` added | `api-user` |
  | Any other `GET /api/*` | **not intercepted** | — |

- **Cost data is never cached.** Two independent locks:
  - the path must be one of the four (an allowlist in the worker);
  - the 200 response must carry `x-offline-cache: 1`, which only those four routes set (lint-tested).

  All four outputs are strict, cost-free schemas, snapshot-tested since M17–M19: waiters see sale prices, never costs.
- **Install:**
  - precaches the three shell pages, fetched with credentials. A response is skipped when it is not 200 `text/html`, is `redirected`, or ends on `/login` or `/pin`;
  - also precaches the same-origin `/_next/static/` URLs found in their HTML (`assetUrls(html)`, from `src`/`href` attributes only);
  - does not call `skipWaiting`. A new worker takes over only when the old tabs are closed, so a page never runs against another version's caches mid-service.
- **Activate:** deletes `static-*` and `shell-*` caches other than the current and the previous version (so an old open tab can still load its chunks), then calls `clients.claim()`.
- **Message `clear-user-data`** (sent beside `resetMe()` on logout, PIN login and demo purge): deletes `api-user`.
- **No user data in the shell HTML:** the role and name come from `/api/me` on the client (ADR-020). `pwa.spec.ts` (step 21) checks the cached HTML for staff names.
- **Proxy:** the matcher in `src/proxy.ts` also excludes `sw.js` and `manifest.webmanifest`, so they are never redirected to `/login`.
- **Headers** (`next.config.ts`): `/sw.js` gets `Cache-Control: no-cache, max-age=0` and `Content-Type: text/javascript; charset=utf-8`.

### 3.7 Flows

1. **Dead spot during an order.**
   1. The waiter adds two dishes and sends secondi. Each tap queues an op, and the runner sends it at once.
   2. The network fails. The ops stay with "In coda", and the badge shows "In coda · 3 · Offline".
   3. Back in range, the `online` event (or the next backoff tick) sends `[add, add, fire]` to `POST /api/sync`.
   4. The server runs three transactions: add → add → `fire_course` with FEFO depletion.
   5. The replies settle the outbox, the badges go, and the kitchen's next 5 s read shows the ticket.
2. **30-minute outage** (Supabase down, Vercel up).
   - Each try gets 503 `sync_unavailable`, and the backoff settles at 15 s.
   - Reads come from the worker's cache ("Dati delle 20:31").
   - On recovery, the next tick sends up to 20 ops per request, in `seq` order, until the outbox is empty.
3. **A 409 in the middle.** Of ops 1–5, op 2 (an edit of a line the kitchen already has) gets `conflict fired`; it is kept in `outcomes` and shown. Ops 3–5 are applied in the same request.
4. **Sold out while offline.**
   - The phone queued `[add L (stew), fire [L, M]]`.
   - The add → `rejected item_unavailable`; the batch stops with `dead_entity`.
   - The phone prunes: the fire becomes `fire [M]` under a new op id, and L's dish is listed as not registered.
   - The next request fires M.
5. **Fire after the dish ran out** (L was added online earlier). The queued fire is `applied`. The fallback batch goes negative, and you and the chef get the `negative_stock` alert (AT9).
6. **Two waiters, one phone.**
   1. A queues ops offline. A then logs out online while `/api/sync` keeps failing (an outage), so the ops stay.
   2. B logs in. Only B's ops are sent. A's ops are held behind the banner, and they also block B's later ops on the same table.
   3. When A logs in again, A's ops are sent.

### 3.9 Tests convention

- **pgTAP:**
  - claims set with `set_config('request.jwt.claims', …)`;
  - fixtures no procedure can write (closed sessions, emptied batches, fault triggers) inserted as the migration owner inside the rolled-back test;
  - errors asserted as `SQLSTATE message`;
  - ops built by a test helper `op(kind, payload, client_ts, user)` that makes fresh uuids.
- **Rows, lines, ops and tickets are found by id, never by index** (`data-line-id`, `data-op-id`, `data-session-id`; SQL by uuid).
- **Two of everything:** two waiters (and two on one phone), two sessions, two tenants, two lines per fire (one dead), two app versions.
- **Vitest:**
  - IndexedDB tests import `fake-indexeddb/auto` per file and use a fresh database name per test;
  - timers use `vi.useFakeTimers()`, and randomness is injected;
  - service-worker tests run `public/sw.js` in `node:vm`, with fakes for `self`, `caches`, `fetch` and `clients` and Node's own `Request`/`Response`. No test hook ships in the worker.
- **Playwright:**
  - **`offline.spec.ts` runs with `serviceWorkers: "block"`:** the outbox path, deterministic on `phone` and `phone-webkit`;
  - **`pwa.spec.ts` runs with workers allowed, on `phone` (Chromium) only** (T4, T5);
  - network loss: `context.setOffline(true)`. Outage: `page.route("**/api/sync", r => r.fulfill({status: 503, …}))`;
  - fake time: `page.clock` (M19 T4, proved on Chromium);
  - server state read by id: `applied_op` and `batch_movement` with the secret key, `order_line` with `runSql` (local).

### 3.10 Performance (no figure promised)

- **Server work:**
  - one RPC per op; its cost is the procedure's plus one PK lookup and one insert on `applied_op`. A duplicate costs a lookup only;
  - a sync request is ≤ 20 sequential RPCs, and the phone sends the next batch only after the previous reply.
- **During an outage:** one small request per 15 s per phone with pending ops.
- **Service worker:** at most 3 s (`SW_TIMEOUT_MS`) on a hanging network before it falls back to the cache, and nothing extra when the network answers.
- **Regression net:** `214` runs `apply_op` of an add and of a fire on the M19 perf fixture under `statement_timeout = '5s'`.

## 4. Alternatives considered

- **Dispatch in TypeScript (calling the existing services), with `applied_op` written in a second RPC:** rejected.
  - The op and its idempotency record would be two transactions.
  - A crash between them gives "applied but not recorded", and a replay would run it again.
  - One SQL function makes the pair atomic (ADR-022).
- **A new SQL procedure per kind for sync:** rejected. It would duplicate every M17–M19 rule. The dispatcher calls the procedures unchanged, and `214` pins them.
- **Applying every op of a batch without stopping on dead entities:** rejected. A queued fire naming a refused add would be refused whole (`line_not_found`), and the other dishes would not reach the kitchen.
- **Server-side pruning of fire ids:** rejected. It would change `fire_course` (refused whole on purpose) or need a read of the lines outside the procedure.
- **Background Sync API:** rejected (ADR-005). Safari support is not assured; replay on `online`, focus and a timer covers service.
- **Serwist, Workbox or next-pwa:** rejected (ADR-005; the brief forbids a new runtime dependency). Each brings a dependency and build-tool coupling for about 150 lines of worker.
- **Stale-while-revalidate for reads (project §3.8):** replaced by network-first with a 3 s timeout. Stale-while-revalidate shows the previous answer first even when online. On the comanda, that could show a line as unsent after it was sent.
- **Caching every `GET /api/*`:** rejected, because owner endpoints carry costs. The design uses an allowlist plus a response header instead.
- **Keeping `/tavoli/[sessionId]` and serving another session's cached HTML for a new id:** rejected. How the App Router hydrates a different dynamic param from cached HTML is unverified; a static route is certain.
- **localStorage for the outbox:** rejected. It is synchronous, holds strings only, is size-limited, and cannot write `seq` and ops in one transaction.
- **Coalescing queued ops on the phone (e.g. add + edit → one add):** rejected. It changes the stamps that last-write-wins compares, and replay is already cheap.
- **A device id with server-side `seq` checks:** rejected. It needs device registration for email users. Order is already kept by the phone's serial replay and the server's in-request order.
- **Version numbers or locking per line:** rejected by PRD 3.1 ("no locking"; ADR-005, ADR-017).
- **Global `op_id` uniqueness across tenants:** rejected. A tenant-scoped key leaks nothing about another tenant's ops.

## 6. Risks and mitigations

- **iOS Safari: service-worker and IndexedDB limits**
  - **Storage eviction.** WebKit may delete a site's script-writable storage (IndexedDB, Cache API, worker registration) after a period without use. Web apps added to the Home Screen are treated differently (T3). Mitigations:
    - the queue is meant for minutes to hours, not days;
    - `navigator.storage.persist()` is requested where it exists;
    - the M25 runbook tells staff to open the app from the Home Screen icon;
    - the pending badge makes a loss visible.
  - **Separate storage.** A Safari tab and the Home Screen app keep separate storage, so ops queued in one are invisible in the other, and the held-ops banner does not cover it. Runbook: one entry point per phone. Recorded for the Gate 3 device check.
  - **No Background Sync; background timers paused.** Ops wait until the app is in front again. Replay runs on `visibilitychange` and `focus`, and the badge tells the waiter to keep the app open until it reads zero.
  - **Unreliable `online` events on iOS:** the 15 s timer and focus cover them.
  - **Private browsing or no IndexedDB:** memory-only mode with a banner (§3.6.1).
  - **Quota:** ops are a few KB, and outcomes are pruned after 24 h.
- **Playwright offline emulation on WebKit (and in general)**
  - **Does `setOffline` cut the worker's own fetches?** Unverified per browser (T4).
    - `offline.spec.ts` blocks workers, so AT6–AT8 do not depend on it.
    - `pwa.spec.ts` (Chromium only) opens with a probe. If a worker-routed fetch still succeeds while offline, the probe fails loudly and the step stops for a re-plan, as the M11 spike did.
  - **Workers and IndexedDB in WebKit's ephemeral Playwright contexts:** unverified (T5).
    - WebKit runs the worker-free `offline.spec.ts`.
    - If IndexedDB is missing there, memory-only mode still passes AT6. The spec records which mode ran, so it cannot pass silently.
  - **`page.clock` on WebKit:** unproven (M19 proved Chromium). The AT7 e2e therefore runs on Chromium, and AT7 is also proved in Vitest with fake timers.
- **The clock**
  - **Phone behind:** its edits lose last-write-wins to colleagues. The ADR-017 bump stops a waiter losing to the line they are looking at, and every loss is a visible conflict or overwritten notice.
  - **Phone ahead by more than 120 s:** stamped writes are `rejected client_time_invalid`, but only if the stamp is still in the future at replay time; an op sent later usually passes. The skew warning (> 60 s) tells the waiter to fix the clock.
  - **Receipt time recorded:** the server stores `received_at` beside `client_ts` (`applied_op`), and `updated_at` beside `client_updated_at` (the line).
  - **Clock-independent:** irreversible states never depend on any clock, and opening and firing ignore stamps.
- **Security**
  - **Definer dispatcher:**
    - role checked first; empty `search_path`; tenant from `app.tenant_id()`;
    - user binding checked before any lookup;
    - kind allowlist in SQL and TS (parity);
    - every procedure re-checks its own role and tenant (steps 2, 5).
  - **Idempotency-key abuse:** keys are tenant-scoped, and the payload hash refuses reuse of an op id with other content (`op_id_reused`).
  - **Cost leakage through the cache:**
    - path allowlist + response header + strict output schemas;
    - the cost endpoints are not intercepted (16);
    - `applied_op` is unreadable by every API role (1).
  - **CSRF:** `/api/sync` is JSON-only (`withApi`); body ≤ 64 KiB; ≤ 20 ops.
  - **Shared phones:** the read cache is cleared on logout and PIN login; ops are bound to their user.
  - **Worker supply chain:** hand-written, same-origin, no `importScripts`, served `no-cache`, no `skipWaiting` (16).
  - **XSS:** notes and names are rendered as text (19).
- **Personal data**
  - **On the phone:** staff display names, dish notes and table names now persist in IndexedDB (ops until sent, outcomes for 24 h) and in the worker's read cache until logout. No guest data.
