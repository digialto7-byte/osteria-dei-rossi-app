## 0. Summary for the lead (plain language)

The SaaS design rests on three things Supabase must do that nobody has tried on our stack yet:

1. **T1.** When Supabase issues or refreshes a sign-in token, it tells our database hook which session it is (`session_id`), for every way
   of signing in. One login for many venues (ADR-038) needs that.
2. **T2.** The hook can give DigiAlto's console a separate database role, `platform_staff`, and the API, file store and live-update service
   accept it (ADR-037). If not, we use the simpler fallback V2.
3. **T3.** After "switch venue", one server-side refresh gives a token for the new venue and keeps the second factor.

Two more checks: **T4** measures how fast three heavy screens stay when the database holds many venues (no target, it guides SP2), and
**T5** proves nobody can create an account by themselves (FD5, invitation only).

Each check runs twice: once on the **local stack in CI** (repeatable, free, re-run whenever the hook changes) and once on a **temporary
Supabase project** that you create in the morning and delete in the evening (the hosted Auth server, API and settings cannot be copied
locally). Nothing touches staging or production. The spike adds **no product code and no migration**: its test SQL lives under
`scripts/spike/sp00/sql/` and is applied only to the CI stack and the temporary project.

You do the dashboard steps (create, configure, delete). The builder writes the scripts; they create the test users and fake venues, print
one result line per check without any secret, and clean up. Twelve questions for you are in **Lead decisions** (§11); each has a default.

## 3. Design

### 3.1 Principles

1. **Split by what each environment can prove** (§3.2). The local part proves our SQL and scripts; the hosted part proves the hosted
   services and settings.
2. **Scratch, not product.** The SP2/SP3 behaviour is imitated by scratch SQL under `scripts/spike/sp00/sql/`, applied with `psql` to the CI
   stack and the temporary project only. It never enters `supabase/migrations/` (guard S13), so `db push` to staging or production can
   never carry it.
3. **The hook keeps its registered name.** The scratch SQL renames today's hook to `app.sp0_real_hook` and installs a wrapper under the
   name `app.custom_access_token_hook`. No hook setting changes, locally (`config.toml` line 301) or in the dashboard. The wrapper calls the
   real hook first, so every tenant, PIN and role claim stays exactly today's, plus one probe claim.
4. **Observe by echo, not by writing.** The hook is `stable` and Supabase's docs say nothing about writes or transactions inside the hook
   (source W2). The wrapper therefore writes nothing: it returns what it saw as a claim `sp0_in`, which the script reads from the token.
5. **Guards first.** Every script refuses any target that is not the local stack or the declared temporary project before it creates a
   client (S1). A refusal message never repeats a URL, key or address.
6. **No secret leaves the shell.** Keys exist only as environment variables of the run (§3.5, §3.11). Reports hold check ids, booleans,
   status codes, counts and durations only.

### 3.2 Why each hosted part cannot be proven locally

| Hosted part | Why the local stack cannot prove it |
|---|---|
| Auth (GoTrue) behaviour: `session_id` in the hook input per method, accepting a custom `role` claim, keeping `aal` on refresh | The local Auth container is the version pinned by the Supabase CLI in `package.json` (`supabase` 2.121.0); the hosted project runs the version Supabase deploys. The hook input is built by Auth's code, so it is version-dependent. Docs do not say whether the role claim may be custom (source W2) |
| Auth settings: sign-up off, e-mail provider on, OTP, TOTP, hook registration | Hosted settings are set in the dashboard, not from `config.toml` (`deploy-staging.yml` lines 3–6; `docs/runbook.md` line 425). The local value proves nothing about a hosted switch |
| PostgREST role switching to `platform_staff`; Storage and Realtime with that role | The hosted API gateway, PostgREST, Storage and Realtime have their own versions and configuration (JWT verification with the project's signing keys, Realtime's own settings). Whether the hosted `postgres` role may create a role and grant it to `authenticator` may differ from the local image [unverified] |
| Mail delivery (code and link) | Locally every mail lands in Mailpit. Hosted, the built-in mailer refuses non-team addresses and is rate limited (source W1); a custom SMTP is a separate setting |
| T4 timings | Free-tier hosted compute and the network path differ from a CI runner's Docker stack; the local numbers only smoke-test the tool |
| Hosted rate limits | Read from the dashboard; local values are in `config.toml` lines 202–217 |

### 3.4 The checks: local part, hosted part, pass rule, fallback

A check result is `pass`, `fail`, `inconclusive` (could not be judged, e.g. HTTP 429) or `recorded` (no pass rule, T4 numbers). Each part
creates its own users and deletes them in `finally`, as AT8 does.

**T1 — `session_id` in the hook input on every sign-in method** (scratch 01)

| Case | T1.L local (CI) | T1.H temporary project |
|---|---|---|
| 1 password | `signInWithPassword` | same |
| 2 e-mail code | `signInWithOtp({shouldCreateUser:false})`, code read from Mailpit, `verifyOtp({type:'email'})` (the app's path) | `auth.admin.generateLink({type:'magiclink'})` → `email_otp` → `verifyOtp({type:'email'})`. **No mail is sent**; delivered mail only under SV4/SV5 |
| 3 magic link | `signInWithOtp` from a PKCE server client (cookie jar), link read from Mailpit, followed with `redirect: 'manual'`, `code` → `exchangeCodeForSession` (the app's path) | a second `generateLink` → `action_link` followed with `redirect: 'manual'`; tokens from the redirect (implicit flow, **not** the app's PKCE path; recorded as such). The PKCE path hosted only under SV4/SV5 |
| 4 token refresh | `refreshSession` after case 1 | same |
| 5 TOTP | enrol, challenge, verify (`totpAt`) after case 1 | same |

- **Pass:** in every case `sp0_in.sid` is true, the issued `session_id` equals the input one, and cases 4–5 keep the `session_id` of the
  session's first token. **Recorded:** `sp0_in.m` per case (e.g. whether a code reports `otp` or `magiclink`).
- **Fallback:** T1.H fail → ADR-038 re-planned before SP2 (the lead decides the replacement; ADR-038's rejected "active tenant per user"
  alternative is the obvious candidate). T1.L fail only → stop and diagnose before the hosted day.

### 3.7 T4 in detail

- **Data.**
  - *Measured tenant:* "Osteria Demo SP0", filled by the existing demo seed (`runSeed`), whose dates are relative to the run day
    (`scripts/lib/demo/main.ts` line 204). This is deliberate: the three reads look at today's business day, so a measured tenant dated
    1998 would return empty payloads. Plus one open table with one fired course (kitchen tickets).
  - *Background tenants:* "Spike Demo 001…", each one clone of the measured tenant's rows in the tables the three reads touch, dated 1998
    (28 years back), fake VAT `IT99` + 9 digits. **Sizes:** 1 tenant (baseline), then +9 (10), then +40 (50). At each point every cloned
    table holds that many times the measured tenant's rows; the exact rows per table are printed by `sp0.t4_fill` and copied into §10. The
    run stops adding tenants when `pg_database_size` would pass `SPIKE_T4_MAX_DB_MB`; the last point reached is recorded.
  - *Limitation of 1998 background data:* date-filtered queries skip old rows whatever their tenant, so this measures the cost of other
    tenants' **history**, not of other tenants' **open service**. An in-window background profile is SV6 (LQ6).
- **How the app is pointed at the temporary project: a local production build (`npm run build` then `npm run start`) on the lead's machine,
  with `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` set to the temporary values in that shell, `SENTRY_DSN` empty.**
  - Why: no Vercel setting changes (preview deployments use Vercel's own Preview environment variables, which are the staging ones; a
    branch-scoped override would be one more place for temporary keys to linger); the app process needs no secret key
    (`src/lib/env/index.ts` lines 22–30); the comparison is relative (1 vs 10 vs 50 tenants through the same network path), and the
    database-side EXPLAIN times have no network in them.
  - Note: `NEXT_PUBLIC_*` values are inlined at build time (`src/lib/env/index.ts` line 61), so the build **must** be made in the shell
    that holds the temporary values, and `.next/` is deleted at teardown.
  - The cost: absolute numbers are not production's (Vercel `fra1` next to Supabase EU). The report says so. A Vercel preview is SV7 (LQ7).
- **Timings collected:**
  1. wall time per request, all three reads (the client's view through the local app);
  2. `Server-Timing` `auth`/`rpc`/`total` for `/api/dashboard` (the only one of the three that sends it today; SV3 adds the other two);
  3. `EXPLAIN (ANALYZE, BUFFERS)` execution time of `dashboard_summary()`, `menu_list()`, `kitchen_tickets()` as the owner (scratch 05),
     5 runs each per point, median recorded. Nested statement plans would need `auto_explain`, whose availability on the hosted project is
     [unverified]; if `load 'auto_explain'` is refused, SP2's index review reads plans itself.
- **No pass threshold.** The numbers inform SP2's index review (platform plan §11 "Performance and cost"). The isolation check (§3.4 T4) is
  the only pass/fail part.

## 4. Alternatives considered

- **Use staging** (as the platform plan first said). Rejected by the lead's rule: staging is shared, carries the founder's settings and the
  demo data, and the spike redefines the hook and drops a unique constraint.
- **Supabase branching / preview databases.** Not chosen: its availability and price on the Free plan were not checked here [unverified],
  and a branch shares the parent's account settings, which is what T5 must isolate.
- **Self-hosted Supabase in Docker as "hosted".** Rejected: it is the same images as the local stack, so it proves nothing about the hosted
  platform (§3.2).
- **Record the hook input by inserting into a table from the hook.** Rejected: the hook is `stable`, and Supabase's docs do not say whether
  hook writes are allowed or how the transaction behaves (W2). Echoing into a claim needs no write.
- **Add the scratch objects as real migrations on a throwaway branch.** Rejected: one wrong merge would ship a redefined hook to
  production; scratch SQL outside `supabase/migrations/` plus guard S13 removes that path.
- **`supabase config push` for the Auth settings.** Rejected: it would push local-only values (`site_url` localhost, the local e-mail rate
  limit that "requires auth.email.smtp" per `config.toml` line 203, `[auth.sessions] timebox`, which needs a paid plan per line 286),
  and production is configured in the dashboard (runbook line 425), so the dashboard path is the one worth rehearsing.
- **Background tenants through the demo seed.** Rejected: the fixture's fixed addresses (`fixture.ts` lines 12–13) allow one demo tenant
  per project, and each seed signs in several users, which would run into Auth's sign-in rate limit dozens of times.
- **A load tool (k6, autocannon).** Rejected: a new dependency for sequential reads the existing perf helpers already time.
- **A CI job inside `ci.yml` (as AT8).** Kept as SV2: it would run on every heavy CI run, although the checks matter only when the hook,
  roles or Auth config change (LQ2).

## 6. Risks and mitigations

**Security and privacy**
- *Scratch SQL reaches a real database.* It lives outside `supabase/migrations/`; S13 fails CI otherwise; the psql helper (S14) and the
  scripts refuse anything but the local stack or the declared temporary project.
- *Wrong target.* Exact-ref guard, staging ref refused by name, `PRODUCTION_PROJECT_REF`/`STAGING_PROJECT_REF` refused when set, an explicit
  opt-in, and `SPIKE_*` names distinct from the app's own variables (S1, S10, S14).
- *Secret exposure.* Keys only in one shell's environment for one day; reports pass a redaction check (S2); the app for T4 holds no secret
  key; the project is deleted the same day (D1). The builder never receives a key (LQ3).
- *Personal data.* Only `example.test` addresses and fake tenants, except SV4/SV5, where one team address exists for a few hours on a project
  deleted the same day and is never printed. No client data is used, so no client personal data is processed.
- *A temporary project open on the internet.* Sign-ups off from L3 onwards; it holds fake data only; it lives one day.
- *Hook wrapper breaks sign-in on the temporary project.* Self-check A runs before T1; if Auth reports a hook error, restore with
  `alter function … rename` (the real hook is kept as `app.sp0_real_hook`), record, and keep the T5/T4 results already taken.

**Validity of the results**
- *Hosted Auth changes later.* Results are dated and carry the Auth version when readable. The local parts re-run on every PR that touches
  migrations or the Auth config (S12), so SP2's hook change re-proves T1–T3 locally.
- *Generated-link flows are not the app's flows.* T1 cases 2–3 and T5 case e hosted use `generateLink`; the app's PKCE link path and real
  delivery are proven locally and, hosted, only under SV4/SV5. The report labels the flow used.
- *T4 noise.* Free compute, the lead's network, pg_cron jobs. Mitigation: relative comparison, 100 iterations, medians and p95,
  database-side EXPLAIN times, overlapping cron runs counted; no threshold.
- *1998 background data understates open-service load* (§3.7). SV6.
- *Rate limits* (hosted values unknown until read): 429 → `inconclusive`, one re-run (§3.8).

**Operations**
- *The organisation's Free project limit* may refuse a new project (`m25-go-live.md` line 918 mentions the limit). LQ11; never pause staging.
- *Built-in mailer:* team addresses only, best-effort, limit "can change without notice" (W1). The base plan sends no mail.

**Dependencies (name, licence, why):** none added. `psql` is already installed by CI (`ci.yml` lines 127–128); `e2e/helpers/totp.ts`,
`createTenant`, `runSeed` and the perf helpers are reused.
