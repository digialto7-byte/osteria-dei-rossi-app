## 0. Summary for the lead (plain language)

The SaaS design rests on three things Supabase must do that nobody has tried on our stack yet:

1. **T1.** When Supabase issues or refreshes a sign-in token, it tells our database hook which session it is (`session_id`), for every way
   of signing in. One login for many venues (ADR-038) needs that.
2. **T2.** The hook can give DigiAlto's console a separate database role, `platform_staff`, and the API, file store and live-update service
   accept it (ADR-037). If not, we use the simpler fallback V2.
3. **T3.** After "switch venue", one server-side refresh gives a token for the new venue and keeps the second factor.

Two more checks: **T4** measures, inside the database, how fast the three heavy screens' queries stay when the database holds many venues
(no target, it guides SP2), and **T5** proves nobody can create an account by themselves (FD5, invitation only).

Each check runs twice: once on the **local stack in CI** (repeatable, re-run whenever the hook changes) and once on a **temporary Supabase
project** that lives for one day. Nothing touches staging or production. The spike adds **no product code and no migration**: its test SQL
lives under `scripts/spike/sp00/sql/`.

**No secret is ever typed into a chat.** You run every database step through the Supabase connector, so no database password is needed.
The founder saves the project's secret key once in the session's secure credential form; the network proxy then puts it into the scripts'
calls to that one host. The scripts only ever hold a placeholder.

**The day:** you create the project and load the migrations (phase A); the founder does a ten-item click-list in the dashboard and saves the
key (phase B); you run the scripts and the SQL (phase C); you delete the project and the founder removes the saved key (phase D). Estimate
(not a promise): about 4½ to 6½ hours in total, of which about 30 minutes are the founder's (§3.8).

## Flags for the lead (read first)

1. **No product change.** No file under `src/`, `supabase/migrations/` or `supabase/tests/` changes. The spike SQL redefines the hook and
   drops a unique constraint **only on throwaway databases**; a guard test (S14) keeps it out of the migration path, and a SQL guard (S4)
   refuses to run on any database that is not the marked temporary project or a CI stack.
2. **The connector can reach every project of the organisation, staging and production included.** A wrong `project_id` is the largest risk
   of the day. Three guards: `sp00-ref-check.ts` before the first connector call (S1); the "fresh database" check before the first
   `apply_migration` (§3.8 A3); and the marker plus fake-tenant check at the top of every scratch SQL file (S4).
3. **Secret key by proxy.** Scripts send the placeholder from `SPIKE_SECRET_KEY` **in the `apikey` header only**, never in
   `Authorization: Bearer` (Supabase: "Send publishable and secret keys on the `apikey` header only", W3). They never validate or decode it.
   Whether the proxy replaces a placeholder in the `apikey` header is **[unverified]**; the preflight (S3) proves it before any check runs,
   and SV8 is the fallback if it does not.
4. **T4 is SQL-level only.** It times `public.mfa_gate()` plus `public.dashboard_summary()`, `public.menu_list()` and
   `public.kitchen_tickets()` as the owner (`set local role authenticated` with the owner's claims). Network, PostgREST and Next.js are not
   in the numbers. Server-Timing is not used in SP0 (LD-5, LD-7). Whether `postgres` may `set role authenticated` inside an `execute_sql`
   call on the hosted project is **[unverified]**; SV9 is the fallback.
5. **Hosted e-mail is not delivered** (LD-4): `generateLink` proves the code and link paths without sending. Delivery is proven locally only.
6. **T5 on the temporary project proves how hosted Auth behaves with sign-up off; it does not prove that staging or production have sign-up
   off.** The founder ticks go-live S8-4 / M-5 separately (LD-10).
7. **Size:** S. 15 steps (scripts, scratch SQL, unit tests, one CI workflow). One run day.

## 3. Design

### 3.1 Principles

1. **Split by what each environment can prove** (§3.2). The local part proves our SQL and scripts; the hosted part proves the hosted
   services and settings.
2. **Scratch, not product.** The SP2/SP3 behaviour is imitated by scratch SQL under `scripts/spike/sp00/sql/`. Locally it is applied with
   `psql` to the CI stack; hosted, the lead passes each file's text to the connector's `execute_sql`. It never enters `supabase/migrations/`
   (guard S14).
3. **The hook keeps its registered name.** The scratch SQL renames today's hook to `app.sp0_real_hook` and installs a wrapper under the
   name `app.custom_access_token_hook`. No hook setting changes. The wrapper calls the real hook first, so every tenant, PIN and role claim
   stays exactly today's, plus one probe claim.
4. **Observe by echo, not by writing.** The wrapper writes nothing; it returns what it saw as a claim `sp0_in`, which the script reads from
   the token (the docs say nothing about writes inside the hook, W2).
5. **No secret in any transcript.** No database URL or password exists in the plan (LD-3, LD-12). The secret key reaches Supabase only
   through the proxy's substitution of a placeholder (§3.5). The publishable key, the project URL, the project ref and row ids are not
   secrets and may appear in plain form. Script reports hold check ids, booleans, status codes, counts and durations only.
6. **Guards first** (Flag 2): every script refuses any target that is not the local stack or the declared temporary project before it
   creates a client; every scratch SQL file refuses any database that is not the marked temporary project or a CI stack.

The hook input is built by Auth's code, so it is version-dependent. The docs do not say whether the role claim may be custom (W2) |

Whether the hosted `postgres` role may create a role and grant it to `authenticator` may differ from the local image [unverified] |
| Secret key handling | Hosted, the key is the project's new-style secret key, sent on `apikey` only (W3) and injected by the proxy; locally it is the CLI's generated key. Only the hosted run proves the proxy path |

### 3.4 The checks: local part, hosted part, pass rule, fallback

A check result is `pass`, `fail`, `inconclusive` (could not be judged, e.g. HTTP 429, or the preflight failed) or `recorded` (no pass rule,
T4 numbers). Users without a membership are deleted in `finally`, as AT8 does. Users with a membership cannot be deleted (the `app_user`
foreign key, and `app_user` allows no delete); they are counted as `kept` and die with the CI runner or the project (D1).

**Preflight (before every hosted run of `sp00-auth.ts` and `sp00-t4-seed.ts`):** `GET /auth/v1/admin/users?page=1&per_page=1` with the
secret-key client. 200 → continue. 401/403 → stop with "secret key not injected" (no value printed); every check needing the key is
`inconclusive`; SV8 applies.

**T1 — `session_id` in the hook input on every sign-in method** (scratch 01)

The T1 user has **no** membership, so it is deleted at the end.

| Case | T1.L local (CI) | T1.H temporary project |
|---|---|---|
| 1 password | `signInWithPassword` | same |
| 2 e-mail code | `signInWithOtp({shouldCreateUser:false})`, code read from Mailpit, `verifyOtp({type:'email'})` (the app's path) | `auth.admin.generateLink({type:'magiclink'})` → `email_otp` → `verifyOtp({type:'email'})`. **No mail is sent** (LD-4) |
| 3 magic link | `signInWithOtp` from a PKCE server client (cookie jar), link read from Mailpit, followed with `redirect: 'manual'`, `code` → `exchangeCodeForSession` (the app's path) | a second `generateLink` → `action_link` followed with `redirect: 'manual'`; tokens from the redirect (implicit flow, **not** the app's PKCE path; labelled `implicit` in the report) |

| 5 TOTP | enrol, challenge, verify (`totpAt`) after case 1 | same |

- **Fallback:** T1.H fail → ADR-038 re-planned before SP2 (ADR-038's rejected "active tenant per user" alternative is the obvious
  candidate). T1.L fail only → stop and diagnose before the hosted day.

### 3.7 T4 in detail (SQL level, LD-7)

- **What is timed, per route (from `src/`, §2):**

  | Route | SQL per request, in order | Measured as |
  |---|---|---|
  | `GET /api/dashboard` | `public.mfa_gate()` (owner at `aal1` → called), `public.dashboard_summary()` | `mfa_gate` + `dashboard_summary` |
  | `GET /api/menu` | `public.mfa_gate()`, `public.menu_list()` | `mfa_gate` + `menu_list` |
  | `GET /api/kitchen/tickets` | `public.mfa_gate()`, `public.kitchen_tickets()` | `mfa_gate` + `kitchen_tickets` |

  `mfa_gate` is timed once per point and reported separately, because all three routes share it.
- **How (`sp0.t4_measure(p_tenant, p_fn, p_runs)`, called through `execute_sql`, locally psql):**
  1. `sp0.guard()`.
  2. Claims of the tenant's owner built in SQL by `sp0.t4_claims`: `sub` (owner's auth id), `role = authenticated`, `tenant_id`,
     `app_role = owner`, `aal = aal1`, a fresh `session_id`. No token is minted or handled.
  3. `select set_config('request.jwt.claims', <claims>, true)`; `set local role authenticated` (through `execute`, inside the function,
     which is not `security definer`).
  4. 5 warm-up calls, then `p_runs` calls of `select public.<fn>()`, each timed with `clock_timestamp()`; then one
     `explain (analyze, buffers, format json) select public.<fn>()`.
  5. `reset role`. Returns one row: `fn`, `n`, `p50_ms`, `p95_ms`, `max_ms`, `explain_exec_ms`, `shared_hit`, `shared_read`, payload item
     count.
  - `p_fn` is checked against the list `mfa_gate`, `dashboard_summary`, `menu_list`, `kitchen_tickets`; anything else raises.
  - One call per function per point, so one `execute_sql` call stays short. Whether `execute_sql` has a statement timeout is
    [unverified]; if a call is cut, the lead repeats it with `p_runs => 50` and records that.
  - Whether `postgres` (the connector's role) may `set role authenticated` on the hosted project is [unverified]; self-check D tests
    `pg_has_role(current_user, 'authenticated', 'member')`. If it may not, SV9 applies.
  - Nested statement plans would need `auto_explain`; its availability is [unverified]. If it is not available, SP2's index review reads the
    plans itself.
- **Data.**
  - *Measured tenant:* "Osteria Demo SP0", filled by the existing demo seed (`runSeed`), whose dates are relative to the run day
    (`scripts/lib/demo/main.ts` line 204), plus one open table with one fired course. Deliberate: the three functions read today's business
    day, so a tenant dated 1998 would return empty payloads.
  - *Background tenants:* `sp0.t4_fill(source, count, max_mb)` creates "Spike Demo 001…" (VAT `IT99` + 9 digits) and copies the measured
    tenant's rows of the tables in `sp0.t4_tables()` into each, with new ids, foreign keys remapped through a temporary map, and every
    date/timestamp column shifted **28 years back** (1998; same weekdays, `tests/guards/no-date-bombs.test.ts` lines 13–14). A table whose
    trigger refuses a direct insert is skipped and listed. **Sizes (LD-8):** 1 tenant, then +9 (10), then +40 (50); `max_mb` is the F9
    limit minus a margin the lead chooses; the fill stops before passing it, and the last point reached is recorded.
  - *Limitation (LD-6 accepted):* date-filtered queries skip old rows whatever their tenant, so this measures the cost of other tenants'
    **history**, not of their **open service**.
- **Isolation:** `sp0.t4_snapshot(tenant, label)` before the first fill and after each fill and the uniqueness swap; `sp0.t4_isolation(tenant)`
  returns pass/fail (§3.4 T4).
- **No pass threshold.** The numbers go to SP2's index review (platform plan §11 "Performance and cost"). They are database-side only:
  no network, no PostgREST, no Next.js.

## 4. Alternatives considered

- **Use staging.** Rejected by the lead's rule: shared, carries the founder's settings and demo data; the spike redefines the hook.
- **Secret key and database URL in the lead's shell, psql and `supabase db push`** (the first version of this plan). Rejected by LD-3 and
  LD-12: a value typed into a shell can end up in a transcript; the connector and the proxy remove every typed secret.
- **`supabase link` with a personal access token.** Rejected by LD-12: one more credential to create and revoke.
- **Run the app against the temporary project (local `next start` or a Vercel preview) and read Server-Timing.** Rejected by LD-7: it
  needs the publishable key built into an app, adds network noise, and only one of the three routes sends Server-Timing today.
- **Send the secret key on `Authorization: Bearer` as well.** Not the default: Supabase says secret keys go on `apikey` only (W3). Kept as
  SV8 only for the case the proxy does not substitute `apikey`.
- **Supabase branching / preview databases.** Not chosen: availability and price on the Free plan not checked [unverified]; a branch shares
  the parent's settings, which T5 must isolate.
- **Record the hook input by inserting into a table from the hook.** Rejected: the docs do not cover hook writes (W2); an echo claim needs
  none.
- **Scratch objects as real migrations on a throwaway branch.** Rejected: one wrong merge would ship a redefined hook; scratch SQL outside
  `supabase/migrations/` plus S14 removes that path.
- **Background tenants through the demo seed.** Rejected: the fixture's fixed addresses (`fixture.ts` lines 12–13) allow one demo tenant per
  project, and each seed signs in several users against Auth's rate limit.
- **A CI job inside `ci.yml` (as AT8).** Rejected by LD-2: it would run on every heavy CI run although the checks matter only when the hook,
  roles or Auth config change.

## 6. Risks and mitigations

**Security and privacy**
- *The connector reaches staging or production by a wrong `project_id`.* `sp00-ref-check.ts` before the first call (S1); A3's "fresh
  database" check before any migration; `sp0.guard()` (marker table plus fake-only tenant names) at the top of every scratch file (S4, S14).
  Staging and production never have `sp0.target_marker`, and both hold non-fake tenant names.
- *A secret in a transcript.* No database URL or password exists in the plan; the secret key lives only in the proxy's credential store
  (F10); scripts hold a placeholder and refuse to print it (S2, S3); the founder never pastes it into a chat; D6 checks the transcript.
- *The placeholder sent to the wrong host.* The proxy substitutes only for `<ref>.supabase.co` [behaviour per the credential form,
  unverified]; any other host receives the placeholder, which is worthless. The script guard allows only that host.
- *Scratch SQL reaches a real database through a merge.* It lives outside `supabase/migrations/`; S14 fails CI otherwise.
- *Personal data.* Only `example.test` addresses and fake tenants. No client data is used, so no client personal data is processed. Query
  results pasted into the transcript hold ids, counts and timings only.
- *A temporary project open on the internet.* Sign-ups off from F1; fake data only; one day.
- *Hook wrapper breaks sign-in on the temporary project.* Self-check A runs before T1; if Auth reports a hook error, restore with
  `alter function … rename` through `execute_sql` (the real hook is kept as `app.sp0_real_hook`), record, and keep the T5/T4 results.

**Validity of the results**
- *Hosted Auth changes later.* Results are dated and carry the Auth version when readable. The local parts re-run on every PR that touches
  migrations or the Auth config (S13), so SP2's hook change re-proves T1–T3 locally.
- *Generated-link flows are not the app's flows.* Hosted T1 cases 2–3 and T5 e use `generateLink`; the app's PKCE link path and delivery are
  proven locally only (LD-4). The report labels the flow used.
- *T4 is database-side only.* No network, PostgREST or Next.js time; the claims are built in SQL, not by Auth. Accepted by LD-7; the numbers
  are for SP2's index review, which looks at database plans.
- *1998 background data understates open-service load* (§3.7, accepted by LD-6).
- *Migration versions on the temporary project differ from the file names* (A4). No check depends on them.
- *Rate limits* (F8): 429 → `inconclusive`, one re-run.

**Operations**
- *More than 200 `apply_migration` calls* make phase A the longest phase. Accepted (LD-12). A failure stops the run; the file is recorded.
- *The organisation's Free project limit* may refuse a new project (`m25-go-live.md` line 918). LD-11: stop and ask the founder.
- *Dashboard labels* may differ from F1–F10 [unverified]; the founder uses the nearest equivalent and the lead records it.

**Dependencies (name, licence, why):** none added. `psql` (CI only) is already installed by CI (`ci.yml` lines 127–128);
`e2e/helpers/totp.ts`, `createTenant`, `runSeed` and the perf helpers are reused.
