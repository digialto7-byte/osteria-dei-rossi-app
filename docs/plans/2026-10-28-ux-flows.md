# Tech plan: Osteria Dei Rossi app · UX audit by user flow, and prioritised fix plan

- **Client slug / internal:** `osteria-dei-rossi`
- **Repo and branch:** `osteria-dei-rossi-app`, worktree `/home/user/osteria-ux`, branch `feat/ux-flows` (from `main` f10b8dd, M0–M18 merged)
- **Author:** architect · **Date:** 2026-10-28
- **ADR:** `docs/adr/adr-020-app-shell-navigation.md` (proposed)

## 1. Goal and scope

**Goal.** Each role reaches its daily jobs from one consistent app shell in three taps or fewer, and a demo never reaches a screen that is broken, empty without a next step, or forbidden for the role. The data, API and design language stay as they are.

**In scope**
- An audit of the five flows the founder named (owner first day, owner daily, chef morning, waiter service, admin). For each flow: the screens and taps it takes today, and its friction, with file and route.
- A prioritised fix list (P0, P1, P2). Each item has the files to change, testable acceptance criteria and a size.
- A build plan in three shippable PRs. PR A is the P0 shell, navigation and home.

**Out of scope**
- New business features. This includes firing and the kitchen tickets (M19), bill and close (M21), KPIs and the dashboard figures (M22), and the push list (M23). This plan only reserves their place in the navigation (§3.1.4).
- The tenant settings that have no screen yet: alert e-mail and channel, business-day cut-off, payment types (§7 Q7).
- Visual restyling. Tokens, components and type stay as in `docs/design/ui-foundation.md`.
- Offline (M20).
- Moving screens into the `(sala)`, `(cucina)` and `(admin)` route groups proposed in project plan §3.2 (§4 explains why).

### 2.2 Friction catalogue (cross-flow; IDs are used in §2.3 and §3)

**Navigation**
- **N1. Home has no nav.** `src/app/page.tsx` (route `/`) is outside `src/app/(owner)/layout.tsx`. The suite says so itself: `e2e/menu-tables.spec.ts:270` "the home page, which has no section nav".
- **N2. The home link list misses the main jobs.** `src/app/page.tsx:78-149` has no link to **Fatture**, Ricette, Costi, Margini or Personale. "Anagrafiche" opens only `/anagrafiche/fornitori`. The owner's first job (upload an invoice) is not reachable from home.
- **N3. Too many items for a phone.** `owner-nav.tsx:19-41` gives the owner 16 pills, the admin 15, the chef 12 and the waiter 7. They wrap onto several rows above **every** page, including the waiter's comanda `/tavoli/[sessionId]`, where they push the sticky course tabs down. Each pill is 44 px tall.
- **N4. The nav does not match the role.** "Fatture", "Fornitori", "Ingredienti", "Ubicazioni" and "Importa" show to every role (`owner-nav.tsx:22,37-40`).
  - The APIs refuse them. `GET /api/invoices` is owner and admin only (`src/app/api/invoices/route.ts:10`). `GET /api/suppliers`, `/api/ingredients` and `/api/locations` refuse the waiter. The `POST`s and `/api/admin/import/*` allow owner and admin only.
  - As a result 5 of the waiter's 7 pills and 2 of the chef's 12 lead to a role error.
  - Two existing e2e assertions **encode this bug**: `e2e/recipes.spec.ts:315` and `e2e/costs.spec.ts:375` expect the waiter to see "Fatture".
- **N5. The nav jumps, and `/api/me` is fetched several times per page.**
  - The pills render without a role, then grow once `/api/me` answers.
  - `/api/me` is fetched separately by `owner-nav.tsx:60`, `src/app/page.tsx:32`, `anagrafiche/ingredienti/page.tsx:38`, `anagrafiche/fornitori/[id]/page.tsx:105`, `magazzino/page.tsx:64` and `tavoli/page.tsx:50`.

## 3. Design (the fix plan)

### 3.1 App shell and navigation model (P0; ADR-020)

#### 3.1.1 One model, pure and tested
`src/lib/nav/nav-model.ts` (new) is the single source of truth for what each role sees. It has no React and no fetch.

```ts
export type GroupKey = "oggi" | "acquisti" | "cucina" | "sala" | "gestione";
export interface Section { href: string; labelKey: MessageKey; group: GroupKey;
  can: (role: AppRole) => boolean; match?: readonly string[] }   // extra prefixes marked current
export interface NavGroup { key: GroupKey; labelKey: MessageKey; landing: string; sections: Section[] }
export function navFor(role: AppRole): NavGroup[];             // fixed group order, empty groups dropped
export function currentGroup(role: AppRole, pathname: string): GroupKey | null;
export function isFocusRoute(pathname: string): boolean;       // /tavoli/<uuid>, /magazzino/conteggi/<uuid>
export function landingFor(role: AppRole): "/" | "/tavoli";    // waiter → /tavoli, others → /
```

Each `can` reuses the existing gates. There are three new gates, each a mirror of the API role list, with a comment naming the route:
- `canReadInvoices` (owner, admin), in `src/lib/invoices/invoice-access.ts`;
- `canReadMasterData` (owner, admin, chef) and `canEditMasterData` (owner, admin), in `src/lib/master/master-access.ts`.

The current-tab rule keeps using `isCurrent` (`src/lib/nav/is-current.ts`) for the section's `href` and its `match` prefixes.

#### 3.1.3 Shell layout
`src/app/(owner)/app-shell.tsx` (new, client) wraps every signed-in page, **including home**. Home moves to `src/app/(owner)/page.tsx`; route groups do not change URLs. All parts reuse the tokens and the current pill style (ink fill with `aria-current="page"`). There are no icons, because ui-foundation §7 rules out images and icon fonts.

- **Header.** The band stays in the root layout. The BrandMark and the wordmark become one link to `/`, named "Osteria Dei Rossi, Oggi".
- **Phone (< 1024 px).**

### 3.3 `GET /api/today` (P1, PR B)

- **Route.** `src/app/api/today/route.ts`, `withApi({ roles: ["owner","admin","chef"] })`. A query string is a 400 (strict, as in `payables/list.ts:41`). The waiter gets 403.
- **Service.** `src/server/today/summary.ts` calls one SQL function, `public.today_counts()`.
  - The function is **SECURITY INVOKER**, so RLS applies to the caller. It is defined in migration `supabase/migrations/<timestamp>_today_counts.sql` and returns `jsonb`:
    - `invoicesToReview`: status in `review`, `duplicate`, `extraction_failed`;
    - `payablesOverdue`: the **same predicate** `payable_list` uses for `overdue`;
    - `payablesUnpaid`;
    - `batchesUseBy`: `expired` or `due_soon` with portions > 0, using the **same predicate** as `batch_list`'s `useByState`;
    - `countOpen`: boolean;
    - setup booleans: `hasLocations`, `hasSuppliers`, `hasIngredients`, `hasApprovedInvoice`, `hasStaff`, `hasDevice`, `hasTables`, `hasMenuItems`.
  - If either predicate is inline in its RPC today, the migration first extracts it into a SQL helper both RPCs call (B1 proves the RPC outputs are unchanged).
  - The alert count reuses `listAlerts`' open filter and `visibleTo(role)` from `src/server/alerts/list.ts` (exported for this). It reads at most `TODAY_ALERT_CAP + 1` rows and returns `{ count, more }`, so it cannot drift from what `/avvisi` shows.
- **Output, per role** (Zod output schema in `src/server/today/types.ts`):
  ```json
  { "cards": [ { "key": "invoicesToReview", "count": 2, "more": false, "href": "/fatture" } ],
    "setup": [ { "key": "locations", "done": true, "href": "/anagrafiche/ubicazioni" } ] }
  ```
  - owner: alerts, invoices, payablesOverdue, payablesUnpaid, batchesUseBy, countOpen, setup;
  - admin: the same without alerts;
  - chef: alerts, batchesUseBy, countOpen, and `setup: null`.
  - No key carries money; a test fails on `/cost|amount|eur|price|margin/i` in any key.
- **Errors.** The standard `{"error":{"code","message"}}` format; a DB failure is a 500 `today_unavailable` with no detail. Oggi then shows its P0 actions without counts and one `ErrorAlert`.

### 3.5 Data model
- **PR A:** no schema change.
- **PR B:** one SQL function, `today_counts()` (SECURITY INVOKER, `search_path = ''`), plus, only if needed, extracted predicate helpers shared with `payable_list` and `batch_list`. No new table and no column.

### 3.6 Invariants check
- **Screens read `/api/*` only.** The shell and Oggi read `/api/me`, and later `/api/today`. Counts are computed in Postgres. The nav model, today actions, `invoiceTitle`, `isInFlight` and the name filter are presentational helpers in `src/lib`, with no money or quantity arithmetic.
- **Waiters never see costs, and the chef never sees €.**
  - The waiter has one group, Sala › Tavoli.
  - A4 asserts there is no "€" in the chef's `body`, including the shell.
  - A5 asserts the chef's Oggi actions carry no "€".
  - B2 asserts the chef's `/api/today` payload has no money key.
- **Roles are enforced in Postgres.** The nav model only hides links. It changes no API role list and no policy.
- **Italian first, English second.** Every new string goes into `it.ts` and `en.ts`. `keys.ts` derives the key type from `it`, so a missing English key fails the type check.

## 4. Alternatives considered
- **A hamburger or drawer menu on the phone.** Rejected: the sections are hidden behind an extra tap, links in a closed drawer are not in the accessibility tree, and the PRD's "phone first, faster than paper" favours a visible bar.
- **A horizontally scrolling pill strip.** Rejected: items fall off-screen, and `expectPhoneFriendly` treats a scrolling box as overflow. ui-foundation §6 chose wrapping for that reason.
- **Keep the flat pills and only filter by role.** Rejected: the owner would still have 16 items wrapping above every page.
- **Moving screens into `(sala)`, `(cucina)` and `(admin)` now (project plan §3.2).** Rejected for this work: it means 100+ file moves for no URL or role-security gain, since role security is in Postgres. Revisit at M19, when the kitchen screen arrives.
- **Read the role server-side in the layout from the JWT claims.** Rejected for now: it would be the first screen code to read the session outside `/api/*`. `useMe` with a fixed-height placeholder removes the jump at the cost of one cached request.
- **A UI library for tabs and sheets (Radix, Headless UI).** Rejected: plain links and CSS do the job, and the rule is no new dependency.
- **Oggi counts computed in the browser from the existing lists.** Rejected: it is data logic in components, it costs N requests, and paginated lists (`payable_list`, `batch_list`) give wrong totals.
- **The enrolment code in a URL or QR code (`/dispositivo?codice=…`).** Rejected: the single-use code would end up in browser history and server logs. A QR code would also need a new dependency or hand-written encoder. Showing the address to type is enough.

## 6. Risks and mitigations

- **Test changes look like weakening.** A1 and A10 change assertions that encode the old nav: the waiter seeing "Fatture", and the chef keeping `/fatture` in `owner-nav.test.ts`. Mitigations:
  - each change is listed in the PR with its before and after;
  - the replacements are stricter (exhaustive role × section table, "every visible link opens" e2e);
  - no test is skipped.
- **Stale role on a shared device.** Cached `/api/me` could leak the previous person's nav. `resetMe()` runs on logout and on PIN login, and both A2 and A6 test it.
- **The fixed bar hides content or fights sticky bars.** Mitigations:
  - focus routes have no bar;
  - `main` has bottom padding equal to the bar plus the safe area;
  - the bar hides while a field has focus;
  - A4 asserts the last element is not covered.
  - Other sticky elements were found only in the two focus routes and the review's document panel, which is `top`-sticky.
- **Layout restructure (A3).** Moving `main` and the auth screens could break fonts, reveal or the wide review layout. `smoke`, `fonts`, `invoice-review` (1280) and the "one `main`" check run on A3 before anything else moves.
- **Security and privacy.**
  - Hiding links is not authorisation; every API role list and RLS policy is unchanged.
  - `/api/today` is role-gated in `withApi` and SECURITY INVOKER under RLS, with strict query parsing.
  - It returns counts only: no personal data and no money. Logs carry codes only, as today.
  - The enrolment address is the page's own host, and the code never enters a URL.
  - Oggi shows only the signed-in user's own name.
- **Secrets.** No new secret. The shell, Oggi and `/api/today` use the user's session cookie (Supabase publishable key in env, as today). The Supabase secret key stays confined to `/api/cron/*`, `scripts/` and `src/server/staff-auth/privileged.ts` (CLAUDE.md rule 2). The existing secrets, including `PIN_PEPPER` and the extraction API key, stay in Vercel environment variables and Supabase Vault (project plan §3.11.7). Nothing here reads them.
- **Performance and cost.**
  - A4 removes 2–5 duplicate `/api/me` calls per page.
  - `/api/today` is one RPC plus one capped alert read.
  - No figures are promised; the M22 dashboard keeps its own load-time test.
  - There is no new paid service.
- **Dependencies.** None added. `@testing-library/react` and `jsdom` are already used (`tests/components/home-links.test.ts`).
- **Scope creep into M19 to M23.** §3.1.4 limits these to reserved rows; no placeholder routes are built.
