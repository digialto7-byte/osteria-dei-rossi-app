## Decisions made
- **Founder decision followed:** `stock_movement` (has `unit_cost`) is SELECT for owner/admin only; `raw_lot` (no cost) is owner/admin/chef; `v_stock_on_hand` is `security_invoker`, so chef and waiter read 0 rows. `031` asserts: chef reads 2 lots, 0 movements, 0 view rows; waiter 0/0/0; owner B 0/0/0. `price_history`, `payable`, `audit_event` are owner/admin only (`030`, `032` assert chef, waiter, owner B read 0).
- `v_stock_on_hand`: all privileges revoked from `anon`, `authenticated`, `service_role`, then SELECT granted to `authenticated` (the plan did not say; `service_role` has no need of it yet, and re-granting is one line).
- `payable`: `payable_no_delete` (row, `app.append_only`) and `payable_no_truncate` are separate triggers from `payable_guard` (UPDATE only), so status updates for M9 pass through.
- `audit_event.reason` also refuses a blank string (`btrim` length ≥ 1), so a procedure must store null for an empty reason (plan step 7 already says so).
- Index named `audit_event_entity_idx`; `004` fixture rows use subselects for the location and app_user ids (the file had no ids for them).
- `toIngredientBase` already existed in `src/lib/units/convert.ts` with the needed behaviour, so no TypeScript production code changed in step 4; only the parity test is new. The parity test skips the factor row with a null unit (TypeScript's type cannot express it; callers check first) and says so in a comment.
- Test-first evidence: each step's tests were run before the migration and failed because the objects did not exist; the append-only (`037`) and parity tests were also mutation-checked (dropped a trigger / changed a vector) and failed as they should.

## Deviations from the plan
1. **`037` TRUNCATE uses `TRUNCATE … CASCADE`.** PostgreSQL refuses a plain TRUNCATE of a table that a foreign key references (0A000) before any trigger runs, so for the referenced tables (`raw_lot`, and `stock_movement` through its own `reverses_id` key) the plan's "TRUNCATE as migration owner → `append_only`" only reaches the trigger with CASCADE. A plain TRUNCATE of a referenced table is therefore still refused, with a different code. Documented in the test header. Plan wording for step 2 should read "TRUNCATE (cascade)".
2. `037` has 8 assertions per append-only table (the plan lists 7; I added DELETE as the migration owner) and 5 for `payable`.
