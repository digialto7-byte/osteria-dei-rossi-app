## Decisions made

1. `extraction_complete` calls `app.automap_invoice` after its header update, not before the duplicate decision. The supplier VAT and name it reads are stored by that update. The status outcome is unchanged, and `016` passes unchanged.
2. Auto-mapping looks up by supplier code first, then by description hash, so a line with an unknown code and a known description is mapped. The shared core is `app.automap_lines(invoice, item default null)`; `automap_invoice` and `propagate_mapping` both use it. A code match wins over a description match: the sort uses `coalesce(... , false)`, because `ORDER BY ... DESC` puts nulls first (found by test `022`).
3. Propagation reaches the same supplier's other invoices in `review`, and also other unmapped lines of the same key in the invoice being edited.
4. Mapping an ingredient equal to the stored suggestion sets `mapping_source = 'auto'` again and removes `ingredient` from `corrected_fields`.
5. Split children inherit `is_stock` and `cost_centre_id` from the parent. The plan said `is_stock` true; splitting a non-stock line would otherwise create stock lines that need an ingredient. For a stock parent it is identical to the plan.
6. `app.line_corrected_fields` returns `{}` for split children (no extraction baseline, and the report counts originals only).
7. `extraction_quality` with `p_status = 'all'` counts `review` and `approved`; `'approved'` counts approved only. This is my reading of "approved only when p_status = 'approved'".
8. `review_set_supplier` with a different supplier clears mappings, suggestions and `pack_corrected`, and recomputes `corrected_fields`; auto-mapping then runs for the new supplier, so a line whose code the new supplier knows is mapped again straight away.
9. `app.header_corrected_fields` measures against `extraction_json` (an invoice without one has no corrections). A missing value the reviewer types counts, except `supplier_vat`, which only counts when one was extracted.
10. Mapping a split child needs a linked supplier (`supplier_required`) like an original line, although it writes no `supplier_item`.
11. New internal helpers, not in the plan: `app.automap_lines`, `app.patch_value`, `app.check_cost_centre`, `app.header_corrected_fields`, and the constants `app.allowed_vat_rates()`, `app.total_tolerance_ten_thousandths()` and `app.line_amount_tolerance_ten_thousandths()` (the parity test reads them from the migration text).
12. T3 and T5 are resolved on PG 16: `normalize(..., NFC)`, `sha256` and `pg_stat_xact_user_tables` all work. Note that an `UPDATE` that changes no row is not counted, so `025` checks the write set as a subset, not an equality.

## Deviations from the plan

- **`invoice_duplicate_override_ck` is looser than planned.** The plan says `not duplicate_override or duplicate_override_at is not null`. Existing test `016` (which must stay unchanged) inserts `duplicate_override = true` with no time. The check is now `duplicate_override_by is null or duplicate_override_at is not null`: a recorded actor must have a time. `review_clear_duplicate` always sets both.
- **Test `015` and fixture `004` changed.** `015` uses `columns_are` on `invoice`, so its list grew by five columns (a schema listing, no assertion weakened). `004` got the cost centre and a mapped, a non-stock and a split line, as the plan said.
- **Step 3 test helper naming:** `description_hash` and `parse_unit_raw` are granted to `service_role`, because `extraction_complete` is security invoker. All other helpers have no grant.
- **Dependencies:** `@anthropic-ai/sdk` was not installed in this environment, so `tsc` had 8 errors before any change. I ran `npm install --no-save --no-package-lock @anthropic-ai/sdk@1.1.0` (the version in `package.json`). The lockfile and `package.json` are untouched.

## Plan statements that did not match the existing schema or tests

- Plan step 4 places the auto-map call "after the line insert, before the duplicate decision". At that point the invoice's `supplier_vat` and `supplier_name` are not yet stored (decision 1).
- The plan's `duplicate_override_at` check conflicts with `016` (deviation above).
- `015` asserts the exact column list of `invoice`; the plan lists only `004` as a test to touch.
- Supabase gives `anon`, `authenticated` and `service_role` EXECUTE on new functions in `public` by default (the native shim copies this). "`authenticated` only" therefore needs an explicit `revoke ... from anon, service_role`; the migrations and `pgTAP` privilege checks do this.

## Open questions

- Should changing a mapped line's `unit` update `supplier_item.invoice_unit`? The plan only writes it at mapping time, so a unit set later on an already-mapped line is not remembered. I followed the plan.
- Is `p_status = 'all'` meant to include `approved` (decision 7)? If not, only the one `any (case ...)` expression in `20261022130700_extraction_quality.sql` and tests `026` change.
- Inactive ingredients can still be chosen by hand in the DB (only auto-mapping skips them). The API or the picker should hide them; say so if the DB should refuse.
- CI `supabase test db` on the real stack should be watched on the first push. Differences from the native shims (roles, default privileges, `auth` functions) are the likely cause of any surprise.
