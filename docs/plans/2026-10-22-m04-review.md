## 1. Goal and scope
- **Goal:** the owner checks and corrects an extracted invoice on one screen (document left, lines right on a laptop; stacked on a phone). Every line action is recorded so the correction rate can be measured, and mappings are remembered per supplier so the next invoice from that supplier arrives already mapped. Nothing is approved and no ledger is written (approval is M5).
- **In scope:**
  - `GET /api/invoices/:id/review`: header, supplier link or suggestion, gate flags and totals difference, lines with unmapped lines first, per-field confidence highlights, line checks, auto-map suggestion, base-unit quantity preview;
  - line actions through `PATCH /api/invoices/:id/lines/:lineId`: map to an ingredient (creates or updates `supplier_item` keyed by `supplier_code`, else `description_hash`), pack conversion, non-stock with a cost centre, credit memo quantity, lot code and expiry, correcting extracted values (qty, unit, unit price, amount, VAT rate, supplier code), "line checked";
  - split and unsplit (`POST …/split`, `POST …/unsplit`);
  - link an existing supplier or create one from the extracted data (`POST /api/invoices/:id/supplier`);
  - header corrections (number, dates, totals) with the totals gate and the duplicate check re-run (`PATCH /api/invoices/:id`);
  - carried over from M3 and context.md: "Non è un doppione" (`POST /api/invoices/:id/not-duplicate`, founder answer M2 V3) and manual retry of `extraction_failed` (`POST /api/invoices/:id/retry`);
  - auto-mapping at extraction completion, plus propagation of a new mapping to other invoices still in review;
  - `corrected` flag and `corrected_fields` per line, `header_corrected_fields` per invoice;
  - `cost_centre` table with `GET/POST /api/cost-centres`;
  - `GET /api/reports/extraction-quality` and a small screen `/fatture/qualita`;
  - the review screen `/fatture/[id]/revisione` in the house style, an opt-in wide layout for laptop, a link from the invoice detail page;
  - a line-level "would need correction" figure in the M3 live contract summary (AT5 live proxy).
- **Out of scope:**
  - `approve_invoice`, reject, `audit_event`, receipts, lots, price history, payables, `supplier_item.last_price` (all M5);
  - per-supplier mapping hints in the extraction prompt (M3 had moved them to M4; deferred, see §4 and "Plan changes");
  - creating an ingredient from the review screen (the screen links to `/anagrafiche/ingredienti`);
  - remembering non-stock articles per supplier (→ V4);
  - separate credit-note documents ("nota di credito") and printed negative lines (Q2, → V1);
  - editing or deactivating cost centres beyond create (the owner adds them on the fly);
  - optimistic-concurrency tokens for two reviewers editing the same line (see §6).

## 3. Design

### 3.1 Decisions
1. **Auto-mapping runs at extraction completion, inside `extraction_complete`** (replaced in step 4), not at review load. Reasons, against the M3 code:
   - `extraction_complete` already inserts the lines in one transaction, with the tenant known and the invoice locked. Mapping there means lines are never visible half-mapped. Drive intake (M10) and the XML path (M39) get mapping for free, matching step 5 of the ADR-004 pipeline.
   - The suggestion stored at that moment (`suggested_ingredient_id`, `suggested_unit`) is the fixed baseline the correction metric compares against. Computing suggestions on each `GET` would move the baseline whenever the memory changes, so "corrected" would not be stable.
   - A `GET` that writes would be unsafe (repeated fetches, effects that run twice in development, caching).
   - **Gap and its fix:** a mapping created after an invoice was extracted (two invoices from a new supplier uploaded together) would not reach the second one. So every mapping action also **propagates** the new mapping to unmapped lines of the same supplier in other `review` invoices, in the same transaction. Linking a supplier also re-runs auto-mapping for that invoice. Only a mapping decision of the reviewer stops this (`invoice_line.mapping_decided_at`: ingredient set or cleared, non-stock chosen; `unit_decided_at` stops the unit fill only, migration `20261022130900`); value edits and "line checked" do not.
   - **Concurrency (migration `20261022131000`):** auto-mapping locks the invoice it writes to (`FOR UPDATE`) and re-checks, in the write, that the invoice still has the item's supplier (and, for propagation, is still in `review`) and that the line's code or description hash still matches the item. Propagation uses `SKIP LOCKED`: an invoice another reviewer is working on is left out, never waited for, so two owners mapping on two invoices cannot deadlock (a wait would: each holds its own invoice and one needs the item row the other holds). A skipped line stays unmapped; its reviewer maps it, or the next propagation does.
   - **After a supplier relink (to confirm with the founder):** (a) `mapping_decided_at` stays set on lines whose manual mapping the relink cleared, so the new supplier's memory does not fill them and the reviewer maps them by hand; (b) a unit the reviewer changed keeps the old supplier's `suggested_unit` as its correction baseline (only a unit the memory filled is cleared). Both follow from "relink keeps the decision markers"; see §3.1.6 for the baseline.
   - **Failure path:** auto-mapping only reads same-tenant rows and writes ids that composite FKs validate. If it raises, the whole completion fails as M3's `store_failed` (non-retryable for SQLSTATE 22/23) and Sentry gets the code. After the fix, the owner can use "Riprova lettura". No exception is swallowed.
2. **The supplier link:** extraction links `invoice.supplier_id` automatically only on an exact VAT match with an active supplier. A name-only match (no VAT) is stored as `supplier_suggestion_id` and needs one tap, consistent with the M2 founder rule that a name match is only a warning. Mapping a line requires a linked supplier (`supplier_required`), because the memory is per supplier.
3. **All writes go through `SECURITY DEFINER` procedures** (`search_path = ''`, tenant from `app.tenant_id()`, role checked by `app.require_invoice_reviewer()`, one transaction each, execute for `authenticated` only). `authenticated` gets **no** UPDATE grant on `invoice`, `invoice_line` or `supplier_item`, so it can never set `corrected_fields` or suggestions directly. Definer functions bypass RLS, so every query inside filters `tenant_id = app.tenant_id()` explicitly, and every procedure has a cross-tenant pgTAP case.
4. **Who may review:** owner and admin, per the role matrix (§3.11.2: invoices, lines and `supplier_item` are owner/admin RW, chef none). The role list lives in one function, `app.require_invoice_reviewer()`, so V3 changes one place plus the policies.
5. **Rows are never deleted.** A split keeps the parent row (`split_at`) and adds children (`parent_line_id`, `sub_position`); a re-split or unsplit marks old children `superseded_at`. "Active lines" below means `split_at is null and superseded_at is null`.
6. **What counts as a correction (base plan; Q5 → V5):** the reviewer changed a value the system proposed. Per line, `app.line_corrected_fields()` recomputes `corrected_fields` after every write, comparing the row with its `extracted` baseline and its suggestions:

   | Field | Counted when |
   |---|---|
   | `qty`, `unit_price`, `line_amount`, `vat_rate`, `supplier_code` | current value is distinct from `extracted` (null → value counts: the model could not read it) |
   | `lot_code`, `expiry` | `extracted` value is not null and the current value differs (typing a missing lot at receiving is **not** a correction, PRD Traceability) |
   | `unit` | `suggested_unit` is not null and `unit` differs |
   | `ingredient` | `suggested_ingredient_id` is not null and `ingredient_id` differs (includes unmapping and marking non-stock) |
   | `pack` | the reviewer changed the pack of an auto-suggested `supplier_item` (`pack_corrected`, sticky) |

   These are not corrections: a first-time mapping of an unmapped line, a split, non-stock marking of an unmapped line, a credit quantity, and "line checked". Changing a value back to the extracted one removes the field. `corrected` is a generated column, `cardinality(corrected_fields) > 0`, so flag and fields cannot drift. Header fields use `header_corrected_fields` the same way (against `extraction_json`).
   After a supplier relink the unit baseline is not reset when the reviewer changed the unit: `suggested_unit` stays the old supplier's (to confirm, see §3.1.1).
7. **"Lines from a mapped supplier"** (PRD acceptance) = original lines with an auto-suggested ingredient (`suggested_ingredient_id is not null`). The report shows this sub-rate next to the overall rate.
8. **The totals gate and line checks are re-run in SQL after edits** (`app.totals_gate`, `app.line_checks`), because a corrected amount must be able to clear `total_mismatch` (M5 refuses approval while it is set). The SQL copies the TS rules of `checks.ts` (gross basis, ±€0.05, `ALLOWED_VAT_RATES`), and a parity test keeps the two in step (step 3). `low_confidence` and `supplier_is_buyer` stay as extracted (informational). Per-field highlights disappear once a line is saved (`reviewed_at`).
9. **The description hash lives in SQL only:** `app.description_hash(text)` = hex SHA-256 (built-in `sha256()`, no extension) of `lower(regexp_replace(normalize(btrim(s), NFC), '\s+', ' ', 'g'))`. With one implementation, no TS mirror can disagree. A line with a `supplier_code` is keyed by code (hash left null); any other line is keyed by hash.
10. **The line unit:** `invoice_line.unit` ∈ `kg, g, l, ml, pz, conf` (`conf` = whole purchase packs, as in `src/lib/units`). Auto-mapping fills it from `app.parse_unit_raw(unit_raw)`, else from the article's remembered `supplier_item.invoice_unit`. Base quantity (a preview here, posted in M5) = `toIngredientBase(qty, unit, ingredient.base_unit, pack)`; `conf` needs the item's pack.

### 3.2 Data model (migrations after `20261022120300`)

**`20261022130000_cost_centre.sql`** (an addition to plan §3.5.2)
- `cost_centre (id, tenant_id default app.tenant_id(), name text check length(btrim) 1–60, is_active bool default true, created_at, created_by default app.app_user_id())`, `unique (tenant_id, id)`, unique index `cost_centre_name_uq (tenant_id, app.normalise_name(name))`.
- RLS: select/insert/update for owner/admin of the tenant. Grants: `select, insert (name), update (name, is_active)` to `authenticated`; `revoke delete, truncate` from `service_role`. No seeded list (Q4).

**`20261022130100_invoice_review_columns.sql`**
- `invoice`:
  - `supplier_id uuid`, FK `(tenant_id, supplier_id) → supplier (tenant_id, id)`;
  - `supplier_suggestion_id uuid`, same FK shape (name-only match);
  - `header_corrected_fields text[] not null default '{}'`, check ⊆ `{number_raw, invoice_date, due_date, net_total, vat_total, gross_total, supplier_vat}`;
  - `duplicate_override_by uuid → app_user`, `duplicate_override_at timestamptz`, check `not duplicate_override or duplicate_override_at is not null`;
  - index `invoice_supplier_status_idx (tenant_id, supplier_id, status)` (for propagation).
- `invoice_line`:
  - `unique (tenant_id, id)` (target of the self FK);
  - `sub_position smallint not null default 0` (≥ 0), and `parent_line_id uuid` with FK `(tenant_id, parent_line_id) → invoice_line`. Check `(parent_line_id is null) = (sub_position = 0)`. The unique key becomes `(tenant_id, invoice_id, position, sub_position)` (replaces `invoice_line_position_uq`);
  - `split_at timestamptz` (only when `parent_line_id is null`), `superseded_at timestamptz` (only when `parent_line_id is not null`);
  - `unit text`, `suggested_unit text`, both checked ∈ `kg, g, l, ml, pz, conf`;
  - `ingredient_id`, `supplier_item_id`, `suggested_ingredient_id`, `suggested_supplier_item_id`, each a composite FK to its tenant's row;
  - `mapping_source text` ∈ `auto, manual`; check `(ingredient_id is null) = (mapping_source is null)`;
  - `is_stock boolean not null default true` and `cost_centre_id` (composite FK), with three checks: `invoice_line_non_stock_ck: is_stock or cost_centre_id is not null`; `is_stock or (ingredient_id is null and supplier_item_id is null)`; `not is_stock or cost_centre_id is null`;
  - `credit_qty numeric(12,4) not null default 0`, check `invoice_line_credit_qty_ck: credit_qty >= 0 and credit_qty <= qty`;
  - `corrected_fields text[] not null default '{}'` (⊆ the §3.1.6 list), `corrected boolean generated always as (cardinality(corrected_fields) > 0) stored`, `pack_corrected boolean not null default false`;
  - `reviewed_by uuid → app_user`, `reviewed_at timestamptz`.
  - Grants unchanged: `authenticated` keeps SELECT only (RLS owner/admin).
- `supplier_item`: `invoice_unit text` ∈ the unit list (the unit this article is invoiced in). Only the review procedure writes it; no new grant.

**`20261022130200_review_helpers.sql`** (all in schema `app`; execute revoked from `public, anon, authenticated`; granted to `service_role` where `extraction_complete` needs it)
- `app.description_hash(text) returns text` (immutable, null → null).
- `app.parse_unit_raw(text) returns text` (immutable): lower-cases, drops dots and spaces, then looks up a fixed list. The initial list will be extended when Q1 samples arrive:
  - `kg, kgs, chilo, chili → kg`;
  - `g, gr, grammi → g`;
  - `l, lt, litro, litri → l`;
  - `ml → ml`;
  - `pz, pezzo, pezzi, n, nr, num, cad, un → pz`;
  - `ct, crt, cartone, cf, conf, confezione, cassa, collo, sc, scatola → conf`;
  - anything else → null.
- `app.line_checks(qty, unit_price, line_amount, vat_rate) returns text[]` (same rules and tolerance as `checks.ts`).
- `app.totals_gate(p_invoice uuid) returns table (flagged boolean, diff numeric)`: Σ active `line_amount` + `vat_total` − `gross_total`; a null total → flagged, diff null. `app.refresh_gate(p_invoice)` writes `totals_diff` and adds or removes only `total_mismatch` in `gate_flags`.
- `app.line_corrected_fields(l public.invoice_line) returns text[]` (§3.1.6).
- `app.require_invoice_reviewer()`: 42501 unless `app.role()` ∈ owner, admin.
- `app.lock_review_invoice(p_invoice uuid) returns public.invoice`: `for update` where `id` matches and `tenant_id = app.tenant_id()`; missing → P0002 `not_found`; status ≠ `review` → P0001 `invoice_not_in_review`.
- `app.recheck_duplicate(p_invoice uuid)`: the duplicate block of `extraction_complete`, factored out. It takes the advisory lock from `app.invoice_dup_lock_key`; a VAT match → `duplicate` + `duplicate_of`; with no VAT, `duplicate_warning_of` is set or cleared. Skipped when `duplicate_override`.

**`20261022130300_automap.sql`**
- `app.automap_invoice(p_invoice uuid) returns int` (lines mapped). It runs as `service_role` from the worker, so every lookup filters `tenant_id` = the invoice's tenant:
  1. If `supplier_id` is null: VAT not null → the active supplier with that VAT → `supplier_id`. VAT null and name not null → exactly one active VAT-less supplier with the same `app.normalise_name` → `supplier_suggestion_id`.
  2. Every active original line with `unit` null: `unit = suggested_unit = app.parse_unit_raw(unit_raw)`.
  3. With a supplier, each active original stock line with `mapping_source` null is looked up: by `(supplier, supplier_code)` when the line has a code, else by `(supplier, description_hash)`. The item must be active and its ingredient active. If found: `ingredient_id = suggested_ingredient_id`, `supplier_item_id = suggested_supplier_item_id`, `mapping_source = 'auto'`; when `unit` is still null, `unit = suggested_unit = item.invoice_unit`.
- `create or replace public.extraction_complete(...)`: unchanged except for `perform app.automap_invoice(p_invoice)` after the line insert, before the duplicate decision. Signature, grants and status outcomes stay the same (pgTAP `016` must stay green unchanged).
- `app.propagate_mapping(p_item uuid) returns int`: for the item's supplier, unmapped active original stock lines of other `review` invoices with the same key are auto-mapped as in item 3 above.

**`20261022130400_review_update_line.sql`**: `public.review_update_line(p_invoice uuid, p_line uuid, p_patch jsonb) returns void` (definer). Order:
1. `require_invoice_reviewer`, then `lock_review_invoice`. The line is locked `for update` (same tenant and invoice, `superseded_at is null`), else P0002; `split_at` set → P0001 `line_split`.
2. Values present in the patch: `qty`, `unit_price`, `line_amount` (on a child → `split_child_locked`), `vat_rate`, `supplier_code`, `unit`, `lot_code`, `expiry`.
3. `is_stock` / `cost_centre_id`: false needs an active same-tenant cost centre (from the patch or the row), else `cost_centre_required`, and clears the mapping. True clears the cost centre.
4. `ingredient_id` (null = unmap), with an optional `pack {count, size, unit, label}`:
   - needs `invoice.supplier_id` (`supplier_required`) and `is_stock` (`non_stock_has_ingredient`);
   - original line: key = `supplier_code`, else `app.description_hash(raw_description)`. An existing item → update `ingredient_id`, the pack if given, and `invoice_unit = unit`. No item → insert one (tenant and `created_by` explicit) with the given pack, else the default `1 × 1 <unit>` when `unit` is a measure unit, else `pack_required`. The units trigger still raises `incompatible_units`;
   - child line: `ingredient_id` only (no memory, `supplier_item_id` null); its unit must be a measure unit (`pack_required`);
   - `mapping_source = 'manual'` unless the ingredient equals the suggestion; then `app.propagate_mapping(item)`.
5. `pack` alone: needs `supplier_item_id` (`not_mapped`) and updates the item. Sets `pack_corrected` when the line was auto-mapped and the pack changed.
6. `credit_qty`: `> qty` → `credit_qty_exceeds_qty` (the check constraint is the backstop).
7. Always: set `reviewed_by` and `reviewed_at`, `checks = app.line_checks(...)`, `corrected_fields = app.line_corrected_fields(row)`, then call `app.refresh_gate(invoice)`. It never touches `invoice.status`, `supplier_item.last_price`, or any table other than `invoice`, `invoice_line` and `supplier_item`.

**`20261022130500_review_split.sql`**
- `public.review_split_line(p_invoice, p_line, p_children jsonb)`, with 2–10 children `{qty > 0, line_amount ≥ 0}`:
  - the parent must be an original line (`split_child_cannot_split`) with `credit_qty = 0` (`split_credit_conflict`);
  - sums must be exact in numeric, `Σqty = qty` and `Σline_amount = line_amount`, else `split_sum_mismatch`;
  - existing active children → `superseded_at`;
  - new children get the next `sub_position`s and `unit_price = round(amount / qty, 4)`. They copy `vat_rate`, `unit`, `lot_code` and `expiry`, and get `is_stock` true, `extracted = '{}'` and `field_confidence = '{}'`;
  - the parent gets `split_at = now()`.
- `public.review_unsplit_line(p_invoice, p_line)`: `not_split` unless split; children superseded; `split_at` null.

**`20261022130600_review_invoice_procedures.sql`**
- `public.review_set_supplier(p_invoice uuid, p_supplier uuid, p_new jsonb)`: exactly one of the two must be given (`invalid_request`).
  - `p_new {name, vat_number, payment_terms_days}` inserts a supplier (23505 on `supplier_tenant_vat_uq` → 409 as in M1).
  - Changing an existing link clears every line mapping and suggestion (they belonged to the other supplier).
  - Sets `supplier_id` and clears `supplier_suggestion_id`. If the supplier has a VAT number distinct from `invoice.supplier_vat`, copies it, and records `supplier_vat` in `header_corrected_fields` when the extracted VAT was not null.
  - Then runs `app.recheck_duplicate`, then `app.automap_invoice`.
- `public.review_update_header(p_invoice, p_patch jsonb)`: fields `number_raw`, `invoice_date`, `due_date`, `net_total`, `vat_total`, `gross_total`. Recomputes `header_corrected_fields` and runs `app.refresh_gate`; runs `app.recheck_duplicate` when the number or date changed (this may move `review → duplicate`).
- `public.review_clear_duplicate(p_invoice)`: `duplicate → review` with `duplicate_of` cleared, or a `review` invoice's `duplicate_warning_of` cleared; sets `duplicate_override`, `_by` and `_at`; otherwise `not_flagged`. M3 asked for an audit row; that comes with `audit_event` in M5, and until then `_by`/`_at` are the record.
- `public.retry_extraction(p_invoice)`: `extraction_failed → received`, `attempts = 0`, `next_attempt_at` and `extraction_error` null; otherwise `not_failed`.

**`20261022130700_extraction_quality.sql`**: `public.extraction_quality(p_from date, p_to date, p_supplier uuid default null, p_status text default 'all') returns jsonb` (SECURITY INVOKER, stable, so RLS limits it to owner/admin).
- It counts **original lines** (`parent_line_id is null`) of invoices in `review` and `approved` (`approved` only when `p_status = 'approved'`), with the extraction date, in the tenant's time zone, between the bounds.
- It returns `{invoices, lines, correctedLines, correctionRate, autoMappedLines, autoMappedCorrected, autoMappedCorrectionRate, manualMappedLines, splitLines, byField{…}, bySupplier[{supplierId, name, lines, correctedLines, correctionRate}]}`. Rates are `null` when there are no lines.
- A range over 366 days → P0001 `range_too_long`.

### 3.4 Flow
1. Upload (M2) → worker (M3) → `extraction_complete` → **`app.automap_invoice`** → `review` / `duplicate` / warning.
2. The owner opens `/fatture/[id]/revisione` → `GET …/review` and `GET …/file-url` (laptop: framed document; phone: "Apri documento" link).
3. No supplier linked → "Collega" (the suggestion, or the list from `GET /api/suppliers`) or "Crea fornitore" prefilled from the extraction → `POST …/supplier` → duplicate re-check → auto-map.
4. For each line in order: map it (ingredient list from `GET /api/ingredients`), set the pack, book it non-stock with a cost centre, record a credit, a lot or an expiry, fix values, or split it → `PATCH`/`POST` → procedure → `{review}`.
5. Mapping a new article creates a `supplier_item`, which is propagated to other invoices in review. The next invoice from that supplier is auto-mapped at extraction, with `corrected = false` unless the owner changes something.
6. `GET /api/reports/extraction-quality` → `/fatture/qualita`.

## 4. Alternatives considered
- **Auto-mapping at review load (`GET`):** rejected (§3.1.1). It means either a `GET` that writes, or suggestions that move with the memory and make `corrected` unstable.
- **Auto-mapping in TypeScript inside `extract-job.ts` before `extraction_complete`:** rejected. It would need a second round of reads with the secret key outside the completion transaction, and the lookups would race with a mapping a reviewer writes at the same moment.
- **Per-supplier hints in the extraction prompt now (M3 deferred them here):** deferred.
  - Deterministic mapping after extraction already gives the PRD's "second invoice nearly automatic".
  - Hints only help the model read descriptions; their benefit is unmeasured, and they add tenant data to every paid call.
  - Revisit if the quality report shows field corrections (not mapping) above 10% on mapped suppliers.
- **Table-level UPDATE grants with RLS and triggers for the line edits:** rejected. The reviewer could then write `corrected_fields` or suggestions directly. Definer procedures keep the rules and the one-transaction guarantee in Postgres, as plan §3.5.3 prescribes.
- **Free-text `cost_centre` on the line (plan §3.5.1 wording) or a fixed enum:** rejected. Free text splits "Pulizie"/"pulizia" in later reports, and an enum needs a migration for every new centre. A small tenant table costs one migration and two endpoints.
- **Splitting by replacing the parent with children (delete):** rejected by the "nothing is deleted" invariant; the parent stays, with `split_at`.
- **An append-only `invoice_line_change` correction log now:** deferred to `audit_event` (M5). `extracted`, `corrected_fields` and `reviewed_by/at` are enough to measure the rate, which is what M4 must prove.
- **A TS copy of the description hash:** rejected; one SQL implementation cannot disagree with itself.
- **A PDF.js viewer for the document panel:** rejected. It would be a new dependency for what the browser's own viewer does on a laptop, and phones open the native viewer.

## 6. Risks and mitigations
- **Security / privacy**
  - *Definer procedures bypass RLS:* every query inside filters `tenant_id = app.tenant_id()`, the role is checked first, `search_path = ''`, and execute is for `authenticated` only. Each procedure test has chef, waiter and owner-B cases (steps 5–7).
  - *Auto-mapping runs as `service_role` in the worker:* every lookup has an explicit tenant filter. `022` includes a tenant-B item with the same code and VAT, which must be ignored (step 4).
  - *Waiters never see costs:* routes are owner/admin only; `invoice_line`, `supplier_item` and `cost_centre` have no waiter policy; `004` is extended with fixture rows (steps 1 and 2); the payload test scans for `last_price` (step 9).
  - *Untrusted extracted text:* descriptions and supplier names come from the document (prompt injection, plan §3.11.5).
    - They are rendered as escaped text (step 16 test) and used only as a hash key.
    - A supplier is created only when the owner submits the prefilled form, which goes through the M1 Zod rules and the VAT checksum (step 12).
  - *Signed URL in the page:* a 5-minute bearer link in the iframe `src`, with `referrerPolicy="no-referrer"`, never logged or stored. The document is served from the Storage origin, so it cannot script our origin. **For M25:** the nonce CSP must allow the Supabase Storage origin in `frame-src` and `img-src`, or the panel breaks.
  - *CSRF:* all writes are JSON-only with SameSite cookies (existing `withApi`).
  - *Logs:* ids and codes only. DB messages never reach the client (the step 10 error mapping), and errors carry no descriptions or prices.
- **Correctness**
  - *Two reviewers on one invoice:* row locks make each action atomic. The later write wins, and both screens refresh from the server on their next action. Accepted for one owner plus the DigiAlto admin; revisit with multi-venue.
  - *Description hash brittleness:* a supplier that prints dates or lot numbers in the description defeats hash matching. Supplier codes are preferred, and the report's per-supplier rate shows where this happens (assumption in §7).
  - *Re-linking a supplier clears mappings:* intended, since they belonged to the other supplier. The screen asks for confirmation before relinking (step 17 test).
  - *A mapping changed on an existing item* does not re-map lines already auto-mapped in other open invoices. They keep the earlier suggestion, which the reviewer sees.
  - *TS/SQL drift of the gate and line checks:* the parity test (step 3) fails on any difference.
  - *Retry costs:* each retry can mean up to 3 paid calls. Retry is owner/admin only, and only from `extraction_failed`.
- **Unverified (checked in the named step):**
  - **T1** Storage signed-URL responses can be framed by our origin (step 19; → VT1). Local Supabase and hosted Storage may differ, so the PR records a manual check on the staging preview.
  - **T2** Chrome refuses to render a PDF inside a `sandbox`ed iframe (reported behaviour, not verified). The plan uses no `sandbox`, so this only matters if a reviewer asks for one.
  - **T3** Postgres `normalize(text, NFC)` and `sha256(bytea)` are available on the Supabase Postgres version (step 3, `021`).
  - **T4** Tailwind v4 `has-[[data-layout=wide]]` on `<main>` works (step 19 width assertions).
  - **T5** `pg_stat_xact_user_tables` counters inside the pgTAP transaction show the procedure's writes (steps 5–7). If they do not, those cases compare row counts and `reviewed_at`/`created_at` markers on every public table before and after the call.
- **Performance / cost:** about 25 invoices a month (unverified). Each write re-reads the review payload (a few indexed queries). No performance figure is promised, and there is no new running cost.
- **Dependencies:** none added.
- **For M5 (hand-off notes):**
  - `approve_invoice` should refuse when an active stock line has no ingredient or no computable base quantity, when no supplier is linked, or when a duplicate warning is not overridden;
  - receipts are posted from active lines only (children, not split parents);
  - payable = gross − Σ (`credit_qty × unit_price`) on active lines; the VAT treatment of credits depends on Q1;
  - `audit_event` rows for the duplicate override and the line corrections, from M5 onwards;
  - set `supplier_item.last_price`.
- **Plan changes to record in DigiAlto-Ops `context.md`:**
  - auto-mapping runs at extraction completion, with propagation (confirms step 5 of the ADR-004 pipeline);
  - per-supplier prompt hints are deferred until the quality report shows a need;
  - `cost_centre` becomes a tenant table (plan §3.5.2);
  - `invoice.supplier_id` arrives in M4 (plan §3.5.1 placed it in M2);
  - header corrections, with the gate and duplicate re-check, are added to M4;
  - the duplicate override is recorded in `duplicate_override_by/at` until `audit_event` (M5);
  - `supplier_item.invoice_unit` is added;
  - the review page opts into a wide laptop layout; every other page stays phone-width.

## 7. Open questions for the founder
- **Q1** (M3 Q2, plan Q20) **Totals basis, still pending with the accountant:** should the check compare lines + VAT with the invoice total (base plan, gross), or the net lines with the taxable amount (→ V2, together with M3 V1)? For the review screen, this decides:
  - which figure "Il totale non corrisponde" compares;
  - which header field a correction must fix;
  - how credited amounts are treated in M5.
- **Q2** (M3 Q3) **Negative lines (discounts, deposits, returns):** do supplier invoices print them?
  - **Today:** such an invoice fails at extraction (`schema_invalid`), so it never reaches the review screen, and "Riprova lettura" will fail again.
  - **M4's credit quantity is not the answer:** it is something **you** record on a normal line for a short or damaged delivery. It cannot represent a printed negative line or a separate credit-note document.
  - **If yes:** M3 V2 is built first, then M4 V1. A negative line is shown as "Sconto o reso" and must be booked as non-stock with a cost centre (e.g. "Sconti", "Cauzioni"). It is not mapped to an ingredient, credited or split, and it counts in the totals.
  - Do suppliers also send separate credit notes (note di credito)? Those would be a later milestone.
- **Q3** **Who may review and correct invoices:** owner and DigiAlto admin (base plan, role matrix), or the chef too (→ V3)? The review screen shows unit prices, so a chef reviewer only works if the chef may see € costs. That is plan Q16, where the lead recommends percentages only, which would rule V3 out.
- **Q4** **Cost centres:** which ones do you want to start with (for example gas, cleaning, service fees, as in the PRD)? Base plan: the owner creates them from the review screen when first needed, and none are preset. No code depends on the list.
- **Q5** **What counts as a "line correction"** for Gate 1 (under 10%) and the PRD's 90% target?
  - **Base plan:** changing a value the reading or the auto-mapping proposed (§3.1.6).
  - **Not counted in the base plan:** splitting a line, mapping a new article the first time, filling a missing lot, booking non-stock, recording a short delivery.
  - Should splits and first-time mappings count too (→ V5)?
- **Q6** **Remember non-stock articles:** should a supplier line booked once as non-stock (e.g. the monthly gas line) be booked the same way automatically next time (→ V4)? Base plan: the owner ticks it on each invoice.
- **Assumptions (confirm):**
  - a supplier is linked automatically only on an exact VAT match; a name-only match is a one-tap suggestion;
  - mapping a line needs the supplier linked first;
  - a split has 2 to 10 parts, and its quantities and amounts must add up exactly;
  - the description key ignores case and extra spaces only (not dates or lot numbers inside the description);
  - the initial list of unit abbreviations in §3.2 (to be extended from the sample invoices of M3 Q1);
  - "Riprova lettura" has no cap beyond owner/admin access;
  - the quality report defaults to the last 30 days.
- **Technical, resolved inside the build:** T1–T5 (§6).
