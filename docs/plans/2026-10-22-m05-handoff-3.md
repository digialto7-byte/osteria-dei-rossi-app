### Payload additions (`src/server/invoices/review-types.ts`)
```
InvoiceReview.approval: null | {                      // only while status is 'review'
  canApprove: boolean,                                // blockers.length === 0
  blockers: [{ code: string, lineIds: string[] }],    // gate order; lineIds [] when not line-specific
  receiptDate: 'YYYY-MM-DD' | null,
  payable: { grossAmount, creditedAmount, amount: number|null, dueDate: 'YYYY-MM-DD'|null, dueDateSource: 'invoice'|'supplier_terms'|null },
  receipts: number,                                   // stock lines that will be received
  locations: { required: boolean, options: [{id, name}], defaultId: string|null }
}
InvoiceReview.decision: null | { action: 'approved'|'rejected', at: ISO timestamp, byName: string|null, reason: string|null }  // reason only for rejected
InvoiceReview.posting: null | {                       // approved only
  payable: { grossAmount, creditedAmount, amount, dueDate, dueDateSource, status: string },
  locationName: string|null
}
ReviewLine.toReceive: null | { qty, unit: 'kg'|'l'|'pz', unitPrice: number|null }   // status review only; null = posts nothing; qty 0 = fully credited
ReviewLine.received:  null | { qty, unit }            // approved only, from raw_lot
ReviewLine.creditAmount: number|null                  // now from the preview, VAT included; null without a preview or without VAT rate
```
`approval.blockers[].code` is always one of the approval error codes (same strings as the `ErrorCode` union). `locations.required` means more than one active location: show the `Select`, send `locationId`. With one location, send `{}`. With none, the blocker is `no_location`.

Which statuses carry what: `approval` only for `review`; `decision` for `approved`/`rejected` (null if the audit row cannot be read); `posting` for `approved`; `creditAmount` comes from the preview, which is read for `review`, `duplicate`, `approved`, `rejected` (so credit amounts still show on decided invoices); nothing is read for `received`/`extracting`/`extraction_failed`. `toReceive` and `received` appear only on the lines the preview/lots name (split children included; a split parent has neither).

Formatting is the UI's job and uses server values only: `formatEuro`, `formatCalendarDate` (dates are plain `YYYY-MM-DD`), `formatDateTime` for `decision.at` (Europe/Rome). `toReceive.unitPrice` is € per base unit, net of VAT.

## Decisions made
- **No new ErrorCode for trigger codes:** `invoice_line_frozen`, `append_only`, `payable_immutable` map to 409 `conflict` with a generic Italian message (no database text); 23505 on ledger keys already mapped to 409 `conflict` via `mapDbError`.
- **`approveBody`/`rejectBody` are `z.strictObject`** (withApi strictens plain objects only; the explicit form also makes direct `safeParse` tests strict). Control/bidi detection reuses `CONTROL_OR_BIDI` from `file-check.ts` (a fresh non-global RegExp, since that constant has the `g` flag).
- **The preview is read for four statuses, not only `review`**, so `creditAmount` (a line figure the M4 screen already showed) does not disappear on decided or duplicate invoices. `approval` is still null outside `review`. Plan test "RPC called once for a review invoice" holds.
- **`toReceive` only in `review`, `received` only from lots of an `approved` invoice**, as plan §3.6.
- **Decision location:** the location name of an approved invoice is read via `audit_event.after.location_id` (one `location` lookup), not from `raw_lot`, so an approval with zero receipts still shows where it was booked. Only `location_id` is taken from `after`; the rest of the JSON is dropped.
- **Cost safety:** the loader's column lists contain neither `unit_cost` nor `last_price`; tests scan both the selected columns and the returned JSON. `toReceive.unitPrice`/`payable` are euro figures but the route is owner/admin only (chef/waiter get 403 before any query or RPC, asserted on GET review, approve and reject).
- `selectByIds` gained a `column` parameter (default `"id"`) and tolerates a null result (PostgREST returns `[]`; the fake returns null).

## Deviations from the plan
1. **TS credit preview removed, tests rewritten.** Plan §3.6 says `creditAmount` comes from the preview. The three M4 `buildReview` tests that pinned the net TS formula (1 × 12,75; zero without credit; cent rounding) were replaced by preview-based tests (5,50 including VAT; null without VAT rate; 0 for no credit). Not a weakening: the behaviour they pinned was deliberately replaced; the cent rounding is now SQL's and covered by `034`/`035`.
2. **Existing M4 action tests changed mechanically:** every review reload now makes one `invoice_approval_preview` RPC, so assertions like `rpc` "called 1 times" became `procedureCalls(client)` (the same check without the preview). No expectation about the procedures themselves changed.
3. **`tests/integration/review.int.ts` line 505** expected `creditAmount: 9.1` (net TS preview). With the SQL figure for the Burro line (credit 1 of qty 2, line amount 18,20, VAT 10) it is 1 × 18,20 ÷ 2 × 1,10 = 10,01; I changed the expectation. **Not run** (needs the local Supabase stack); please run `npm run test:integration` in step 12.
4. Plan test for step 9 said `lines_unmapped` etc. carry the §3.8 `{n}` sentences; the API message is count-free (see above).
