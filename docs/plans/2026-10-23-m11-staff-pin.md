## 1. Goal and scope

- **Goal:** chefs and waiters log in on an enrolled venue device by tapping their name and typing a 4-digit PIN. The session carries their role and tenant, and ends at the business-day cut-off. Brute force is bounded by device enrolment, a server-only pepper and lockouts. The owner creates staff, sets and resets PINs, and enrols, revokes and unlocks devices from the phone. No app table holds a PIN or anything derived from it.
- **In scope:**
  - **T1 spike** (step 0, local stack) and its recorded result (§5.0).
  - **Schema:**
    - `app_user.login_method`;
    - `venue_device`, `device_enrolment`, `auth_attempt`, `staff_session`, `app.enrol_failure`;
    - the audit list widening;
    - the business-day cut-off helper.
  - **Definer RPCs:**
    - enrolment (create code, redeem);
    - PIN login begin/finish with lockouts;
    - device overview, revoke and unlock;
    - staff list, create, update and PIN change (prepare, record);
    - staff session check and logout;
    - the daily purge.
  - **Access token hook** extended for `pin` accounts (email accounts unchanged).
  - **Alert kind `device_locked`** (owner, in-app), raised inside `pin_login_finish` through `app.try_raise_alert`.
  - **pg_cron job `auth-purge`** (daily retention purge, `app.job_run` record).
  - **TS:**

## 3. Design

### 3.1 Decisions

1. **Where the PIN is verified (AT5).**
   - A PIN account is a Supabase auth user:
     - email: `staff-<app_user.id>@<STAFF_EMAIL_DOMAIN>` (default `staff.invalid`, an RFC 2606 reserved TLD that can never receive mail; T1 checks Supabase accepts it, else V3);
     - created with `email_confirm: true`, so Auth sends nothing;
     - password: `derivePinPassword(pepper, appUserId, pin) = base64url(HMAC-SHA256(PIN_PEPPER, appUserId + ":" + pin))`, 43 characters (under bcrypt's 72-byte limit; over `minimum_password_length`).
   - The `app_user.id` is generated in TS before the auth user exists, so the derivation never needs the auth id.
   - **The PIN and the derived value exist only in the memory of one request.** They are never sent to Postgres, never stored in an app table, never logged, and never put into a Sentry event.
2. **`login_method` separates PIN accounts from email accounts.**
   - New enum `public.login_method ('email', 'pin')` and column `app_user.login_method not null default 'email'`, with check `login_method = 'email' or role in ('chef', 'waiter')`.
   - Existing rows, the owner, admins and every test fixture stay `email` and behave **exactly** as today (`003` and every chef/waiter fixture stay green).
   - Only `public.create_staff` makes `pin` rows. The M0 INSERT grant does not include the column, so a direct insert can only create `email` rows.
3. **Device enrolment (AT4).**
   - **Code creation:** owner/admin `POST /api/devices/enrolment-codes {label}`. TS generates an 8-character code from the Crockford base32 alphabet (`0123456789ABCDEFGHJKMNPQRSTVWXYZ`, 40 bits, crypto random) and sends `HMAC-SHA256(PIN_PEPPER, "code:" + code)` as hex (a plain SHA-256 of 40 bits could be brute-forced from a leaked table) to `create_enrolment_code`, which stores it with `expires_at = now() + 15 min`. The plain code is returned once (`no-store`) and shown as `K7M2-QX9P`.
   - **Redemption:** public `POST /api/devices/enrol {code}`:
     - TS normalises the code (uppercase, drop spaces and `-`, `I/L → 1`, `O → 0`), hashes it, generates a 32-byte device token and hashes the client IP (`HMAC-SHA256(PIN_PEPPER, "ip:" + ip)`);
     - the privileged RPC `redeem_enrolment_code` checks:
       - the IP limit: 10 failed redemptions per IP hash in 15 min → 429 `enrol_rate_limited`;
       - the code: unknown → 404 `enrolment_code_invalid`; used → **410** `enrolment_code_used`; expired → **410** `enrolment_code_expired`;
     - each failure inserts an `app.enrol_failure` row;
     - on success it creates the `venue_device` row and marks the code used, in one transaction;
     - the route sets the cookie.
   - **Cookie:** `__Host-odr_device=<token base64url>; HttpOnly; Secure; SameSite=Strict; Path=/; Max-Age=34560000` (400 days, the browser cap). Only `sha256(token)` is stored, in `venue_device.token_hash`.
   - **Who enrolled it:** the device row's `created_by` = the code's creator, recorded in `audit_event venue_device.enrolled`.
4. **PIN login, two phases around Supabase Auth (AT1, AT2, AT3).** `POST /api/auth/pin {userId, pin}`:
   1. **No device cookie → 401 `device_missing`.** Nothing is called: no RPC, no Auth.
   2. `pin_login_begin(token_hash, user_id)` (privileged, one transaction) locks the device row, then a per-user advisory lock, and returns:
      - `device_unknown` / `device_revoked` → **401, no Auth call**;
      - `device_locked` → 423;
      - `attempt_in_progress` (a pending attempt under 30 s on this device or for this user) → 429;
      - a user that is not an active `pin` chef/waiter of the device's tenant → a recorded failure, answered like a wrong PIN (401 `pin_invalid`, no Auth call);
      - `user_locked` with `lockedUntil` → **423, no Auth call**;
      - else it inserts a `pending` `auth_attempt` and returns `{attemptId, authEmail}` (the email read from `auth.users`).
   3. TS derives the password and calls `signInWithPassword` on the cookie-bound server client (publishable key), with a 10 s timeout.
   4. `pin_login_finish(attempt_id, outcome, auth_session_id)` (privileged; same lock order):
      - outcome `success` (session id from the new access token's `session_id` claim) → opens a `staff_session` ending at the next cut-off and updates `venue_device.last_login_at` → 200 `{user, endsAt}`;
      - `failure` (Auth `invalid_credentials`) → applies the lockouts → 401 `pin_invalid {attemptsLeft}`, or 423 `user_locked {lockedUntil}` / `device_locked`;
      - `error` (Auth 429 → 429 `auth_rate_limited`; 5xx or timeout → 502 `upstream_error`) → not counted.
      - On a `finish` failure after a successful sign-in, the route signs out locally and answers 502.
5. **Lockout rules (AT3; thresholds in SQL only).**
   - **User:**
     - `app.user_lock_until(user, at)` reads the user's 5 most recent *verified* attempts (`success`, `failure`, `pin_reset`, and `pending` older than 30 s, which counts as a failure) on any device;
     - if all 5 are failures, the user is locked until the newest one's `started_at + 15 min`;
     - the 5th wrong PIN already answers 423, and the 6th attempt, even correct, gets 423 without reaching Auth;
     - after 15 minutes a correct PIN works; one more wrong PIN locks again for 15 minutes (Q7 → V7);
     - `attemptsLeft` = 5 − the current run of failures;
     - an owner PIN reset inserts a `pin_reset` row, which ends the run.
   - **Device:**
     - the 20th failure on a device within 60 minutes (counting only attempts after `venue_device.unlocked_at`) sets `locked_at` and ends the device's open sessions (`device_locked`);
     - it raises **one** `device_locked` alert through `app.try_raise_alert` (`entity_type 'venue_device'`, the device id, audience `{owner}`, caller `pin_login_finish`) in the same transaction;
     - a locked device stays locked until the owner unlocks it (Q6 → V6);
     - the alert deduplicates per device per business date (M6).
   - **Concurrency:** begin and finish lock the device row (`for no key update`), then `pg_advisory_xact_lock(hashtext('pin_user'), hashtext(user_id::text))`, always in that order. At most one attempt per user and per device is in flight, so parallel requests cannot pass more guesses than the limits allow (race `pin-same-user`).
6. **Hook gate: a `pin` user gets tenant claims only through our flow.** `app.custom_access_token_hook` keeps the M0 branch for `email` users byte for byte. For an active `pin` user:
   - if `authentication_method = 'password'` and a `pending` attempt for this `app_user` was started under 30 s ago on a device that is neither revoked nor locked, it adds `tenant_id`, `app_role`, `login: 'pin'`;
   - if `authentication_method = 'token_refresh'` and `app.staff_session_open(claims.session_id, app_user.id, now())`, it adds the same claims;
   - **otherwise** it adds no tenant claims and adds `session_state: 'ended'`.
   - The PIN branch sits in an exception block that strips the claims on any error, so a bug there can never block owner logins.
   - Consequence: a password sign-in that bypasses `/api/auth/pin` (for example with a leaked pepper) yields a token with no tenant, so RLS returns nothing.
7. **Session end (AT7) and immediate revocation.**
   - **`ends_at`:** `staff_session.ends_at = app.next_cutoff(started_at, tenant.timezone, app.business_day_cutoff(tenant))`. The cut-off is `tenant.settings.business_day_cutoff` (`HH:MM`; missing or malformed → `02:00`, project Q18, Q3 here).
   - **DST rule:** the session ends at the **first instant at which the venue clock reads the cut-off or later**:
     - an ambiguous 02:00 (2026-10-25) → the first occurrence, `00:00Z`;
     - a missing 02:00 (2027-03-28) → the jump, `01:00Z`.
   - **`withApi` gate:** for claims with `login = 'pin'`, `withApi` calls `public.staff_session_active()` on every request; `false` → **401 `session_ended`** and a local sign-out. Claims with `session_state = 'ended'` → 401 `session_ended` before the tenant check.
   - **`staff_session_active()`** is true only while the session is not ended, `now() < ends_at`, the device is neither revoked nor locked, and the user is active.
   - Revocation, device lock, PIN reset and deactivation set `ended_at`/`end_reason` on the open sessions, so the next API call fails.
   - **Direct Data API calls** are cut at the next refresh by the hook (≤ `jwt_expiry` 3600 s; risk §6).
   - **Logout** (`POST /api/auth/logout`) ends the staff session first.
8. **Staff management (owner and admin, Q5).**
   - **Create:** `POST /api/users {displayName, role: 'chef'|'waiter', pin}`:
     1. PIN policy (422 `pin_trivial`);
     2. `assert_staff_manager()` (owner session);
     3. privileged `createStaffAuthUser(newId, derived)`;
     4. `create_staff(newId, authId, displayName, role)` (owner session; role check, tenant, audit);
     5. if step 4 fails, privileged `deleteOrphanStaffAuthUser(authId)`, which deletes only an auth user whose email starts `staff-` and has no `app_user`.
   - **Update:** `PATCH /api/users/:id {displayName?, role?, active?}` → `update_staff`. Deactivation ends sessions. A role change applies at once because `app.role()` is live.
   - **PIN set/reset (AT6):** `POST /api/users/:id/pin {pin}`:
     1. policy check;
     2. `prepare_pin_change(id)` (owner session; returns the auth id of an active `pin` chef/waiter of the tenant);
     3. `record_pin_change(id)` (owner session: a `pin_reset` attempt row, ends the user's sessions, `audit_event app_user.pin_set`); it runs before Auth so a PIN never changes without an audit row;
     4. privileged `setStaffAuthPassword(authId, derived)`; if it fails the route answers 502 and the owner retries (changed after review: the order was Auth first).
     After a reset the old PIN fails, because Supabase now holds only the new hash.
   - **Trivial PINs** (`src/server/staff-auth/pin-policy.ts`, Q4) → 422 `pin_trivial`:
     - all digits equal (`0000`…`9999`);
     - ascending runs (`0123`…`6789`);
     - descending runs (`9876`…`3210`);
     - `ABAB` repeats (`1212`, `9090`).
     A PIN that is not exactly 4 ASCII digits → 400 (strict Zod).
9. **Devices (owner and admin).** `GET /api/devices` → `device_overview()` returns devices (label, status `attivo|bloccato|revocato`, enrolled, last login, locked since) and unused unexpired codes (label, expiry; never the code). `DELETE /api/devices/:id` → `revoke_device` (a state change, idempotent; ends sessions; audit). `POST /api/devices/:id/unlock` → `unlock_device` (sets `unlocked_at`, clears `locked_at`; audit; a revoked device → 409).
10. **Retention purge (Q2 = project Q14) — retention, not ledger editing.**
    - **Why deletion is allowed:** `auth_attempt`, `staff_session`, `device_enrolment` and `app.enrol_failure` are not ledgers (project §3.6 rule 2 lists the ledgers; none of these feeds a balance or a business record). They are security logs of personal data, kept only as long as lockouts and support need them (GDPR storage limitation).
    - **What it deletes:** `app.purge_auth_data(p_at)`, run daily by pg_cron job `auth-purge` at `30 3 * * *` UTC:
      - `auth_attempt` rows not `pending` with `started_at < p_at − 30 days`;
      - `staff_session` rows with `coalesce(ended_at, ends_at) < p_at − 30 days`;
      - unused enrolment codes expired more than 30 days ago;
      - `app.enrol_failure` older than 1 day.
    - **How it is constrained:**
      - The run is recorded with `app.job_run('auth-purge', items)`.
      - **No API role can delete these rows**: no DELETE or TRUNCATE grant (pgTAP `001`), and a guard trigger refuses every DELETE unless the transaction-local setting `app.auth_purge = 'on'` is set, which only `app.purge_auth_data` sets, and only for rows past retention.
      - `audit_event` rows about staff and devices are **not** purged (they follow the audit trail's retention, project Q14).
11. **Device lockout alert (M6 kind table).**
    - Registry row: `('device_locked', false, 'warning', '{owner}')`. Not cost-bearing, but owner only by audience; the chef never sees it, and admin and waiter read no alerts (M6).
    - Payload `{device_id, device_label, failures_count, window_minutes, locked_at}`. No staff name (M6 rule).
    - The device label is owner-typed text capped at 60 characters, and the label field hints "Non usare nomi di persone".
    - Raised only inside `pin_login_finish`. **No hourly rule is added**, so `app.alert_rules_body` (M9) and `app.run_alert_rules` are not touched (`089` pins both).
12. **What the owner sees about people (Q10).** The staff list shows name, role, active, and "Bloccato fino alle 21:15" while locked. **No per-person login times.** Devices show their own last login.
13. **Logs (AT5).**
    - Routes log status codes and ids only.
    - `withApi` already reports unexpected errors without bodies.
    - `scrubEvent` additionally replaces the value of any key matching `/pin|password|token|code|pepper/i` in `extra`, `contexts` and breadcrumbs with `[redacted]`.
    - Auth errors are reduced to `{status, code}` before any log.
    - The privileged module never logs its arguments.

### 3.6 Flows

1. **Enrol:** owner `/dispositivi` → "Crea codice" → `POST /api/devices/enrolment-codes` → code shown → staff phone `/dispositivo` → `POST /api/devices/enrol` → `redeem_enrolment_code` (privileged) → cookie → `/pin`.
2. **Login:** `/pin` → `GET /api/auth/device` (privileged `device_staff_list`) → name → PIN → `POST /api/auth/pin` → `pin_login_begin` (privileged) → `signInWithPassword` (publishable key; the hook adds claims because a pending attempt exists) → `pin_login_finish` (privileged) → 200 → `/`.
3. **Request during service:** any `/api/*` → `withApi` → claims `login: 'pin'` → `staff_session_active()` → true → handler.
4. **Cut-off:** after `ends_at`, the next request → `staff_session_active()` false → 401 `session_ended` → sign-out → `/pin`. The next refresh → hook → `session_state: 'ended'`.
5. **Lockout:** 5th wrong PIN → 423 `user_locked`. 20th failure on a device in an hour → `locked_at`, sessions ended, `device_locked` alert → owner `/avvisi` → `/dispositivi` → "Sblocca" or "Revoca".
6. **Staff:** owner `/personale` → `POST /api/users` (`assert_staff_manager` → admin `createUser` → `create_staff`) → `POST /api/users/:id/pin` (`prepare_pin_change` → `record_pin_change` → admin `updateUserById`).
7. **Purge:** pg_cron 03:30 UTC → `app.purge_auth_data()` → `app.job_run`.

## 4. Alternatives considered

- **Custom JWTs signed by the app; `generateLink` + `verifyOtp`:** rejected in project plan §4; nothing has changed.
- **PIN hash in an app table:** rejected; it violates AT5.
- **Writing `auth.users` from Postgres to avoid the secret key:** rejected. Supabase manages that schema; the identities rows and the column layout are internal; the derived password would cross into Postgres.
- **A queue: owner writes a pending request, a cron job creates users with the secret key:** rejected. The pending row would have to hold the derived password (violates AT5), and PIN set would be asynchronous.
- **A Supabase Edge Function holding the secret key:** rejected. It moves the same exception to a second deployable and adds a runtime the project does not use.
- **Pre-login RPCs callable by `anon` as the default (D1-B):** kept as variant V1. The default keeps zero new anon surface and one choke point. B needs the finish step split so anon cannot forge a success.
- **A lock state table instead of deriving locks from `auth_attempt`:** rejected. Derivation keeps one source of truth, and the purge cannot leave a stale lock behind.
- **Counting failures without an in-flight limit:** rejected. Parallel requests would pass more guesses than the limit before the count updates.
- **Session end inside `app.tenant_id()`:** rejected (ADR-010). It would change every policy's helper and break every existing chef/waiter fixture.
- **Ending staff sessions with Supabase's global `timebox`:** rejected; it is one value for every user (owners need 30 days).
- **Device lock lifting itself after an hour:** variant V6. The default keeps a human in the loop after a brute-force signal.
- **An hourly alert rule for lockouts:** rejected. The lock happens inside `pin_login_finish`, so raising there is immediate and leaves M9's `alert_rules_body` untouched.

## 6. Risks and mitigations

- **Security / privacy**
  - *D1 widens secret-key use:*
    - mitigations: one module with seven fixed functions and no client export; input validated before any call; ESLint allow-list plus a lint test; an RLS-checked owner RPC before every Auth admin call and an `audit_event` after it; pre-login RPCs that validate everything themselves (steps 3, 5, 12, 15);
    - residual: a code-execution bug in a public route's process could reach the key (as for cron routes today). Founder/lead decision (Q1).
  - *PIN brute force:*
    - 10 000 PINs, but every guess needs an enrolled device (256-bit token), and Auth cannot be tried directly without the pepper;
    - limits: 5 per user and 20 per device per hour, one in-flight attempt per user and per device (race `pin-same-user`);
    - the hook refuses tokens from sign-ins that did not pass `pin_login_begin` (steps 5, 6, 10, 16).
  - *Enrolment code guessing:* 40-bit single-use codes, 15 minutes, 10 failures per IP per 15 minutes.
    - The IP comes from `x-forwarded-for`. **Whether Vercel overwrites a client-sent `x-forwarded-for` is not verified here (T4):** a spoofed header would only spread an attacker's failures across buckets, still bounded by the code space and the 15-minute life.
    - Checked during manual step M-1.
  - *Supabase sign-in rate limit shared by all staff* (server-originated sign-ins share Vercel's egress IPs as Supabase sees them; not documented): our checks run before Auth, so wrong PINs beyond the lockouts never reach it. T1 measures 30 sequential sign-ins locally, and on staging with your OK; the remedy is the dashboard setting (M-2).
  - *A stolen access token after revocation or the cut-off:* `withApi` refuses at once; a direct Data API call works until the token expires (≤ 3600 s) because the hook only acts at refresh. The cookie is HttpOnly, so the token is hard to extract. Accepted (ADR-010).
  - *Hook bugs locking everyone out:* the PIN branch is wrapped so errors strip claims instead of failing; email users take the unchanged M0 path; `003` and `085` include a fail-safe case (step 6).
  - *Lockout as denial of service:* a co-worker can lock a colleague for 15 minutes or a device until the owner unlocks it. The owner can unlock or reset in a few taps, and the alert says why. Q6 and Q7 ask whether you prefer otherwise.
  - *Personal data:*
    - stored: names, role, device labels (hint against personal names), the attempt log, login sessions (30 days), and IP hashes (pseudonymised, 1 day);
    - no email, phone or PIN; no per-person login history shown (Q10);
    - Sentry key scrub and log tests (steps 13, 14);
    - lawful basis and register entry: client (project Q13).
  - *iOS home-screen apps have their own cookie storage:* a device enrolled in Safari is not enrolled in the installed app. The `/dispositivo` note covers it, and the runbook (M25) should repeat it (Q12).
  - *`PIN_PEPPER` leak or rotation:* a leak lets an attacker try PINs directly against Supabase Auth for known synthetic emails. Mitigations: per-environment values, server-only, rotation by resetting every PIN (runbook M25), and the hook refusing tenant claims without a pending attempt, so even a guessed PIN yields no data.
- **Correctness**
  - *DST at the cut-off:* explicit vectors for both 2026-10-25 and 2027-03-28 (step 2). Postgres's own resolution of ambiguous or missing local times is not relied on: `app.local_instant` checks the offsets itself, and the vectors prove it (T2).
  - *Fixtures using email chef/waiter:* unchanged by design (`login_method` default), proved by step 16's "email users unaffected" case and every existing suite staying green.
  - *Kind list tests:* `044` and `072` assert exact lists; step 4 updates them deliberately in the same commit as the registry row.
  - *Device lock alert dedup:* one alert per device per business date (M6 dedup), so a second lock on the same day after an unlock raises no new alert. The device screen still shows "Bloccato".
  - *Merge with later milestones:* M10 will also widen `app.job_run`'s job list (`drive-poll`), and M17+ will widen `audit_event`. Whichever merges second keeps both values (the pattern in `20261024100000`).
- **Unverified (checked in the named step):**
  - **T1** (a)–(e) of §5.0: step 0 (local); staging via M-1.
  - **T2** Postgres `timestamp at time zone` behaviour for ambiguous and nonexistent Rome times: step 2 (the vectors fix the required output whatever Postgres does by default).
  - **T3** the hook's `authentication_method` values (`password`, `token_refresh`) and `session_id` in `claims` as documented: step 16 (real GoTrue: AT1 and AT7 refresh cases).
  - **T4** `x-forwarded-for` handling on Vercel: M-1.
- **Performance / cost:** each PIN login is two small RPCs plus one Auth call, and each staff API request adds one small indexed RPC. No figure is promised. No new provider and no running cost.
- **Dependencies:** none added (`node:crypto` for HMAC, SHA-256 and random bytes).
