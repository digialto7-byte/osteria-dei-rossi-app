## 1. Goal and scope

- **Goal:** the chef's recipes live in the app as immutable versions under a stable key, with sub-recipes, batch and plate types and yields; an edit never changes history; a cycle of sub-recipes is refused; the admin can import a template file idempotently with a preview; and allergens are inherited from ingredients with an explicit "da confermare" state, so a blank is never read as allergen-free.
- **In scope:**
  - Ingredient allergen state: `ingredient.allergens` becomes nullable (null = not stated), plus `allergens_confirmed_at` / `allergens_confirmed_by`; migration of existing rows; the M1 import and PATCH follow the new rule; `POST /api/ingredients/:id/allergens/confirm` (owner, admin).
  - Tables `recipe_key` (stable identity), `recipe` (one immutable row per version), `recipe_line` (immutable with its version), `recipe_price` (sale price and target GP%, owner/admin only); view `v_recipe_current`.
  - Types `batch`, `plate`, `sub`; fields output quantity and unit, portions per batch, shelf life, prep time, min and target portions, sale price, target GP%.
  - Definer procedures `create_recipe`, `create_recipe_version`, `set_recipe_active`, `import_recipes` (with dry run), `export_recipes`, and the read function `recipe_allergen_summary`.
  - Cycle detection (recursive CTE) inside every version-creating procedure, made race-safe by one per-tenant lock.
  - Yield factor rules: > 0 (else 422), above 1 allowed with a warning, at most `MAX_YIELD_FACTOR` (Q5).
  - API: `/api/recipes`, `/api/recipes/:key`, `/api/recipes/:key/versions[/:version]`, `/api/admin/import/recipes`, `/api/admin/export/recipes`, ingredient allergen confirm.

  - A design note (not built) settling the alert money-guard limit before chef-audience alert rules (§8).

  - All costing (M8): no cost view, no `recipe_cost_at`, no margin, no price variance.

## 3. Design

### 3.1 Decisions

1. **Identity and versions are separate tables (ADR-007).**
   - `recipe_key` is the stable identity of a recipe: its id is the `recipe_key` the plan names (menu items in M17 and sub-recipe lines point at it). It holds the fixed `type`, `is_active`, and two values maintained only by the procedures: `current_version` and `name_norm` (the normalised name of the current version, for the unique index and import matching).
   - `recipe` is one row per version: `version` 1, 2, 3…, `valid_from`, name and every content field. `recipe_line` rows belong to one version. Both are **append-only for every role** (`app.append_only()`), so "UPDATE on a version row raises" holds for the migration owner too (AT1).
   - An edit is always a new full version (n+1). There is no PATCH of content.
   - `valid_from = greatest(clock_timestamp(), previous valid_from + 1 µs)`: never client-set, strictly increasing per key, distinct even inside one transaction (pgTAP `049`).
2. **Lines reference ingredients by id and recipes by key, never by version.** A plate keeps pointing at "the stew", and the version in force is resolved by the reader: the current version for screens and allergens, the version in force on a date for M8's `recipe_cost_at`, and the version frozen in `batch.recipe_version` for M14.
3. **Line semantics (outlive M7, ADR-007):**
   - `qty` is the **net, usable** quantity the recipe needs, in the line's unit. The raw quantity taken from stock is `qty ÷ yield_factor` (M14). This matches PRD 1.4: cost = qty × unit cost ÷ yield. With `yield_factor` 1 (the default) the stew fixture's 5.0 kg of beef is also the raw quantity, as M14 AT2 and M16 AT1 assume.
   - `yield_factor` must be > 0 (AT3: 0 or negative → 422 `recipe_invalid`, detail `yield_factor_not_positive`) and ≤ `MAX_YIELD_FACTOR` = 10 (a typo guard: 82 instead of 0.82; Q5). Above 1 is allowed and returns the warning `yield_above_one` (cooking gain, e.g. rice or polenta absorbing water).
   - Unit per target:
     - ingredient line: `kg, g, l, ml, pz`, same dimension as the ingredient's base unit (g on a kg ingredient is fine; pz on kg → `incompatible_units`);
     - `sub` line: a measure unit with the dimension of the sub-recipe's current `output_unit`;
     - `batch` line: unit `porz` (portions; 0.5 allowed), and only inside a `plate` recipe.
   - Which type may use which (else `line_target_not_allowed`): `batch` lines hold ingredients and subs; `sub` lines hold ingredients and subs; `plate` lines hold ingredients, subs and batches (portions). **No line may point at a plate.** So a cycle can only form through subs (and a self-reference), but the check is general. A batch inside a batch is not allowed (M14 consumes raw lots only; Q4 → V4).
4. **Fields per type** (checked in the procedure; DB checks and a trigger as backstop):

   | Field | batch | sub | plate |
   |---|---|---|---|
   | `output_qty` > 0, `output_unit` (`kg, l, pz`) | required | required | must be null |
   | `portions_per_batch` integer 1–10 000 | required | null | null |
   | `shelf_life_hours` 1–8 760 | required (M14 use-by) | null | null |
   | `prep_time_min` 0–1 440 | optional | optional | null |
   | `min_portions`, `target_portions` 0–10 000, target ≥ min | optional (M16 reads them) | null | null |
   | `sale_price`, `target_gp_pct` (in `recipe_price`) | not allowed (`price_not_for_type`) | not allowed | optional |

   Portion size is derived (`output_qty ÷ portions_per_batch` in `output_unit`), so the PRD's `portion_unit` is not stored (plan change, §6).
5. **Sale price and target GP% live in `recipe_price`, readable by owner and admin only** (ADR-003 split-table pattern, as `batch_cost`). Every column is visible through PostgREST once a role can select a row, so RLS on `recipe` cannot hide two of its columns from the chef; a separate table can.
   - One `recipe_price` row per plate version, immutable like the version. A price change is a new version (plan §3.6 rule 4: the sale price is part of the version).
   - **Chef (founder 2026-10-22, AT5):** the chef creates versions, but a content body from the chef that contains `sale_price` or `target_gp_pct` at all, even unchanged, is refused with 42501 `recipe_price_forbidden` (→ 403). The chef's new version copies the base version's price row.
   - **Chef read (Q16 = V6, founder 2026-10-23):** the chef reads `sale_price` and `target_gp_pct` (the `recipe_price` read policy includes the chef; writes stay owner/admin only). No recipe table, view or RPC returns a € cost or € margin to the chef. Note: with V6 the chef can derive a € figure (price × food cost %); the founder accepted percentages plus the public menu price.
   - Owner or admin: price keys absent → copied from the base version; present (number or null) → set.
   - `sale_price` is stored as on the menu, **VAT included** (column comment; Q3 → V3). M8 derives the ex-VAT figure.
6. **Allergen state on ingredients: nullable list plus a confirmation, chosen over either alone (ADR-007).**
   - `allergens public.allergen[]` **nullable, no default**: null = "not stated". `'{}'` means only "declared: none".
   - `allergens_confirmed_at timestamptz`, `allergens_confirmed_by uuid` (composite FK to `app_user (tenant_id, id)`): set together, only by `confirm_ingredient_allergens` (owner only; Q6 = owner only, founder 2026-10-23; built as a follow-up migration after step 7, and a guard refuses a `_by` that is not an owner of the tenant). A check forbids a confirmation without a list.
   - Derived `allergen_status` (stored generated column): `confirmed` (confirmed_at set), `unknown` (list null), `declared` (list set, not confirmed). Screens show "da confermare" for `unknown` and `declared`.
   - Why both:
     - **A nullable list alone** would make the column honest, but then an import or a PATCH that writes a list would also be the confirmation: a CSV typo would become a food-safety statement with no name or time. It also could not hold the chef's declared list while waiting for the owner.
     - **A flag alone** would keep `'{}'` meaning "nothing stated" in the column. Every later reader (menu M17, labels M28, HACCP M31) would have to remember the flag, and one that forgets reads allergen-free, which is the failure the lead asked us to remove. With null, a careless `not ('glutine' = any(allergens))` evaluates to null and filters the row out, the safe direction.
   - **Editing clears the confirmation.** Trigger `app.ingredient_allergen_guard()` (before update): if `allergens` changes and `allergens_confirmed_at` does not, both confirmation columns are set to null. Only the definer can change `allergens_confirmed_at` (no column grant), and it always writes `clock_timestamp()`, so a confirmation is never cleared by its own statement.
   - **Import:** a blank cell is "not stated". For a **new** ingredient that stores null (unknown). For an **existing** ingredient a blank keeps the stored list and its state (founder decision M1 Q5: a blank keeps the stored value). The clear mark `-` and JSON `null` now clear to **unknown** (M1 cleared to `'{}'`, i.e. allergen-free; that is exactly the bug). A new word `nessuno` (CSV) or `[]` (JSON) declares "none", unconfirmed. **An import never confirms** (Q2 → V7).
   - **Existing rows:** confirmation did not exist before M7, so no row is confirmed. Every `'{}'` row becomes null (unknown); a non-empty list stays as `declared`. The conversion is `app.allergens_blank_to_unknown()`, called once by the migration (it reports the count with `raise notice`) and tested on fixture rows in `047`.
7. **Recipe allergens are derived, never stored.** `public.recipe_allergen_summary(p_keys uuid[])` (SECURITY INVOKER, so the caller's RLS applies) walks each key's current version, recursively through sub-recipe and batch lines (their current versions), to the ingredients:
   - `allergens` = the union of the declared lists;
   - `confirmed` = true only if **every** reached ingredient is `confirmed`; one `unknown` or `declared` ingredient anywhere below makes the recipe "da confermare";
   - `unconfirmed_ingredient_ids` = those ingredients, for the screen's "Da confermare: …" list.
   Allergens are a present-tense safety statement, so historical versions also report through the current versions and current ingredient states (stated on the screen and in ADR-007; A3).
8. **One lock order for every recipe writer (race-safe cycle check).**
   1. `app.lock_recipe_graph(tenant)` = `pg_advisory_xact_lock(class, obj)`: one lock per tenant for the recipe graph;
   2. the `recipe_key` row(s) `FOR NO KEY UPDATE`, ordered by id (`current_version`/`name_norm` are non-key columns; the line FKs take KEY SHARE, which this does not conflict with);
   3. inserts.

   `create_recipe`, `create_recipe_version`, `set_recipe_active` and `import_recipes` all take lock 1 first. Under READ COMMITTED each later statement takes a new snapshot, so once a writer holds the tenant lock it sees every version committed before it. Two concurrent versions creating A→B and B→A therefore cannot both pass the check: the second waits for the first, then finds the cycle and fails with `recipe_cycle` (race case `cycle-crossed`). Serialising recipe writes per tenant costs nothing at this volume (a few edits a day).
   - Locking only the rows of the reachable keys was rejected (§4): the reachable set can change while a writer waits.
   - The two-integer advisory form is used (class = `hashtext('recipe_graph')`, object = `hashtext(tenant_id::text)`). A collision with another lock key only adds a wait, never a wrong result.
9. **Two editors at once: optimistic version check.** `create_recipe_version(p_key, p_base_version, …)` raises `version_conflict` (→ 409, detail: the current version) when `p_base_version <> recipe_key.current_version`. The second of two editors who both started from v1 waits on the locks, then gets the conflict instead of silently overwriting the first edit with stale content (race case `version-twice`). `unique (tenant_id, recipe_key, version)` is the backstop. A body identical to the base version → 422 `recipe_unchanged` (no junk versions from a double submit).
10. **Cycle detection in SQL.** After the new version and its lines are inserted (phase 2 of §3.4), `app.assert_recipe_acyclic(p_tenant, p_keys uuid[])` runs a recursive CTE over the current versions' recipe lines, starting from the changed keys, carrying the path as an array; if a changed key is reached again → P0001 `recipe_cycle` (→ 422) with the path's key ids in the detail. The whole transaction rolls back. A depth limit (`MAX_RECIPE_DEPTH` = 12) raises `recipe_too_deep` as a guard against pathological data; the path array already stops infinite recursion.
11. **Import = the same procedures' code path, preview = the same path rolled back.**
    - `import_recipes(p_rows jsonb, p_dry_run boolean)` takes the tenant lock, then runs the apply step in a `begin … exception` block. In a dry run the apply step ends with a sentinel exception (`P0001 recipe_import_dry_run`), the block rolls back to its savepoint and the function returns the result built inside it. plpgsql variables are not transactional, so the preview is exactly what the import would have done, including cycle and unit checks (technical check T1, proved in `052`).
    - Matching (idempotency): by normalised name against `recipe_key.name_norm`. Not found → new key + v1. Found → the file's recipe is compared with the current version's canonical content (`app.recipe_version_content`): equal → `unchanged`; different → a new version (base = current). Re-importing the same file creates nothing.
    - A name that matches a recipe of another type → `recipe_type_conflict`; an inactive recipe → `recipe_inactive` (reactivate first).
    - References: ingredients by normalised name (must exist and be active: `unknown_ingredient`, `ingredient_inactive`; no auto-create, ingredients come from the M1 import first); recipes by name, in the file or already stored (`unknown_sub_recipe`). The order inside the file does not matter: keys are created first, then versions, then the checks run once over the whole graph.
    - Price columns: present → set (owner/admin only, which the import route requires); blank → kept from the base version (M1 Q5 rule); `-` → cleared.
    - One call is one transaction: any error rolls everything back. `MAX_IMPORT_ROWS` 1 000 lines (as M1).
    - Export: `public.export_recipes()` returns every active recipe's current version in the template's JSON shape (§3.6), built from the same canonical function, so import → export → import is stable by construction (AT4).
12. **Validation happens twice, the database decides.** The TS service validates shapes and ranges first and returns 422 `recipe_invalid` with `details [{field, code}]` (as M1's `import_invalid`), so the screen can point at a field. The procedure re-checks everything and is the authority; DB check constraints are the last backstop. The strict Zod body accepts any finite number for `yieldFactor` and quantities, so an out-of-range value is a 422 domain error, not `withApi`'s 400 (AT3 asks for 422).
13. **Waiters see nothing of recipes in M7** (§3.11.2: "recipes and versions — waiter —"). No policy on any recipe table; every recipe route is 403 for waiters. Their only future view is M17's menu.
14. **Admin = DigiAlto support.** Admin has the owner's recipe rights (RW, import, prices) per §3.11.2 and PRD "recipe import". The import route keeps M1's `owner, admin` (the owner already has full recipe rights, so this grants nothing new; A4). The chef does not import (bulk versions and prices). Deactivating a recipe is owner/admin (the chef's RW in §3.11.2 is "new versions"; A2).
15. **Audit:** versions carry their own `created_by`/`valid_from` and never change, so they need no audit row. `audit_event` widens to `entity_type in ('invoice', 'ingredient', 'recipe')` with actions `ingredient.allergens_confirmed`, `recipe.deactivated`, `recipe.reactivated` (before/after lists or states).

  - key `allergens` absent: new row → `null`; existing → kept;
  - JSON `null` → `null` (unknown); an array (also `[]`) → that sorted set;
  - comparison with `is distinct from` on the sorted arrays (null-safe), so unknown → a list counts as `updated`;
  - the insert names `allergens` only when present, so the column has no default to fall back on.
- The guard trigger (step 1) clears a confirmation when an import changes a confirmed list.

### 3.4 Flows

1. **New recipe:** `/ricette/nuova` → `POST /api/recipes` → TS validation → `rpc('create_recipe')` → phase 1 key, phase 2 version and lines, phase 3 validate and cycle check → 201 `{recipe, warnings}` (re-read with the detail builder).
2. **New version:** `/ricette/[key]/nuova-versione` pre-filled from `GET /api/recipes/:key` → `POST /api/recipes/:key/versions {baseVersion, …}` → `create_recipe_version` → 201, or 409 `version_conflict` (the screen says someone else saved and offers a reload), or 422.
3. **Allergen confirm:** `/anagrafiche/ingredienti` → "Conferma allergeni" (checkboxes prefilled with the declared list) → `POST /api/ingredients/:id/allergens/confirm {allergens}` → `confirm_ingredient_allergens` → the row shows "Confermati il …" (date only; no staff name in M7); recipes that only waited for it report confirmed on the next read.
4. **Import:** `/anagrafiche/importa`, kind "Ricette" → `POST /api/admin/import/recipes {format, …, dryRun: true}` → preview list → "Importa" → the same body with `dryRun: false` → counts.
5. **Export:** `GET /api/admin/export/recipes` → the JSON template, downloadable from the import screen ("Scarica ricette (JSON)").

## 4. Alternatives considered

- **One `recipe` table with `recipe_key` as a plain column (no identity table):** rejected. Sub-recipe lines and M17's menu items could not have a foreign key to a non-unique column, the name uniqueness and the version lock would need ad-hoc advisory keys, and `type` could drift between versions.
- **Mutable recipe rows with an `audit_event` history:** rejected by the invariant (recipes are immutable versions) and by M8/M14, which must resolve "the version in force".
- **Lines pointing at a sub-recipe *version*:** rejected. Every sub-recipe edit would force new versions of every recipe above it; M8's "cost in force on the day" works by resolving keys at a date.
- **Price columns on `recipe` with a chef read through a definer function only (no chef SELECT on `recipe`):** rejected. It would push every chef read through functions and break the "views over tables with RLS" pattern; the split table is the ADR-003 pattern already used for `batch_cost`.
- **`allergens_confirmed` boolean flag only, or nullable list only:** rejected, §3.1.6.
- **Storing the recipe allergen union on the version:** rejected; ingredients are confirmed after recipes are written, so a stored union would be stale. Derived on read (§3.1.7).
- **Cycle check by locking the reachable keys' rows in id order:** rejected. The reachable set is only known after reading the graph, and it can change while the writer waits; one per-tenant advisory lock is simple and correct at this volume.
- **SERIALIZABLE isolation for version writes:** rejected. Supabase clients run READ COMMITTED; retries on serialization failures would need client logic; the explicit lock gives a deterministic wait.
- **Import auto-creating unknown ingredients:** rejected. Ingredients need a fixed base unit and an allergen state; silently creating them would hide typos and produce unknown allergens in bulk.
- **A separate preview implementation (TS diff of the file against the database):** rejected. Two implementations would drift; the savepoint dry run is the real import rolled back (T1).
- **CSV export:** not built. JSON export is enough for AT4 and avoids formula-escaping conflicts with the `-` mark; revisit if the chef wants to edit an exported spreadsheet.
- **Warning before saving (a validate endpoint):** rejected for M7; a yield above 1 is allowed, so showing the warning with the saved version (and as a badge on the line) is enough. A wrong value is fixed by the next version.

## 6. Risks and mitigations

- **Security / privacy**
  - *Definer procedures bypass RLS:* every public procedure checks the role first, uses an empty `search_path`, takes the tenant from `app.tenant_id()` and filters every query by it; `app.*` helpers are not executable by any API role (steps 1, 5, 7). Composite foreign keys stop a line from pointing at another tenant's ingredient or recipe (step 4).
  - *Price columns reaching the chef:* split table with owner/admin RLS, TS omission, a chef-visible-columns pgTAP check and a JSON string scan (steps 4, 10). Waiters reach no recipe table (no policy) and no route (steps 4, 10, 12).
  - *Import abuse:* owner/admin only, strict template, row caps and body size limit (M1 values), formula-leading cells refused, errors report row numbers and codes, never contents (steps 9, 11).
  - *Allergen safety:* null can never read as "none"; editing clears a confirmation; imports never confirm (base plan); recipes inherit "da confermare" through any depth (steps 1, 2, 6). Remaining risk: a person confirms a wrong list. The confirmation is recorded with user and time and audited, and the screen tells them to check supplier labels (step 14). Who may confirm is Q6.
  - *Personal data:* only staff ids (`created_by`, `allergens_confirmed_by`, audit rows), as already present elsewhere; no new category; no staff names are returned by M7's endpoints. Retention follows project Q14.
- **Correctness**
  - *Concurrent edits:* one lock order (tenant graph lock → key rows in id order → inserts) and the optimistic base version; four race cases (step 8). The confirm procedure uses FOR NO KEY UPDATE, so it never conflicts with the KEY SHARE a new recipe line takes on its ingredient.
  - *Version growth:* every price or par-level change is a version (plan rule 4). Rows are small; the list endpoint reads only current versions.
  - *Allergen summary cost:* a recursive read per request; bounded by 200 keys per call and the depth guard. No figure is promised.
  - *Changed M1 behaviour:* the `-` mark and JSON `null` now mean "unknown" for allergens, not "none". The existing tests are rewritten to the new rule in step 2 (a deliberate change of meaning, not a weakened test) and the import help text says it (step 14). Recorded below.
  - *Historical allergens follow current data:* a past version's allergen view uses current sub-recipe versions and ingredient states (§3.1.7, A3); the past-version page says so (step 13).
- **Unverified (checked in the named step):**
  - **T1** plpgsql variables keep values assigned inside a `begin … exception` block after the block's savepoint is rolled back, so the dry run returns the real preview: proved in `052` (step 7).
  - **T2** a stored generated column may reference `allergens` and `allergens_confirmed_at` after the type change in the same migration: proved in `047` (step 1).
- **Performance / cost:** no provider, no running cost; a handful of rows per recipe. No performance number is promised.
- **Dependencies:** none added.

## 8. Design note for M12/M16/M19: alert rule isolation (not built in M7)

**The problem today (M6, `20261022150400_alert_rules.sql`, `20261022150600_alert_rules_warning.sql`, ADR-006):**
1. `app.run_alert_rules` runs the whole `app.alert_rules_body` in **one** savepoint. One refused `raise_alert` (or any error) in any rule rolls back every alert of that hour, for **every tenant** and every rule, and the run is only recorded as `rule_failed`.
2. The key guard matches `_eur$` but not `eur`, `euro` or camelCase `valueEur`, so `{"eur": 12}` reaches a chef-audience payload.
3. The value guard (`€|(^|[^a-z])eur(os?)?([^a-z]|$)`) refuses harmless supplier text such as "Quartiere EUR" (a district name in an address) or "euro-pallet". With free supplier text in payloads, (1) turns that false positive into a lost hour of alerts for everyone.
4. Callers that raise alerts **inside a ledger transaction** (M8 `approve_invoice`, M12 consumption and waste, M19 `fire_course`) would have the whole ledger write rolled back by a refusal; for `fire_course` that breaks plan §3.6 rule 8 (firing never fails).

**Decision: a combination, with (a) as the control and (b) as containment.**
- **(a) No free text in chef-audience payloads, enforced by an allow-list.** When the final audience includes the chef, every payload key must end in `_id`, `_key`, `_qty`, `_count`, `_hours`, `_days`, `_date` or `_at`, or be exactly `unit`; every string value must be a token (uuid, ISO date or instant, a unit, or a code `^[a-z0-9_]{1,40}$`). Anything else → P0001 `alert_payload_not_allowed`. Names (ingredient, recipe, supplier, lot) are resolved at render time from the ids through the reader's own RLS (the chef can read those tables, §3.11.2), so they are never stored in a chef payload. Consequences:
  - money cannot reach the chef by any key word or any text, so (2) is closed without an ever-longer deny-list;
  - the value guard's false positives (3) cannot arise, because supplier text is never in a chef payload;
  - the money guards (deny-list keys, value guard) apply **only when the chef is in the audience**. An owner-only alert may carry text (the owner sees € anyway), so an M10 file name like "euro-pallet.pdf" is no longer refused. The deny-list stays as a second check for chef payloads and gains `eur`, `euro` and `…Eur`.
- **(b) Isolation per tenant × rule.** The hourly body loops over tenants and calls each rule (a static call per rule, no dynamic SQL) inside its own `begin … exception` block. A failure rolls back only that tenant's run of that rule, is written to `app.alert_rule_failure (run_id, rule, tenant_id, sqlstate, at)` (outside `public`, no payload, no message), and the run ends `ok = false`, `error_code 'rule_partial'`, `items` = the alerts that did commit. Ledger-transaction callers use `app.try_raise_alert(...)`, which wraps `raise_alert` in a nested block that catches only the alert guard codes, logs kind and code as a warning, and returns null, so a refused alert can never undo a receipt, a consumption or a firing.
- **Why not (a) alone:** a rule can still fail for reasons other than the guard (a bug, a division by zero), and one tenant's bad data must not silence another tenant's alerts. **Why not (b) alone:** it contains the damage but keeps refusing legitimate alerts and keeps the deny-list racing against new money words; the leak in (2) stays open.
