## 1. Goal and scope

- **Goal:** the raw layer works as an explainable ledger. The chef can:
  - see what is in each location, lot by lot with expiries;
  - record waste with a reason;
  - move stock between locations;
  - undo a mistake by reversing it.

  Every balance is a fold of the movements. Consumption follows FEFO. Waste is valued in € for the owner. A shortage is recorded and alerted, never blocked. M13, M14 and M19 reuse the same engine.
- **In scope:**
  - Movement types `consumption`, `waste`, `transfer` and `count`. `count` is defined here and posted by M13.
  - Shape checks per type, the eight waste reason codes, and a trigger that refuses any reversal row not mirroring its original.
  - The FEFO engine `app.post_stock_outflow`: override lot first, then expiry ascending with lots without expiry last, then an explicit unlotted shortfall row. It is used by:
    - `public.consume_raw_fefo()`;
    - `public.post_waste()`;
    - later, by M14 and M19.
  - `public.post_transfer()` and `public.reverse_movement()`, which reverses per operation.
  - One stock advisory lock per ingredient.
  - `v_stock_on_hand` kept as the canonical fold. Its AT2 property test is a Vitest suite against the real stack, plus a fixed pgTAP sequence.
  - The `negative_stock` alert kind (owner and chef, quantities only, one per ingredient per day), raised inside the procedures through `app.try_raise_alert` in a contained block.
  - The chef-payload allow-list in `app.raise_alert` (M7 §8 (a)), and alert-name resolution at render time.
  - Quantity-only read functions for owner, admin and chef: `stock_on_hand`, `stock_lots`, `stock_movements`. An owner/admin € function: `raw_waste_costs`.
  - API:
    - `GET /api/stock`, `GET /api/stock/lots`, `GET /api/stock/movements`, `GET /api/stock/waste-costs`;
    - `POST /api/stock/waste`, `POST /api/stock/transfers`, `POST /api/stock/movements/:id/reverse`.
  - Screens (Italian, phone first): `/magazzino`, `/magazzino/[ingredientId]`, `/magazzino/sprechi`, plus a "Magazzino" nav tab.
  - Race cases, the integration suite, and Playwright at 360 px.
- **Out of scope:**
  - Counts, the variance report and the nightly invariant check (M13). M12 only defines the `count` type and the lock contract.
  - Batch production and `batch_input` (M14). Batch actions, staff meals and the combined raw + batch waste report (M15).
  - Expiry, purchase and prep alerts (M16). Firing (M19).
  - A screen for bare manual consumption: kitchen deductions are waste with a reason (PRD 2.5). See Q6 → V6.
  - Reversing a receipt (an invoice correction, M5 Q8 → M5 V8).
  - Labels and decanting (M28).
  - Loosening the money guards for owner-only payloads (the other half of M7 §8 (a)). Not needed by M12, and recorded in §6 as a deferred plan change.

## 3. Design

### 3.1 Decisions

1. **Balances stay derived (plan §3.6 rule 1).**
   - `v_stock_on_hand` is kept exactly as M5 built it: by ingredient, location and lot (including the `raw_lot_id` null bucket), `security_invoker`, so owner and admin only.
   - Every M12 read is computed from `stock_movement` on each call. No table or column stores a quantity on hand.
   - **AT2** is proved two ways:
     - **(a) a Vitest property test against the real local stack** (step 15): random sequences of real procedure calls, then three checks: view = fold, view = independent model, no negative lot;
     - **(b) a fixed-sequence pgTAP file** (step 8) for the native DB job.

     Vitest was chosen for the property itself because the oracle (an independent FEFO model) is far simpler and more readable in TypeScript than in plpgsql. It runs the real procedures, RLS and view, and needs no new dependency: a hand-written seeded generator (mulberry32) with the seed printed on failure.
2. **Movement shapes (one migration of check constraints; comparisons on `type::text`, see T1).**

   | type | sign | `raw_lot_id` | `reason_code` | `ref_type` / `ref_id` | `unit_cost` |
   |---|---|---|---|---|---|
   | `receipt` (M5) | > 0 | required | null | `invoice_line` / line | required |
   | `consumption` | < 0, or > 0 only when `reverses_id` is set | lot or null (shortfall) | null | `manual` (M12), `batch` (M14), `order_line` (M19), … / not null | basis in force, or null if unknown |
   | `waste` | as consumption | lot or null | one of 8 codes, required | `manual` (M12), later others / not null | as consumption |
   | `transfer` | either (legs) | lot or null | null | `transfer` / operation id | null |
   | `count` (M13) | either | lot or null | null | `count_session` / session id | M13 decides |

   - **Reversal rows** have the same `type` as the original, `ref_type 'reversal'`, `ref_id` = the reversal operation id, and `reverses_id` = the original row.
   - Every non-receipt row needs `ref_type ~ '^[a-z_]{1,40}$'` and a non-null `ref_id`.
   - **Waste reason codes** (PRD 2.5): `spoilage`, `expired`, `over_production`, `plating_error`, `staff_meal`, `comp`, `breakage`, `count_correction`.
     - They are listed once in SQL (`app.stock_reason_codes()`, used by the check constraint) and once in TS (`src/server/stock/reasons.ts`). Both are pinned to the same literal list by `090` and `reasons.test.ts`.
   - **Reversal guard trigger** `app.stock_movement_reversal_guard` (`BEFORE INSERT`, only when `reverses_id` is set). The original must:
     - exist in the same tenant;
     - itself have `reverses_id is null`;
     - have the same ingredient, location, lot (`is not distinct from`), type, reason and `unit_cost` (`is not distinct from`);
     - have `qty = −original.qty`.

     Otherwise P0001 `reversal_mismatch`. This is defence in depth: a future procedure bug cannot write a reversal that does not mirror its original.
   - A new index `(tenant_id, ref_type, ref_id)` supports reading operations.
3. **Operations.**
   - Every call of a write procedure is one **operation**. Its rows share `(ref_type, ref_id)`, and `ref_id` is a fresh `gen_random_uuid()` for `manual`, `transfer` and `reversal`.
   - FEFO can split one waste into several rows (lots plus shortfall). A transfer is two rows per lot moved (out, in).
   - The history screen and the reversal treat an operation as one unit.
4. **FEFO engine (`app.post_stock_outflow`, AT1). Used by `consume_raw_fefo`, `post_waste`, M14 and M19.** Inputs:
   - tenant, user, ingredient, location;
   - `qty` in base units (> 0);
   - `type` (`consumption` | `waste`), reason;
   - optional override lot;
   - `ref_type`, `ref_id`;
   - `p_at` (the posting instant, which gives `effective_on`), `p_cost_at` (null = current basis);
   - `p_caller` (for the alert record).

   Steps:
   1. `app.lock_ingredient_stock(tenant, array[ingredient])`. It is re-entrant: a caller that already locked several ingredients in id order (M14) loses nothing.
   2. **Buckets** (`app.fefo_buckets`): Σ `qty` of the ingredient's movements at that location, grouped by `raw_lot_id`, keeping only buckets with Σ > 0.
      - Order: `raw_lot.expiry asc nulls last`, then `raw_lot.received_on asc`, then `raw_lot_id asc`.
      - A positive unlotted bucket (which can exist after a shortfall is reversed) comes last.
      - Expired lots are included, so a pure FEFO picks them first (Q7 → V7).
   3. **Override lot** (if given):
      - it must be a lot of this tenant **and ingredient**, else P0002 `lot_not_found` (no hint that it exists elsewhere);
      - its bucket at this location must be > 0, else P0001 `lot_empty` (409);
      - take `min(qty, bucket)` from it first, then continue with the remaining buckets in FEFO order.
   4. Take from each bucket in order until `qty` is covered. Each slice is one row with `qty = −slice`.
   5. **Shortfall:** any remainder is one row with `raw_lot_id null` and `qty = −remainder`. No lot is ever driven below zero by M12 procedures (asserted by the property test).
   6. `unit_cost` for every row = `app.ingredient_unit_costs(tenant, array[ingredient], p_cost_at).unit_cost`, read once. Null when there is no purchase, never 0 (ADR-008). M12's public procedures pass `p_cost_at = null` (the current basis, AT3). M14 passes `produced_at`.
   7. `effective_on = app.venue_date(p_at, tenant.timezone)`.
   8. **Negative check, contained (§3.1.7)**, after all inserts.
   9. Returns `table (movement_id uuid, raw_lot_id uuid, qty numeric)` in insert order. M14 builds `batch_input` from it.
5. **Transfers (`public.post_transfer`, AT4).**
   - Same lock. The source buckets come from `app.fefo_buckets` at the source location; an override lot, if given, is taken first.
   - For each slice: a row `−slice` at the source and a row `+slice` at the destination, with the **same lot**, `ref_type 'transfer'`, the same `ref_id`, and `unit_cost` null.
   - **The quantity must be covered by the location total, and by positive buckets:** otherwise P0001 `insufficient_stock` (409) and nothing is written (Q5 → V5). The location total counts every bucket, a negative "senza lotto" one included (`app.location_on_hand`), so a transfer never leaves the source below zero and raises no `negative_stock` alert; the positive-bucket check stays because only positive lots can be sliced. Moving more than the ledger shows is a recording error, not a consumption.
   - `from = to` → `same_location` (422). An inactive or foreign location → `location_not_found` (the existing `app.resolve_location`).
   - The ingredient total is unchanged by construction: Σ of the legs = 0.
6. **Reversal (`public.reverse_movement(p_movement)`, AT5).**
   1. Role check.
   2. Load the row in the caller's tenant (else P0002).
   3. Load its operation: all rows with the same `(ref_type, ref_id)`.
   4. Refuse with 409 in these cases:
      - `movement_is_reversal`: the operation's `ref_type` is `reversal`;
      - `movement_not_reversible`: the type is `receipt` or `count`, or the `ref_type` is not `manual` / `transfer` (M14/M19 rows have their own corrections);
      - `already_reversed`: any row of the operation is already reversed.
   5. Lock the operation's ingredients in id order.
   6. Re-check `already_reversed` in a new statement after the lock.
   7. For a transfer: each destination leg (`+q` at location D, lot L) needs bucket (D, L) ≥ q, else `transfer_already_used` (409).
   8. Insert one mirror row per original row, with a new `ref_id`, `effective_on` = today (Rome), the same `unit_cost` and reason.
   9. The unique `stock_movement_reverses_uq` is the backstop: a 23505 is mapped to `already_reversed`.

   All of it is one transaction. A reversal never needs a negative check: it adds back what an outflow took, and transfer reversals are refused before they could go negative.
7. **Negative stock (AT6; founder M6 decisions; plan §3.6 rule 8).**
   - After an outflow, `on_hand` = Σ of all buckets of the ingredient at that location. If < 0, raise the alert:
     - kind `negative_stock`, `entity_type 'ingredient'`, `entity_id` = ingredient;
     - business date = Rome date of `p_at` (dedup → **one alert per ingredient per day**, the PRD's "one per item per day"; later shortfalls that day are visible on the screen);
     - severity `warning`, audience = the kind's default `{owner, chef}`, not cost-bearing.
   - Payload, quantity-only:

     ```
     {ingredient_id, location_id, on_hand_qty, unit, movement_id}
     ```

     - It passes the chef allow-list. Names are resolved at render time.
     - `on_hand_qty` is the location total after the write. `movement_id` is the shortfall row, or else the last row written.
   - Raised by `app.raise_negative_stock(p_tenant, p_ingredient, p_location, p_movement, p_at, p_caller)` through `app.try_raise_alert(... p_caller)`.
   - The core calls it inside:

     ```
     begin perform app.raise_negative_stock(...); exception when others then perform app.record_alert_refusal(tenant, 'negative_stock', 'ingredient', ingredient, caller, 'check_failed', sqlstate); end;
     ```

     This is M8's pattern: a guard refusal is absorbed by `try_raise_alert`, any other error by the block, and **the movement always commits**. The stock lock is taken before the block, so a rolled-back block cannot release it.
   - The negative check also fires when the location was already negative before this movement (the dedup keeps it to one per day).
8. **Chef payload allow-list in `app.raise_alert` (M7 §8 (a); the first chef-audience kind with data).**
   - `create or replace app.raise_alert`, starting from the **current merged definition** (`20261022150600`, or M11's if it replaced it), with one new step **after** every existing guard.
   - The new step: when the final audience includes `chef`, `app.chef_payload_allowed(p_payload)` must be true, else P0001 `alert_payload_not_allowed`. The rule:
     - every key, at any depth, matches `^[a-z][a-z0-9_]{0,40}(_id|_key|_qty|_count|_hours|_days|_date|_at)$` or is exactly `unit`;
     - every string value is a token: a uuid, `YYYY-MM-DD`, an ISO instant, a unit (`kg`, `l`, `pz`, `g`, `ml`) or a code `^[a-z0-9_]{1,40}$`.
   - Placing it last keeps every existing `044` case, and its error code, unchanged.
   - `app.alert_guard_codes()` is replaced to add `alert_payload_not_allowed`, so `try_raise_alert` (not replaced; md5 in `076` unchanged) absorbs it. `060`'s expected list becomes seven codes (a deliberate registry change).
   - Owner-only payloads are not touched: no loosening, no tightening.
   - TS mirror `src/server/alerts/chef-payload.ts` (`chefPayloadAllowed`), tested with the same vector table as `091`.
9. **Names in alerts are resolved when shown.**
   - `src/server/alerts/names.ts`: `collectNameRefs(rows)` collects `ingredient_id` and `location_id` values from rows whose template declares `nameRefs`.
   - `loadNames(supabase, refs)` runs one `select id, name … in (…)` per table on the **reader's** session: RLS applies, and owner and chef read both tables.
   - `renderAlert(row, locale, names)` passes the names to the template. A missing name renders "ingrediente non disponibile" / "ubicazione non disponibile".
   - No name is stored in a chef payload.
10. **Roles (plan §3.11.2 read together with §3.3).** The matrix row "stock and batch ledgers (quantities)" says owner R, admin R, chef R + writes via procedures, while §3.3 lists the stock POST endpoints for owner, admin and chef. **Q1 = owner+chef+admin write (founder 2026-10-23):** owner, admin and chef call the write procedures; nobody inserts directly; the waiter has no access at all. The matrix row "stock and batch ledgers (quantities)" of §3.11.2 is read as: owner R+W, admin R+W, chef R+W, always through procedures; V1 is unused.

    |---|---|---|---|---|---|---|
    | `consume_raw_fefo`, `post_waste`, `post_transfer`, `reverse_movement` | ✓ | ✓ (Q1) | ✓ | 42501 | `app.require_stock_writer()` first | `withApi({roles: owner, admin, chef})` |
    | `stock_on_hand`, `stock_lots`, `stock_movements` (quantities) | ✓ | ✓ | ✓ | 42501 | `app.require_stock_reader()` | same |
    | `raw_waste_costs` (€) | ✓ | ✓ | 42501 | 42501 | `app.require_cost_reader()` (M8) | owner, admin |
    | direct INSERT/UPDATE/DELETE on `stock_movement`, `raw_lot` | 42501 | 42501 | 42501 | 42501 | no grant; append-only triggers | — |
    | SELECT `stock_movement`, `v_stock_on_hand` | rows | rows | 0 rows | 0 rows | M5 RLS (unchanged) | — |
    | SELECT `raw_lot` | rows | rows | rows | 0 rows | M5 RLS (unchanged) | — |
    | `negative_stock` alert | reads | — (M6: admin reads no alerts) | reads | — | M6 RLS | `/api/alerts` |
    | reverse a movement posted by someone else | ✓ | ✓ | ✓ (Q2) | — | procedure | — (→ V2) |

    - Every public function is `security definer`, `set search_path = ''`, checks the role **first**, takes the tenant from `app.tenant_id()` and the user from `app.app_user_id()`, filters every query by tenant, and is executable by `authenticated` only (revoked from `public`, `anon`, `service_role`). Every `app.*` helper is revoked from all API roles.
    - **No €** in any return of the seven quantity functions (column-name scan, step 7; JSON key allow-list, steps 5, 12, 13).
11. **Concurrency.**
    - `app.lock_ingredient_stock(p_tenant, p_ids uuid[])` = `pg_advisory_xact_lock(hashtext('ingredient_stock'), hashtext(tenant || ingredient))` per distinct id, in id order. It is a separate class from M8's `ingredient_cost`.
    - Every M12 write takes it **before** its first balance read. In READ COMMITTED, each later statement takes a new snapshot and sees the previous holder's committed rows.
    - Cases:
      - two consumers on one lot: the second waits, then sees the reduced bucket;
      - two reversals of one operation, even through different rows of it: the second waits, then gets `already_reversed`;
      - a reversal of a transfer vs a consumption at the destination: serialised, then `transfer_already_used` if needed.
    - **Global lock order** for current and future procedures: recipe graph (shared) → ingredient cost locks → ingredient stock locks, each in id order.
      - `approve_invoice` takes only the first two and **no** stock lock (it is not replaced), so a receipt is not serialised with a consumption (accepted, §6).
      - M12 takes only stock locks. M13 `close_count` and M14 `produce_batch` must take the stock locks of their ingredients (contract §3.9).
12. **Quantities and units.**
    - Input `qty` > 0 with a `unit` in `kg, g, l, ml, pz`. It is converted with the existing `app.base_factor(unit, ingredient.base_unit, null, null, null)` and rounded to 4 decimals.
    - `conf`, or a unit of another dimension → `unit_mismatch` (422). A result ≤ 0 or over `STOCK_QTY_MAX` → `qty_invalid` (422).
    - An ingredient with `is_stock = false` → `ingredient_not_stock` (422).
    - An inactive ingredient may still be wasted or moved (it can be physically there).
13. **Location default.** `p_location` null → `app.resolve_location(tenant, null)`, the same rule as approval: the only active location, else `location_required` (422) or `no_location` (422).
14. **Expiry state for the screens** is computed in SQL, so React never compares dates:
    - `app.expiry_state(p_expiry date, p_today date)` (immutable) returns `none` (null expiry), `expired` (< today), `due_soon` (≤ today + `EXPIRY_SOON_DAYS`, which is 1, PRD 2.4) or `ok`;
    - today is `app.venue_date(now(), tenant.timezone)`;
    - no expiry is ever derived from `received_on` (M5 Q1 note; Q8 → V8).
15. **Waste € (AT3).**
    - `raw_waste_costs(p_from, p_to)` (owner/admin) works over `type = 'waste'` rows (originals **and** reversals) with `effective_on` in the range.
    - Per reason and ingredient: `qty = −Σ qty` and `value_eur = −Σ (qty × unit_cost)` over the rows with a cost.
    - `unvalued_count` = the number of rows with a null cost. They are never valued at 0.
    - All values are numeric, rounded to 4 dp. The screen formats cents.
    - A reversal is dated when it is posted, so it reduces the waste of its own period (A3).
16. **Retention and personal data.**
    - Movements carry `created_by` (staff id) as M5 does. No new personal field and no free text: there is no note on waste (A4).
    - The chef sees other people's names in the history only as "un collega" (§3.5). Owner and admin see display names, which they already read.
    - Retention follows the ledgers (project Q14).

### 3.4 API

All routes:
- use `withApi`, with the user-session client (RLS and definer checks apply);
- take strict Zod bodies and queries (an unknown key or parameter → 400);
- require `application/json` on writes (else 415);
- return errors as `{"error":{"code","message"}}`.

**No stock response contains a € value or a cost-like key, whatever the role.** € appear only in `/api/stock/waste-costs`.

| Endpoint | Roles | Body / query | Success | Errors |
|---|---|---|---|---|
| `GET /api/stock` | owner, admin, chef | `?location=<uuid>` | 200 `{asOf, items: [StockItem]}` | 400; 401; 403 waiter; 404 foreign location |
| `GET /api/stock/lots` | owner, admin, chef | `?ingredient=<uuid>` (required), `?empty=1` | 200 `{ingredient: {id, name, baseUnit}, today, units, locations: [{id, name}], lots: [LotItem]}` (`units` = `UNITS_FOR_BASE[baseUnit]`; `locations` = the active locations, read through the caller's RLS) | 400; 401; 403; 404 |
| `GET /api/stock/movements` | owner, admin, chef | `?ingredient=<uuid>`, `?before=<createdAt>_<uuid>` | 200 `{operations: [StockOperation], nextCursor}` | 400 (bad cursor too); 401; 403; 404 |
| `POST /api/stock/waste` | owner, admin, chef | `{ingredientId, qty, unit: 'kg'\|'g'\|'l'\|'ml'\|'pz', reason, locationId?, lotId?}` | 201 `{operationId, movements, onHandQty, negative}` | 400; 401; 403; 404 (`ingredient_not_found`, `lot_not_found`); 409 `lot_empty`; 415; 422 `reason_invalid`, `unit_mismatch`, `qty_invalid`, `ingredient_not_stock`, `location_required`, `no_location`, `location_not_found` |

- **Shapes** (`src/server/stock/types.ts`):
  - `StockItem = {ingredientId, name, baseUnit, isActive, onHandQty, negative, locations: [{locationId, name, onHandQty, unlottedQty, negative}]}`. It is grouped in the service from `stock_on_hand` rows; `negative` comes from the SQL sign test in the service (no arithmetic beyond grouping and `< 0`).
  - `LotItem = {rawLotId | null, lotCode | null, locationId, locationName, expiry, expiryState, receivedOn, supplierName, qtyReceived, onHandQty, fefoRank}`.
  - `StockOperation` as returned by SQL.
  - Quantities are JSON numbers with 4 decimals.
- **Services:** `src/server/stock/{constants,types,schemas,errors,reasons,on-hand,lots,movements,waste,transfer,reverse,waste-costs}.ts`.
- **Error mapping** (`errors.ts`):
  - 42501 → 403; P0002 → 404;
  - the P0001 codes → 409 or 422 per the table;
  - 23505 on `stock_movement_reverses_uq` → 409 `already_reversed`;
  - anything else → 500, reported with the SQLSTATE only (never quantities, names or ids of other tenants).
- **Output schemas** are Zod `.strict()`. A key allow-list test fails on any key matching `/eur|cost|price|margin|value|amount/i` in the quantity endpoints.

### 3.6 Flows

1. **Waste:** `/magazzino/[id]` → `POST /api/stock/waste` → `post_waste` → stock lock → buckets → rows (lots, then shortfall) → contained negative check → `try_raise_alert` → commit → 201 → the screen refetches lots and movements.

### 3.9 Contract for M13, M14, M15, M19

- **The engine:** `app.post_stock_outflow(...)` (signature §3.2) is the only way to write consumption or waste. Callers pass:
  - their own `ref_type` (`batch`, `order_line`, `staff_meal`, `batch_discard`, …) and `ref_id`;
  - `p_at` (posting instant), `p_cost_at` (M14: `produced_at`; M19: `fired_at`);
  - `p_caller`.

  It never refuses for lack of stock (plan §3.6 rule 8). It refuses only invalid input (lot of another ingredient, empty override lot).
- **Locks:**
  - a caller touching several ingredients first calls `app.lock_ingredient_stock(tenant, all ids)` (id order);
  - global order: recipe graph (shared) → ingredient cost locks → ingredient stock locks;
  - M13 `close_count` must take the stock locks of the counted ingredients before reading expected quantities.
- **M14:**
  - builds `batch_input (batch_id, raw_lot_id, qty)` from the engine's rows;
  - the shortfall row has `raw_lot_id` null, so `batch_input.raw_lot_id` must allow null, or M14 records the shortfall separately (M14's decision);
  - movements of M14 are not reversible through `reverse_movement` (§3.1.6).
- **M19:**
  - direct raw ingredients go through the engine with `ref_type 'order_line'`;
  - the negative alert is already raised and contained by the engine (caller `fire_course`);
  - batch negatives use `negative_stock` with `entity_type 'batch'` and a quantity-only payload (the allow-list applies).
- **M13:**
  - count rows: `type 'count'`, `ref_type 'count_session'`, lot or null;
  - the reconciliation identity reads `consumption`, `waste` (originals and reversals, by `effective_on`), `transfer` (nets to zero per ingredient) and `count`;
  - its invariant check should add "no lot bucket below zero except through counts";
  - and "every reversal mirrors its original" (also enforced by the trigger).
- **M15:**
  - the waste € report by reason extends `raw_waste_costs` with batch waste;
  - V6.3 (chef waste report in quantities) can use `stock_movements` or a new quantity-only function, never `raw_waste_costs`.

## 4. Alternatives considered

- **Shortfall charged to the last FEFO lot (no unlotted bucket):** rejected (ADR-011). Lots would show quantities nobody received, and M16 expiry alerts and M14 traceability would read invented lot balances.
- **Strict override (all from the chosen lot, even below zero):** rejected. It creates negative lots; "start with this lot" meets AT1's "override is respected".
- **Refuse consumption beyond on-hand:** rejected by plan §3.6 rule 8 and AT6.
- **Split `unit_cost` into `stock_movement_cost` and give the chef SELECT on `stock_movement`:** rejected. It needs `approve_invoice` replaced (pinned in `076`) for a read path that definer functions provide without touching M5/M8.
- **Change `v_stock_on_hand` into a definer view for the chef:** rejected. The tenant and role filter would live in a view body, and `031` pins today's behaviour. Definer functions with an explicit role check are testable per role.
- **`SELECT … FOR UPDATE` on `raw_lot` rows instead of an advisory lock:** rejected. It does not cover the unlotted bucket, and the rows to lock are known only after reading balances.
- **Row-level reversal:** rejected. Half of a FEFO split or one transfer leg could be undone alone.
- **Allowing reversal of a reversal ("redo"):** rejected. To redo, post the movement again. Reversal chains complicate the history and the guard.
- **Waste valued at the lot's purchase price:** rejected for the base plan (PRD/AT3 say the current basis). Variant V4.
- **Allow-list enforced only in M12's payload builder:** rejected. It would not protect M16/M19 chef kinds. Enforcing it in `raise_alert` costs one guard and one test change (`060`).
- **A distinct guard code vs reusing `alert_payload_invalid`:** a distinct `alert_payload_not_allowed` was chosen, so `app.alert_refusal` rows and logs tell an oversize payload from a disallowed key. The cost is replacing `app.alert_guard_codes()` and updating `060`.
- **`fast-check` for the property test:** rejected as a new dependency. A seeded generator plus a printed seed and action list is enough at this size. Shrinking is the missing feature, and the printed action list (≤ 30 actions) replaces it.
- **Property test in pgTAP:** rejected for the property itself. An independent FEFO oracle in plpgsql would be a second copy of the code under test in the same language. pgTAP keeps a fixed-sequence fold check (step 8).
- **One alert per ingredient and location per day:** rejected. The dedup key has one entity id, and "one per item per day" (PRD 2.4) names the item. The payload names the location of the first shortfall, and the screen shows all of them.
- **Manual consumption screen:** not built (Q6 → V6). Waste reasons cover kitchen deductions (PRD 2.5).

## 6. Risks and mitigations

- **Security / privacy**
  - *Definer functions bypass RLS:* every public M12 function checks the role first, uses an empty `search_path`, takes the tenant from `app.tenant_id()`, filters every query by it, and is executable by `authenticated` only. The `app.*` engine has no API grant (steps 4–7).
    - Foreign lots and ingredients return P0002, never another tenant's data. Composite foreign keys already stop cross-tenant rows (M5).
  - *€ reaching the chef (Q16 = V6) or the waiter:*
    - stock tables keep their M5 RLS;
    - the quantity functions have no cost column (column scans, steps 6 and 7) and return no cost key (allow-lists, steps 5, 12, 13);
    - `raw_waste_costs` is in M8's catalogue scan (`059`, step 6);
    - the screens render no € except `/magazzino/sprechi` (owner/admin), with string scans in steps 16 and 18;
    - the chef alert payload holds only ids and quantities, enforced by the allow-list in `raise_alert` (step 2).
  - *Text in chef alerts:* names are never stored in a chef payload. They are resolved at render time through the reader's own RLS (step 3).
  - *Personal data:*
    - movements hold staff ids (M5 pattern);
    - the chef sees other staff only as "un collega";
    - there is no free-text field;
    - logs and error reports carry SQLSTATEs and ids only (step 11);
    - retention follows the ledgers (project Q14); there is no new processor.
  - *IDOR:* malformed or foreign ids → 404 before or from the tenant-filtered lookups (steps 5, 12, 13).
  - *CSRF:* writes require `application/json` (`withApi`).
- **Correctness**
  - *Replacing `app.raise_alert` (M6/M8 pipeline):*
    - built from the current merged definition, with one check appended after all existing guards;
    - `044`, `045`, `046`, `075` and `076` run unchanged, and `060` changes only its expected code list;
    - if M11 merges first and replaced `raise_alert`, step 2 starts from M11's body.
  - **Known limit: stock at a deactivated location.** Stock held at a location that is later deactivated cannot be wasted, consumed or moved out until the location is reactivated, because `app.resolve_location` refuses inactive locations (`location_not_found`).
  - *Lot balances can overstate after a shortfall* while an unlotted negative exists. The screen shows the unlotted line and asks for a count; M13 corrects it (ADR-011).
  - **Known limit (lead and founder decision 2026-10-23): `approve_invoice` is not touched.** The receipt-vs-consumption overlap below is accepted and recorded as a known limit.
  - *Receipts are not serialised with consumption* (`approve_invoice` takes no stock lock and is not replaced). A consumption committed during an approval may write a shortfall and an alert that the receipt then covers. Accepted: the alert asks for a count, and the totals are right after both commit.
  - *Alert failures hidden by containment:* each one leaves an `app.alert_refusal` row (`check_failed` or a guard code) and a database warning. M13's job-health check must read them (already noted by M8 and M9).
  - *Reversal dating:* a reversal is dated when posted, so it changes the waste of the month in which it is posted (A3). M13's reconciliation uses `effective_on` consistently.
  - *Expired lots consumed first under pure FEFO:* the expiry badges push the chef to waste them; V7 changes the rule if wanted.
  - *Enum values used before commit (T1):* the values are added in their own migration, and the constraints compare `type::text`.
- **Unverified (checked in the named step):**
  - **T1** `ALTER TYPE … ADD VALUE` inside a transaction makes the value unusable until commit ([PostgreSQL docs, ALTER TYPE](https://www.postgresql.org/docs/17/sql-altertype.html)). Whether the Supabase CLI wraps several migration files in one transaction is not verified. The `type::text` comparisons work either way, which `npx supabase db reset` in step 1 proves.
  - **T2** `pg_advisory_xact_lock` is re-entrant within one transaction, and READ COMMITTED gives each later statement a new snapshot ([advisory locks](https://www.postgresql.org/docs/current/functions-admin.html#FUNCTIONS-ADVISORY-LOCKS), [READ COMMITTED](https://www.postgresql.org/docs/current/transaction-iso.html#XACT-READ-COMMITTED)).
