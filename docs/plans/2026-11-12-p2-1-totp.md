## 1. Goal and scope

- **Goal:** a stolen password (or a stolen e-mail inbox) alone no longer opens an admin account, or an owner account whose owner chose
  the code; the check is made by Postgres on every query, not only by the screens.
- **In scope**
  - **Supabase Auth TOTP** for owner and admin accounts (e-mail login, ADR-029): enrol (QR and key), verify, sign-in challenge, factor
    list with a backup factor, self-removal.
  - **The `aal` gate in Postgres** (§3.2): `app.tenant_id()`, `app.role()` and `app.app_user_id()` stop answering for an owner or admin
    who must be at `aal2` and is not; `app.require_aal2()` for the MFA procedures. Admin always required (once enforcement is on);
    owner only after enrolling a verified factor.
  - **Enforcement mode per tenant** (`off` | `enrolled` | `required`), set only by a founder-run script, so the rollout is staged
    (§3.7).
  - **Recovery (D2, as decided on 2026-11-12, Q-T1 = V1):** a second, backup TOTP factor; the **audited reset is DigiAlto's script only**
    (`scripts/mfa-reset.ts`); another owner or admin can see, as status only, that an admin has no factor and tell DigiAlto.
  - **Audit events:** enrol, unenrol, reset (and reset failed, by the script), enforcement change; plus F13's `pin_set_failed`. Wrong-code
    attempts go to `app.mfa_failure` and are deleted after 30 days (Q-T2 = V2).
  - **App rate limit on codes:** a per-account lock after repeated wrong codes (§3.6).
  - **Screens (Italian):** sign-in challenge, forced enrolment (admin), owner offer, factor list with a read-only status of the other accounts
    (no reset screen).
  - **Folded follow-ups:** **F13** PIN-change window (§3.10) and **F16** money-guard key gaps (§3.11).
  - Local `supabase/config.toml` change; staging and production steps for the founder (§3.12, §7).
- **Out of scope**
  - **Passkeys / WebAuthn** (ADR-029, Q204): not in P2-1 (Q-T8).
  - **SMS or phone MFA** (provider cost, phone numbers as new personal data).
  - **Supabase recovery codes** (Q-T9): not documented for our version; D2 uses a backup factor.
  - **Second factor for staff PIN accounts**: PIN accounts are only chef and waiter (`app_user_login_method_ck`), and ADR-010's device
    gate already applies to them.
  - **An in-app alert** on a lock or a reset (alerts stay as they are; D3 and the alert registry are unchanged).
  - **Loosening the value guard for owner-only alert payloads** (F17, "Keep"). The "Quartiere EUR" false positive therefore stays (§3.11).
  - Any change to the access-token hook, the PIN login procedures except `pin_login_finish` (F13), cron routes, the public booking
    functions or the offline op set.

## 3. Design

### 3.1 Decisions

**Founder decisions (binding, not re-opened):** admin required, owner optional (C1); `aal` checked in Postgres; D2 recovery = backup TOTP
factor + audited reset (founder 2026-11-12, Q-T1 = V1: by DigiAlto's script only, not by the other admin or owner), owner offered and not forced; staff PIN sessions unchanged.

**Design decisions of this plan:**
- **T-1 One gate, in the three membership helpers.** `app.tenant_id()`, `app.role()` and `app.app_user_id()` return null for an owner or
  admin who needs `aal2` and whose token is not `aal2`. Every RLS policy, every definer that resolves the tenant or the role, Storage
  policies and Realtime inherit it: writes, user management, exports, settings and cost reads all fail closed. Rejected alternatives in §4.
- **T-2 Who needs `aal2`** (`app.mfa_needs_aal2(role, tenant, auth_id)`):
  `role in (owner, admin) and tenant.mfa_enforcement <> 'off' and (has a verified TOTP factor or (role = admin and mode = 'required'))`.
  Chef and waiter never, whatever their login method.
- **T-3 Enforcement mode per tenant**, `tenant.mfa_enforcement`: `off` (kill switch: no gate), `enrolled` (default after the migration:
  only accounts that enrolled are gated), `required` (admins must also enrol). Set only by `public.set_mfa_enforcement` (service role),
  called by `scripts/set-mfa-enforcement.ts`, which the founder runs (M-5). `required` is refused while any active admin of the tenant
  has no verified factor.
- **T-4 Exempt paths are few and named.** Postgres: `public.mfa_status`, `public.mfa_gate`, `public.mfa_attempt_allowed`,
  `public.mfa_enrol_check`, `public.mfa_record_enrolled`, `public.mfa_unenrol_check`, `public.mfa_record_unenrolled`,
  `public.mfa_record_failure` (each acts on the caller's own account only and returns nothing about the venue except its name as the
  issuer). API: `GET /api/me/mfa`, `POST /api/me/mfa/factors`, `POST /api/me/mfa/factors/:id/verify`, `DELETE /api/me/mfa/factors/:id`,
  `POST /api/auth/mfa/challenge`, plus `POST /api/auth/logout` (already `authenticated`-only). **`/api/me` is not exempt.**
- **T-5 The API answers early and clearly.** `withApi` calls `public.mfa_gate()` only for owner/admin requests whose token is not `aal2`
  and returns 403 `mfa_required` or `mfa_enrol_required`. Postgres stays authoritative; the API check is for a clear answer, not for
  security.
- **T-6 Codes are verified server-side in one request** with `challengeAndVerify`, so the challenge and the verify leave from the same
  function invocation (Supabase requires the same IP). The browser never talks to Supabase (existing invariant).
- **T-7 Two factor slots, fixed names.** `principale` and `riserva` (friendly names "Principale" / "Riserva"). No free-text device names,
  so nothing personal is typed. At most two verified TOTP factors per account (`app.mfa_max_factors()` = 2).
- **T-8 Audit first, then compensate.** The script's reset writes `app_user.mfa_reset` before the Auth call and `app_user.mfa_reset_failed`
  if the call fails; F13 applies the same pattern to PIN changes (`app_user.pin_set_failed`). A reset can never happen without an audit row.
- **T-9 App lock on wrong codes:** 5 failures in 15 minutes per account → 429 `mfa_locked` until the oldest failure in the window is
  15 minutes old (§3.6). Counted from `app.mfa_failure` rows (Q-T2 = V2), which a daily job deletes after 30 days.
- **T-10 Reset rules (Q-T1 = V1):** no in-app reset. DigiAlto runs `scripts/mfa-reset.ts` (A13) as the service role, naming an active admin
  of the target's tenant as the actor; the target must be an active owner or admin (never chef or waiter). All of the target's factors
  are deleted. Deleting a factor does **not** sign anyone out on Supabase (found on the real stack, mfa.int.ts test 6), so
  `mfa_reset_service_begin` itself runs `delete from auth.sessions where user_id = <target auth id>`; the refresh tokens go with the
  sessions (`on delete cascade`), so no session of the target can refresh. That delete is the **only** write to an `auth` table by any
  function in `public` or `app` (pgTAP 341 scans `pg_proc` source text for insert, update, delete, truncate and merge on `auth.`), and the
  function stays executable by `service_role` only. An access token already issued is a signed JWT that PostgREST accepts until it
  expires (one hour at most): the Postgres gate does not look at sessions, and for a token already at `aal2` it passes (the gate asks for
  `aal2`, not for a live session). How far the residual window reaches depends on the project's **JWT signing algorithm**: when the project signs
  JWTs with **HS256**, route handlers resolve the token against the Auth server (`getUser`), which refuses it, so the handlers fail and only the
  direct Data API is exposed; with **asymmetric signing keys**, `getClaims()` verifies the token **locally**, so `/api/*` route handlers may accept
  the reset target's last `aal2` access token for up to 1 h too. In either case every data read and write is still refused by Postgres, because the
  factors are gone and the gate re-checks them. This residual window is accepted and recorded, not closed (closing it would put a session lookup in
  the hot path of every policy); the go-live checklist item "JWT signing algorithm; residual window after reset" has the founder confirm the
  algorithm. The row `app_user.mfa_reset` is
  written after the delete in the same transaction and records `after {"sessions_revoked": n}`: the number only, no ids.
  **Order:** sessions are deleted in `begin`, before the script deletes the factors. If the factor delete then fails, the sessions are
  already gone and `mfa_reset_failed` is written: the person has to sign in again, which is fail-safe (nothing is left open). The reset is
  idempotent, so the script is simply run again. `mfa_reset_service_begin` and the audit row are one transaction (T-8 is unchanged).
- **T-11 The owner is offered, not forced (D2):** after any sign-in of an owner or admin without a factor while not forced, the sign-in
  goes through `/login/offerta-codice` ("Attiva ora" / "Non ora"). No state is stored, so the offer returns at each sign-in, about
  once a month per phone (Q-T5, V5).
- **T-12 QR shown as an image from a `data:` URL** on `/login/attiva-codice`, `/login/offerta-codice` ("Attiva ora" opens the enrolment in place) and
  `/doppia-verifica` only; the CSP gains `data:` in `img-src` on those three paths only (B1; list in `src/lib/security/data-image-paths.ts`).
  An SVG loaded as an image cannot run script. The CSP is chosen per fully loaded document and an App Router client navigation keeps the first
  document's, so every way into one of the three pages is a full document load (`navigateTo`, a plain `<a>` in the nav, `location.assign`).

### 3.2 The gate in Postgres (migration `20261201100000_mfa_gate.sql`, step A1)

```sql
alter table public.tenant
  add column mfa_enforcement text not null default 'enrolled'
    check (mfa_enforcement in ('off', 'enrolled', 'required'));
-- ADD COLUMN with a constant default: existing tenants read 'enrolled' (no gate for anyone without a factor).
-- authenticated can SELECT the column (the gate helpers read it) and service_role can UPDATE it through the table-wide grant; secret-key holders
-- are trusted. The supported path is scripts/set-mfa-enforcement.ts (public.set_mfa_enforcement, service role), which writes the audit row.

-- The token's assurance level; a missing claim counts as aal1 (Supabase docs).
create function app.jwt_aal() returns text language sql stable set search_path = ''
as $$ select coalesce(nullif(auth.jwt() ->> 'aal', ''), 'aal1') $$;

create function app.mfa_has_verified_factor(p_auth uuid) returns boolean
  language sql stable security definer set search_path = ''
as $$ select exists (select 1 from auth.mfa_factors f
                      where f.user_id = p_auth and f.status = 'verified' and f.factor_type = 'totp') $$;

create function app.mfa_needs_aal2(p_role public.app_role, p_tenant uuid, p_auth uuid) returns boolean
  language sql stable security definer set search_path = ''
as $$
  select p_role in ('owner', 'admin')
     and coalesce((select t.mfa_enforcement from public.tenant t where t.id = p_tenant), 'enrolled') <> 'off'
     and (app.mfa_has_verified_factor(p_auth)
          or (p_role = 'admin'
              and (select t.mfa_enforcement from public.tenant t where t.id = p_tenant) = 'required'))
$$;

-- The M0 lookup without the gate: ONLY for the exempt MFA procedures (T-4). Pinned by A2's reference scan.
create function app.membership_ungated()
  returns table (app_user_id uuid, tenant_id uuid, role public.app_role, auth_id uuid) ...;

-- app.tenant_id(), app.role(), app.app_user_id(): the M0 body plus
--   and (not app.mfa_needs_aal2(u.role, u.tenant_id, u.auth_id) or app.jwt_aal() = 'aal2')
-- (create or replace: same signature, owner and grants).

create function app.require_aal2() returns void ...   -- P0001 'mfa_required' when the ungated member needs aal2 and the token is not aal2
```

- **Grants:** the new `app.*` helpers have no API grant; `app.tenant_id()` / `app.role()` keep `execute` for `authenticated` (M0).

| Event | Supabase does | The app adds |
|---|---|---|
| First factor verified (device A) | session A → `aal2`; every other session of the user below `aal2` is **deleted**; unverified TOTP factors deleted | `mfa_enrolled` row. ### 3.6 Rate limiting of codes

- **Supabase already:** single-use challenges that expire; one-step skew; challenge and verify limited by `RateLimitChallengeAndVerify`
  (burst 30, one-minute window). Our server calls Supabase from Vercel, so, like the sign-in limit in ADR-029, that limit is very likely
  shared by every account of every venue (Q-T7); a flood could briefly block code entry for everyone. Accepted, as in ADR-029.
- **The app adds (T-9):** a per-account lock in Postgres, checked **before** Supabase is called: 5 wrong codes within 15 minutes → 429
  `mfa_locked` with the minutes left. The lock reads `mfa_failure`, so it survives restarts and is the same on every instance.
- **What the app lock cannot stop:** someone who already has the password can sign in to Supabase Auth directly with the public key and
  try codes against Supabase without our routes; only Supabase's own limit applies to them. The per-account Supabase hook that would
  close this is Teams/Enterprise only (§2.2). Listed in §6.
- **Risks of the app lock.** (a) The lock check and the failure recording are not atomic: parallel wrong codes can pass the check together
  and exceed 5 per window; the excess is bounded by Supabase's own challenge and verify limit. (b) `mfa_record_failure` is callable through
  `/rest/v1/rpc` at aal1 by a signed-in caller, so a caller can grow `app.mfa_failure`; the growth is bounded
  by the 30-day retention.
- No 800 ms floor (ADR-029) on the code routes: the caller is already signed in, so the time reveals no account.

### 3.7 Rollout and go-live (nobody locked out)

1. **Deploy PR 1, then PR 2.** Every tenant reads `enrolled`; nobody has a factor; nothing changes for anyone. Owners and admins see the

2. **M-2/M-3 (founder):** on staging, the DigiAlto admin enrols the main and the backup factor, signs out and in, passes the challenge.

   not done. Then the same on production, on a day without service.
4. **Kill switch:** `--mode off` turns the gate off for that tenant at once (the next query), without a deploy. `--mode enrolled` returns

### 3.8 The 30-day cap and token refresh

- The cap counts from the **earliest** `amr` timestamp (`session-age.ts`). A TOTP verify adds a `totp` entry with a later timestamp, so
  the 30 days still run from the password (or e-mail code) sign-in: the code never extends a session. After 30 days, sign-in again:
  password, then code.
- A refresh keeps the session's `aal`; the code is asked **once per sign-in**, not at every app open.
- "Recent sign-in" (password change without the current password, ADR-029; reset, T-10) uses the **latest** `amr` timestamp, so passing
  the code counts as a recent authentication. That is consistent with ADR-029: the code step only happens right after a password or
  e-mail-code sign-in.
- Staff PIN sessions keep their business-day cut-off (ADR-010); nothing here touches them.

### 3.10 F13: PIN-change window (`20261201100300_pin_change_window.sql`, step A5)

- **Today:** `record_pin_change` (audit, `pin_reset` attempt row, end sessions) runs **before** the Auth password change. A PIN sign-in with
  the **old** PIN in that gap opens a session that survives; and a failed Auth call (502) leaves an audit row for a change that did not happen.
- **Fix:**
  - `public.finish_pin_change(p_user uuid, p_outcome text)` (staff manager, gated like the other staff procedures), called by `setPin`
    after the Auth call:
    - `success` → a second `pin_reset` attempt row at that instant and `app.end_staff_sessions(…, 'pin_reset', now)` again;
    - `failure` → one `app_user.pin_set_failed` audit row; the route then answers 502 as today.
  - `public.pin_login_finish` refuses a `success` (outcome stored as `failure`, reason `superseded`, no session) when a `pin_reset` row
    for the user is newer than the attempt's `started_at`.
  - Together: any sign-in that started before the new password was in place is refused or ended; sign-ins with the new PIN after it are
    untouched. A new-PIN sign-in inside the few milliseconds between the Auth update and `finish_pin_change` is also ended (the person signs
    in again); accepted.

## 4. Alternatives considered

- **Restrictive RLS policies on every table (the Supabase docs pattern)** — rejected: almost every write and many reads go through
  `security definer` procedures, which bypass RLS, so the policies would gate little; and a policy would have to be added (and never
  forgotten) on every table.
- **`require_aal2()` called in each procedure** — rejected as the main mechanism: about two hundred pinned procedures re-pinned, one
  forgotten call is a hole, and RLS reads stay open. Kept only for the MFA procedures (T-4).
- **Check only in `withApi` (M11 V9)** — rejected: anyone with the password can call the Data API directly with the public key; breaks
  "roles enforced in Postgres".
- **An `mfa_required` claim added by the access-token hook** (no RPC in `withApi`) — rejected: stale for up to `jwt_expiry` after a
  mode change or a reset, and it widens the change to the hook that guards PIN sessions. Cost of the choice: one RPC per request for an
  owner or admin who is not `aal2` (in practice, owners without a factor).
- **Gating inside the access-token hook (no tenant claims until `aal2`)** — rejected: the claims would be wrong until the next refresh
  after the challenge, and the hook's PIN branch (ADR-010) would share the risk.
- **Enforcement flag as an environment variable** — rejected: Postgres cannot read it, and it is per deployment, not per tenant.
- **Enforcement switch in the app (admin button)** — rejected: an attacker in a session could switch it off; the script keeps it with the
  founder and the secret key (scripts are allowed to use it, CLAUDE.md rule 2).
- **Reset by deleting rows of `auth.mfa_factors` from a definer** — rejected for the reason ADR-010 gives for the `auth` schema (managed by
  Supabase, unsupported) and because it would not end the target's sessions.
- **Recovery codes** — not offered by the documented API for our version (Q-T9); D2 chose the backup factor.
- **Phone/SMS factor** — rejected: an SMS provider (cost, a new processor) and phone numbers as new personal data.
- **Passkeys now (Q204)** — deferred (Q-T8): hosted availability and the client API are still unverified (ADR-029).
- **`otpauth` / `otplib` for the test helper** — rejected: a few lines of `node:crypto` with RFC vectors do the job (§3.9).
- **QR rendered by a library from the `otpauth://` URI** — rejected: a new dependency for something Supabase already returns.
- **`data:` images allowed on every page** — rejected for the path-scoped rule of T-12.

## 6. Risks and mitigations

- **Security / privacy**
  - *A gate bug locks the owner or admin out of everything.* The matrix (A1), the coverage scan (A2) and the integration run (A15) test
    it; the kill switch (`--mode off`, §3.7) restores access at the next query without a deploy.
  - *A definer that resolves the tenant without the three helpers escapes the gate.* A2's catalogue scan fails on any such function;
    `app.membership_ungated` is reference-scanned so only the MFA procedures use it.
  - *Direct attempts against Supabase Auth with a stolen password bypass the app lock (§3.6).* Bounded by Supabase's own limit; the
    per-account hook needs Teams/Enterprise. Revisit if the plan changes or evidence of guessing appears in Supabase's Auth logs.
  - *Shared Supabase limit for all server-side code checks* (Q-T7): a flood could briefly block code entry for everyone; accepted like
    ADR-029's sign-in bucket.
  - *A new admin, or an admin just reset, is forced to enrol: whoever has that password first could enrol their own authenticator.*
    The runbook says to create admins and to reset only after a phone call with the person, and to enrol at once; `required` is refused
    while an admin is unenrolled (T-3), which covers the rollout moment.
  - *Reset abuse:* there is no in-app reset (Q-T1 = V1); the script needs the secret key on the founder's machine and a named admin actor,
    signs the target out everywhere and is audited. The runbook says to confirm identity with the person by phone first.
  - *Lock DoS:* anyone with the password can type 5 wrong codes and block code entry for 15 minutes; the real user's existing `aal2`
    sessions keep working. Accepted.
  - *The secret on screen:* shown once, over HTTPS, `no-store`, never cached, never logged (AT-T10). The QR is an image from a `data:`
    URL on two pages only (B1).
  - *Factor enrolled but no audit row (crash between Supabase and the record call):* the record functions are idempotent and verify the
    factor in `auth.mfa_factors`; Supabase's own Auth audit log holds the event too. Accepted; reported as an error.
  - *Personal data:* new audit rows about owner/admin security events (Q-T2, V2). No IP, no device, no code, no secret, no free text.
    Supabase Auth stores the factor secret (Supabase is already a processor in DPA-1; no new processor).
  - *Secrets:* no new secret. The Supabase secret key stays in Vercel environment variables (server only) and on the founder's trusted
    machine for `scripts/`; the TOTP secrets live in Supabase Auth; the backup authenticator's secret lives where Q-T11 / Q26 decide (the
    account owner's password manager or a second phone), never in the repo or DigiAlto-Ops.
- **Performance / cost**
  - *Extra work in the membership helpers* for owner/admin queries (§3.2); compared on staging with the perf workflow before PR 1 is
    marked ready; no number promised. *One extra RPC per request* for owner/admin at `aal1` (T-5).
  - *E2E time:* up to 30 s per fresh TOTP step (at most four in the spec).
  - No new paid service; TOTP is free on Free (Supabase guide).
- **Dependencies:** none added (`tests/config/no-new-deps.test.ts` unchanged). `otpauth`, `otplib` considered and rejected (§3.9).
- **Supabase behaviour drift:** the §2.2 facts come from the docs source and the Auth server code on GitHub, not the hosted service;
  A15 and the staging steps (M-2, M-3) prove them on a real project; the Vercel egress IP must stay the same between challenge and verify
  inside one request (T-6), proved on staging (M-3).
