## 1. Goal and scope

- **Goal:** one command fills a fake but realistic osteria week, so every merged screen can be shown. One owner action or one command removes all of it before go-live, without weakening the ledgers of real tenants.
- **In scope:**
  - a `tenant.is_demo` flag that never changes, at most one demo tenant, and a service-role `create_demo_tenant`;
  - guards that allow DELETE only during a demo purge of a demo tenant;
  - `purge_demo_tenant` (owner, from the app) and `purge_demo_tenant_by_id` (script);
  - an audit log of every purge that outlives the tenant;
  - `scripts/demo/seed-demo.ts` (`--target local|staging`, `--reset`, `--purge`, `--cleanup`);
  - the manual workflow `.github/workflows/demo-staging.yml`;
  - the demo banner, the purge page and `POST /api/demo/purge`.
- **Out of scope:**
  - Menu, tables and orders (M17/M18): they join the demo later through §3.9;
  - demo data on production (Q90 → V3);
  - back-dating operations (A1).

## 3. Design

### 3.1 Decisions

1. **A separate demo tenant on staging.**
   - Name "Osteria Demo (dati di prova)", VAT `IT00000000099`, Europe/Rome.
   - `tenant.is_demo boolean not null default false`. It is set only by `create_demo_tenant`.
   - **The trigger `tenant_is_demo_guard` refuses any UPDATE that changes it, for every role.** A real tenant can never become purgeable, and the demo can never become "real".
   - At most one demo tenant: `create unique index tenant_one_demo_uq on public.tenant ((true)) where is_demo`.
   - The real tenant(s) on staging are never written. Every write of the seed is one of these:
     - a demo user's session (RLS pins it to the demo tenant);
     - a service-role function that checks `is_demo` first;
     - a cross-tenant job that the hourly or nightly cron runs anyway (`alert_rules_run`, `ledger_invariants_run`; both deduplicate).
2. **Data goes through the real procedures, as the right role.**
   - The seed signs in as each demo user and calls the same RPCs, or the same `src/server/<area>` service functions, that the routes call.
   - **Owner:** master data, invoices (review and approval), payables, recipes and versions, cost settings, reorder rules, staff, devices.
   - **Chef (real PIN flow):** productions, split, discard, adjust, staff meal, waste, transfer, manual use, daily count.
   - **Service role, three narrow exceptions:**
     - `create_demo_tenant` (tenant, owner and admin; there is no admin-creation procedure);
     - `demo_stage_invoice` (the worker's step, without Claude: decision 4);
     - `redeem_enrolment_code` and `pin_login_begin`/`finish`, which the device and PIN routes call with the secret key too.
   - No table is written with the secret key.
3. **Logins without secrets.** Each demo user gets a random password, held only in the process memory, so the seed can sign in. Nothing about it is logged.
   - At the end every password is replaced with a new random value that is thrown away, and every session is ended.
   - **Owner:** *(superseded by §0)* the Auth email is the fixed `titolare.demo@example.test`; nobody signs in with it.
   - **Admin:** "Supporto DigiAlto (demo)", `supporto.demo@osteria-demo.invalid`. It is visible in the staff list and cannot sign in.
   - **Chefs and waiters:** `staff-<id>@staff.invalid`, the M11 shape. The chef acts through the real PIN gate: `pin_login_begin` on the seed's own enrolled device, sign-in, then `pin_login_finish`.
     - **The pepper is not used:** the password is random, not derived from a PIN.
     - The founder sets each PIN on `/personale`, which derives the real password on the server, and enrols their own phone on `/dispositivi`.
   - **Output:** counts, the tenant id and the login identities only. The owner email is masked (`d***@g***.com`); the staff are listed by display name and role.
4. **Invoices without the extraction provider.** `public.demo_stage_invoice(p_tenant, p_invoice, p_file_path, p_file_size, p_created_by, p_result)` is service-role only. In **one transaction** it:
   - checks `app.tenant_is_demo(p_tenant)` (otherwise `not_demo_tenant`, 42501);
   - checks that `p_created_by` is an active owner of that tenant;
   - checks that the path is `<p_tenant>/<yyyy>/<p_invoice>.pdf`;
   - inserts the invoice as `received`, moves it to `extracting` with a claim token, and calls the real `public.extraction_complete(…, p_result, 'demo-seed')` (automap included).
   - The invoice is never visible as `received`, so the staging `extract-invoices` job can never claim it, and Claude is never called.
   - The PDF itself (a one-page fake, "FATTURA DI PROVA (demo) — senza valore fiscale") is uploaded first through the **owner's session**, with the M2 insert policy.
5. **Deletion design** (ADR-018).
   - `app.demo_purge_allows(p_tenant uuid) returns boolean` (stable, definer, closed to API roles) is true only when **both**:
     - `current_setting('app.demo_purge', true) = p_tenant::text`;
     - `exists (select 1 from public.tenant where id = p_tenant and is_demo)`.
   - The flag holds a tenant id, not "on", so a purge of tenant X can never delete a row of tenant Y.
   - `app.append_only()` and the four staff-auth guards gain one branch, before their existing logic: `tg_op = 'DELETE' and app.demo_purge_allows(old.tenant_id)` → `return old`. `append_only` reads the id with `(to_jsonb(old) ->> 'tenant_id')::uuid` (null → refused).
   - **Unchanged:**
     - UPDATE is still always refused;
     - the TRUNCATE triggers are untouched;
     - `app.auth_purge` keeps its exact meaning.
   - No API role gains DELETE.
   - The GUC is read first, so a real tenant's path costs no lookup.
6. **The purge** (`app.purge_demo_tenant_core(p_tenant, p_via, p_actor_auth)`, one transaction):
   1. Lock the tenant row `for update`, and refuse unless `is_demo`. A concurrent hourly alert insert waits on this lock and then fails its FK inside its own isolated rules block.
   2. Collect the `auth_id`s of the tenant's `app_user` rows, and count the rows per table (`app.demo_tenant_row_counts`).
   3. `set_config('app.demo_purge', p_tenant::text, true)`.
   4. Delete `where tenant_id = p_tenant` from every table of `app.demo_purge_tables()`, in its fixed child-first order (§3.2), plus `app.alert_refusal`.
      - The two reference cycles are each deleted in one statement with a data-modifying CTE, because NO ACTION foreign keys are checked at the end of the statement (T1): `venue_device` ↔ `device_enrolment`; `tenant` with `app_user` (`tenant.created_by`, `app_user.created_by`).
   5. Insert one row into `app.demo_purge_log (tenant_id, tenant_name, via, actor_auth, purged_at, row_counts, auth_ids, cleaned_at null)`. It is in schema `app`, has no FK, RLS on, no API privilege.
   6. Clear the flag. Return `{tenantId, rowCounts}`.
   - **App path:** `public.purge_demo_tenant(p_confirm_name text)`, `authenticated`. It checks the role first (owner only, otherwise 42501). The tenant comes from `app.tenant_id()`: not a demo → `not_demo_tenant` (42501); a name that is not exactly `tenant.name` → `confirm_name_mismatch` (P0001).
   - **Script path:** `public.purge_demo_tenant_by_id(p_tenant, p_confirm_name)`, service role, the same checks except the role.
   - **Afterwards (Auth and Storage).** Postgres cannot call the Auth or Storage APIs. The script's cleanup:
     - reads `public.demo_purge_pending()` (log rows with `cleaned_at` null);
     - **removes the Storage objects under `<tenant>/`** (Storage API, secret key), then **deletes the Auth users by the stored ids**. Objects go first, because an object may still name its Auth owner;
     - then calls `public.demo_purge_cleanup_done(p_log, p_auth_deleted, p_objects_deleted)`. That sets `cleaned_at`, nulls `auth_ids`, and deletes any `app.alert_refusal` row of that tenant written after the purge.
     - **The script purges first, then cleans up.** From the app, cleanup waits for DigiAlto's `--cleanup` (Q92 → V1).
     - Until cleanup, the leftover Auth users have no `app_user`, so the hook gives them no tenant and RLS answers nothing. The leftover PDFs match no tenant in any policy, and they hold no personal data.
7. **Audit.**
   - `create_demo_tenant` writes `audit_event` `tenant.demo_created` (entity `tenant`). That is the one new action; the check is the union of all 26 earlier values plus it.
   - The purge's own record must outlive the tenant: `audit_event.created_by` references `app_user`, which the purge deletes. So it goes to `app.demo_purge_log`, the same pattern as `app.job_run`.
8. **Dates relative to now, in Europe/Rome.**
   - `scripts/lib/demo/dates.ts`: `romeToday(now)` uses `Intl.DateTimeFormat('en-CA', {timeZone: 'Europe/Rome'})`; `addDays(isoDate, n)` does calendar arithmetic on the date, never adds milliseconds.
   - Every fixture date is an offset from `D` = Rome today. The demo looks current on any day it is seeded.
9. **Re-running.** `demo_tenant_status()` (service role) returns `{exists, tenantId, name, createdAt}`.
   - Seed with a demo present → **refuse**, exit 1, "esiste già: usa --reset".
   - `--reset` = script purge + cleanup + seed.
   - If seeding fails, the script **purges the tenant it created in this run** (by id; never another run's) and exits 1.
   - Two parallel seeds: the second fails on `tenant_one_demo_uq` and deletes nothing.
10. **Personal data (GDPR).**
    - The only real personal data is the founder's own login address, in staging Auth, removed at cleanup.
    - PIN attempts and sessions of demo users live in the demo tenant and are purged.
    - Logs and outputs hold counts, ids and codes only.
    - No new processor: Supabase EU only; Claude is not called.
    - Retention of `app.demo_purge_log`: Q96.

## 4. Alternatives considered

- **Demo rows inside the real tenant, tagged `is_demo` per row:** rejected. Every table, read, report and ledger would need the tag, and a missed one mixes fake and real numbers. The tenant boundary already isolates everything.
- **`session_replication_role = replica`, or disabling triggers during the purge:** rejected. It switches off every guard and FK for the transaction (also for other tenants' rows the code might touch), it needs privileges the hosted `postgres` role may not have (project T3), and it is invisible to pgTAP. A per-tenant flag inside each guard is narrow and testable.
- **A flag that is just "on" (like `app.auth_purge`):** rejected. With "on", a bug in the purge's WHERE clause could delete another tenant's ledger. A tenant id bound to `is_demo` cannot.
- **Raw SQL inserts (a big `seed.sql`):** rejected. They bypass the procedures, so balances, frozen costs and audit could disagree, which the nightly check would flag. They also break whenever a procedure changes.
- **Passwords printed in the job summary:** rejected. Summaries are visible to every repo collaborator and kept for months. The magic link and PINs set on the users screen need no secret output.
- **The app's purge route also deleting Auth users and Storage with the secret key:** rejected for now. It needs a second exception to ground rule 2 (CLAUDE.md), which only the founder can grant → V1.
- **Back-dating operations with an injectable clock in the procedures:** rejected. It would change every write procedure and weaken "costs frozen at the time of the operation" (A1).
- **Using `extraction_claim` for demo invoices:** rejected. It claims the oldest due invoice of any tenant, so on staging it could take a real tenant's invoice.

## 6. Risks and mitigations

- **Security / privacy**
  - *Real data reset by mistake (§0):* the marker `demo_data_since` is set only by `begin_demo_data` on a tenant that holds no operational data and can never change any other way, not even on INSERT (1); every reset path checks it under a row lock and clears it (4); the guards check the setting's tenant id and the marker (2); pgTAP proves that other tenants are untouched, that a cleared marker can never be purged again, and that users, sessions and devices that are not the demo's survive (2, 4). *Superseded text below still says `is_demo`.*
  - *The guard branch abused:* no API role has DELETE; the GUC alone does nothing for a real tenant; `demo_purge_allows` is closed to API roles (2, 5).
  - *Seeding the wrong project:* local by default; staging needs an opt-in and the exact host, in both the script and the workflow (6, 15); any other hosted project is refused.
  - *Secrets in logs:* random passwords live in memory only and are rotated at the end; the output is scanned in tests (6, 8); the workflow pins the secret references (15); the pepper and the Claude key are not used.
  - *Workflow input injection:* the input goes through an env variable and a fixed `case` (15).
  - *Personal data:* only the founder's own address, masked in the output and removed at cleanup; no processor added; demo login logs are purged with the tenant.
  - *Purge from the app:* owner only, role checked before the RPC and in SQL, the name typed by hand, JSON only (CSRF), recorded in `app.demo_purge_log`.
- **Correctness**
  - *A future table or guard forgotten by the purge:* `194` and `196` fail (§3.9).
  - *The nightly check sees drift:* every write goes through the procedures; the seed runs `ledger_invariants_run` and fails on `ledger_drift` (11).
  - *A half-seeded tenant:* auto-purge of this run's tenant (8).
  - *An hourly run during the purge:* it waits on the tenant lock, then fails inside its isolated block; cleanup removes the late refusal row (4).
  - *Cross-tenant jobs run by the seed:* the same functions the cron runs, deduplicated per day; no new job.
- **Unverified (proved in the named step):**
  - **T1** NO ACTION foreign keys are checked at the end of the statement, so a data-modifying CTE can delete both rows of a reference cycle ([PostgreSQL: CREATE TABLE, "NO ACTION … check is deferred until the end of the statement"](https://www.postgresql.org/docs/current/sql-createtable.html); [WITH queries, data-modifying statements](https://www.postgresql.org/docs/current/queries-with.html)). Proved in `193` (step 4).
  - **T2** Supabase Storage objects are removed through the Storage API, not by SQL on `storage.objects`; the design never deletes them in SQL. Proved in `demo-data.int.ts` (step 11).
- **Performance / cost:** one purge of a small tenant. No promised figure, no new job, no provider. GitHub minutes: §8 fallback (Q95).
- **Dependencies:** none added.

### Running the demo (for the founder)

The demo runs from the Actions tab or, while Actions minutes are exhausted (Q95), from a trusted machine. Either way the demo data is written into the tenant you name, and only while that tenant holds no data. Your own account, every existing user and every other tenant are never read or changed.

**With Actions (when there are minutes).** Actions, "Demo data on staging", Run workflow on `main`, pick `seed`, `reset`, `purge` or `cleanup`. The `staging` environment holds four secrets: `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY`, `SUPABASE_SECRET_KEY` and `DEMO_TENANT_ID` (the uuid of your tenant; not needed for `cleanup`). The run form has only the action: the tenant id is never typed into a form, because the inputs of a run on a public repository are shown with it. The run stops if a secret is missing, if the URL is not the staging project or if the tenant id is not a uuid. GitHub masks the secret in the log. The result line is in the job summary.

**By hand (the fallback), from a trusted machine, on a clean checkout of `main`:**

1. Open your own terminal in the project folder and run `npm ci`.
2. Put the values into your own shell. Type them yourself or read them from your password manager. Never paste a key into chat, a file, a ticket or a command line:
   - `export NEXT_PUBLIC_SUPABASE_URL=https://wjowhjsfpcdykxwgjipq.supabase.co`
   - `read -rs NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY; export NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`
   - `read -rs SUPABASE_SECRET_KEY; export SUPABASE_SECRET_KEY`
   - `read -r DEMO_TENANT_ID; export DEMO_TENANT_ID` (the uuid of your tenant, typed by you)
   - `export DEMO_STAGING_OK=yes`
3. Run one of:
   - `npm run demo -- --target staging --tenant "$DEMO_TENANT_ID"` to fill the tenant with demo data (it refuses a tenant that already holds data, real or demo; `--force` skips only the script's own check, the database still refuses);
   - `npm run demo -- --target staging --tenant "$DEMO_TENANT_ID" --reset` to reset the demo data (it must carry the demo marker) and fill it again;
   - `npm run demo -- --target staging --tenant "$DEMO_TENANT_ID" --purge` to reset it, then remove the demo logins and fake PDFs;
   - `npm run demo -- --target staging --cleanup` to finish the login and PDF removal after you pressed "Elimina dati di prova" in the app (no tenant needed).
4. The script prints one line of counts and masked names, no password, PIN or key. Check it says `"ok":true`.
5. Close the shell, or run `unset NEXT_PUBLIC_SUPABASE_URL NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY SUPABASE_SECRET_KEY DEMO_TENANT_ID DEMO_STAGING_OK`.
