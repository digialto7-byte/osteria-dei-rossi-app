## 3. Design

### 3.1 Decisions

1. **CSP (ADR-028): static, no nonce, pre-rendering kept.**
   - `buildCsp({ supabaseOrigin, deployment, dev })` (`src/lib/security/csp.ts`) returns:

     ```
     default-src 'self'; script-src 'self' 'unsafe-inline'; style-src 'self' 'unsafe-inline';
     img-src 'self' <supabase>; frame-src <supabase>; font-src 'self'; connect-src 'self';
     worker-src 'self'; manifest-src 'self'; object-src 'none'; base-uri 'self'; form-action 'self';
     frame-ancestors 'none'[; upgrade-insecure-requests]
     ```

     - `'unsafe-eval'` is added to `script-src` only when `next.config.ts` runs in `PHASE_DEVELOPMENT_SERVER` (`next dev`). The CI server is `next start`, so it gets none.
     - `upgrade-insecure-requests` is added only for production and preview builds.
     - `<supabase>` is the origin of `NEXT_PUBLIC_SUPABASE_URL`, which each environment's build already has.
   - `securityHeaders(deployment, { supabaseOrigin, dev })` sends it on `/:path*`, next to `nosniff`, `Referrer-Policy`, `X-Frame-Options: DENY` and HSTS (production).
   - **Why `'unsafe-inline'` stays in `script-src`:**
     - Next.js's inline flight scripts carry each page's data, so they differ per page and per build;
     - a header fixed at build cannot hash them;
     - and adding any hash makes browsers ignore `'unsafe-inline'`.
   - **What still limits the residual risk:**
     - React escaping, plus guards forbidding raw-HTML sinks in `src/` (step 2);
     - no external script origin;
     - exfiltration narrowed (`connect-src 'self'`, `img-src` and `frame-src` = self and Supabase, `form-action 'self'`);
     - `HttpOnly` cookies;
     - `object-src 'none'`, `base-uri 'self'`, `frame-ancestors 'none'`.

     A top-level navigation cannot be blocked by any CSP.
   - **Pre-rendering:** the route list in `.next/prerender-manifest.json` after a build equals the list captured from `0f1df68` (step 4, T2).
2. **Header check (AT2).**
   - `checkHeaders(replies, expect)` (`src/lib/security/header-check.ts`) checks `GET /login`, `GET /api/health` and `GET /sw.js`. All three must have:
     - `nosniff`;
     - `Referrer-Policy: strict-origin-when-cross-origin`;
     - `X-Frame-Options: DENY`;
     - a CSP with `default-src 'self'`, `object-src 'none'`, `base-uri 'self'`, `form-action 'self'`, `frame-ancestors 'none'` and `connect-src 'self'`;
     - **no `'unsafe-eval'`** and **no origin other than `'self'`** in `script-src`.
   - `'unsafe-inline'` in `script-src` is accepted and reported as `note: unsafe-inline (ADR-028)`, not as a failure.
   - HSTS (`max-age` ≥ 31 536 000 and `includeSubDomains`) is required only for `--expect production`.
   - `scripts/check-headers.ts`:
     - `https` only, except localhost;
     - `redirect: "manual"`;
     - sends `x-vercel-protection-bypass` from `VERCEL_AUTOMATION_BYPASS_SECRET` when set (T8);
     - prints one JSON line with header names only;
     - exit code 1 on a finding.
3. **Audit gate (AT3).** As in the first version:
   - `npm audit --json`;
   - a high or critical advisory that is not excepted fails;
   - exceptions in `docs/go-live/audit-exceptions.json` carry a reason and a review date;
   - stale or expired exceptions fail;
   - it replaces `npm audit --omit=dev --audit-level=high` in the `checks` job.
4. **Rate-limit review.**
   - `docs/go-live/rate-limits.md` has one row per sensitive route and for `warm-reads`, each with a verdict `ok` or `accepted` and a reason.
   - Hosted Supabase Auth limits are read by the founder (§8).
   - Nothing changes by default.
5. **Backups (AT4; Q181–Q185, Q195 answered).**
   1. **Daily dump** (`backup-daily.yml`, cron `15 2 * * *` UTC = 03:15 CET / 04:15 CEST):
      - It runs after the 02:00 Europe/Rome cut-off (01:00 UTC in winter, 00:00 UTC in summer) and after `kpi-rollup` has finalised the day.
      - It runs before `ledger-invariants` (02:45 UTC) and `auth-purge` (03:30 UTC).
      - Steps:
        1. secrets and host guards;
        2. `npm ci`;
        3. `supabase db dump --db-url "$SUPABASE_DB_URL"` three times: `--role-only`, schema, `--data-only --use-copy` (T3);
        4. `manifest.json` (migrations, table counts);
        5. `tar`;
        6. `gpg --batch --pinentry-mode loopback --symmetric --cipher-algo AES256 --passphrase-fd 0` (passphrase on stdin, ≥ 32 characters, T4);
        7. SHA-256;
        8. Drive resumable upload with MD5 verification into the Shared Drive folder through the service account (T5);
        9. retention: keep the newest **14** `osteria-backup-*-<target>.tar.gpg` (`vars.BACKUP_KEEP_COPIES`, default 14);
        10. **keep-alive ping** `GET <SUPABASE_URL>/auth/v1/health` with the publishable key (§3.1.7, T12);
        11. `if: always()` clean-up of `$RUNNER_TEMP/backup`;
        12. **`if: failure()`**: create or comment on a GitHub issue labelled `backup-failure` with the run link only (`GITHUB_TOKEN`, `issues: write`, the `gh` CLI that ships on the runner).
   2. **Weekly restore check** (`backup-restore-weekly.yml`, cron `0 4 * * 1` UTC = Monday 05:00 CET / 06:00 CEST). It touches only Drive and the runner, never production, so any quiet hour works; it runs after Monday's dump. Steps:
      1. download the **newest** production copy from Drive and verify its MD5;
      2. decrypt;
      3. start an **empty** local stack (temporary workdir: `config.toml` only, no migrations, no seed);
      4. `psql --single-transaction -v ON_ERROR_STOP=1`: roles, schema, `set session_replication_role = replica`, data;
      5. in the same transaction, `delete from cron.job` and the removal of the Vault secrets `app_base_url` and `cron_secret` (T11).

      It passes when:
      - (a) `app.ledger_checks_body` returns no row for any tenant (A2);
      - (b) the counts equal the manifest's;
      - (c) the migrations equal the manifest's;
      - (d) `cron.job` is empty;
      - and the newest copy is younger than 36 hours. This proves that the daily job ran, and gives a second pause signal.

      On failure it opens the same `backup-failure` issue.
   3. **Self-test** (`backup-selftest.yml`): local stack plus demo data, a fake passphrase, dump → encrypt → stop → empty stack → decrypt → restore → checks (a)–(d). No secret and no upload. It runs on ready PRs and `main` pushes touching `scripts/backup/**`, `scripts/lib/backup/**`, `supabase/migrations/**` or `.github/workflows/backup-*.yml`, and by hand.

Secrets: `SUPABASE_DB_URL`, `BACKUP_ENCRYPTION_PASSPHRASE`, `BACKUP_DRIVE_SA_JSON`, `BACKUP_DRIVE_FOLDER_ID`, `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY`.    - **The fact:** Supabase pauses Free projects after a period of inactivity (one week in Supabase's documentation as far as known; not re-checked from this session, T13). A paused project serves nothing: the app fails and pg_cron stops.
   - **What keeps it active, and how sure:**

     | Source | When | Certainty |

     | Daily backup: a database connection through the pooler, plus `GET /auth/v1/health` | every day, 03:15/04:15 Rome | **Likely, not verified** (T12): whether these count as "activity" is not documented in what this session could read |
     | pg_cron jobs (internal SQL) | continuous | **Not counted on**: they run inside the database, with no external request |

     So a closure longer than a week (holidays) relies on the backup job alone (Q196).
   - **Detection:**
     1. the daily run fails at the dump or the ping, which opens a `backup-failure` issue (the founder watches the repo's issues, §8);
     2. the weekly restore fails its 36-hour freshness check;
     3. staff cannot sign in;
     4. the dashboard shows the project as paused.

     GitHub's own e-mails for failed scheduled runs go to the user who last changed the cron line, which may not be the founder (T13). That is why an issue is opened.

     1. Supabase dashboard → the project → resume/restore (wait until healthy);
     2. sign in as the owner;
     3. run "Daily backup" by hand;
     4. expect a `job_stale` line in the next `ledger_drift` alert, because jobs did not run while paused;
     5. tell staff to reopen the app so queued ops replay.

     Rehearsed once on staging before go-live (checklist).

9. **CI and backup minutes (Q180 answered "B", Q195).**
   - **Baseline (lead):** heavy job B ≈ 23 min, Playwright P ≈ 16–18, the rest O = B − P ≈ 5–7 (npm ci, stack start, pgTAP, integration, build, browser install).
   - **S** = the simulation's time (measured in step 17).
   - **X** = what shard 2 repeats: npm ci, stack start, `psql` check, build, browser install. X ≤ O, because X has no pgTAP and no integration.
   - **The sharded `supabase` job** (step 18): matrix `shard: [1, 2]`, `fail-fast: true`, each `timeout-minutes: 30`.
     - **Shard 1:** start → pgTAP → integration → build → `--shard=1/2`.
     - **Shard 2:** start → build → `--shard=2/2`.
     - **pgTAP and integration run once, in shard 1, before its Playwright half (today's order).**
     - Each shard builds for itself: the build inlines that runner's local Supabase settings, and passing `.next` between jobs as an artifact would cost upload and download minutes.
     - `fail-fast: true` cancels the other shard when one fails. A pgTAP failure in shard 1 therefore also stops shard 2 (minutes saved).
   - **Billed minutes per heavy run:** **23 + S + X ≤ 28–30 + S** (+ up to 1 rounding minute per job). This is the `supabase` part; `db-races` and `t1-spike` are unchanged.
   - **Wall time:** max(shard 1, shard 2):
     - with an even split, shard 1 ≈ O + (P + S)/2 ≈ 13–16 + S/2 and shard 2 ≈ X + (P + S)/2;
     - worst case, the whole simulation in shard 1: ≈ 13–16 + S, still under 30 while S < 14.
     - Step 18 records both shards' times. **If either exceeds 25 minutes, the PR says so and asks the founder before any further CI change.**
   - **Backups (estimates for budgeting, to be measured on the first runs in steps 13 and 14; not promises):**

     | Job | Per run | Runs | Per month |
     |---|---|---|---|
     | Daily backup (npm ci, a Postgres image pull, 3 dumps, gpg, upload, ping; rounded up) | **≈ 2–4 min** | 1 per day | ≈ 60–124 |

     | **Total backups** | **≈ 2–4 min per day on six days, ≈ 7–11 on Mondays** | | **≈ 80–160** |

1. **Page request:** Vercel serves the pre-rendered page (or renders it) with the static headers from `next.config.ts`. The proxy only refreshes the session.
2. **Daily (02:15 UTC):**
   1. `backup` job (`production-backup`);
   2. guards;
   3. `npm ci`;
   4. dump → manifest → tar → gpg → SHA-256;
   5. Drive upload with MD5 check, retention 14;
   6. keep-alive ping;
   7. clean-up;
   8. on failure, an issue.
3. **Weekly (Monday 04:00 UTC):**
   1. `restore` job;
   2. Drive: newest copy, age ≤ 36 h, MD5;
   3. decrypt → empty stack → restore → checks (a)–(d);
   4. summary (names and counts only);
   5. clean-up and `supabase stop --no-backup`;
   6. on failure, an issue.
4. **Release:**
   1. merge → CI → staging migrations;
   2. the founder runs `deploy-production` (approval);
   3. the founder promotes the Vercel deployment (T9);
   4. header check on production.

## 4. Alternatives considered

- **A per-request nonce CSP (first version):** rejected by the founder to keep pre-rendering (ADR-028).
- **Hashes in a static CSP:** impossible for Next.js's per-page flight scripts, and any hash disables `'unsafe-inline'` (ADR-028).
- **`require-trusted-types-for 'script'`:** not verified with Next.js 16 and React 19, and needs reporting to trial (ADR-028).
- **CI options A (timeout 40), C (two workers), D (own job):** the founder chose B. C is unsafe today: a shared sign-in budget (`supabase/config.toml` lines 212, 214) and specs that run cross-tenant jobs (`alert-rules`, `reports`, `dashboard`, `exports`, `push-forecast`, `demo-data`, `seed-order` helpers).
- **Shards sharing one build through an artifact:** rejected. The build inlines each runner's local Supabase settings, and the upload and download cost minutes.
- **pgTAP and integration in a separate job before the shards (`needs:`):** rejected. It costs one more `npm ci` + `supabase start` per run (more minutes) for the same order. `fail-fast` already stops shard 2 when shard 1's database tests fail.
- **A restore check inside the daily job:** rejected. It is weekly by the founder's answer, and a separate job that downloads from Drive also proves the real recovery path (download + MD5).
- **Supabase Pro daily backups:** not chosen (Q187, Free).
- **`googleapis`, `rclone`, `age`, plain `pg_dump`, GitHub artifacts, Workload Identity Federation:** rejected as in the first version (no new dependency; version match; no production data in artifacts).
- **A keep-alive through a scheduled call to the app:** rejected. `/api/health` does not touch Supabase. The backup job already connects every day, and it pings Auth directly.
- **`public.ledger_invariants_run()` for "clean":** rejected. It writes and includes environment-dependent job health (A2).

## 6. Risks and mitigations

- **Security and privacy**
  - **`script-src 'unsafe-inline'` (ADR-028):**
    - an HTML-injection bug would let inline script run;
    - mitigated by React escaping and the raw-HTML guard (2);
    - no external script origin;
    - narrowed exfiltration (`connect-src`, `img-src`, `frame-src`, `form-action`);
    - `HttpOnly` cookies.

    Recorded as an accepted risk in the walk (20).
  - *The CSP breaking a flow:* every spec runs under it; violation collectors in 4 and 17; the invoice iframe covered (4); the founder checks preview first (§8).

    - AES-256 with a passphrase only the founder holds (Q181);
