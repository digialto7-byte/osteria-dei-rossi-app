## 3. Design

### 3.1 Decisions

1. **CSP (ADR-028).**
   - `buildCsp` (`src/lib/security/csp.ts`) is called in `updateSession` for every proxied request.
   - The nonce is `newNonce()`: 16 bytes from `crypto.getRandomValues`, base64.
   - `'unsafe-eval'` is added only when `process.env.NODE_ENV === "development"` (`next dev`). It never depends on `deployment`: the CI server is a production build with `VERCEL_ENV` unset.
   - `upgrade-insecure-requests` is added only when `deployment` is `production` or `preview`. On `http://localhost` it would rewrite the local Storage URLs.
   - The root layout calls `await connection()` (`next/server`), so it renders per request (T1).
2. **Static headers.**
   - `securityHeaders()` drops `Content-Security-Policy`.
   - It keeps `nosniff`, `Referrer-Policy`, `X-Frame-Options: DENY` (framing protection on the paths the proxy skips), and HSTS on production (`max-age=63072000; includeSubDomains`, no `preload`, Q191).
3. **Header check (AT2).**
   - `src/lib/security/header-check.ts` is pure. `checkHeaders(responses, expect)` takes the replies of `GET /login`, `GET /api/health` and `GET /sw.js` and returns findings.
   - **Required on every reply:** `nosniff`; `Referrer-Policy: strict-origin-when-cross-origin`; `X-Frame-Options: DENY`.
   - **Required on `/login` and `/api/health`:** a CSP with `default-src`, a nonce in `script-src`, no `'unsafe-inline'` in `script-src`, `object-src 'none'`, `base-uri 'self'`, `frame-ancestors 'none'`, `worker-src 'self'` and `manifest-src 'self'`.
   - **HSTS is required only when `expect === "production"`:** `max-age` ≥ 31 536 000 and `includeSubDomains`. On `preview` and `local` it is not asserted either way, because Vercel may add its own on `*.vercel.app` (not verified).
   - **`scripts/check-headers.ts --base-url <url> --expect local|preview|production`:**
     - `https` only, except for `localhost`/`127.0.0.1`;
     - `redirect: "manual"`;
     - sends `x-vercel-protection-bypass` only when `VERCEL_AUTOMATION_BYPASS_SECRET` is set (T8);
     - prints one JSON line `{ ok, findings: [{ path, header, problem }] }` with header **names** only, never the bypass value;
     - exit code 1 on any finding.
4. **Audit gate (AT3).**
   - `scripts/audit-check.ts` runs `npm audit --json` (argument list, no shell) and reads the `vulnerabilities` map.
   - It fails on every `high` or `critical` entry (dev or runtime) that is not in `docs/go-live/audit-exceptions.json`.
   - Each exception is `{ advisory, package, severity, devOnly, reason, reviewBy }`. It fails when `reviewBy` is past, when `reason` is empty, or when the exception matches nothing (stale).
   - The `checks` job runs it instead of `npm audit --omit=dev --audit-level=high`.
   - A high advisory with a fix inside the same major version is fixed in step 6 by a lockfile update. The dependency names do not change, so `no-new-deps.test.ts` stays green unchanged.
5. **Rate-limit review.**
   - `docs/go-live/rate-limits.md` has one row per sensitive route: auth, devices, enrolment, upload, extraction retry, sync, cron. Plus the SW `warm-reads` message.
   - Columns: limit, where it is enforced, the test that proves it, verdict (`ok` or `accepted`), reason.
   - Hosted Supabase Auth limits are a founder step (§8), because they live in the dashboard.
   - No limit is changed by default. A route the review finds unbounded on a paid call (the extraction retry) gets the verdict and its reason. If the reason is not acceptable, it goes to the PR's open questions.
6. **Backups (AT4, project plan §3.9, Q27 → Q181–Q186).**
   1. **Dump** (`scripts/lib/backup/commands.ts`), with the existing Supabase CLI dev dependency, so `pg_dump`'s version matches the server (T3):
      - `supabase db dump --db-url <url> -f roles.sql --role-only`;
      - `-f schema.sql`;
      - `-f data.sql --data-only --use-copy`.
      - The URL comes from `SUPABASE_DB_URL` (the session-pooler connection string, T6). It is an argument of the CLI call, but it never appears in a log line: the runner masks the secret, and every script message passes through `redact()`.
   2. **Manifest:** `manifest.json` = `{ createdAt, migrations: [names], counts: { "<schema>.<table>": n } }`, for `public` and `app` tables and `auth.users`. Names and integers only.
   3. **Archive and encryption:**
      - `tar` of the four files;
      - `gpg --batch --yes --pinentry-mode loopback --symmetric --cipher-algo AES256 --passphrase-fd 0 -o osteria-backup-<YYYY-MM-DD>-<target>.tar.gpg`;
      - the passphrase arrives on **stdin**, never in argv, and must be ≥ 32 characters;
      - the SHA-256 of the encrypted file goes to the job summary.
   4. **Upload** (`scripts/lib/backup/drive.ts`, Node `crypto` + `fetch`, no Google library):
      1. a service-account JWT (RS256, scope `drive.file`) is exchanged for a token;
      2. a resumable upload goes to `BACKUP_DRIVE_FOLDER_ID` (`supportsAllDrives=true`);
      3. the `md5Checksum` returned is compared with the local MD5;
      4. retention: files named `osteria-backup-*-<target>.tar.gpg` beyond the newest `BACKUP_KEEP` (default 8, Q182) are deleted. No other file is touched.

      Drive behaviour is T5.
   5. **Restore check** (`scripts/backup/restore-check.ts`, the same in the self-test and the weekly run):
      1. decrypt **the encrypted file that was uploaded** (not the clear dump);
      2. start an **empty** local stack from a temporary workdir: a copy of `supabase/config.toml`, no migrations, no seed;
      3. `psql --single-transaction -v ON_ERROR_STOP=1` with `roles.sql`, `schema.sql`, `set session_replication_role = replica`, `data.sql`;
      4. in the same transaction, `delete from cron.job` and the removal of the Vault secrets `app_base_url` and `cron_secret`, so a restored copy can never call the app (T11).

      It passes when:
      - (a) `select t.id, b.check_key, b.rows_count from public.tenant t cross join lateral app.ledger_checks_body(t.id, now()) b` returns **no rows** (the ledger part of `check_ledger_invariants`; job-health findings depend on the environment, A2);
      - (b) the restored counts equal the manifest's;
      - (c) the restored migration list equals the manifest's;
      - (d) `cron.job` is empty.

      The target URL must pass `assertLocalDbUrl`.
   6. **Where it runs:**
      - `backup-selftest.yml`: the local stack with demo data and a fake passphrase. No secret, no upload. It runs on ready PRs and pushes to `main` that touch `scripts/backup/**`, `scripts/lib/backup/**`, `supabase/migrations/**` or the backup workflows, and by hand.
      - `backup-weekly.yml`: production on a schedule (Monday 03:30 UTC, Q195); staging or production by hand from `main`. Real secrets, upload, retention and the restore check every run (Q183).
   7. **Clear text** lives only under `$RUNNER_TEMP/backup` and is removed by an `if: always()` step, followed by `supabase stop --no-backup`. No backup ever goes to a GitHub artifact.
7. **Production migrations.**
   - `deploy-production.yml` runs only by hand, only from `main`, in the GitHub environment `production` (required reviewer: the founder). It does a `supabase db push --dry-run`, then `--yes`.
   - It refuses when:
     - `vars.PRODUCTION_PROJECT_REF` is unset;
     - the secret `SUPABASE_PROJECT_REF` differs from it;
     - the ref equals the staging ref.
   - The release order (Q190) is in the runbook: migrations first, then promote the Vercel deployment.
8. **Service simulation (AT1).**
   - `e2e/simulation/service.spec.ts` is one test in project `service-sim`: Chromium Pixel 7 at 360 × 740, service workers allowed (the offline helpers need them).
   - It runs in stages (`test.step`, so the report gives each stage's time and S). The full test is in §5 step 15.
   - **Actors:** owner, chef, waiter A "Cameriere Demo", waiter B "Cameriere Due Demo", each in its own context. Everyone signs in by magic link (A1).
   - **Stages:**
     1. invoices approved on screen;
     2. one batch produced on screen and one through the chef's API;
     3. 6 tables × 3 courses: waiter A has tables 1–3, waiter B has 4–6. Waiter B is offline for the whole second course: ops are queued, the kitchen does not see them, then they replay with every result `applied`;
     4. tables closed, Tavolo 6 without a receipt number;
     5. day close;
     6. KPIs and app vs register, from the API and on screen;
     7. ledger checks clean for the tenant;
     8. portion and stock balances equal produced − sold;
     9. **zero CSP violations in all four contexts.**
   - **Dates** come from `GET /api/tables` `businessDate` (house lesson).
9. **CI budget (Q180).**
   - **Baseline (lead's figures):** the heavy `supabase` job takes **B ≈ 23 min**, of which Playwright is **P ≈ 16–18 min**. So everything else in it (npm ci, stack start, pgTAP, integration, build, browser install) is **O = B − P ≈ 5–7 min**.
   - **S** = the simulation's own run time, measured in step 15 from the Playwright report. It is unknown today.
   - Billed minutes are per job, and GitHub rounds each job up to a whole minute (GitHub billing documentation, not re-checked from this session). `db-races` and `t1-spike` are unchanged in every option.

   | Option | What changes | Billed minutes per heavy run (heavy `supabase` part only) | Wall time of that part | Risks / work |
   |---|---|---|---|---|
   | **A. Raise `timeout-minutes` to 40 (default)** | The simulation is its own Playwright project inside today's job | **23 + S** | 23 + S | Slowest feedback. A failure anywhere still reruns everything. The 40 cap is checked against the measured run (step 16) |
   | **B. Shard Playwright across N jobs** (`--shard i/N`); each repeats `npm ci`, `supabase start`, build and browser install; pgTAP and integration stay in shard 1 | Per shard the repeated set ≤ O | **≤ 23 + (N − 1)·O + S**: N = 2 → **≤ 28–30 + S**; N = 3 → **≤ 33–37 + S** (+ up to 1 rounding minute per job) | ≈ O + (P + S)/N if the split is even: N = 2 → ≈ 13–16 + S/2 | Most minutes. Each shard has its own stack, so no shared-state risk |
   | **C. Two workers in one job** | `workers: 2` | Between **O + (P + S)/2 ≈ 13–16 + S/2** (perfect 2×) and **23 + S** (no gain). Unknown until measured: private-repo runners are documented with 2 vCPUs (not re-checked), shared by Next, the Supabase containers and two browsers | Same as the minutes | **Not parallel-safe today** (§3.1.9.1). Needs V3's work first |
   | **D. The simulation in its own job** (`service-simulation`, heavy gate) | New job: `npm ci`, `supabase start`, build, Chromium only, `--project service-sim`; the old job runs the other projects | **23 + O′ + S, with O′ ≤ O → ≤ 28–30 + S** | max(23, O′ + S) | Isolated stack (own GoTrue budget, clean DB). One more job to maintain. The `ci-budget` and Playwright-install pins change (V1) |

   - **Illustration only, with an assumed S = 5 min (not a measurement or a promise):** A 28 · B(2) ≤ 33–35 · C 18.5–28 · D ≤ 33–35.
   - **Default: A.** It adds the fewest minutes: the founder's 2026-10-24 rule is no extra spend.
   - **Separately,** `backup-selftest.yml` costs **R** minutes per ready PR or `main` push that touches backups or migrations, not per heavy run. R covers npm ci, stack start, demo seed, dump, stack stop, empty stack start, restore and check. It is measured on its first run in step 10. The weekly backup costs about the same, **W**, once a week.

   - **Shared GoTrue budget.** All workers sign in from `127.0.0.1`, and the local limits are `sign_in_sign_ups = 30` and `token_verifications = 30` per 5 minutes per IP (`supabase/config.toml` lines 212, 214). Two workers double the sign-in rate.

A worker could see the other's job runs and alerts.

### 3.3 Sequence of calls

1. **Page request** → `proxy` → `updateSession`:
   1. nonce;
   2. request headers `x-nonce` and `content-security-policy`;
   3. `getClaims()`;
   4. response (or redirect) with the CSP.

   Then `next.config` adds `nosniff`, `Referrer-Policy`, `X-Frame-Options` and HSTS on production. Next.js renders dynamically and puts the nonce on its inline scripts (T1).
2. **Weekly backup (production):**
   1. schedule → `backup` job (environment `production-backup`, `main` only);
   2. secrets guard and host guard;
   3. `npm ci` (no secrets);
   4. dump → manifest → tar → gpg → SHA-256;
   5. Drive upload, MD5 verify, retention;
   6. decrypt the encrypted file → empty local stack → restore → checks (a)–(d);
   7. summary: file name, size, SHA-256, counts, result;
   8. `always()`: remove `$RUNNER_TEMP/backup`, `supabase stop --no-backup`.
3. **Release (after go-live, runbook):**
   1. merge → CI green → staging migrations (existing);
   2. the founder runs `deploy-production` (reviewer approval) → migrations on production;
   3. the founder promotes the Vercel deployment (Q190, T9);
   4. header check against production.

## 4. Alternatives considered

- **CSP:** a static `'unsafe-inline'` policy, experimental hashes, per-route policies, or a report-only phase. All rejected in ADR-028.
- **The `googleapis` library (Apache-2.0) for the Drive upload:** rejected. It is a large dependency for three HTTP calls, and M10 (where the project plan put it) is deferred. Node's `crypto` signs the JWT; `fetch` does the rest.
- **`rclone` in the workflow for the upload:** rejected. It is a new tool installed at run time (a supply-chain surface), and its service-account quota behaviour is the same as the API's.
- **`age` instead of `gpg`:** rejected for now. `age` is not on the runner image and would be installed at run time (apt). `gpg` symmetric AES-256 with a passphrase matches the project plan's `BACKUP_ENCRYPTION_PASSPHRASE` and is pre-installed (T4).
- **Plain `pg_dump` from the runner's PostgreSQL client:** rejected. Its major version may not match the server's. The Supabase CLI runs a matching `pg_dump` in Docker and handles Supabase's managed schemas (T3).
- **Keeping backups as GitHub Actions artifacts:** rejected. They would be production data at GitHub with a 90-day cap, and they do not answer Q27.
- **Workload Identity Federation instead of a service-account key:** not the default. It needs a GCP identity pool and a third-party action (`google-github-actions/auth`). The key is scoped to one folder and rotatable (runbook). It is a fair upgrade later.
- **Restore check only in the self-test (no weekly restore of real data):** not the default. A dump that does not restore is only found when it is needed. Monthly instead of weekly is V4 (Q183).
- **Running `public.ledger_invariants_run()` for "invariants clean":** rejected for the checks. It writes `job_run` and alerts and includes job-health findings (A2). The read-only body is the ledger part.
- **The simulation through PIN logins on enrolled devices:** not the default (A1). PIN login and enrolment have their own specs (`staff-pin.spec.ts`) and a Gate 3 device check. Adding them would use more of the shared GoTrue budget.
- **A database-level `backup_reader` role:** V5 (Q184). It needs a migration and a founder-set password.
- **Auto-deploying production migrations after CI:** rejected. The founder approves every production change (house constraint).

## 6. Risks and mitigations

- **Security and privacy**
  - *A CSP that breaks a flow in production:*
    - every Playwright spec runs under it;
    - the simulation and `security-headers.spec.ts` fail on any violation (5, 15);
    - the document iframe is covered (5);
    - the founder checks preview before production (§8).
  - *Nonce reuse in cached shell pages:* bounded and recorded in ADR-028. The worker caches three pages, with their own policy.
  - *Backups:*
    - encrypted with AES-256 (passphrase ≥ 32, stdin only);
    - clear text only in `$RUNNER_TEMP` and removed in `always()`;
    - never a GitHub artifact;
    - the Drive key is scoped to `drive.file` and one folder;
    - the secrets live in environment-scoped GitHub secrets that only `main` can use.
  - **Personal data on GitHub runners (GDPR):** the dump and the restore process staff display names, supplier data (possibly natural persons) and Auth users in clear text on a GitHub-hosted runner. This is a sub-processor change against project plan §3.11.8 ("GitHub: CI, no production data"). It goes to the founder as Q185, with project Q13 (DPA, sub-processor list).
  - *Backup retention is personal-data retention:* 8 weekly copies by default (Q182, with project Q14).
  - *A restored copy calling production:* `cron.job` and the two Vault secrets are removed inside the restore transaction (`restoreSql` in 9; check (d) in 10).
  - *The database URL in process arguments:* `supabase db dump` takes it as `--db-url`, so it is visible to other processes of the same short-lived runner. It is never logged (`redact`, step 9) and the runner masks the secret.
  - *The backup connection uses a privileged database user:* environment-scoped secret, rotation in the runbook; V5 (Q184) gives a read-only role.
  - *Header check leaking the bypass secret:* only header names are printed (4).
  - *The audit gate weakened by stale exceptions:* exceptions expire and stale ones fail (6).
  - *Production protected by Vercel Authentication:* go-live blocker Q188; the checklist item fails until a custom domain serves production.
- **Correctness**
  - *The simulation crossing the 02:00 cut-off:* it fails with an explicit message; rerun. It only happens when a run starts less than S minutes before 01:00 UTC (winter) or 00:00 UTC (summer).
  - *Shared helpers changed:* `openTableAndOrder` keeps its default; its existing callers' specs must stay green (14).
  - *Dynamic rendering cost:* no number is promised. The founder re-runs `perf-order-entry.yml` and `perf-dashboard-4g.yml` on staging and reads them against the PRD NFRs (G9, §8).
- **Unverified (proved in the named step or by the founder's run)**

Proved in 5 (each script's `.nonce` equals the header's and changes per load). If it does not, stop and re-plan with the architect. nextjs.org could not be reached from this session.
  - **T2:** headers set on `NextResponse.next()` and on redirects in the proxy reach the final response of pages and route handlers, next to the `next.config` headers. Proved in 5 (`checkHeaders` on the live local server).
  - **T3:** `supabase db dump` with `--role-only`, with no flag (schema) and with `--data-only --use-copy`, restored with `psql` into an empty local stack, rebuilds `public`, `app`, `auth.users` and the migration list. Proved in 10 (counts and migrations equal). supabase.com could not be reached from this session. If it fails, stop and re-plan.
  - **T4:** `gpg` is installed on `ubuntu-latest` and supports the loopback-pinentry symmetric mode. Proved in 10.
