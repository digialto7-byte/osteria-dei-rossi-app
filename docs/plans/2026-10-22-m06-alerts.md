## 1. Goal and scope

- **Goal:** build one alert pipeline that every later rule reuses:
  - a rule calls `app.raise_alert(...)`;
  - the same alert on the same Europe/Rome day is stored once;
  - each role sees only the alerts meant for it in the app, and no € figure ever reaches the chef or a waiter;
  - one tap acknowledges an alert;
  - an hourly SQL job runs the rules and records each run.
- **In scope:**
  - `app.job_run` and its write helpers. `withCron` records every authorised run of the existing extract route, and the hourly rules job records its own runs.
  - `alert` (kind, severity, payload, business date, audience, ack) with the dedup index, and the kind registry `app.alert_kind`.
  - `app.raise_alert()` with its cost guards and a stable contract for M8, M9, M13, M16, M19.
  - `public.acknowledge_alert()` and `POST /api/alerts/:id/ack`.
  - Two test alert kinds and `POST /api/alerts/test`. The owner uses them to check that alerts work, and the end-to-end tests use them to raise real alerts.
  - `app.run_alert_rules()` with a replaceable rule body, run hourly by the pg_cron job `alert-rules` (no rules yet, no route call).
  - `GET /api/alerts` and the `/avvisi` screen (owner, chef), with Italian and English rendering of payloads per kind.
  - Two two-session race cases.
- **Out of scope:**
  - Every alert rule: price variance (M8), payable reminders and weekly digest (M9), Drive health (M10), PIN lockout alert (M11), ledger drift and job-health checks (M13), prep, purchase and expiry (M16), negative stock (M12, M19).
  - Every outbound channel: email (later option, §4), Telegram (project plan V1 or M26), WhatsApp (M46), web push.
  - Alert settings and `/api/settings`. Nothing is configurable in M6.
  - A kitchen-sized screen in a `(cucina)` route group. It comes with the kitchen screens; meanwhile the chef uses `/avvisi`.
  - Business-day cut-off for alert dates, a retention purge, and hiding all alerts from the chef. These are variants V1–V3, each behind a founder answer.

## 3. Design

### 3.1 Decisions

1. **Alerts are append-only except for one set-once step.**
   - After insert, an alert row only changes when `acknowledged_at` and `acknowledged_by` go from null to a value, once and never back. Trigger `app.alert_guard()` enforces this for every role, the migration owner included.
   - DELETE and TRUNCATE raise for every role.
   - The row itself records who acknowledged it and when, so no `audit_event` row is written.
2. **`raise_alert` lives in schema `app` and takes the tenant as a parameter.**
   - Rules run from pg_cron with no JWT, so the tenant cannot come from `auth.jwt()`.
   - Safety comes from privileges: no API role (`public`, `anon`, `authenticated`, `service_role`) can execute `app.raise_alert`. Only definer procedures owned by the migration owner can call it.
   - M8's `approve_invoice` will pass `app.tenant_id()`; M9 and M16 rules pass the tenant they loop over.
3. **Deduplication.**
   - Unique index `alert_dedup_uq (tenant_id, kind, entity_type, entity_id, business_date) nulls not distinct`.
   - Inserts use `insert … on conflict do nothing` with no conflict target.
   - A tenant-level alert uses `entity_type 'tenant'` and the tenant id, so `nulls not distinct` is only a backstop.
4. **Business date = the venue calendar date** in the tenant's time zone.
   - `app.alert_business_date(p_tenant, p_at)` = `app.venue_date(p_at, tenant.timezone)`, computed in SQL, never in TS.
   - A caller may pass `p_business_date` explicitly. M9's weekly digest uses the ISO week's Monday (plan §3.10).
   - No trading-day cut-off (Q4 default; V1 adds one).
5. **Audience and costs: three layers.**
   - **Audience:** `audience_roles` always includes `owner` and may add `chef`. `admin` and `waiter` are refused (role matrix §3.11.2: "alerts … waiter: none in MVP").
   - **Kind registry:** each kind is registered in `app.alert_kind` with `cost_bearing`, and the flag is copied onto the alert row.
     - A check constraint forbids `chef` in the audience of a cost-bearing alert.
     - `raise_alert` checks this first and raises `alert_audience_cost`.
   - **Payload guard:** a non-cost kind is refused if its payload has a money-like key at any depth (`alert_payload_cost_key`).
     - Money-like means keys ending in `_eur`, or containing `cost`, `price`, `prezz`, `margin`, `amount`, `importo`, `total` (so also `totale`), `valore` or `imponibile`, or holding `iva` or `vat` as a word (`iva`, `VAT_rate`, `vatRate`, `rateIva`; not `attiva` or `relativa`). Case-insensitive.
     - A non-cost kind is also refused (`alert_payload_cost_value`) if any string value at any depth contains the euro sign or the word EUR or euro (`12,50 €`, `10 EUR`, `10eur`; not `Euroricambi`). Numbers are not looked at: the key rule covers them.
     - Both widenings come from code review round 1 and live in `20261022150600_alert_rules_warning.sql` (§3.2). A cost-bearing kind is unchanged: its audience never includes the chef, and it keeps money keys and values.
     - Payload convention (§3.5): every money value sits under a key ending in `_eur`, so the guard and the renderer agree. A quantity key such as `total_qty` is refused too: name it `needed_qty` or `sum_qty`.
   - **RLS:** the owner reads every alert of the tenant; admin reads none (founder 2026-10-23). The chef reads only alerts where `'chef' = any(audience_roles) and not cost_bearing`. Waiters have no policy.
     - This applies the founder's decision of 2026-10-22 that the chef never sees € costs.
     - As a result, € figures reach only the owner.
6. **Who acknowledges:** anyone who can read the alert (the owner, and the chef for kitchen alerts).
   - One acknowledgement counts for everyone (assumption A2).
   - A second acknowledgement is a no-op that returns the first one (AT4).
7. **In-app only (founder, 2026-10-23).**
   - There is no outbound channel, no delivery state and nothing to configure. An alert is "delivered" by being readable on `/avvisi` until someone acknowledges it.
   - "The owner is the recipient" means the owner reads every alert in the app and no other role is a recipient; admin sees no alerts (A1, founder 2026-10-23).
   - The kind registry has no channel column (§4). The email milestone adds one when it has a meaning.
8. **`job_run` is kept, in schema `app`, outside `public`.**
   - Why keep it:
     - plan §3.9 says every scheduled run writes `job_run`;
     - M10 (Drive) and M13 (ledger drift, job health) read it;
     - M6 already has two writers: the extract route (every authorised run, through `withCron`) and the hourly `alert-rules` job;
     - without it, a silently stopped scheduler is invisible until M13.
   - Why not `public`:
     - a run spans tenants (extraction claims the oldest invoice of any tenant), so it has no tenant;
     - pgTAP `001` requires a non-null `tenant_id` on every `public` table.
   - `app.job_run` holds no tenant data. It has RLS enabled with no policy and no grant to any API role.
   - This is a deliberate exception to "every table has `tenant_id`", recorded in ADR-006.
9. **The rules runner uses a fixed wrapper and a replaceable body.**
   - `app.run_alert_rules(p_at)` begins a `job_run`, then calls `app.alert_rules_body(p_at)` inside a `begin … exception` block (a savepoint), then ends the run.
   - If the body raises:
     - its work is rolled back to the savepoint;
     - the run is recorded `ok = false`, `rule_failed`;
     - the function returns normally, so the record survives.
   - Re-raising would roll the `job_run` row back too, which is why the earlier draft's "record and re-raise" was dropped.
   - Rule milestones replace only `app.alert_rules_body` (§3.5).
   - pgTAP can stub the body to prove the failure path in M6.
   - M6's body raises nothing and returns 0.
10. **Rendering is per kind and per locale, on the server.**
    - The database stores structured `payload` and no message text.
    - `src/server/alerts/templates.ts` holds a strict Zod payload schema and the message keys for each kind. `render.ts` produces `{title, body}` in the request's locale (default `it`).
    - A payload that fails its schema, or an unknown kind, renders as "Avviso / Apri l'app per i dettagli." and is reported by id and kind only.
    - React only shows the strings.
11. **Nothing in M5 changes.**
    - M5 raises no alert today, and M6 does not touch `approve_invoice`.
    - The price variance alert belongs to M8. It will call `app.raise_alert` inside `approve_invoice`, so a rolled-back approval leaves no alert (§3.5).

### 3.2 Data model (migrations after `20261022141000`)

**`20261022150000_job_run.sql`**
- Table `app.job_run`:
  - `id bigint generated always as identity primary key`;
  - `job text not null check (job in ('extract', 'alert-rules'))`;
  - `started_at timestamptz not null default now()`, `finished_at timestamptz`;
  - `ok boolean`, `error_code text check (error_code ~ '^[a-z_]{1,40}$')`, `items integer check (items >= 0)`.

  Check `(finished_at is null) = (ok is null)`; index `(job, started_at desc)`. RLS is enabled with no policy, and `revoke all` from `public, anon, authenticated, service_role`. M10 and later milestones widen the job list.
- `app.job_run_begin(p_job text) returns bigint` and `app.job_run_end(p_id bigint, p_ok boolean, p_error_code text, p_items int)`: definer, empty `search_path`. A second `end` → P0001 `job_run_finished`.
- Thin definer wrappers for `withCron` and the integration suite, executable by `service_role` only:
  - `public.job_run_start(p_job text) returns bigint`;
  - `public.job_run_finish(p_id bigint, p_ok boolean, p_error_code text, p_items int) returns void`;
  - `public.job_run_latest(p_job text) returns table (started_at, finished_at, ok, error_code, items)`.

**`20261022150100_alert.sql`**
- `create type public.alert_severity as enum ('info', 'warning', 'critical')`.
- Registry `app.alert_kind`:
  - columns `kind text primary key check (kind ~ '^[a-z][a-z0-9_]{2,40}$')`, `cost_bearing boolean not null`, `default_severity public.alert_severity not null`, `default_audience public.app_role[] not null`;
  - checks `default_audience <@ '{owner,chef}'` and `default_audience @> '{owner}'` and `not (cost_bearing and 'chef' = any(default_audience))`;
  - no grant to any API role.

  Rows in M6:
  - `test_alert`: not cost-bearing, `info`, `{owner}`;
  - `test_alert_kitchen`: not cost-bearing, `info`, `{owner,chef}`.
- `app.alert_business_date(p_tenant uuid, p_at timestamptz) returns date` (stable, definer, empty `search_path`) = `app.venue_date(p_at, t.timezone)`. Unknown tenant → P0002.
- `app.payload_money_keys(p_payload jsonb) returns text[]` (immutable): every key at any depth (objects and arrays) matching `(_eur$|cost|price|prezz|margin|amount|importo)`, case-insensitive.
- Table `public.alert`:
  - **Columns:**
    - `id uuid pk default gen_random_uuid()`, `tenant_id uuid not null → tenant`;
    - `kind text not null references app.alert_kind (kind)`;
    - `entity_type text not null check (entity_type ~ '^[a-z][a-z_]{1,40}$')`, `entity_id uuid` (no FK: alerts outlive and point at many tables);
    - `business_date date not null`, `severity public.alert_severity not null`, `audience_roles public.app_role[] not null`, `cost_bearing boolean not null`, `payload jsonb not null`;
    - `created_at timestamptz not null default now()`, `created_by uuid → app_user` (null when a scheduled job raised it);
    - `acknowledged_at timestamptz`, `acknowledged_by uuid`.
  - **Acknowledger FK:** composite `(tenant_id, acknowledged_by) → app_user (tenant_id, id)`, adding `unique (tenant_id, id)` on `app_user` if it is missing. An acknowledgement can only name a user of the same tenant.
  - **Checks:**
    - `alert_audience_ck`: `audience_roles @> '{owner}' and audience_roles <@ '{owner,chef}'`;
    - `alert_cost_audience_ck`: `not (cost_bearing and 'chef' = any(audience_roles))`;
    - `alert_payload_ck`: `jsonb_typeof(payload) = 'object' and octet_length(payload::text) <= 8192`;
    - `alert_ack_ck`: `(acknowledged_at is null) = (acknowledged_by is null)`.
  - **Indexes:** unique `alert_dedup_uq (tenant_id, kind, entity_type, entity_id, business_date) nulls not distinct`; `(tenant_id, created_at desc, id desc)`; `(tenant_id, created_at desc) where acknowledged_at is null`.
  - **Triggers:**
    - `alert_guard` (before update, `app.alert_guard()`): any change other than `acknowledged_at`/`acknowledged_by` going from null to a value → P0001 `alert_immutable`. This includes `created_at`.
    - `alert_no_delete` (`app.append_only()`) and `alert_no_truncate`.
  - **RLS** `alert_select`: `tenant_id = (select app.tenant_id()) and ((select app.role()) = 'owner' or ((select app.role()) = 'chef' and 'chef' = any(audience_roles) and not cost_bearing))`.
  - **Grants:** `select` to `authenticated`; nothing else for `authenticated` or `service_role`.

**`20261022150200_raise_alert.sql`**
- `app.raise_alert(p_tenant uuid, p_kind text, p_entity_type text, p_entity_id uuid, p_payload jsonb default '{}', p_severity public.alert_severity default null, p_audience public.app_role[] default null, p_at timestamptz default now(), p_business_date date default null) returns table (alert_id uuid, inserted boolean)` (definer, volatile, empty `search_path`). Order:
  1. Look up the kind in `app.alert_kind` (unknown → P0001 `unknown_alert_kind`). `p_tenant` must exist (else P0002).
  2. Audience = `coalesce(p_audience, default_audience)` ∪ `{owner}`, de-duplicated and sorted. `admin` or `waiter` in it → P0001 `alert_audience_invalid`.
  3. Cost guards:
     - cost-bearing kind with `chef` → P0001 `alert_audience_cost`;
     - non-cost kind with `app.payload_money_keys(payload) <> '{}'` → P0001 `alert_payload_cost_key`;
     - payload not an object, or over 8 KB → P0001 `alert_payload_invalid`.
  4. `business_date = coalesce(p_business_date, app.alert_business_date(p_tenant, p_at))`.
  5. `insert into public.alert (…, created_by = app.app_user_id()) … on conflict do nothing returning id`. Inserted → return `(id, true)`.
  6. Not inserted → select the existing id by the dedup key and return `(id, false)`.
- `revoke all on function app.raise_alert(...) from public, anon, authenticated, service_role`.
- `public.alert_kind_list() returns table (kind text, cost_bearing boolean)`: definer, `service_role` only. Used by the integration parity check (step 10).

**`20261022150300_alert_ack.sql`**
- `public.acknowledge_alert(p_alert uuid) returns jsonb` (definer):
  - role must be owner or chef (else 42501, also for admin and waiter, also for no claims);
  - `select … for update` the alert where `tenant_id = app.tenant_id()` **and** the caller can read it under the same rule as `alert_select`. Otherwise P0002, so a chef cannot learn that an owner-only alert exists;
  - already acknowledged → return the stored `{acknowledgedAt, acknowledgedBy}` unchanged;
  - else set both to `now()` and `app.app_user_id()`.
- `public.raise_test_alert(p_include_kitchen boolean default false) returns jsonb` (definer):
  - owner only (admin → 42501);
  - calls `app.raise_alert(app.tenant_id(), case when p_include_kitchen then 'test_alert_kitchen' else 'test_alert' end, 'tenant', app.tenant_id(), '{}')`;
  - returns `{alertId, inserted}`.
- Both are executable by `authenticated` only.

**`20261022150400_alert_rules.sql`**
- `app.alert_rules_body(p_at timestamptz) returns integer` (definer, empty `search_path`): in M6 it does `return 0`. Rule milestones replace it (§3.5). It returns the number of alerts inserted.
- `app.run_alert_rules(p_at timestamptz default now()) returns void` (definer, empty `search_path`):
  1. `v_run := app.job_run_begin('alert-rules')`;
  2. `begin v_items := app.alert_rules_body(p_at); exception when others then v_failed := true; end;`
  3. `app.job_run_end(v_run, not v_failed, case when v_failed then 'rule_failed' end, coalesce(v_items, 0))`.

  It makes no route call and queues no pg_net request.
- Revoke execute on `app.alert_rules_body` and `app.run_alert_rules` from every API role.
- `cron.schedule('alert-rules', '0 * * * *', $$select app.run_alert_rules()$$)`.

**`20261022150500_alert_collation.sql`** (follow-up, already pushed): `create or replace` of `app.payload_money_keys` and `public.alert_kind_list` with `collate "C"` on the sorts, so results do not depend on the database collation (CI's Supabase image uses en_US, a plain local Postgres uses C).

**`20261022150600_alert_rules_warning.sql`** (code review round 1; the committed migrations above are not edited):
- `app.run_alert_rules` is replaced (same signature and privileges). On a failing body it also does `raise warning 'alert rule failed: %', sqlstate;` before recording the run. The SQLSTATE only: no message, detail or payload. The record (`rule_failed`, 0 items) and the normal return are unchanged. pgTAP `046` checks the function source for the warning and for the absence of `sqlerrm`, and that a second SQLSTATE (22012) is still recorded as `rule_failed`.
- `app.payload_money_keys` is widened as in §3.1.5, keeping the `collate "C"` sort.
- `app.payload_has_money_value(p_payload jsonb) returns boolean` (immutable, no API role): `jsonb_path_exists` over `strict $.**` for a string matching `€|(^|[^a-z])eur(os?)?([^a-z]|$)`, case-insensitive.
- `app.raise_alert` is replaced (same signature): after the object-and-size check, a non-cost kind with such a value raises P0001 `alert_payload_cost_value`. The new code is distinct from `alert_payload_cost_key`, so a log tells a key from a value. Nothing maps it in TypeScript: no API role can call `raise_alert`.

### 3.4 Rules runner

- Flow: pg_cron (hourly) → `app.run_alert_rules()` → `job_run` begin → `app.alert_rules_body(now())` in a savepoint → `job_run` end.
- No Vault secret, route or network is involved, so local, CI and staging stacks behave the same. Each hour adds one `job_run` row with `items = 0` until M9/M16 add rules.
- A rule that raises rolls back the whole body of that hour. The run is recorded `rule_failed`, and the next hour retries it. Dedup makes the retry safe.
- A later milestone that wants one rule's failure not to block the others wraps that rule in its own nested block.

### 3.5 Contract for the rule milestones (stable from M6)

- **Call:** `perform app.raise_alert(p_tenant, p_kind, p_entity_type, p_entity_id, p_payload [, p_severity, p_audience, p_at, p_business_date])`.
  - Call it from a definer procedure owned by the migration owner, inside the rule's own transaction.
  - M8 calls it inside `approve_invoice`, so a rolled-back approval leaves no alert.
  - Tests pass `p_at` for a fake clock (M9 AT1, M16 AT6).
- **New kind = three edits in one commit:**
  1. an `insert into app.alert_kind` in the milestone's migration;
  2. a template in `src/server/alerts/templates.ts` (Zod payload schema + message keys);
  3. `alerts.kind.<kind>.title|body` in `it.ts` and `en.ts`.

  The integration parity test (step 10) fails if the SQL and TS registries differ.
- **Payload conventions:**
  - money: `<name>_eur` (a number, € net unless the key says `_gross_eur`);
  - quantities: `<name>_qty` with a sibling `unit` (`kg`, `l`, `pz`);
  - calendar dates: `<name>_date` (`YYYY-MM-DD`); instants: `<name>_at` (ISO with zone);
  - names: text up to 200 characters, always rendered as text;
  - **no staff names** (people are referenced by id, if at all).
- **Hourly rules:** M9 and M16 `create or replace app.alert_rules_body` to add their rule call and add its count to the return value. They never replace `app.run_alert_rules`. Each of those milestones' pgTAP asserts that every earlier rule still runs after the replacement.
- **Dedup key choice:**
  - one kind per stage that must fire once (`payable_due_7d`, `payable_due_today`, `payable_overdue_3d`, plan §3.10);
  - the entity is what the alert is about (recipe key, ingredient, batch, payable, tenant).

- `withCron` records a handler's `ApiError` in `job_run` as `api_error` (other errors: `internal`; `ConfigError`: `config_missing`).

### 3.7 Flow

1. A rule (M8+) or the test button calls `app.raise_alert`. This writes one `alert` row, or returns the existing one, inside the caller's transaction.
2. The owner opens `/avvisi` → `GET /api/alerts` → rendered items. "Ho visto" → `POST /api/alerts/:id/ack` → `acknowledge_alert` → the refreshed item.
3. Every hour, pg_cron runs `app.run_alert_rules()` → one `job_run` row (§3.4).
4. Every authorised call to `POST /api/cron/extract` → `withCron`:
   - `job_run_start('extract')` → handler → `job_run_finish`;
   - a 401 or 405 records nothing.

## 4. Alternatives considered

- **Email now through Resend, using an outbox with a lease and an idempotency key** (the 2026-10-22 base plan): rejected by the founder on 2026-10-23 (in-app only, no third-party processor).
- **Email later (documented option, not built).** Adding it later would be its own milestone or a variant of one, re-planned when the founder asks. The work would be:
  - a channel column on `app.alert_kind`;
  - a `public.alert_delivery` outbox table (tenant, alert, channel, status, attempts, next attempt, lease with `claim_token`, sent time, provider message id, error code), inserted by `app.raise_alert` in the same transaction;
  - no recipient table at all (no address in M6); alerts are read by the owner only, admin none;
  - a `POST /api/cron/dispatch-alerts` route behind `withCron`:
    - it claims one delivery at a time with `for update skip locked`, a lease and a claim token;
    - it sends with an idempotency key `alert-email/<delivery id>`;
    - every retry must stay inside the provider's key window.

  `alert` stays immutable, so M6's tables need no change beyond the new column. That milestone must first answer: the provider, its prices and fees, its data location and retention, its DPA, the sender domain, and the recipient address.
- **Registry column `emailed` kept and always false:** rejected. A column with one possible value is dead weight; the email milestone adds a channel column when it has a meaning.
- **Web push notifications instead of email:** rejected for M6. They need a service worker subscription flow and send through the browser vendors' push services, which are third parties. That conflicts with the decision.
- **Dropping `job_run` now that there is no dispatcher:** rejected (§3.1 decision 8). Plan §3.9, M10 and M13 rely on it, it already has two writers, and it costs one table and two helpers.
- **Rules runner that records the error and re-raises:** rejected. The re-raise rolls back the `job_run` row in the same transaction, so the failure is never recorded (§3.1 decision 9).
- **Rule registry table with dynamic dispatch (`execute format(...)` per registered function):** rejected. It isolates rules better, but adds dynamic SQL and a table for zero rules today. The replaceable body is simpler, and pgTAP can stub it.
- **`job_run` in `public` with a tenant:** rejected; cross-tenant runs have no tenant (§3.1 decision 8).
- **Per-person acknowledgement:** rejected for the base plan. The PRD asks for one-tap acknowledgement of an alert, and one shared state is simpler to read in the kitchen (A2).
- **Rendering messages in SQL and storing them:** rejected. Plan §3.10 stores structured payloads, so both locales render from one row and a template fix also applies to old alerts.

## 6. Risks and mitigations

- **Security / privacy**
  - *Definer procedures bypass RLS:*
    - user-called procedures check the role first, use an empty `search_path` and take the tenant from `app.tenant_id()`;
    - `app.raise_alert`, `app.run_alert_rules` and `app.alert_rules_body` are not executable by any API role, so the tenant parameter cannot be abused (steps 4, 6).
  - *Costs reaching the chef or a waiter:* three layers in Postgres (registry flag with check constraint, payload key guard, RLS), plus the TS filter and string scans (steps 3, 4, 8, 9).
    - Remaining gap: a rule author could put a money amount, as a number, under a key the guard does not match (e.g. `"spesa": 12`), or write it into text without a euro sign or EUR. The guard now matches more words (`total`, `valore`, `imponibile`, `iva`, `vat`) and refuses strings with `€` or EUR, but it cannot know every word.
    - Mitigated by the `_eur` convention, the template test (step 8) and code review of every new kind, which must be done before any chef-audience kind arrives (M12, M16, M19).
  - *Personal data:* **none leaves the system in M6.**
    - No email, no push and no provider are involved; alerts stay in Supabase (EU) behind RLS.
    - Payloads may name suppliers (possibly sole traders, so personal data; project Q13) but never staff.
    - `acknowledged_by` is a staff user id; erasure follows plan §3.11.8 (the display name is pseudonymised).
    - Error reports carry ids, kinds and SQLSTATEs only (steps 8, 9). Sentry is not yet enabled (context Q-D); `reportError` already scrubs.
  - *Cron route abuse:* unchanged from M3. The bearer is compared in constant time before any database call, and a 401 now also proves that no `job_run` row is written (step 2).
  - *`job_run` wrappers:* `service_role` only; a user session gets permission denied (steps 1, 10).
  - *Test-alert abuse:* owner only. Dedup limits it to one row per test kind per tenant per day, and it has no external effect.
- **Correctness**
  - *Nobody is notified outside the app.* An M8 price alert or M9 payable reminder is seen only when someone opens `/avvisi`, so it could go unnoticed for days. This follows from the founder decision.
    - Follow-ups for the founder: an open-count badge on the home link, or the later email or Telegram channel.
    - Neither is in M6.
  - *One failing rule blocks that hour's rules:* the body runs in one savepoint (§3.4). The failure is recorded in `job_run` (`rule_failed`), and M13's job-health check reads it.
  - *If `run_alert_rules` itself fails before the savepoint,* nothing is recorded. M13's `job_stale` check (no run in the last N hours) covers that gap.
  - *Each rule milestone replaces `alert_rules_body`:* a later `create or replace` could drop an earlier rule. Each rule milestone's pgTAP asserts that its predecessors' rules still run (§3.5).
  - *`job_run` grows* by one row an hour plus one per extract run. Rows hold no personal data, and the period is set by M13 (Q3).
  - *DST:* every date decision is made in SQL (`app.venue_date`), with the vectors of steps 3 and 4.
- **Unverified (checked in the named step):**
  - **T1** `on conflict do nothing` with a `nulls not distinct` unique index (Postgres 15+): checked in steps 3, 4 and 7, on Postgres 17 (local stack) and 16 (races).
- **Performance / cost:** a few indexed rows per alert and one SQL call an hour. No provider, so no running cost from M6. No performance figure is promised.
- **Dependencies:** none added. `resend` (plan §3.12) is not installed.
- **Plan changes to record in DigiAlto-Ops `context.md`:**
  - **M6 is in-app only (founder, 2026-10-23).** This changes the project plan as follows:
    - no `POST /api/cron/dispatch-alerts` and no `dispatch-alerts` pg_cron job (plan §3.3 cron row, §3.9);
    - no Resend for alerts: the `RESEND_API_KEY` row of §3.11.7 is unused, Resend is not a sub-processor of alert content (§3.11.8), and `resend` is not installed (§3.12);
    - §5a.1 M6 AT3 is superseded (mapping in §5).
  - `alert` has no `message`, `channel` or `sent_at` columns. It adds `kind` (the PRD's `type`), `cost_bearing`, `payload`, `business_date`, `audience_roles` and `acknowledged_by`.
  - There is no alert address and no `settings.alert_email`. M6 creates no `/api/settings`; the first milestone that needs settings creates the route.
  - `job_run` is `app.job_run` (outside `public`, no tenant), with jobs `extract` and `alert-rules`. `withCron` records every authorised run.
  - `raise_alert` is `app.raise_alert(p_tenant, …)` and returns `(alert_id, inserted)`. Rule milestones replace `app.alert_rules_body`, never `app.run_alert_rules`.
  - ADR-006 is revised to the in-app pipeline.
  - **For the lead (not decided here):** M0 decision Q-G says "Resend SMTP in M6" for magic-link emails. M6 no longer configures any Resend, so Q-G needs a new decision. Until then, staging keeps Supabase's built-in sender, and `RESEND_API_KEY=replace-me` stays in `.env.example`, unused.
