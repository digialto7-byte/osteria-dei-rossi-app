## 1. Goal and scope

- **Goal:** one alert pipeline that every later rule reuses. A rule calls `app.raise_alert(...)`; the same alert on the same Europe/Rome day is stored once; it is emailed once (with retries) to the owner's alert address; each role sees only the alerts meant for it, with no € figure ever reaching the chef or a waiter; one tap acknowledges it. All of it runs on the pg_cron + pg_net + Vault set-up that M3 built.
- **In scope:**
  - `app.job_run` and its write helpers; every cron route (extract and dispatch-alerts) and the SQL rules job record a run;
  - `alert` (kind, severity, payload, business date, audience, ack), with the dedup index; `alert_delivery` (email channel, status, attempts, lease); the kind registry `app.alert_kind`;
  - `app.raise_alert()` with its cost guard and a stable contract for M8, M9, M13, M16, M19;
  - `alert_settings` (alert email and email language), `GET/PATCH /api/settings` (alert keys only);
  - `public.acknowledge_alert()`, `POST /api/alerts/:id/ack`;
  - two test alert kinds and `POST /api/alerts/test` (the owner checks the address and the email path; it also gives the end-to-end tests a real way to raise alerts);
  - dispatcher procedures (claim with lease, complete, fail with backoff, release, unconfirmed), `POST /api/cron/dispatch-alerts` (Resend over `fetch`, idempotency key per delivery), pg_cron jobs `dispatch-alerts` (every 5 min when due) and `alert-rules` (hourly runner, no rules yet), using M3's `app.call_cron_route`;
  - `GET /api/alerts`, the `/avvisi` screen (owner, admin, chef), Italian and English rendering of payloads per kind, the email template;
  - three new two-session race cases.
- **Out of scope:**
  - every alert rule: price variance (M8), payable reminders and weekly digest (M9), Drive health (M10), PIN lockout alert (M11), ledger drift and job-health checks (M13), prep, purchase and expiry (M16), negative stock (M12, M19);
  - Telegram (project plan V1 or M26) and WhatsApp (M46);
  - a kitchen-sized screen in a `(cucina)` route group (comes with the kitchen screens; the chef uses `/avvisi` meanwhile);
  - grouped emails, quiet hours, several recipients, business-day cut-off for alert dates, retention purge, chef without alerts, in-app only: variants V1–V7, each behind a founder answer.

## 3. Design

### 3.1 Decisions

1. **Alerts are not a ledger, but they are append-only except for one set-once step.** An alert row never changes after insert except `acknowledged_at` + `acknowledged_by`, which go from null to a value once and never back (trigger `app.alert_guard()`, every role, the migration owner included). DELETE and TRUNCATE raise for every role. The row itself is the record of who acknowledged it and when, so no `audit_event` row is written for an acknowledgement. Delivery state (which changes on every attempt) lives in a separate table, `alert_delivery`, so the alert stays immutable.
2. **`raise_alert` lives in schema `app` and takes the tenant as a parameter.** Rules run from pg_cron with no JWT, so the tenant cannot come from `auth.jwt()`. Safety comes from privileges: `app.raise_alert` is executable by **no** API role (`public`, `anon`, `authenticated`, `service_role` revoked). Only other definer procedures owned by the migration owner can call it (M8's `approve_invoice` passes `app.tenant_id()`; M9/M16 rules pass the tenant they loop over).
3. **Deduplication** is the unique index `alert_dedup_uq (tenant_id, kind, entity_type, entity_id, business_date) nulls not distinct` and `insert … on conflict do nothing` (no conflict target, so the index's null handling needs no inference). A tenant-level alert uses `entity_type 'tenant'` and the tenant id, so `nulls not distinct` is only a backstop.
4. **Business date = the venue calendar date** in the tenant's time zone (`app.alert_business_date(p_tenant, p_at)` = `app.venue_date(p_at, tenant.timezone)`), computed in SQL, never in TS. A caller may pass `p_business_date` explicitly (M9's weekly digest uses the ISO week's Monday, plan §3.10). The trading-day cut-off of plan Q18 is not applied to alerts (→ V4).
5. **Audience and costs: three layers.**
   - `audience_roles` is normalised to always include `owner` and `admin` and may add `chef`; `waiter` is refused (role matrix §3.11.2: "alerts … waiter: none in MVP").
   - Each kind is registered in `app.alert_kind` with `cost_bearing`. The flag is copied onto the alert row. A check constraint forbids `chef` in the audience of a cost-bearing alert; `raise_alert` raises `alert_audience_cost` first, with a clear code.
   - A non-cost kind is refused if its payload has a money-like key at any depth (`alert_payload_cost_key`: keys ending `_eur` or containing `cost`, `price`, `prezz`, `margin`, `amount`, `importo`). Payload convention: every money value is a key ending `_eur` (§3.5), so the guard and the renderer agree.
   - RLS: owner/admin read every alert of the tenant; the chef reads only `'chef' = any(audience_roles) and not cost_bearing`; waiters have no policy. This applies the founder's decision (M5 plan, 2026-10-22) that the chef never sees € costs; with it, the € figures of cost-bearing alerts reach only the owner, the admin and the alert email address.
6. **Who acknowledges:** anyone who can read the alert (owner, admin, the chef for kitchen alerts). One acknowledgement counts for everyone (assumption in §7). A second acknowledgement is a no-op that returns the first one (AT4). Acknowledging before the email went out cancels that email (`skipped`, `acknowledged`).
7. **Email: one per alert, to one address, sent through an outbox with a lease.** `raise_alert` inserts an `alert_delivery` row (`pending`) in the same transaction when the kind is `emailed`. The dispatcher claims one due delivery at a time with `for update skip locked`, a lease and a `claim_token` (M3's `extraction_claim` pattern), sends it with `Idempotency-Key: alert-email/<delivery id>`, then completes it with the token. "Sends once" means: two runs never hold the same delivery; a run killed after Resend accepted the email but before `complete` is reclaimed after the lease and re-sends **the same key**, which Resend answers without sending again, because Resend keeps a key for 24 hours (§8). So every retry must happen within 24 hours of the first attempt: the backoff schedule sums to about 4 h 21 min, and a delivery whose alert is older than `ALERT_EMAIL_MAX_AGE_HOURS` (24) is never sent (`skipped`, `stale`; it stays visible in the app).
8. **No alert address → in-app only.** A due delivery for a tenant without an address is marked `skipped`, `no_recipient` at claim time (final). It is not held back, because setting an address later must not release a flood of old emails. Owner and admin see a banner on `/avvisi`.
9. **The alert address lives in `alert_settings`, not in `tenant.settings`.** `tenant.settings` is readable by every role of the tenant, waiters included, so a personal address there would leak to all staff. `alert_settings (tenant_id pk, alert_email, email_locale, updated_at, updated_by)` has an owner/admin SELECT policy and is written only by `public.update_alert_settings()`, which writes an `audit_event` **without the address** (`{email_set, email_locale}`), because audit rows are kept for good and cannot be deleted.
10. **`job_run` lives in schema `app`, not `public`.** A cron run spans tenants (extraction claims the oldest invoice of any tenant), so a run has no tenant, and pgTAP `001` requires a non-null `tenant_id` on every `public` table. `app.job_run` holds no tenant data (job name, times, ok, error code, item count). It has RLS enabled with no policy and no grant to any API role, and is written by definer helpers. M13's invariant check reads it in SQL. This is a deliberate exception to "every table has `tenant_id`"; it is recorded in ADR-006 and in the plan changes (§6).
11. **Plain `fetch`, no SDK** (§4). One endpoint, an explicit `Idempotency-Key` header, an `AbortSignal` timeout, and a status table we control and test with a fake `fetch`, like the Anthropic fake.
12. **The sender is configuration, not code:** `ALERT_EMAIL_FROM` (Vercel env, not secret). The domain is a client fact (Q2). No address literal goes into `src/`.
13. **Rendering is per kind and per locale, on the server.** The database stores structured `payload` and no message text. `src/server/alerts/templates.ts` holds, per kind, a strict Zod payload schema and the message keys; `render.ts` produces `{title, body}` for the API (in the request's locale, default `it`) and for the email (in `alert_settings.email_locale`). A payload that fails its schema, or an unknown kind, renders as a generic "Avviso / Apri l'app per i dettagli." and is reported by id and kind only. React only shows the strings.
14. **Nothing in M5 changes.** M5 raises no alert today and M6 does not touch `approve_invoice`. The price variance alert is M8's: it will call `app.raise_alert` inside `approve_invoice`, after step 6 of that procedure, so a rolled-back approval leaves no alert (§3.5).

**`20261022150200_raise_alert.sql`**
- `app.raise_alert(p_tenant uuid, p_kind text, p_entity_type text, p_entity_id uuid, p_payload jsonb default '{}', p_severity public.alert_severity default null, p_audience public.app_role[] default null, p_at timestamptz default now(), p_business_date date default null) returns table (alert_id uuid, inserted boolean)` (definer, volatile, empty `search_path`). Order:
  1. kind from `app.alert_kind` (P0001 `unknown_alert_kind`); `p_tenant` must exist (P0002);
  2. audience = `coalesce(p_audience, default_audience)` ∪ `{owner, admin}`, de-duplicated and sorted; `waiter` in it → P0001 `alert_audience_invalid`;
  3. cost-bearing kind with `chef` → P0001 `alert_audience_cost`; non-cost kind with `app.payload_money_keys(payload) <> '{}'` → P0001 `alert_payload_cost_key`; payload not an object or over 8 KB → P0001 `alert_payload_invalid`;
  4. `business_date = coalesce(p_business_date, app.alert_business_date(p_tenant, p_at))`;
  5. `insert into public.alert (…, created_by = app.app_user_id()) … on conflict do nothing returning id`;
  6. inserted and the kind is `emailed` → insert `alert_delivery` (`pending`, `next_attempt_at = now()`);
  7. not inserted → select the existing id by the dedup key; return `(id, false)`.
- `revoke all on function app.raise_alert(...) from public, anon, authenticated, service_role`.
- `public.alert_kind_list() returns table (kind text, cost_bearing boolean, emailed boolean)`: definer, `service_role` only (integration parity check, §5 step 15).

**`20261022150300_alert_settings_ack.sql`**
- `public.alert_settings (tenant_id uuid primary key → tenant, alert_email text check (alert_email ~ '^[^@\s<>]{1,64}@[^@\s<>]{1,190}$' and alert_email = lower(alert_email)), email_locale text not null default 'it' check (email_locale in ('it', 'en')), updated_at timestamptz not null default now(), updated_by uuid → app_user)`. RLS SELECT owner/admin of the tenant; `select` to `authenticated`; no write grant; no delete/truncate (triggers).
- `audit_event` checks widened: `entity_type` gains `'tenant'`; `action` gains `'tenant.alert_settings_changed'`. Acknowledgements write no audit row (§3.1 decision 1).
- `public.update_alert_settings(p_email text, p_locale text default null) returns jsonb` (definer): owner/admin (42501 otherwise); email trimmed and lower-cased, empty → null, invalid → P0001 `invalid_request`; upsert for `app.tenant_id()`; `audit_event` `tenant.alert_settings_changed` with `before`/`after` = `{email_set, email_locale}`; returns `{email, locale}`.
- `public.acknowledge_alert(p_alert uuid) returns jsonb` (definer): role ∈ owner, admin, chef (42501 for waiter or no claims); `select … for update` the alert where `tenant_id = app.tenant_id()` **and** it is readable by the caller under the same rule as `alert_select` (else P0002, so a chef cannot learn that an owner-only alert exists); already acknowledged → return the stored `{acknowledgedAt, acknowledgedBy}` unchanged; else set both to `now()` and `app.app_user_id()`; the delivery is not touched here (the claim skips acknowledged alerts, decision 6).
- `public.raise_test_alert(p_include_kitchen boolean default false) returns jsonb` (definer): owner/admin; calls `app.raise_alert(app.tenant_id(), case when p_include_kitchen then 'test_alert_kitchen' else 'test_alert' end, 'tenant', app.tenant_id(), '{}')`; returns `{alertId, inserted}`.
- Execute on these three for `authenticated` only.

**`20261022150400_alert_dispatch.sql`**
- All `public`, definer, empty `search_path`, execute for `service_role` only, one transaction each:
  - `alert_dispatch_claim(p_lease_seconds int, p_max_attempts int, p_max_age_hours int) returns table (delivery_id, alert_id, tenant_id, tenant_name, kind, severity, entity_type, entity_id, business_date, payload, created_at, recipient, email_locale, claim_token, attempts)`:
    1. stale leases (`sending`, `claimed_at < now() − lease`) with `attempts ≥ max` → `failed`, `lease_expired`;
    2. loop (at most 50 rows per call): the oldest due row (`pending` and `next_attempt_at ≤ now()`, or `sending` with an expired lease) `for update of d skip locked limit 1`, joined to its alert and `alert_settings`:
       - alert acknowledged → `skipped`, `acknowledged`; alert `created_at < now() − max_age` → `skipped`, `stale`; no `alert_email` → `skipped`, `no_recipient`; continue;
       - otherwise `status = 'sending'`, `attempts + 1`, `claimed_at = now()`, new `claim_token`; return the row.
  - `alert_dispatch_complete(p_delivery uuid, p_claim_token uuid, p_provider_message_id text) returns void`: P0001 `stale_claim` unless `sending` with that token; → `sent`, `sent_at = now()`, token cleared.
  - `alert_dispatch_fail(p_delivery, p_claim_token, p_code text, p_retryable boolean, p_backoff_seconds int[], p_max_attempts int) returns text`: retryable and `attempts < max` → `pending`, `next_attempt_at = now() + backoff[attempts]` (last element repeats); else `failed`; `last_error_code = p_code`; returns the status.
  - `alert_dispatch_release(p_delivery, p_claim_token, p_code text, p_delay_seconds int) returns void`: → `pending`, `attempts − 1`, `next_attempt_at = now() + delay`, `last_error_code = p_code` (configuration and quota faults do not burn an attempt).
  - `alert_dispatch_unconfirmed(p_delivery, p_claim_token, p_code text) returns void`: → `unconfirmed` (final, never re-sent).
  - Each of complete, fail, release and unconfirmed raises `stale_claim` unless the row is `sending` with that token.
- `app.alert_dispatch_due(p_lease_seconds int default 120, p_max_age_hours int default 24) returns boolean`: a due `pending` row whose alert is younger than the age limit, or an expired lease.
- `app.alert_skip_stale(p_max_age_hours int default 24) returns integer`: marks `pending` deliveries of older alerts `skipped`, `stale` (keeps an inert staging queue from growing for ever).
- `app.run_alert_rules(p_at timestamptz default now()) returns void` (definer): `job_run_begin('alert-rules')`; `app.alert_skip_stale()`; **no rule calls in M6** (M9 and M16 replace this function and add theirs, §3.5); `job_run_end(ok, items = alerts raised)`; then `perform app.call_cron_route('/api/cron/dispatch-alerts')` when `app.alert_dispatch_due()`. pg_net queues the request and sends it after the transaction commits, so the dispatcher sees the new alerts (T3). An error inside a rule is caught, recorded as `job_run.ok = false`, `error_code = 'rule_failed'`, and re-raised.
- Revoke execute on `app.alert_dispatch_due`, `app.alert_skip_stale`, `app.run_alert_rules` from every API role.
- `cron.schedule('dispatch-alerts', '*/5 * * * *', $$select app.call_cron_route('/api/cron/dispatch-alerts') where app.alert_dispatch_due()$$)`;
- `cron.schedule('alert-rules', '0 * * * *', $$select app.run_alert_rules()$$)`.

### 3.4 Dispatcher (`src/server/cron/dispatch-alerts-job.ts`)

`runDispatchJob({admin, fetch, now, readEnv?, constants?})`:
1. `readAlertEmailEnv()` first: `RESEND_API_KEY` and `ALERT_EMAIL_FROM`; a missing one throws `ConfigError` (names only) before anything is claimed (fails closed, as M3).
2. Up to `ALERT_DISPATCH_MAX_PER_RUN` times: `rpc('alert_dispatch_claim', …)`; none → stop.
3. Render with `renderAlertEmail(row, origin)` (subject `"{tenantName} · {title}"`, text and escaped HTML, the business date, created time in Europe/Rome, a link to `<origin>/avvisi`, where `origin` is the cron request's own origin, which pg_cron built from Vault `app_base_url`). A render exception → `alert_dispatch_fail('render_failed', false)` and `reportError` with ids only.
4. `sendEmail` (`src/server/alerts/resend.ts`): `POST RESEND_API_URL`, headers `Authorization: Bearer <key>`, `Content-Type: application/json`, `Idempotency-Key: alert-email/<delivery id>`; body `{from, to: [recipient], subject, text, html}`; `AbortSignal.timeout(RESEND_TIMEOUT_MS)`. The outcome is classified by HTTP status, then by the error body's `name` when the status alone is ambiguous (T2):

   | Response | Outcome | Procedure | Run continues? |
   |---|---|---|---|
   | 200 with `id` | sent | `complete(id)` | yes |
   | 401, 403 | `provider_auth` | `release(900 s)` + `reportError` | no |
   | 429 `daily_quota_exceeded` | `quota_daily` | `release(until next 00:00 UTC + 60 s)` + report | no |
   | 429 `monthly_quota_exceeded` | `quota_monthly` | `release(3600 s)` + report | no |
   | 429 other | `rate_limited` | `release(max(Retry-After, 1) s)` | no |
   | 409 `concurrent_idempotent_requests` | `idempotency_in_flight` | `release(30 s)` | yes |
   | 409 `invalid_idempotent_request` | `idempotency_conflict` | `unconfirmed` + report (a request with this key was already processed; re-sending under a new key could duplicate) | yes |
   | other 4xx (400, 422) | `rejected_by_provider` | `fail(retryable = false)` + report | yes |
   | 5xx | `server_error` | `fail(retryable = true)` | yes |
   | timeout | `timeout` | `fail(true)` | yes |
   | network error | `network` | `fail(true)` | yes |

5. Returns `{sent, retried, failed, skipped, unconfirmed}` (counts only).
- **Logs and Sentry:** delivery id, alert id, kind, attempt, outcome, HTTP status, duration. Never the recipient, the payload, the subject or the response body (AT3 "the Sentry event has no payload").
- **Route:** `src/app/api/cron/dispatch-alerts/route.ts`, `export const maxDuration = 60`, `POST = withCron({job: 'dispatch-alerts', items: (r) => r.sent}, …)`.

### 3.7 Flow

1. A rule (M8+) or the test button calls `app.raise_alert` → one `alert` row (or the existing one) and one `pending` `alert_delivery`, in the caller's transaction.
2. pg_cron every 5 min (and straight after the hourly rules run): `app.alert_dispatch_due()` → `app.call_cron_route('/api/cron/dispatch-alerts')` → pg_net → `withCron` (bearer; `job_run_start`) → `runDispatchJob` → claim → render → Resend → complete / fail / release / unconfirmed → `job_run_finish`.
3. The owner opens `/avvisi` → `GET /api/alerts` → rendered items; "Ho visto" → `POST /api/alerts/:id/ack` → `acknowledge_alert` → the refreshed item.
4. Without Vault secrets (local, CI, unconfigured staging), step 2 stops at `app.call_cron_route` (notice, null); deliveries wait and the hourly sweep marks them `stale` after 24 h.

## 4. Alternatives considered

- **The `resend` SDK (plan §3.12):** rejected. It wraps one POST; plain `fetch` gives the same call with an explicit `Idempotency-Key` header and timeout, a status table under our tests, no new package to audit and update, and the fake-`fetch` test pattern the project already uses. Revisit if M37 (email-in) needs more of Resend's API.
- **Dispatch in `raise_alert` through pg_net directly from SQL:** rejected. The API key would have to sit in Vault and the retry and idempotency logic in plpgsql, which cannot be unit-tested like TS; the route keeps the key in Vercel env only.
- **Delivery columns on `alert` (`sent_at`, `channel`, as plan §3.5.1):** rejected. Attempts, leases and errors change on every run, which would make the alert mutable; one row per channel also fits Telegram (project V1/M26) without changing `alert`.
- **An attempt log table (one row per send attempt):** rejected for now; `attempts`, `last_error_code`, `job_run` and Sentry show what is needed. Revisit if Resend disputes arise.
- **Exactly-once without an idempotency key (mark `sent` before sending):** rejected; a crash after marking would lose the email. With the key, "send then mark" never duplicates within 24 h.
- **Claiming many deliveries per call:** rejected; one at a time keeps the lease short and lets two runs share the queue.
- **`alert_email` in `tenant.settings` (plan §3.5.1):** rejected; readable by every staff role (§3.1 decision 9).
- **`job_run` in `public` with a tenant:** rejected; cross-tenant runs have no tenant (§3.1 decision 10).
- **Per-person acknowledgement:** rejected for the base plan; the PRD asks for one-tap acknowledgement of an alert, and one shared state is simpler to read in the kitchen (§7 assumptions).
- **Rendering messages in SQL and storing them:** rejected; plan §3.10 stores structured payloads so both locales render from one row, and a template fix applies to old alerts.

## 6. Risks and mitigations

- **Security / privacy**
  - *Definer procedures bypass RLS:* role check first, empty `search_path`, tenant from `app.tenant_id()` for user-called procedures; `app.raise_alert` and the dispatch helpers are not executable by any API role, so the tenant parameter cannot be abused (steps 4, 6).
  - *Costs reaching the chef or a waiter:* three layers (registry flag and check constraint, payload key guard, RLS) plus the TS filter and string scans (steps 3, 4, 10, 13). A rule author could put a money value under a key the guard does not match (e.g. `"valore": 12`); mitigated by the `_eur` convention, the template test (step 10) and code review of every new kind.
  - *Alert address exposure:* a separate owner/admin table, not `tenant.settings`; no address in audit rows, logs or Sentry (steps 5, 11, 15).
  - *Third-party processor:* Resend receives the address and the alert content, including € figures for owner alerts; DPA, location and retention are Q3. The email may also be read in a shared or forwarded mailbox; the settings hint asks for the owner's own address.
  - *Email content injection:* payload strings are escaped in HTML; the recipient is validated and sent as a JSON array (no header injection); the sender is validated at boot (step 8).
  - *Cron route abuse:* the bearer is compared in constant time before any DB or provider call; the route fails closed without `CRON_SECRET` (existing `withCron`, step 2 tests). A wrong bearer costs nothing; no extra rate limiter.
  - *Secret key misuse:* dispatch code lives in `src/server/cron/**` and `src/app/api/cron/**` (lint rule); user-facing routes use the session client (steps 13, 14).
  - *Test-alert abuse:* dedup limits it to one email per test kind per day per tenant.
- **Correctness**
  - *Exactly-once depends on Resend's key behaviour (T1):* if Resend stored a failed response under a key and replayed it, a retry would fail until the attempts run out; the delivery then ends `failed` and stays visible in the app. The live check (step 18) verifies the replay of a successful send.
  - *pg_net is fire-and-forget:* the lease reclaims a killed run; `job_run` shows unfinished runs; the job-health alert itself is M13's.
  - *Stale emails are never sent* (24 h rule): an outage longer than a day leaves alerts in the app only, which is intended (§7 assumptions).
  - *`run_alert_rules` is replaced by each rule milestone:* a later `create or replace` could drop an earlier rule; each rule milestone's pgTAP asserts its rules still run after the replacement (§3.5).
  - *DST:* every date decision is in SQL (`app.venue_date`) with the vectors of steps 3 and 4.
- **Unverified (checked in the named step):**
  - **T1** Resend returns the original response for a repeated `Idempotency-Key` within 24 h and does not send again (documented, §8); the behaviour when the first request failed is not documented: step 18.
  - **T2** Resend error bodies carry a `name` field (`daily_quota_exceeded`, `concurrent_idempotent_requests`, …): the names come from Resend's error reference (§8); the exact JSON shape is checked in step 18; classification falls back to the HTTP status.
  - **T3** pg_net sends a request queued inside a transaction after it commits: relied on by `run_alert_rules`; if it did not, the dispatcher would find the alerts on its next 5-minute run.
  - **T4** `on conflict do nothing` with a `nulls not distinct` unique index (Postgres 15+): steps 3, 4 and 7, on Postgres 17 (local stack) and 16 (races).
  - **T5** The cron request's origin on Vercel equals `app_base_url`: step 18. If it does not, step 18 fails and the architect re-plans the email link before the PR leaves draft.
- **Performance / cost:** a few indexed rows per alert; the dispatcher runs only when something is due. No performance figure is promised. Email cost depends on Resend's plan and volume (Q3); no price is estimated.
- **Dependencies:** none added. `resend` (plan §3.12) is not installed (§4).
- **Plan changes to record in DigiAlto-Ops `context.md`:**
  - the alert address and email language live in `alert_settings` (owner/admin), not in `tenant.settings`;
  - `alert` has no `message`, `channel` or `sent_at` columns; delivery state is in `alert_delivery`; `alert` adds `kind` (the PRD's `type`), `cost_bearing`, `payload`, `business_date`, `audience_roles`, `acknowledged_by`;
  - `job_run` is `app.job_run` (outside `public`, no tenant); `withCron` records every authorised run;
  - `raise_alert` is `app.raise_alert(p_tenant, …)` and returns `(alert_id, inserted)`;
  - Resend is called with `fetch`; the `resend` package is not used; new env var `ALERT_EMAIL_FROM`;
  - `GET/PATCH /api/settings` exists with alert keys only (M8 extends it);
  - ADR-006 records the pipeline.

## 7. Open questions for the founder

**Q1 Who receives alert emails?** (client fact; PRD: "email to one address", "the owner is the single alert recipient")
- **Default:** one address that you (or DigiAlto as admin) type in the app under "Avvisi". Until it is set, alerts appear only in the app.
- **Consequence:** owner alerts can contain prices, amounts and margins, so the address should be the owner's own mailbox, not a shared kitchen one.
- **Several addresses** → V3.

**Q2 Sender address and sending domain** (client fact; project Q12)
- Which domain should alert emails come from (for example `avvisi@<your domain>`)? It must be a domain whose DNS you or DigiAlto can edit, because the email provider needs SPF/DKIM records there.
- **Default:** none is set; the app sends no email until `ALERT_EMAIL_FROM` is set and the domain is verified; alerts stay in the app.

**Q3 Email provider: Resend, its cost and its data handling** (not decided by this plan)
- **Cost:** Resend's documentation lists a free plan of 3,000 emails a month and 100 a day, with no overage on the free plan. Please confirm the current terms on Resend's pricing page yourself; no price is estimated here. Alert volume is unknown until M8, M9 and M16. If the same account also sends magic-link login emails, they share the quota.
- **Account:** who opens and owns the Resend account (project Q9, Q26)?
- **Data:** Resend receives your alert address and the alert content (supplier and ingredient names, quantities, and in owner alerts prices and amounts). DigiAlto and the client have the same owner, so no DPA is needed between them; **Resend is a separate processor**, and its own DPA (or terms), where it processes and stores data, and how long it keeps sent emails must be checked and accepted by you (project Q13). One third-party DPA lists Resend, Inc. as a US company; sources disagree on how long Resend keeps email logs.
- **Default:** the code is built for Resend, but nothing is sent until you provide the key and the sender.
- **Alternatives:** no email at all, alerts in the app only (→ V7); or another provider (a re-plan of steps 9 and 11 only).

**Q4 Channel and frequency**
- **Default:** email, one email per alert, sent within about 5 minutes of the alert (the dispatcher runs every 5 minutes). Telegram stays a later option (project Q6, V1/M26).
- **Consequence:** on a busy morning you may get several emails in a row.
- **Alternative:** group alerts into one email per run, or one digest at a time you choose (→ V1). The weekly payables digest (M9) is a separate alert whatever you choose.

**Q5 Which roles get which alerts by default?** M6 builds the mechanism; each rule milestone uses your answer.
- **Proposal** (§3.5 table): price, payable and digest alerts → owner and admin only; prep, purchase, expiry and negative-stock alerts → owner, admin and the chef in the app; system alerts (ledger drift, Drive or job failures) → owner and admin. Every alert also goes to the alert email address. Should DigiAlto get system alerts too (project Q9)?

**Q6 Should the chef see alerts that mention quantities but no costs?**
- **Default:** yes, in the app (prep, purchase, expiry, negative stock), never with € figures (your decision of 2026-10-22). The chef gets no emails: staff accounts have no real mailbox.
- **Alternative:** the chef sees no alerts (→ V6).

**Q7 Quiet hours?**
- **Default:** none; an alert raised at night is emailed at night.
- **Alternative:** hold emails during a window you set, for example 23:00–07:00, and send them when it ends (→ V2).

**Q8 How long are alerts kept?** (project Q14)
- **Default:** kept for good; there is no delete path. Payloads may name suppliers (possibly sole traders, so personal data, project Q13) but never staff.
- **Alternative:** delete alerts and their delivery records after a period you choose (→ V5).
- Also: run records (`job_run`) hold no personal data; the proposal is to keep them until M13 sets a period.

**Q9 Which "day" counts for "one alert per item per day"?**
- **Default:** the calendar day in Italian time (midnight to midnight, DST handled).
- **Alternative:** the trading day with the cut-off of project Q18 (for example 02:00), so an alert at 01:30 counts for the evening before (→ V4).

**Q10 Email language.** **Default:** Italian; the setting allows English.

**Assumptions (confirm; a different answer means a re-plan, not a variant):**
- one acknowledgement counts for everyone: if the chef taps "Ho visto", the owner sees it as seen, with the time (and the name for owner and admin);
- acknowledging an alert in the app before its email went out cancels that email;
- an alert that could not be emailed within 24 hours is not emailed later (it stays in the app);
- waiters see no alerts in the MVP (role matrix §3.11.2);
- the owner can send one test alert per day (and one kitchen test alert) to check the address.
