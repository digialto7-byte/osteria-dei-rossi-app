## 1. Goal and scope
- **Goal:** a deployable, tested, empty Italian app in the EU, with the tenant, role and RLS foundations and the owner/admin magic-link login that every later milestone builds on.
- **In scope:** Next.js 16 scaffold and tooling; CI; local Supabase stack; `tenant` and `app_user` tables, `app.tenant_id()` and `app.role()`, the access-token hook, RLS and pgTAP guards; `withApi` and the error format; env schema; i18n and formatters; Sentry with PII scrubbing; security headers; `/api/health`, `/api/me`, `/api/auth/{magic-link,callback,logout}`; Italian login page and logout; 44 px tap tokens; `scripts/create-tenant.ts`; the lint rule for the secret-key client; `vercel.json` set to `fra1`; all 12 acceptance tests.
- **Out of scope:** staff PIN (M11); business tables (M1+); applying migrations to staging, and staging Auth/SMTP settings (these need the founder's OK and happen after merge); a production Supabase project (M25, Q10); MFA enrolment and enforcement (see Q-C); custom SMTP; the full nonce-based CSP (M25); `GET/PATCH /api/settings` (plan §3.3 lists it under M0/M8, but no M0 test needs it, so it moves to M8); browser-side Sentry (V2); app-level rate limiting (M11/M25).

## 3. Design
### 3.1 Versions (verified 2026-10-21; the lockfile pins them)
- `next` latest is **16.4.2**, engines `node >=20.9.0` ([npm](https://registry.npmjs.org/next/latest)). The Node version is pinned to 24 LTS in `.nvmrc` and `engines`; step 1 confirms Vercel offers it.
- Next 16 deprecates `middleware` in favour of `proxy`. The file is `src/proxy.ts`, with a default or named `proxy` export. It runs on the Node.js runtime only and accepts an optional `config.matcher` ([Next docs](https://raw.githubusercontent.com/vercel/next.js/canary/docs/01-app/03-api-reference/03-file-conventions/proxy.mdx)). `next lint` is not used: the lint script calls `eslint .` directly.
- `@supabase/ssr` 0.12.7 needs `@supabase/supabase-js ^2.114.0` ([npm](https://registry.npmjs.org/@supabase/ssr/latest)). Supabase's Next.js guide uses `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` and `auth.getClaims()` for server checks, never `getSession()` ([guide](https://supabase.com/docs/guides/auth/server-side/nextjs)).
- `@sentry/nextjs` 11.8.0 has peer `next ^16.0.0-0` and is MIT ([npm](https://registry.npmjs.org/@sentry/nextjs/latest)). `tsx` 4.23.15 is MIT ([npm](https://registry.npmjs.org/tsx/latest)).
- Hook URI format: `pg-functions://postgres/<schema>/<fn>`. `supabase_auth_admin` needs schema usage and execute on the function, and execute is revoked from `anon`, `authenticated` and `public` ([Auth hooks](https://supabase.com/docs/guides/auth/auth-hooks)). The local mail catcher is **Mailpit** on port 54324 (formerly Inbucket; the config section is still `[inbucket]`) ([local dev](https://mintlify.com/supabase/supabase/cli/local-development)). CI uses `supabase/setup-cli@v1` ([action](https://github.com/supabase/setup-cli)).

### 3.3 Data model (migrations in `supabase/migrations/`)
- `…_tenancy.sql`:
  - schema `app`, with usage granted to `authenticated` and `supabase_auth_admin`;
  - type `public.app_role` enum (`owner`, `chef`, `waiter`, `admin`);
  - helpers `app.tenant_id()` = `nullif(auth.jwt()->>'tenant_id','')::uuid` and `app.role()` = `auth.jwt()->>'app_role'`, both `stable`, with `search_path=''`.
- **`public.tenant`:**
  - columns: `id uuid pk default gen_random_uuid()`; `name text not null` (1–200 chars); `vat_number text not null unique` with check `^[A-Z]{2}[0-9A-Z]{2,13}$`; `timezone text not null default 'Europe/Rome'`; `currency char(3) not null default 'EUR'`; `settings jsonb not null default '{}'`; `created_at timestamptz not null default now()`; `created_by uuid null` (rows are created by a script).
  - It is the tenancy root, so its tenant key is `id`. This is the only exemption in `rls_every_table`, and it is named in that test.
  - Policy `tenant_select`: `id = (select app.tenant_id())`. There is no insert or update policy in M0.
- **`public.app_user`:**
  - columns: `id uuid pk`; `tenant_id uuid not null → tenant`; `auth_id uuid not null unique → auth.users(id)` (one tenant per login in M0, Q-F); `role app_role not null`; `display_name text not null` (1–100 chars); `is_active bool not null default true`; `deactivated_at timestamptz null`; `created_at`; `created_by uuid null → app_user`. Index on `tenant_id`.
  - Policies:
    - `app_user_select`: same tenant, and either the caller's role is owner or admin, or `auth_id = (select auth.uid())`;
    - `app_user_insert` (with check): same tenant, the caller's role is owner or admin, and `role <> 'admin' or app.role()='admin'`;
    - `app_user_auth_admin_read`: `for select to supabase_auth_admin using (true)`.
- **Grants:**
  - `revoke all on tenant, app_user from anon`;
  - `revoke delete, truncate … from authenticated`;
  - `grant select on app_user to supabase_auth_admin`.
- `…_access_token_hook.sql`:
  - `app.custom_access_token_hook(event jsonb) returns jsonb`. It is placed in `app`, which PostgREST does not expose (§4). It looks up the active `app_user` by `event->>'user_id'`, sets `claims.tenant_id` and `claims.app_role`, and leaves every required claim untouched. A missing or inactive user gets no claims added.
  - Grants: `grant execute … to supabase_auth_admin`; `revoke execute … from public, anon, authenticated`.
- `…_create_tenant.sql`: `public.create_tenant_with_owner(name, vat, auth_id, display_name) returns uuid`. It inserts the tenant and the owner `app_user` in one transaction. `security invoker`, execute granted to `service_role` only and revoked from `public`, `anon` and `authenticated`.
- `supabase/seed.sql`: one tenant, "Osteria Demo", `IT00000000000`. No auth users. pgTAP tests build their own fixtures inside `begin … rollback`.
- `supabase/config.toml` (local):
  - `[auth]`: `site_url="http://127.0.0.1:3000"`, `additional_redirect_urls=["http://127.0.0.1:3000/api/auth/callback","http://localhost:3000/api/auth/callback"]`, `enable_signup=false`;
  - `[auth.email]`: magic link on;
  - `[auth.sessions]`: `timebox="720h"`;
  - `[auth.hook.custom_access_token]`: `enabled=true`, `uri="pg-functions://postgres/app/custom_access_token_hook"`;
  - `[inbucket]`: `enabled=true`, port 54324.

### 3.4 API (all JSON; errors `{"error":{"code","message"}}`, never a stack trace or an internal message)
- `withApi({ roles, body }, handler)`. `roles` is `'public' | 'authenticated' | readonly AppRole[]`. `body` is a `z.strictObject`. The checks run in this order:
  1. A POST, PUT, PATCH or DELETE without `Content-Type: application/json` → 415 `unsupported_media_type` (CSRF control, plan §3.11.3).
  2. No claims → 401 `unauthenticated`.
  3. A role list was given and there is no `tenant_id` claim → 403 `no_tenant`; the role is not in the list → 403 `forbidden`.
  4. Bad JSON or a Zod failure, including unknown keys → 400 `invalid_request`.
  5. Any other throw → 500 `internal_error`, with fixed message "Internal error" and `Sentry.captureException`.
- The handler receives `ctx = {request, body, auth: {userId, tenantId, role, supabase} | null}`.

| Endpoint | Roles | Input | Success | Errors |
|---|---|---|---|---|
| `GET /api/health` | public | — | 200 `{"status":"ok"}`, no DB call, no version | — |
| `GET /api/me` | owner, chef, waiter, admin | — | 200 `{"user":{"id","displayName","role","tenantId"}}` (own `app_user` row via RLS) | 401, 403 `no_tenant` |
| `POST /api/auth/magic-link` | public | `{email: z.email().max(254), next?: string ≤ 512}` | 202 `{"status":"sent"}`, the same whether or not the user exists. `signInWithOtp({shouldCreateUser:false, emailRedirectTo: origin + '/api/auth/callback?next=' + safeNext(next)})` | 400, 415, 429 `rate_limited` (Supabase limit) |
| `GET /api/auth/callback` | public | `?code&next` | `exchangeCodeForSession(code)` → 303 to `safeNext(next)` | bad or missing code → 303 `/login?errore=link` |
| `POST /api/auth/logout` | authenticated | `{}` | `signOut()` → 204 | 401, 415 |

- **Flow (AT8):**
  1. Global setup runs the `create-tenant` script.
  2. The `/login` form calls `POST /api/auth/magic-link`. Supabase sends the email to Mailpit.
  3. The test reads the link through the Mailpit API.
  4. The link goes to Supabase verify, which runs the hook (adds the claims) and redirects to `/api/auth/callback?code…`.
  5. The callback exchanges the code and sets the cookies, then redirects to `/`. The proxy refreshes the session.
  6. `GET /api/me` returns `owner`.

## 4. Alternatives considered
- **Hook in `public`** (the docs' example): rejected. `app` is not in the PostgREST `schemas`, so the hook cannot be called through `/rpc` even if a revoke is lost. Execute is revoked anyway.
- **`node --experimental-strip-types` for scripts:** rejected. It does not resolve `tsconfig` `paths` (`@/…`) and requires `.ts` extensions in relative imports, while `admin.ts` and `env.ts` follow Next conventions. `tsx` (MIT, dev-only) runs them unchanged.
- **`import 'server-only'` in `admin.ts`:** rejected. That package throws outside the `react-server` condition, which would break `tsx` scripts. The lint rule plus a non-`NEXT_PUBLIC_` name (never inlined in client bundles) cover the same risk.
- **Lint rule by file-name glob (`src/server/**/cron*`):** rejected as fragile. The rule is directory-based: the admin client may be imported only from `src/app/api/cron/**`, `src/server/cron/**`, `scripts/**`, `src/lib/supabase/admin.ts` itself and `tests/lib/supabase/admin.test.ts`. From M3 on, cron services in other modules receive the client as a parameter from `src/server/cron/*`.
- **Seeding `auth.users` in `seed.sql` for E2E:** rejected because it is coupled to GoTrue internals. E2E creates its owner through `scripts/create-tenant.ts`, which also tests the script end to end.
- **Component tests (Testing Library + jsdom) for the login page:** rejected for M0 to avoid two dependencies. Playwright covers the page, and Vitest coverage is measured on `src/lib/**`, `src/app/api/**` and `scripts/**`.
- **`supabase db start` (DB only) in CI:** rejected because AT8 needs Auth and Mailpit. The full `supabase start` runs in CI.

## 6. Risks and mitigations
- **Security and privacy:**
  - *Secret key misuse:* steps 5 and 6 (AT11). The key is not on Vercel in M0, and CI holds no secrets.
  - *Cross-tenant or role leakage:* RLS plus AT2, AT3 and AT10. The hook is not callable through the API (step 10).
  - *Open redirect:* `safeNext` plus the allow-list (AT12).
  - *User enumeration via magic link:* a generic 202 (step 15).
  - *CSRF:* SameSite=Lax plus a JSON-only rule on writes (step 4).
  - *Brute force and email abuse:* M0 relies on Supabase Auth's own OTP rate limits. App-level limits come in M11/M25.
  - *Personal data:* owner email (Supabase `auth.users`) and display name only. Logs carry ids only. Sentry is scrubbed (step 8). Fixtures use `*.demo.test` addresses and fake VAT numbers. GDPR roles and Sentry retention are plan Q13.
  - *CSP:* only `frame-ancestors` in M0. The full nonce CSP comes in M25.
- **Environment (dev container):**
  - Docker registries are rate-limited here, so `supabase start` cannot run in the container. DB tests run locally against native Postgres 16 + pgTAP through `scripts/test-db-native.sh` and a small auth shim (`auth.users`, `auth.uid()`, `auth.jwt()` from `request.jwt.claims`, and the roles `anon`, `authenticated`, `supabase_auth_admin`, `service_role`).
  - The shim is outside `supabase/migrations` and `supabase/tests`, so it never ships. It can diverge from real Supabase (GoTrue calling the hook, default grants). **CI's full stack is the gate:** `db` runs pgTAP on real Supabase, and `e2e` (AT8) proves the hook end to end. No step may be marked done on shim results alone.
- **Unverified tool details:**
  - The variable names printed by `supabase status -o env` and the Mailpit API paths are not confirmed. The CI env-mapping step and `e2e/helpers/mailbox.ts` isolate them, and they are checked on the pinned CLI version at step 19.
  - `Intl` output (NBSP before €) depends on ICU; Node is pinned via `.nvmrc`.
- **Preview deploys:** these point at a staging project with no migrations, so `/api/health` works and login does not until the founder approves migrating staging (Q-A).
- **Performance / cost:** no figures promised. No provider prices are estimated (plan Q10).
- **Dependencies (licences re-checked at install; anything non-permissive goes to the founder):**
  - `next`, `react`, `react-dom` (MIT): the framework.
  - `tailwindcss` + `@tailwindcss/postcss` (MIT): styling.
  - `zod` (MIT): validation.
  - `@supabase/supabase-js` + `@supabase/ssr` (MIT): DB and auth client, cookie sessions.
